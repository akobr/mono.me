# Decisions That Cannot Be Changed Later

The production environment of the 2S Platform is created once and lives on (see the spec [Azure Production Environment of the 2S Platform](specs/2026-11-09%20Azure%20Production%20Environment%20of%20the%202S%20Platform.md)). Most of its settings can change at any time. The ones below cannot, or only at a high price: a migration of the data, new tokens and certificates for every machine and user, or a new resource. Fix them before the first deployment.

Each entry says what to decide, why it is final, a recommendation, and what was decided (2026-11-09).

### One WorkOS environment for the products of 42for.net

**Goal:** one login and one account for everything of 42for.net. Users and organizations belong to a WorkOS environment, so separate environments would give separate accounts: every product signs users in through the one production environment and `auth.42for.net`.

**What one environment shares.** One issuer (`https://auth.42for.net`, and also without the custom domain: WorkOS gives every application the issuer of the default application's client id), one key pair and one JWT template, so one `aud` for every token the environment issues. The 2S API accepts a token by its issuer, `aud` and signature (`Auth:AuthKit:Issuer`, `Audiences`), and gives every signed-in user `User.Impersonation`. A token that another 42for.net product gets for a user is therefore also a full token of that user for the 2S API: if that product leaks or hands its tokens on (a compromised front end, an assistant or MCP server, a log), the leak reaches 2S too.

**The plan.**

1. **One environment, one custom domain** `auth.42for.net` (decisions 3 and 4), shared by every product, once it is added ([424-247](https://linear.app/424fun/issue/424-247/add-the-custom-authkit-domain-auth42fornet-before-the-first-customer)).
2. **One WorkOS Application per product** ([Applications](https://workos.com/docs/authkit/applications)): each has its own client id, redirect URIs, session settings and branding, while users and organizations stay shared. Password resets, sign-in flows and invitation links route to the application they were started from; invitations sent from the dashboard use the **default application**, which is the 2S Platform (its admin UI and `sform`). Invitations sent through the API or the User Management widget keep the application of the API key or widget that sent them, so **each product sends its invitations with its own application's API key or widget**, never with the 2S key (`authkit-api-key`), or its invitations would lead to the 2S admin UI.
3. **`aud` stays `https://2s.42for.net`** in the one JWT template while 2S is the only product (it must equal `Auth__AuthKit__Audience`, or be one of `Auth__AuthKit__Audiences__<n>`). The template is per environment and renders into the tokens of every application, so it can't give each product its own audience.
4. **Before a second product signs users in, each API accepts only its own audience**, as WorkOS recommends ([Verify WorkOS access tokens in your own API](https://workos.com/blog/verify-workos-access-tokens-in-your-own-api): "one audience per API"). With Multiple Applications enabled, "tokens carry an `aud` identifying the application", so the 2S API accepts only the audiences of the 2S applications: `Auth:AuthKit:Audiences` (`authKitAudiences` in Bicep), which overrides the single `Auth:AuthKit:Audience` ([424-239](https://linear.app/424fun/issue/424-239), done in the API). Tokens of other products are then refused, while the user still signs in once. The issuer doesn't separate them, not even without the custom domain: WorkOS gives every application of an environment the same `iss`. Enabling Multiple Applications changes the `aud` of every token, and WorkOS doesn't document the application's `aud` nor how it combines with the template's: **WorkOS staging** finds out first what the values are made of (production lists its own, for example its client id), and production lists the new audience next to the old one while it switches, then drops the old one before the second application is created ([runbook](runbook-azure-production.md#enabling-multiple-applications-in-workos)). If no application `aud` separates the products, the fallback is a check of the token's `client_id` claim, which WorkOS documents per application but its verification guidance doesn't use; not built until staging shows it is needed.
5. **Check with the second product** that a session of one application signs the user in to the others without a new password prompt; the WorkOS docs describe "a unified login experience" but don't say it outright.

### Without the custom AuthKit domain (until the first customer)

The WorkOS custom domain costs about 99 USD a month, so production starts without it (decided 2026-11-11). Until it is added ([424-247](https://linear.app/424fun/issue/424-247/add-the-custom-authkit-domain-auth42fornet-before-the-first-customer)):

- **Issuer:** the admin UI and `sform` get their tokens from the WorkOS API, which issues them as `https://api.workos.com/user_management/<client id>` (checked on a production token on 2026-11-11), so that is `Auth:AuthKit:Issuer` (`authKitCustomDomain = false` in `prod.bicepparam`). The sign-in pages are on the environment's `….authkit.app` domain. With the custom domain, the issuer has to be checked again on a real token (424-247).
- **The admin UI's session:** AuthKit keeps the refresh token in `localStorage` (devMode) instead of an HttpOnly cookie on our domain, because the browser would block the cookie of `api.workos.com` as a third-party one. The admin UI allows that outside localhost only with the explicit `authLocalStorageSession` of its `app-config.json` (`AUTH_LOCAL_STORAGE_SESSION=true` at deployment). A script injected into the page through an XSS bug could read the token. **Accepted only while the owner and testers are the only users.**
- **Switching later loses nothing:** accounts are the WorkOS user ids (`sub`) of the environment, not of the domain, and machines use Storyteller's own tokens. Everyone signs in again once. So decision 4 is "final" only once customers sign in.

### GitHub environments

The repository holds many projects, so a GitHub environment is named `<environment>.42.<area dotted path>`: the 2S Platform's production is **`prod.42.Platform`** (decided 2026-11-11; it was `production`). The deployment identity's federated credential pins it (`repo:akobr/mono.me:environment:prod.42.Platform`), so a rename means a new credential (`New-DeploymentApplication.ps1 -GitHubEnvironment`). The credential's name can't hold dots: the script names it `github-<environment, other characters as '-'>-<8 hex of its SHA-256>`, so distinct environments never share a name, and keeps any existing credential of the same subject (such as `github-prod-42-Platform`) whatever its name. The admin UI's own environment name (`VITE_ENVIRONMENT_NAME`, for Sentry and PostHog) stays `production`.

Accepted exposure:

- **The Key Vault is reachable from the public internet** (`publicNetworkAccess` on, network rules `Allow`). Every request still needs an Entra token with an RBAC role on the vault; the Flex Consumption API has no fixed outbound address to allow, and a virtual network is not part of this phase. When one comes (the NAT gateway for BYOK, spec section 13), restrict the vault to it with an IP firewall or a private endpoint: a setting, not a decision that can't change.

### The exhibition

The exhibition is the demo project that the onboarding of the admin UI offers to a new user, who joins it as a Reader (decided 2026-11-15, [424-267](https://linear.app/424fun/issue/424-267/admin-ui-onboarding-wizard-eu-hosting-security-and-federated-auth-join); [access](../Storyteller/access.md#exhibition)).

- **Names:** the organization `fourth-wall` and the project `toons-and-tyrants`, with the data set `exhibit` of DbCreator in the view `default`: the names of the set's `set.json`. Every visitor's membership holds them, and there is no rename (decision 10). Changed on 2026-11-23 from `exhibition` / `exhibition`, decided first: production was seeded with the set's own names, and the parameters follow the seed.
- **Owner:** the operator's own production account. It is the `--owner` of the seed and the app setting `Exhibition__Owner`, and the API offers and joins the exhibition only while it is the Owner of the project and no other account is an Administrator or Owner of it. Anyone who signs in may register a free organization name, so without the owner, settings that are live before the seed would hand the exhibition to the first person who registers the names: every newcomer's onboarding would offer their project, and they would list the name and email of everyone who joins. The owner's role alone is not enough, because an Owner can make any existing account an Owner without its consent (`POST v1/access/grant`): whoever registered the names could add the operator's account to a project of their own. So the operator stays the only Administrator or Owner of the project. A second one switches the exhibition off (`404` and a warning) until that role is removed or lowered.
- **What the check does not cover:** it tells who manages the project now, not who created it, because the access map does not say who created a project. What somebody wrote into a project before they left it stays. The order below covers that: the seed creates the project.
- **Order:** the seed, the key/value pairs, one resolved read as a check, and only then the three parameters of `prod.bicepparam` ([runbook](runbook-azure-production.md#turning-the-exhibition-on)). Until then the parameter file does not set them, and production has no exhibition. Production's seed ran with the operator's account, and `prod.bicepparam` sets the three since 2026-11-23.

### The wording about hosting and sign-in in the admin UI

The onboarding of the admin UI repeats the hosting and sign-in facts of this environment to every new user. Its residency step says that customer data, configuration, secrets, machine access and the AI data processing within the platform stay in the EU (Sweden, decision 5), and that the sub-processors are Microsoft Azure, Sentry and PostHog in the EU and WorkOS in the USA (decisions 3 and 4), with what WorkOS receives and that 2S makes and records every authorization decision in the EU. Its security step says that people sign in with WorkOS AuthKit while 2S alone decides what they may do, names the three safeguards (blocked impersonation, a recent sign-in for secrets, the append-only audit log of access changes), and points a customer that needs an EU-only identity provider to its own SSO provider or to self-hosting. The texts, the list of sub-processors and the links are the constants of `src/Platform/ui.admin/src/app/utils/onboarding.ts`.

- **Change them together.** A change of a region, of a sub-processor, of what WorkOS receives, or of the identity providers changes that file in the same pull request. A merge to `main` publishes the admin UI at once.
- **The three safeguards show always.** The switch `safeguardsLive` of the same file is gone (2026-11-16): the security step names the safeguards of [424-262](https://linear.app/424fun/issue/424-262), [424-263](https://linear.app/424fun/issue/424-263) and [424-264](https://linear.app/424fun/issue/424-264) without a condition, and the entry of WorkOS says that every authorization decision is made and recorded by 2S in the EU. The platform opens to the public only once all three run in production (the production API runs a build with them, runbook phase 11.1, and the WorkOS dashboard check of 424-262 is recorded), so no public user sees the claim before it holds. The owner and the testers of production may see it earlier; their onboarding does not wait for the safeguards.

### Who can sign in as a user (the WorkOS trust boundary)

Decided 2026-11-15 ([424-262](https://linear.app/424fun/issue/424-262/refuse-workos-impersonation-tokens-in-the-api-and-lock-down-who-can)).

**The boundary.** WorkOS authenticates a person. Only the roles that 2S keeps in Cosmos DB (EU) authorize them. A valid WorkOS token for `user_X` gets X's roles, so this split holds only while nobody but X can get such a token. Three paths give someone else one:

1. **Impersonation.** A dashboard Admin can turn on user impersonation for an environment. Then any dashboard member can sign in as any user. The token carries `act`, with the impersonator's email as `act.sub`. **Covered:** on API routes, the API refuses every AuthKit user token with `act`, answering `401` and logging a Warning with the subject and `act.sub` ([How AuthKit tokens are checked](../Storyteller/authentication.md#how-authkit-tokens-are-checked)). The user token exchange refuses such a subject token with `400 invalid_grant`. Impersonation also stays off in every environment. Production and Staging had it off when checked through the WorkOS API on 2026-11-15.
2. **Account takeover through the dashboard or the management API.** A dashboard member, or whoever holds the management key (`authkit-api-key`), can change a user's email or delete their MFA factors, then sign in as that user. The `sub`, and so the account and its roles, stays the same. **Mitigated:**
   - one or two named dashboard members, each with the least role and MFA, or SSO through an identity provider that enforces MFA;
   - the management key only in the vault;
   - a Warning from the API when a token's user name differs from the stored one, with its own message for an Administrator or Owner ([Changed user names](../Storyteller/authentication.md#changed-user-names)).
3. **WorkOS itself.** A leaked signing key, an insider, or a legal order to WorkOS, Inc., a US company, could produce a valid token for any user. **Accepted, and disclosed** on the trust page and in the DPA annex: such a token can't be told from a real one.

**Privacy.** The refusal logs the impersonator's email, and the user name check logs the old and the new user name. Both go to Application Insights, which keeps them for the workspace's 30 days (`monitoring.bicep`). Both are Warnings, so Sentry gets them only as breadcrumbs, with emails scrubbed.

**For customers who refuse WorkOS or a US identity provider.** `Auth:Provider` also takes `Keycloak`, which the customer can host in the EU, and `EntraId`, the customer's own tenant. Microsoft is a US company too, but the tenant and its admins are the customer's. Either means a deployment of its own, with these limits today:

- A deployment has one provider at a time.
- Switching a deployment's provider orphans its accounts. The account ids differ by provider, and nothing migrates them ([Account ids](../Storyteller/authentication.md#account-ids)).
- The admin UI signs in through AuthKit only. `sform` signs in under Entra ID but not under Keycloak, where people call the API with tokens of the realm.

**Wording for the trust page and the DPA annex.** Both are kept outside the repository. Their owner copies this text and keeps it in step with this entry:

> Sign-in to the 2S Platform is provided by WorkOS, Inc. (USA). WorkOS verifies who a person is, and a valid WorkOS sign-in lets that person in. What a person may do with any data is decided only by the roles that the 2S Platform stores in the European Union. WorkOS's user impersonation is turned off, and the 2S API refuses impersonated sessions. Access to the WorkOS dashboard is limited to named members who use multi-factor authentication. When a person reads their account (as the admin application does when it opens) or signs in through the MCP server under another email than the one the 2S Platform has stored, the 2S API logs it. One risk remains: WorkOS itself could issue a valid sign-in for any person, through a compromise of its signing keys or under a legal order, and the 2S Platform cannot tell such a sign-in from a real one. Customers who do not accept WorkOS can use a dedicated deployment that signs people in with an identity provider of their own instead: a Keycloak server, which can be hosted in the European Union, or their own Microsoft Entra ID tenant. Such a deployment uses one identity provider, and the admin web application is not available in it.

**Evidence.** At each production verification ([runbook step 12](runbook-azure-production.md#12-verify-c17)), a WorkOS Admin checks the dashboard: impersonation is off in every environment, the members and their roles are the named ones, and each member has MFA. Where SSO stands in for it, the Admin checks that the identity provider enforces MFA; SSO with a password-only sign-in does not count. The Admin records the date, the reviewer and the result in the ISO 27001 supplier notes, which are also kept outside the repository.

### The MCP server

Decided 2026-11-17 with the spec [Deploy the MCP Server to Azure Container Apps](specs/2026-11-17%20Deploy%20the%20MCP%20Server%20to%20Azure%20Container%20Apps.md) ([424-287](https://linear.app/424fun/issue/424-287/deploy-the-mcp-server-to-production-on-azure-container-apps)); the cost, its budget and the cool-down on 2026-11-22 with the spec [Cost Range and Budget of the MCP Server](specs/2026-11-22%20Cost%20Range%20and%20Budget%20of%20the%20MCP%20Server.md) ([424-305](https://linear.app/424fun/issue/424-305/arch-the-0-usd-a-month-mcp-server-sits-on-a-public-unrestricted)). The steps are the [runbook](runbook-mcp-server.md). None of these is final: the server holds no data, and each can change with a run of the templates.

- **Azure Container Apps, one replica always on.** The server is an ASP.NET Core app with its own host and long-lived HTTP requests, not a set of functions, so it doesn't share the Function App. A workload profiles environment with the Consumption profile only (`prod-2s-cae`) has no base fee. The app (`prod-2s-mcp-ca`, 0.25 vCPU, 0.5 GiB, 1 to 3 replicas) started scaled to zero, inside the monthly free grant of Container Apps (0 USD), with a cold start of a few seconds on the first call after an idle period. Since 2026-11-22 one replica always runs (`mcpMinReplicas = 1`): no cold start, for **about 4–5 USD a month** (the replica's 648,000 vCPU-seconds and 1,296,000 GiB-seconds a month, less the free grant, at the idle rate between calls; about 14 USD at most if it were busy all the time). `mcpMinReplicas = 0` goes back to scale to zero. A request may take at most 240 seconds (the ingress), so a longer tool call is cut off.
- **Its own identity with no Azure role** (`prod-2s-mcp-mi`), not the API's, which reads every secret of the vault. It proves the server to the API as the actor `mcp`, with a token for the application `2S Platform Token Exchange`, which stands for the exchange and nothing else. No secret and no certificate exist. The API pins the identity's issuer, object id and audience; optionally, the application accepts tokens only for that identity (`New-TokenExchangeApplication.ps1 -McpIdentityName`).
- **The scope is `openid`, which gates nothing; the API is the gate.** MCP clients register themselves at the AuthKit domain, and such clients get no WorkOS permission. An environment-wide default scope would be in every token of every 42for.net product, so it would gate nothing either. That is the exposure: any client can register itself, ask for the MCP resource, and once the person consents on one screen, act as that person through the actor `mcp`. The client is unknown and unbounded, and WorkOS documents no allow-list or block-list of clients. What it may do is decided by the API: the exchange refuses a person without a Storyteller account, their roles decide every call, `NoSecretReveal` withholds secret values, and a client that isn't trusted only reads (the next point). The MCP audience (`https://mcp.2s.42for.net/mcp`) is only the actor's subject audience, never one of the API's bearer audiences, so a leaked MCP token can't call the API directly. With the custom AuthKit domain only that `aud` keeps a self-registered client's token off the API's routes, so the runbook checks it before the switch ([later](runbook-mcp-server.md#later-the-custom-authkit-domain)).
- **Every MCP client reads only, until it is trusted.** Decided 2026-11-22 with the spec [Client Attribution, Deny List and Read-Only Default of the User Token Exchange](../Storyteller/specs/2026-11-22%20Client%20Attribution,%20Deny%20List%20and%20Read-Only%20Default%20of%20the%20User%20Token%20Exchange.md) ([424-302](https://linear.app/424fun/issue/424-302/arch-production-turns-on-the-mcp-token-exchange-with-no-client-allow)). The client is the subject token's `azp`, `appid` or `client_id`; the API writes it into the exchanged token and, as `ViaClient`, into the audit of every change made through it, and logs it with every request. Every client outside `mcpTrustedClientIds` gets `mcpUntrustedClientRestrictions`, `ReadOnly` and `NoSecretReveal`: the API refuses its changes (`ActorReadOnly`), and the MCP server hides its write tools. A sign-in that names no client counts as untrusted. `mcpTrustedClientIds` stays empty until a sign-in of a client with a Client ID Metadata Document (CIMD) of web redirects only has been recorded, because it is not verified that AuthKit's `client_id` is the document's URL; a wrong entry fails safe, and the client stays read only. A dynamically registered client is never trusted: its id is random per registration. `mcpDeniedClientIds` cuts off one client with a stable id; `mcpAllowedClientIds`, set to the trusted list, cuts off every other client, the dynamically registered ones too. The accepted risk:
  - A client the person consents to, trusted or not, reads everything the person can read, except secret values: annotations, configurations, members' and invitees' emails, the audit trails and the machines' metadata.
  - Every read and every refused write is logged with the client. Every change is in the audit with `ViaClient`.
  - A dynamically registered client is attributed per registration, not per app.
  - The deny list does not hold against a client that registers again. `mcpAllowedClientIds`, or turning dynamic client registration off in WorkOS, does.
  - Every change of the lists needs the API to restart with the new settings, which takes minutes.
  - A trusted client writes with the person's full roles, as before, and reads secrets only while the actor allows secrets.
  - Clients whose CIMD lists a loopback redirect are not trusted: any local process can present their URL.
- **A public image on GitHub Container Registry** (`ghcr.io/akobr/2s-platform-mcp`). The repository is public, the image holds no setting and no secret, and the Container App pulls it without a credential; an Azure Container Registry (about 5 USD a month) isn't needed. Only the workflow `Platform.Storyteller.Mcp.yml` builds it, from `main`, once per commit and tagged with it; the deployment waits for the reviewer of `prod.42.Platform` and runs the image by its digest, so what was approved is what every replica pulls, and the deployment identity has Container Apps Contributor on the Container App only.
- **The template that writes the app binds its domain.** A Container App has no binding resource of its own, and a write of the app without its domains removes them. So `main.bicep` binds `mcp.2s.42for.net` (`mcpCustomDomain`, the binding type `Auto` with the environment's free managed certificate), not `domains.bicep`, and keeps the bound certificate and the image the workflow deployed on later runs.

## Must be decided before the first deployment

| # | Decision | Why it can't change later | Recommendation |
| --- | --- | --- | --- |
| 1 | **The API domain** (`api.<domain>`) | It is `MachineAuth:Federation:PublicBaseUrl`: every federated machine's rule pins the `TokenEndpoint` built from it as its audience, and clients, pipelines (`STORYTELLER_ENDPOINT`) and SDK settings of customers hold it. A new domain breaks every federation rule and every customer configuration | A domain you will own for good, for the product rather than a person: e.g. `api.2s.42for.net` or a product domain bought now. Never the `*.azurewebsites.net` name |
| 2 | **The trust domain** (`MachineAuth:TrustDomain`) | It derives the issuer (`urn:storyteller:{trust domain}`) and the audience of every Storyteller token, machine and user. | 3 | **The identity provider and its production environment** (AuthKit, WorkOS production) | Account ids are the provider's user ids (`sub`). Members, roles, invitations, audit stamps and the base account are keyed by them. Moving users to another provider or another WorkOS environment gives them new ids, and every membership has to be migrated | AuthKit in **WorkOS production** from day one; staging stays for local work. Testers sign up in production too |
| 4 | **The custom AuthKit domain** (`auth.<domain>`) | It is the issuer the API checks (`Auth:AuthKit:Issuer`), and the domain users see when they sign in; changing the issuer invalidates every session and needs a coordinated change of API and UI | A subdomain of the same domain as #1, set up in WorkOS before the first customer (until then the WorkOS API is the issuer; see "Without the custom AuthKit domain") |
| 5 | **The region** (Sweden Central) | Cosmos DB, the vault and the storage account can't move between regions. A move means new resources and a migration of the data and of every key | Sweden Central (data residency in Sweden) |
| 6 | **The Cosmos DB free tier** | It is chosen when the account is created and can't be added later; there is one per subscription | On, in the production subscription's only Cosmos account. Don't create any other Cosmos account in this subscription first, or the free tier is taken |
| 7 | **The Cosmos account name** | Account names are global and final; the endpoint is in the connection string | `cosmos-2s-prod-sdc-<suffix>` |
| 8 | **The Key Vault, and purge protection** | Every project's key-encryption key lives in it, and the envelopes in Cosmos name its keys by URI: a new vault means re-wrapping every secret. Purge protection can't be turned off once on, which is the point: a deleted key would lose every secret of its project | One Premium vault, purge protection **on**, RBAC mode, a delete lock; its name fixed in the parameter file |
| 9 | **The database layout** (one database `42.Platform.2S`, shared throughput) | Changing it means moving every item, and a hierarchical partition key can only be set when a container is created. A container per organization stops at 25 containers in a shared database and at 500 per account (a limit that can't be raised) | One shared container `organizations` with the key `/Organization`, `/PartitionKey`, before the first deployment |
| 10 | **The organization and project names you create** | Organization and project names are part of every key, container name (`org.{organization}`), configuration path, Key Vault key name (`kek-` + a hash of `{organization}/{project}`) and the HYOK `2s` header; there is no rename | Pick the final names of the first customers' organizations; never use a customer's organization for tests |
| 11 | **The base account** (`baseAccount:id` of DbCreator) | It becomes the owner of the platform's first organization and project; it is the WorkOS production user id of the owner | Your own WorkOS production user, created before the first run of DbCreator |

| 15 | **The signing key and certificate authority stay in production** | They are created in the `core` container on first use. Whoever reads it can mint tokens, so it must never have been copied to a development machine or shared with a test environment | Never copy production data to a local emulator; development gets its own account later |

## Can change any time (no need to decide now)

Function App plan and instance size, always-ready instances, Static Web App plan, the Log Analytics cap, Sentry and PostHog projects, which machine credential kinds are turned off (`MachineAuth:DisabledCredentialKinds`), the projects' key/value policies, adding the development subscription, the MCP server and its client lists (`mcpTrustedClientIds`, `mcpUntrustedClientRestrictions`, `mcpAllowedClientIds`, `mcpDeniedClientIds`; each change restarts the API, [runbook](runbook-mcp-server.md#trust-a-client)), the NAT gateway and mTLS.

The window of the [step-up](../Storyteller/authentication.md#recent-sign-in-step-up) can change any time too: `stepUpMaxAgeSeconds` of `parameters/prod.bicepparam` (`Auth:StepUp:MaxAge`, 10 minutes by default, 60 to 86400 seconds). `stepUpEnabled = 'false'` is the escape hatch when a client cannot satisfy the step-up: it turns it off until the client is fixed, and nothing else changes. Turning MFA on in WorkOS production (the [MFA policy](../Storyteller/authentication.md#mfa-policy)) changes how people sign in, not their accounts.
