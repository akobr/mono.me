# Configuration Templates

This document describes how Storyteller inserts autogenerated JSON into a configuration while that configuration is calculated, and how templates are managed and versioned.

A template is a JSON object stored once per annotation type, project, and view. Calculation merges it into every configuration of that type in that view, across all annotation partitions. Views are isolated: each view has its own templates, its own version history, and its own cache invalidation. The annotation's own stored document is merged afterwards, so a value written on the annotation replaces the generated one.

## Overview

Effective configuration is produced by `CosmosConfigurationService.CalculateAndCacheConfigurationAsync`. For one annotation the method:

1. Merges the calculated configuration of each ancestor.
2. Merges the view template for this annotation's type, when that item exists.
3. Merges this annotation's stored `Content`.
4. Writes the result to `CalculatedContent` and caches it on the configuration item.

`TryAutogeneratePropertiesAsync` performs step 2. It reads one `GenerateTemplateEntity` and merges `Content` into the object accumulated so far. A missing template leaves the accumulated object unchanged. All nodes of one inheritance graph are in the same view, so one calculation reads the template of a type at most once, even when several nodes have the same type.

The stored document and the calculated document stay separate. Template properties appear in the calculated document. They are left out of the stored `Content`, out of configuration version history, and out of the hierarchy view.

Templates are created, changed, and deleted through `IConfigurationTemplateService` (see [Managing templates](#managing-templates)). Every change is versioned, and every change clears the cached calculations that used the template.

## Document

`GenerateTemplateEntity` (`Backend.CosmosDb/src/Entities/Configurations/GenerateTemplateEntity.cs`) extends `Entity` with three properties:

| Property | Role |
| --- | --- |
| `Content` | JSON object merged into the calculation. |
| `Author` | Author of the current version. |
| `Version` | Current version number, starting at `1`. |

The base `Entity` fields are `id`, `PartitionKey`, `ProjectName`, `ViewName`, `AnnotationKey`, `Name`, and `_ts`. Calculation addresses the item by `id` and partition key. It reads `Content` and leaves the other fields unused.

Items live in the organization container (`org.{organization}` in database `42.Platform.2S`). Property names are Pascal case; the item id is `id`.

### Identity

```text
id           = {viewName}.gen.{typeCode}
partition    = {project}.template
```

A template is identified by organization, project, view, and type code. It does not depend on an annotation partition. Each view of a project has at most one template per annotation type. All views of the project share the `{project}.template` partition, and the view prefix in the id keeps them apart, the same way configuration ids (`{viewName}.cnf.{annotationKey}`) do. The dedicated project partition follows type-level configuration schemas (`cfs.{typeCode}` in `{project}.schema`).

`typeCode` is `AnnotationKey.TypeCode`, lower-cased:

| Code | Annotation type |
| --- | --- |
| `rst` | Responsibility |
| `unt` | Unit |
| `sbt` | Subject |
| `usg` | Usage |
| `cnt` | Context |
| `exe` | Execution |
| `uxe` | Unit of execution |

`default.gen.exe` in `billing.template` is merged into every execution of the project `billing` in the `default` view, under every responsibility. `rollout.gen.exe` in the same partition is a separate template for the `rollout` view; neither one affects the other view.

```json
{
  "id": "default.gen.exe",
  "PartitionKey": "billing.template",
  "ProjectName": "billing",
  "ViewName": "default",
  "AnnotationKey": "exe",
  "Name": "exe",
  "Author": "platform",
  "Version": 2,
  "Content": {
    "retries": 3,
    "features": ["audit"],
    "owner": "platform"
  }
}
```

`AnnotationKey` and `Name` both hold the type code.

### Earlier storage location

Before templates were versioned, a template lived inside the annotation partition (for example `default.gen.exe` in `billing.rst.invoicing`). The id has the same shape as today, but the partition differs. Items in that location are no longer read and were not migrated. They stay in place as dead items.

## Managing templates

`IConfigurationTemplateService` (`Backend.Core/src/Configuring/`) is implemented by `CosmosConfigurationTemplateService` (`Backend.CosmosDb/src/Configuring/`). Every method takes organization, project, view, and type code. Type codes are case-insensitive; an unknown code throws `ArgumentOutOfRangeException`.

| Method | Behaviour |
| --- | --- |
| `GetTemplateAsync` | Returns the current template, or `null`. |
| `CreateOrUpdateTemplateAsync` | Creates the template, or merges the input into the current content with the same rules as configuration writes (`MergeInto`, then `$remove`, then `$patch`). If the result equals the current content, nothing is written. |
| `PatchTemplateAsync` | Applies a JSON Patch (RFC 6902). Throws `TemplateNotFoundException` when there is no template. |
| `DeleteTemplateAsync` | Deletes the template and keeps its history. Returns `false` when there is no template. |
| `GetTemplateVersionsAsync` | Lists the history versions and the current version, oldest first. |
| `GetTemplateVersionContentAsync` | Returns the content of one version, or `null`. |
| `GetTemplateVersionChangesAsync` | Diff of `version - 1 → version`, or of any `from → to` pair. Version `0` is an empty object. An unknown version throws `InvalidOperationException`. |

Every write uses the ETag of the item it read. When another writer changed the template in the meantime, the write is retried on fresh data, up to three times.

Template content is not validated against configuration schemas.

### HTTP API

The routes include the view, like configuration routes:

| Method | Route | Operation |
| --- | --- | --- |
| GET | `v1/{organization}/{project}/{view}/template/{annotationType}` | `GetTemplate` |
| POST, PUT | same | `SetTemplate` |
| PATCH (`application/json-patch+json`) | same | `PatchTemplate` |
| DELETE | same | `DeleteTemplate` |
| GET | `…/template/{annotationType}/versions` | `GetTemplateVersions` |
| GET | `…/template/{annotationType}/versions/{version}` | `GetTemplateVersion` |
| GET | `…/template/{annotationType}/versions/{version}/diff` | `GetTemplateVersionDiff` |
| GET | `…/template/{annotationType}/versions/{version}/diff/{versionFrom}` | `GetTemplateVersionDiffCustom` |

- Reads require one of the scopes `Configuration.Read`, `Configuration.Write`, `Default.Read`, `Default.Write`, plus access to the project.
- Writes require `Configuration.Write` or `Default.Write` and the `Contributor` role in the project.
- Diff endpoints return a `DiffResult`, or unified diff text with `?format=unified`. An unknown version returns `404`.

## Versions

Versioning follows configuration versioning:

- A new template starts at version `1`. Each change that alters the content increments `Version`.
- Before a change, the current item is copied into a `GenerateTemplateHistoryEntity` with id `{viewName}.gnv.{typeCode}.{version}`, in the same `{project}.template` partition. Every view has its own version sequence. The copy and the change are written in one transactional batch.
- A delete also writes the history item of the deleted version. A template created again later continues the numbering after the highest history version.
- History items expire after 365 days (`ttl`). The current version never expires.
- `ConfigurationVersion` describes a version: `Version`, `Author`, `CreationTime`, `ExpirationTime` (`DateTimeOffset.MaxValue` for the current version).

## Merge

`JObject.MergeInto` (`Backend.CosmosDb/src/JsonExtensions.cs`) calls Newtonsoft `JObject.Merge` with:

- `MergeArrayHandling.Union` — array items are appended, and an item that is already present is skipped.
- `MergeNullValueHandling.Ignore` — a null in the incoming object leaves the current value in place.

Objects merge property by property. A scalar written by the incoming object replaces the current value. An array is unioned with the current array. Nested objects merge the same way. Merged tokens are copied, so the template item stays unchanged.

`$remove` and `$patch` are write-time instructions. `CreateOrUpdateConfigurationAsync` applies them to stored content through `RemoveRequested` and `ApplyPatchRequested`. Calculation uses `MergeInto` only, so a `$remove` or `$patch` property inside a template is copied into the calculated document as an ordinary property.

## Where the template sits

`CalculateAndCacheConfigurationAsync` runs this sequence for the annotation being read and, recursively, for each ancestor:

1. Return the stored `CalculatedContent` when the configuration item already has one. The template is left unread on that path.
2. Start from an empty object.
3. Calculate each direct ancestor and merge it. Ancestors are ordered by `AnnotationType`: Responsibility, Unit, Subject, Usage, Context, Execution, Unit of execution.
4. Merge this node's template (`TryAutogeneratePropertiesAsync`).
5. Merge this node's stored `Content` when a configuration item exists.

The graph built by `BuildInheritanceGraph` makes the effective order:

| Annotation being calculated | Merge order |
| --- | --- |
| Responsibility, Subject | Template, then stored content |
| Unit | Responsibility, then the unit template, then the unit content |
| Context | Subject, then the context template, then the context content |
| Usage | Responsibility, subject, then the usage template, then the usage content |
| Execution | Responsibility, subject, usage, context, then the execution template, then the execution content |
| Unit of execution | The unit's calculated document, then the execution's calculated document, then the unit-of-execution template, then the unit-of-execution content |

Each ancestor's calculated document already contains that ancestor's template. A responsibility template is inherited by a usage. The usage template is then merged on top of that inherited document, and the usage's stored content is merged last.

On a unit of execution the execution document is merged after the unit document. The execution document carries the responsibility again, so a responsibility value there replaces the same property contributed by the unit. The unit-of-execution template and stored content are merged after both.

Later steps win for scalars. Arrays grow by union across the whole sequence. A null never erases an earlier value.

### Worked example

Responsibility `rst.invoicing`, stored content:

```json
{ "currency": "EUR", "retries": 1, "features": ["vat"] }
```

Execution template `default.gen.exe` of the project `billing`, for the `default` view:

```json
{ "retries": 3, "features": ["audit"], "owner": "platform" }
```

Execution `exe.northwind.invoicing.production`, stored content:

```json
{ "retries": 5, "features": ["vip"] }
```

Calculation of that execution, with no other stored documents and no other templates:

1. Responsibility calculated document: `{ "currency": "EUR", "retries": 1, "features": ["vat"] }`.
2. Execution template overwrites `retries`, unions `features`, and adds `owner`.
3. Execution content overwrites `retries` and unions `features` again.

```json
{
  "currency": "EUR",
  "retries": 5,
  "features": ["vat", "audit", "vip"],
  "owner": "platform"
}
```

`owner` exists because the template added it and the execution document left it alone. `retries` is `5` because stored content is merged after the template. `currency` is inherited from the responsibility because neither the template nor the execution replaced it.

## Cache

When the merged object has at least one property, calculation persists it:

- An existing configuration item is upserted with `CalculatedContent` and `CalculatedContentHash`. Stored `Content`, `Version`, and `Author` stay as they were.
- A missing configuration item is created with empty `Content`, `Author` set to `"system"`, `CalculatedContent` set to the merge, and `Name` set to the annotation name. The id is the normal configuration id, `{viewName}.cnf.{annotationKey}`.

`CalculatedContentHash` is eight lowercase hex digits. It is MurmurHash3 32-bit, seed `42`, of the calculated JSON serialized with `JsonSettingNames.Unique` (properties ordered by name).

The next read of an item whose `CalculatedContent` is present returns that object and skips both ancestor walks and template reads. `GetRawConfigurationAsync` follows this short path.

These writes clear cached calculations, which makes the following read load the template again:

- `CreateOrUpdateConfigurationAsync`, when the configuration item already exists, sets `CalculatedContent` to null on that item and calls `InvalidateConfigurationsAsync` for affected configurations.
- `PatchConfigurationAsync` does the same.
- `ClearConfigurationAsync`, when stored `Content` has values, deletes the item and then invalidates affected configurations. `DeleteAsync` deletes the item and then invalidates.
- Every template write (`CreateOrUpdateTemplateAsync` with a changed content, `PatchTemplateAsync`, `DeleteTemplateAsync`) invalidates the configurations that merge the template, after the template has been written.

Invalidation (`ConfigurationCacheInvalidator`, `Backend.CosmosDb/src/Configuring/`) sets `CalculatedContent` and `CalculatedContentHash` to null and increments `AffectedCounter`. The patches are sent in transactional batches of at most 100 items per partition, which is the Cosmos DB limit. A failed batch is reported as an error. If an item was deleted in the meantime, its batch falls back to patching items one by one, skipping deleted ones.

A configuration update invalidates descendants:

- A responsibility update invalidates every configuration in that responsibility partition and view.
- Other types invalidate the descendants listed in `CosmosConfigurationService.InvalidateConfigurationsAsync`.
- The first insert of a configuration item, when none exists yet, returns after `CreateItemAsync` and leaves descendant caches as they are.

A template write invalidates, in the template's view only, all configurations of the template's type and of every type that inherits from it:

| Template type | Invalidated configuration types |
| --- | --- |
| `rst` | `rst`, `unt`, `usg`, `exe`, `uxe` |
| `unt` | `unt`, `uxe` |
| `sbt` | `sbt`, `usg`, `cnt`, `exe`, `uxe` |
| `usg` | `usg`, `exe`, `uxe` |
| `cnt` | `cnt`, `exe`, `uxe` |
| `exe` | `exe`, `uxe` |
| `uxe` | `uxe` |

This is a cross-partition operation over all annotation partitions of the view. Changing an `rst` or `sbt` template touches almost every configuration in the view. Configurations of other views are never touched.

A template item written directly into Cosmos, bypassing the service, leaves existing `CalculatedContent` in place. That template is applied on the next calculation, after one of the writes above has cleared the cached document.

`ClearConfigurationAsync` returns immediately when `Content` is empty, so a system-created item stays in place. `DeleteAsync` calls `ForceDeleteConfigurationAsync`, which deletes that item directly and writes no history row. A system-created item gains history once a caller writes real `Content` into it.

## What each read returns

| Read | Template content |
| --- | --- |
| `GetRawConfigurationAsync` | Included. This is the calculated document. |
| `GetResolvedConfigurationAsync` and the with-secrets / without-secrets variants | Included, then walked for `@` bindings. |
| `GetConfigurationHierarchyViewAsync` | Omitted. The view is a map of each annotation key to its stored `Content`. |
| `GetConfigurationVersionContentAsync` | Omitted. A version stores the document that was written. |

`GetResolvedConfigurationInternalAsync` loads the calculated document first. Its binding snapshot is a deep clone of that document, so `@config` sees values that arrived from a template. Strings contributed by a template are bound with the same rules as strings stored on the annotation. See [binding.md](binding.md).

While that walk visits nested objects it records a follow-up for logic operations and template processing (`TODO: [P3]` in `GetResolvedConfigurationInternalAsync`). Today a nested object is only queued so its strings can be bound. Type templates have already been merged during calculation.

Schema validation runs on stored `Content` inside `CreateOrUpdateConfigurationAsync` and `PatchConfigurationAsync`. It sees the document being written. Template content and the calculated merge are outside that check.
