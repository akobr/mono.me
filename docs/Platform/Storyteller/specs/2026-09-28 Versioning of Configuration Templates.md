# Versioning of Configuration Templates

> **Revision 2026-09-30.** Templates are now scoped to **project + view** instead of project only (decision D2). A template change then invalidates only the configurations of one view, not of the whole project. Phase A was first implemented project-wide (commit `956060d`) and was then changed to match this revision.

## Problem

Configuration templates (`GenerateTemplateEntity`, see [templating.md](../templating.md)) inject autogenerated JSON into every calculated configuration of one annotation type. Three things are wrong with them today:

1. **Wrong scope.** A template is stored inside an annotation partition (`{project}.rst.{responsibility}` or `{project}.sbt.{subject}`) and per view (`{view}.gen.{typeCode}`). One logical "execution template" therefore has to be copied into every responsibility partition, and the copies drift apart. A template should be a view-level concept, stored the way type-level configuration schemas are: **one template per annotation type per project and view**. Views stay fully isolated, so a template change in one view never affects another view.
2. **No management and no history.** There is no service method, API endpoint, or CLI command for templates; they can only be written directly into Cosmos. They have no version and no history, so nobody can see who changed a template, when, or what it looked like before.
3. **Stale caches.** Writing a template leaves every cached `CalculatedContent` in place; the new template only takes effect after an unrelated configuration write clears the cache.

Configurations already have versioning (a `Version` counter, `cfv` history items, version listing, version content, and diffs). Templates should be versioned the same way, and stored in a dedicated project partition the way type-level schemas are, with the view in the id as configurations have it.

## Phase A — Backend and API

### 1. Template identity and storage

A template is identified by **organization + project + view + type code**. It does not depend on an annotation partition.

| Field | Value |
| --- | --- |
| Partition | `{project}.template` (all views of the project share it) |
| `id` | `{view}.gen.{typeCode}`, e.g. `default.gen.exe` |
| `ProjectName` | project |
| `ViewName` | view |
| `AnnotationKey`, `Name` | type code |

- Add `PartitionKeys.GetTemplate(string projectName)` → `$"{projectName}.template"` and `GetCosmosTemplate(...)` to `Backend.CosmosDb/src/PartitionKeys.cs`. A subject or responsibility named `template` is not a problem, because annotation partitions always include `.rst.` or `.sbt.`.
- `EntityIdPrefixTypes`: add `GenerateTemplate = "gen"` and `GenerateTemplateVersion = "gnv"`.
- Type codes are lower-cased and must be in `AnnotationTypeCodes.ValidCodes`. All seven types can have a template.
- The template applies to every configuration of its type **in its view**, across all annotation partitions. Other views are not affected.
- The id has the same shape as the old per-partition template ids, but lives in a different partition, so the two never collide.

### 2. Entities

- **`GenerateTemplateEntity`**: add `public ulong Version { get; init; }`.
- **New `GenerateTemplateHistoryEntity`** (`Entities/Configurations/`): same shape as `ConfigurationHistoryEntity` (`Version`, `Content`, `Author`, `CreationTime`, `ttl` of 365 days). Id is `{view}.gnv.{typeCode}.{version}` in the `{project}.template` partition, so every view has its own version sequence. Add `GetExpirationTime()` for it. The existing expiration calculation becomes a shared private helper that both history entities use.

### 3. Calculation read path

`TryAutogeneratePropertiesAsync` changes to read `{key.ViewName}.gen.{typeCode}` from `PartitionKeys.GetCosmosTemplate(key.ProjectName)`. Merge position and semantics do not change: ancestors first, then the template, then the stored content.

All nodes of one inheritance graph are in the same view, so the template for a type is the same for the whole calculation. `CalculateAndCacheConfigurationAsync` therefore gets a per-calculation memo (`Dictionary<string, JObject?>` keyed by type code). The memo is passed down the recursion, so each type's template is read at most once per calculation. It is not cached across requests, because an invalidation (section 6) must take effect immediately.

Items in the old location (`{view}.gen.{type}` inside annotation partitions) are **no longer read** and are not migrated (decision D1).

Add a new `TemplateNotFoundException` in `Backend.Core/src/Configuring/`, modelled on `ConfigurationNotFoundException`.

The implementation is `Backend.CosmosDb/src/Configuring/CosmosConfigurationTemplateService.cs`. Register it in `EntryPoint.AddCosmosDbAnnotations` with `services.AddSingleton<IConfigurationTemplateService, CosmosConfigurationTemplateService>()`. It uses the organization container.

| Method | Behaviour (mirrors) |
| --- | --- |
| `GetTemplateAsync` | Point read `{view}.gen.{type}`. Returns `null` if missing. |
| `CreateOrUpdateTemplateAsync`, no item | Apply `RemoveRequested` and `ApplyPatchRequested`. Set `Version = max(history.Version) + 1` from the `{view}.gnv.{type}.*` items. Create the item, then invalidate (section 6). *(configuration create branch)* |
| `CreateOrUpdateTemplateAsync`, item exists | Clone `Content`, run `MergeInto(value)`, `RemoveRequested`, `ApplyPatchRequested`. Equal content → return the current template with no write. Otherwise run one transactional batch: create history `{view}.gnv.{type}.{Version}` from the current item, then upsert the item with `Version + 1`, the new content, and the new author. Then invalidate. |
| `PatchTemplateAsync` | Missing → `TemplateNotFoundException`. `Content.ApplyPatch(ops)`. Equal content → return current. Otherwise the same history + upsert batch, then invalidate. *(`PatchConfigurationAsync`)* |
| `DeleteTemplateAsync` | Missing → `false`. Otherwise one batch: create history of the current version, delete the item. Then invalidate and return `true`. *(`ClearConfigurationAsync`)* |
| `GetTemplateVersionsAsync` | History items with id prefix `{view}.gnv.{type}.`, ordered by `Version`, plus the current item last (`ExpirationTime = DateTimeOffset.MaxValue`). |
| `GetTemplateVersionContentAsync` | The history item. Otherwise the current item when its `Version` matches. Otherwise `null`. |
| `GetTemplateVersionChangesAsync` | Uses `JsonContentDiffer` (below). Version `0` is an empty object. An unknown version throws `InvalidOperationException`. |

Where this differs from configurations, on purpose:

- **Concurrency.** The upsert inside the batch carries `IfMatchEtag` of the item that was read. The history `CreateItem` also fails with 409 if another writer already archived that version. On either conflict, re-read and retry up to 3 times, the same retry policy as `UpsertWithOptimisticConcurrencyAsync`. Only one template exists per type per project and view, so concurrent writers are much more likely than for a single configuration.
- **Invalidate after writing, not before.** If invalidation ran first, a read between the two steps could calculate with the old template and cache the result again.
- **Atomic writes.** History and item are always written in one batch.
- **No view diff.** Configurations have a view-to-view diff; templates do not get one in this spec. It can be added later if templates need to be promoted between views.
- **No schema check.** Template content is not validated against configuration schemas (unchanged).

Shared code extracted from `CosmosConfigurationService`, without behaviour change:

- **`Configuring/JsonContentDiffer.cs`**: an `internal sealed class` built from `IJsonSerializationSettingsProvider`. It takes `GetConfigurationChangesAsync`, `ComputeWordSegments`, `BuildSegments`, and `BuildHunks` (lines 237–458). `CosmosConfigurationService` delegates to it.
- **`Configuring/ConfigurationCacheInvalidator.cs`**: an `internal static class` that takes the two static `InvalidateConfigurationsAsync` overloads (lines 1186–1269) and adds the fix from section 6. `CosmosConfigurationService` keeps its per-type switch and calls the helper.

New mapping file `Backend.CosmosDb/src/TemplateMappings.cs` with `ToConfigurationTemplate(...)` and `ToConfigurationVersion(...)` for both entities.

### 6. Cache invalidation on template writes

A template for type `T` in view `V` is merged into every configuration of type `T` in view `V` of the project. Every descendant of those configurations inherits it too. After a create, update, patch, or delete, clear `CalculatedContent`, clear `CalculatedContentHash`, and increment `AffectedCounter` on every configuration item (ids starting with `{V}.cnf.`, never history or annotation items) with `ProjectName == project`, `ViewName == V`, and a type in:

| Template type | Invalidated configuration types |
| --- | --- |
| `rst` | `rst`, `unt`, `usg`, `exe`, `uxe` |
| `unt` | `unt`, `uxe` |
| `sbt` | `sbt`, `usg`, `cnt`, `exe`, `uxe` |
| `usg` | `usg`, `exe`, `uxe` |
| `cnt` | `cnt`, `exe`, `uxe` |
| `exe` | `exe`, `uxe` |
| `uxe` | `uxe` |

This table comes from `BuildInheritanceGraph`: each type plus every type that has it as a direct or indirect ancestor. Put it as a static lookup on `ConfigurationCacheInvalidator`. The predicate is `config.ProjectName == project && config.ViewName == view && config.Id.StartsWith($"{view}.cnf.") && codes.Any(c => config.AnnotationKey.StartsWith(c + "."))`, written out as an explicit `||` chain so the Cosmos LINQ provider can translate it. Other views are never touched.

**Cross-partition invalidation fix (also applies to configurations).** A template change is cross-partition across all annotation partitions of the view, so it can touch far more items than a configuration change. The shared invalidator changes as follows:

- Read ids through a `FeedIterator` (async, paged) instead of the synchronous `.ToList()`.
- Split the patch operations per partition into batches of at most **100** operations (the Cosmos transactional batch limit), and run them with bounded parallelism.
- Check `TransactionalBatchResponse.IsSuccessStatusCode` and throw on failure, so a partially invalidated cache is not silently accepted. The template write has already committed at that point. A retry of the same request is safe, because re-invalidating is idempotent.

The single-partition overload gets the same 100-operation chunking. That fixes the existing latent failure for partitions with more than 100 configurations.

Items created by the system (empty `Content`, only `CalculatedContent`) are invalidated like any other item and get recalculated on the next read.

## Decisions

- **D1 — Existing templates in the old location are left unused.** Items `{view}.gen.{type}` inside annotation partitions are no longer read once section 3 ships. None are in use, so there is no migration and no cleanup. They stay in place as dead items.
- **D2 — Templates are per view (revised 2026-09-30).** There is one template per type per project **and view**, and views are fully isolated: separate content, separate version history, and separate cache invalidation. The first version of this decision made templates project-wide, for all views. It was changed because every template write then invalidated configurations across the whole project.
- **D3 — Eager cache invalidation.** A template write invalidates all affected configurations in the same request, as described in section 6, including the fix for the 100-operation batch limit. Lazy invalidation (stamping calculated documents with template versions and comparing on read) is not planned. With per-view templates the invalidation covers one view only. Revisit it only if eager invalidation proves too slow for large views.

## Open questions

- **Q4 — Template vs. schema.** Template content becomes part of the calculated document but is not validated against the type schema, so a template can make calculated configurations violate their schema. Setting a template could validate each configuration's stored content + template + ancestors against the combined schema, but that means recalculating the whole view on every template write. This plan leaves the check out; it can be added in a follow-up spec if needed.

## Out of scope / known limitations

- `set` and `edit` use **merge** semantics, the same as configuration. A property deleted in the editor stays on the server unless `$remove` is used, and arrays are unioned. `sform story config edit` has the same limitation. It should be fixed for both in a separate change.
- There is no CLI `config versions` command. Adding one would give configuration parity, but it is outside this spec.
- A template written directly into Cosmos gets no version, no history, and no cache invalidation.
