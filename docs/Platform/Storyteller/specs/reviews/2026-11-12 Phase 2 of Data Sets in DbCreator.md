# Phase 2 of Data Sets in DbCreator

## Overview

Phase 2 of the spec [Data Sets in DbCreator](../2026-11-12%20Data%20Sets%20in%20DbCreator.md) (424-252) covers section 2, the bulk writer of annotations: a new interface `IAnnotationBulkWriter` with its options and result types in `Backend.Core/src/Annotating`, its Cosmos implementation as the partial `CosmosAnnotationService.Bulk.cs` (so the items come from the same mapping, serializer and audit store as a create), registered by `AddCosmosDbAnnotations`, and the small additions it needs: a parallelism and a cancellation token for `BatchPlan`, and a chunked read of nodes in `AnnotationItemStore`. `IAnnotationService` and its fakes are untouched. It is the commits `refactor(platform): prepare batch plans and item reads for bulk writes (424-252)` and `feat(platform): add a bulk writer of annotations (424-252)`. DbCreator does not use the writer yet (phase 3).

## What Was Done

### 1. `IAnnotationBulkWriter` and its types (Backend.Core)

- `IAnnotationBulkWriter.cs`: `CreateMissingAnnotationsAsync(organization, project, view, IReadOnlyList<Annotation> annotations, AuditActor actor, AnnotationBulkOptions? options = null, CancellationToken cancellationToken = default)` returning `AnnotationBulkResult`, as in the spec. Its comment adds that the outcomes are those of a sequential import with `Existing = Skip`, and that **the project and view of the call win** over the `ProjectName` and `ViewName` of the annotations (the writer normalizes each annotation into the target, so a caller cannot write outside it by mistake).
- `AnnotationBulkOptions.cs`: `DryRun`, `MaxParallelBatches` (4), `MaxUnitsPerPlan` (2 000), `Progress` (`IProgress<int>`), as in the spec. A value below 1 for either limit throws `ArgumentOutOfRangeException`.
- `AnnotationBulkResult.cs`: `(IReadOnlyList<AnnotationBulkItem> Items, IReadOnlyList<string> AncestorsCreated, int RelationUpdates)`; `AnnotationBulkItem.cs`: `(AnnotationKey Key, ViewImportResult Result)`. Each type is in its own file (StyleCop `SA1402`). `Items` are in input order, one per input annotation (a duplicate included).

### 2. `CosmosAnnotationService.Bulk.cs`

`public partial class CosmosAnnotationService : IAnnotationBulkWriter`. It reuses the private members of the service: `Store`, `ToStoredEntity`, `Stamp`, `PendingWrite` / `PendingKind`, `RelationsWave`, `_serializer`, `_audit` (`Prepare`, `Write`, `NewEntry`) and `_timeProvider`. The algorithm, by the steps of the spec:

1. **Validate, normalize, deduplicate** (`ReadBulkInputs`, once per call, before any read). The second and later occurrences of a key fail with `DuplicateFile` (`The input holds the annotation {key} more than once; only the first counts.`), as the second file of an archive does; a duplicate fails nothing below it, the first occurrence counts. A key that breaks `AnnotationRules` fails with `InvalidAnnotation` and the message of `ViewAnnotationDocument.TryRead` (`The annotation '{key}' is not valid: …`). The others are normalized with `AnnotationFactory.Normalize(annotation with { ProjectName = project, ViewName = view }, key)`. Then, in the order of an import (depth, type, key), every key below a failed one is `Skipped` with `DependencyFailed` and counts as failed for the keys below it, so the messages list the same ancestors as the import's overlay does (`The ancestors sbt.bad, cnt.bad.c failed in this import.`).
   - **Decision:** an annotation whose `AnnotationKey` does not parse throws `InvalidInputException` (`InvalidKey`) for the whole call instead of failing one item, because an `AnnotationBulkItem` needs a key; the callers read the keys from file names and `annotations.jsonl`, where a bad key is already reported.
2. **Read the closure** (`CreateMissingCoreAsync`, once per attempt): the candidates and every ancestor of them, read with `AnnotationItemStore.ReadNodesAsync(…, withAudit: false)` (annotation items with their ETags). The audits are read after the decision, only for the nodes that will be written (`LoadAuditsAsync`), and not at all in a dry run, so a re-run over an existing set does not read the audits of active keys. A missing key with an orphan audit continues it: `Prepare` appends the entry to the read audit and `AnnotationAuditStore.Write` replaces it under its ETag, as in `CreateCoreAsync`.
3. **Decide** per candidate in the order of the import, mirroring `ImportCoreAsync` and `ImportActiveAsync`: an active key is `Unchanged` when `AnnotationAuditDiff.Compute(stored, normalized)` is empty, otherwise `Skipped` with `DocumentExists`. Otherwise the keys it writes are its ancestors that are not active and not created by an earlier key of the input (the import's overlay), plus itself; any deleted one among them skips it with `AnnotationDeleted` and the import's message. Otherwise they are marked for creation: an ancestor with `AnnotationFactory.CreateDefault(ancestor, project, view, copyFrom: the key)` and the audit cause `Ancestor` with the key, and the result is `Created` with the import's `AncestorCreated` warning. The messages come from helpers that `CosmosAnnotationService.Import.cs` now uses too (`DependencyFailedResult`, `DeletedSkippedResult`, `DocumentExistsResult`, `AncestorCreatedWarning`), so both say the same words.
4. **Relation arrays** (`AddBulkRelations`), set-wise: per parent and array, the names it gains in order. A created parent gets the names of its created children in the order they are created (which equals the order of a sequential import); an active parent gets, in one ETag-guarded replace in `RelationsWave` (no audit entry, `Modified` kept), first the active children of the closure it does not list (in import order: the repair of an earlier run whose relations wave failed), then the created children it lacks. `AnnotationRelations.AddRange` (new) appends the missing names at once and returns the same reference when nothing changes, so an unchanged parent is not written.
5. **Write**, unless a dry run: one `PendingWrite` per created key (`ToStoredEntity(model) with { Created = stamp, Modified = stamp }`, one stamp and one `now` per attempt) and one unit per write (the annotation `CreateItemStream` plus the audit create or replace, in the key's partition). `WriteBulkCreatesAsync` runs the waves by depth, each wave sorted by partition (so a partition's units share as few batches as possible) and cut into plans of at most `MaxUnitsPerPlan` units with `MaxParallelBatches` batches at once; the streams are serialized per plan and released when it is disposed. `WriteBulkRelationsAsync` then writes the replaces of active parents, in plans of the same size. `Progress` is told the number of annotations this call committed after each plan of creates; a dry run reports nothing.
6. **Retries:** an `AnnotationConcurrencyException` (409, 412 or 404 of a batch) runs the whole procedure again at once; a `CosmosException` with 429 waits its `RetryAfter`, or `attempt` seconds without one, and runs it again; at most 5 attempts. After the last, a concurrency failure becomes a `ConflictException` (`Conflict`), and a 429 is rethrown. The `Committed` callbacks of the batches record, over the attempts, the keys this call created and the parents it replaced (`BulkCommits`, thread-safe, because the batches of a wave run in parallel). A later attempt decides a key it committed as missing (its state before the call), so it is still reported `Created` with the same warnings, and it is not written again; its name reaches an active parent through the repair of step 4.
   - `AncestorsCreated` lists the ancestors marked for creation in the order they are created (in a dry run: would be), plus, after a concurrent change, an ancestor an earlier attempt committed that no key needs any more. `RelationUpdates` is the number of parents whose replace committed during the call (in a dry run: the planned replaces).
- Registration (`EntryPoint.cs`): `services.AddSingleton<IAnnotationBulkWriter, CosmosAnnotationService>()`, next to the other services of `AddCosmosDbAnnotations`.
  - **Decision:** a second instance rather than a forward to the `IAnnotationService` registration: the service holds no state, and `Api.Web` registers `IAnnotationService` again, which a forward would follow.

### 3. `BatchPlan` and `AnnotationItemStore`

- `BatchPlan(OrganizationContainer repository, int maxParallelBatches = 8)` (below 1 throws) and `ExecuteAsync(CancellationToken cancellationToken = default)`: the token is checked before each wave and passed to the throttle and to every batch. Every existing caller uses the defaults, so nothing changes for them.
  - **Addition:** a batch that fails with 429 throws a private `BatchFailedException : CosmosException` that overrides `RetryAfter` with the response's (a `CosmosException` made by its public constructor carries none), so the bulk writer can honour it. It is still a `CosmosException` of the same status and message for every other caller.
- `AnnotationItemStore.ReadNodesAsync(IEnumerable<FullKey> keys, bool withAudit, CancellationToken)` returns a node per key text (Missing without an annotation item), and `LoadAuditsAsync(IEnumerable<AnnotationNode> nodes, CancellationToken)` completes nodes read without their audits. Both go through one private reader that sends the ids in `ReadManyItemsStreamAsync` calls of at most 1 000 items (the size of the client's own queries), one after another, and dispatches the documents by id to `ReadAnnotation` or `ReadAudit` with their `_etag`. The existing `ReadManyAsync` and `ReadStatesAsync` are unchanged.

### 4. Tests

`Backend.CosmosDb/test/CosmosAnnotationBulkWriterTests.cs` (new, 11 tests, each in its own project of `42dotnet`; the writer from DI, or over an `InterceptedRepositoryProvider` for the failure tests):

- `CreateMissing_WritesTheItemsAndReportsTheOutcomesOfAnImport`: nine annotation files in a shuffled order (values with a decimal, a date string and nesting; a unit with its type and definition; a unit of execution with a validity window, time zone, labels and flag whose ancestors are created with defaults; an equal, a different and a deleted-ancestor key; children of active parents) go through the `ViewImporter` of phase 1 with `Skip` into view `imported`, and through the bulk writer into view `bulkload`, over the same pre-existing annotations. Every bulk item equals the import's result (`BeEquivalentTo`, warnings included), the ancestors and the 3 relation updates are as expected, and the annotation and audit items of all 13 active keys are equal as JSON once the system properties, the id, the view, the times of the stamps and entries, the entry ids and the audit size are removed.
- `CreateMissing_LeavesAnEqualAnnotationUnchangedAndSkipsADifferentOne`: `Unchanged` and `Skipped DocumentExists`; nothing is written (one audit entry each).
- `CreateMissing_AddsTheNewNamesToTheArraysOfActiveParents`: units under an active responsibility and an execution under an active subject: the arrays gain the names in import order, two replaces, `Modified` and the audit of the parent unchanged.
- `CreateMissing_SkipsADeletedKeyAndWhatHangsOnIt`: a deleted subject and its deleted context, with keys on, below and beside them: the import's `AnnotationDeleted` messages, nothing of the subtree or its missing ancestors written.
- `CreateMissing_FailsInvalidAndDuplicateKeysAndSkipsWhatHangsOnThem`: `InvalidAnnotation`, `DuplicateFile` (the first occurrence written), and `DependencyFailed` one and two levels below.
- `CreateMissing_DryRunDecidesEverythingAndWritesNothing`: the outcomes, warnings, ancestors and relation updates of a dry run, no progress, nothing written; the real run afterwards returns an equivalent result.
- `CreateMissing_ContinuesTheAuditOfAMissingKey`: the annotation item of a key is deleted under its audit; the bulk create continues the audit (two `Created` entries).
- `CreateMissing_RunsAgainAfterAConcurrentChangeAndReportsWhatItCommittedCreated`: the first relations batch fails with 412 after the keys committed; the second attempt writes no key again (no 409), reports them `Created` with the ancestor warning, and completes the array.
- `CreateMissing_WaitsOutAThrottleAndRunsAgain`: the first batch fails with 429; the call waits and completes.
- `CreateMissing_AgainRepairsTheArraysOfAFailedRelationsWave`: every relations batch fails with 503 (not retried), so the call throws with the keys written and the arrays incomplete; a second call reports the keys `Unchanged` and repairs both arrays in two replaces, without audit entries.
- `CreateMissing_WritesThousandsOfKeysOverManyPartitions`: 2 030 annotations (30 responsibilities with 30 units, 120 subjects with 8 contexts, 20 executions whose usages are created) over 150 partitions with `MaxUnitsPerPlan = 250`: all `Created`, 20 ancestors, 2 050 annotations stored with full arrays in order, the audits by the actor and with the ancestor cause, ascending progress ending at 2 050, and a second run all `Unchanged`.

Results, with `STORYTELLER_TESTS_USE_CONTAINER=true`, each class in its own `--filter-class` run of `Backend.CosmosDb/test`: on vNext, `*CosmosAnnotationBulkWriterTests` 11 passed (also 11 on the classic emulator), `*CosmosViewImportTests` 32, `*CosmosAnnotationServiceTests` 14, `*CosmosAnnotationLifecycleTests` 23 (delete and restore), `*CosmosAnnotationConditionalWriteTests` 15, `*CosmosAnnotationPatchTests` 8, `*CosmosAnnotationAuditTests` 7 (1 skipped on vNext, classic only), `*AnnotationHierarchyTests` 7 and `*CosmosViewTransferTests` 22. `dotnet test --project src/Platform/Storyteller/Backend.Core/test` passed 1 386 of 1 386. A full rebuild of `Backend.CosmosDb.UnitTests` (with Backend.Core, Backend.CosmosDb and DbCreator) has the same warnings, per file and rule, as before the phase.
