# Phase 4 of Data Sets in DbCreator

## Overview

Phase 4 of the spec [Data Sets in DbCreator](../2026-11-12%20Data%20Sets%20in%20DbCreator.md) (424-252) covers the last items of section 3 and section 4: the built-in set `showcase`, written from the admin UI's showcase mock by a Vitest test (3.11, with its entry in 3.9), the Aspire resource `db-seed` (3.12), the unit test of the new set (4.1), the integration test project `DbCreator/testint` against a Cosmos DB emulator (4.2), and CI (4.3). Phases 1 to 3 delivered the importer, the bulk writer, the sets, the commands and `DbCreator/test` (see their reviews). It is the commits `feat(platform): add the built-in data set showcase of DbCreator from the admin UI's mock (424-252)`, `feat(platform): seed the data set showcase from the Aspire host (424-252)`, `test(platform): seed data sets against a Cosmos DB emulator in DbCreator's integration tests (424-252)` and `ci(platform): run DbCreator's integration and unit tests in the Cosmos DB workflow (424-252)`. The documentation of section 5 is the next step; this phase touched only the pages its changes would otherwise make wrong (see 3.12 and 4.3).

### 3.11 The admin UI's showcase as the set `showcase`

- `src/Platform/ui.admin/src/test/unit/mock/showcase-set.test.ts` (Vitest, `// @vitest-environment node`: it needs no DOM):
  - builds the scope `fabrikam` / `invoicing-suite` / `default` with `buildShowcaseScope` from `@/mock/showcase` (the builder that does not memoize) under a frozen clock: `vi.useFakeTimers({ toFake: ['Date'] })` and `vi.setSystemTime(new Date('2026-11-01T00:00:00Z'))`, as `showcase.test.ts` freezes it, restored before any assertion. The scope computes `ValidFrom` and `ExpiresAt` from now, so the clock keeps them stable;
  - writes, as a Git export of the view gives them: per active annotation `annotationDocument(annotation)` (`transfer-handlers.ts`) at `getPath('Annotation', undefined, key)`, and per document of the scope the content of its current version at the path `getPath` gives for its kind (configuration, template, type, annotation and descendant-type schema; the `DocumentId` of the mock is mapped to the kind, type and key in `documentPath`), as 2-space JSON with a final newline;
  - **decision**: like the export (`viewDocuments`), the documents of a deleted annotation are left out (the showcase deletes `cnt.trey-research.sandbox` and `exe.vanarsdel.portal.production` with their descendants; the scope's `annotations` holds only the active ones), and so is a document whose current version has no content. Without this, the seed would report `Skipped AnnotationNotFound` for them;
  - one test per file, `await expect(text).toMatchFileSnapshot(path)` into `src/Platform/Storyteller/DbCreator/src/data-sets/showcase/`, so a changed file names itself; a first test checks the shape (more than 150 annotations, the documents of the documentation's example); a last one lists the set folder (hidden paths left out, as the import skips them) and fails with the files the scope no longer gives, `set.json` excepted. A missing file fails under `CI=true`, where Vitest writes no snapshot; locally Vitest writes it (its default).
  - Regenerate with `npx vitest run test/unit/mock/showcase-set.test.ts -u` in `src/Platform/ui.admin/src`. **Note:** the path comes first: in Vitest 4 `-u` takes an optional value, so `vitest run -u <path>` reads the path as that value and runs every test file. The comment of the test says so.
  - A checkout with `core.autocrlf` is fine: Vitest compares a CRLF snapshot file with an LF value after normalizing it, and the hash of a set counts CRLF as LF (phase 3).
- The set (`DbCreator/src/data-sets/showcase/`): 398 generated files, 242 annotations (6 `rst`, 3 `unt`, 22 `sbt`, 35 `cnt`, 52 `usg`, 92 `exe`, 32 `uxe`), 153 configurations, the descendant-type schemas `rst.invoicing.usg` and `sbt.northwind.cnt` and the template `uxe`, and `set.json` written by hand: `Name` `showcase`, `Version` 1, target `fabrikam` / `invoicing-suite` / `default`, `ProjectDescription` the description of the mock project, and a `Description` that names the scope and says that the documents are generated by the test and must not be edited by hand. The dates are absolute from the frozen clock, so a scheduled annotation becomes active over time. The one binding of the scope, `@(northwind.adyen-merchant, primaryVault)` in `exe.northwind.payments.production`, has a hyphen and is stored as it is: the import does not resolve bindings, but a resolved read of that configuration on a real platform fails (see Open points).

### Review findings

A review of the phase reported three findings, all low. All three held against the code and were fixed; none was rejected. The sections above describe the phase as first committed, so their counts (242, 153, 398) and the binding of 3.11 are those of that commit.

1. **The step `DbCreator unit` was skipped whenever an emulator suite failed** (fixed in `ci(platform): run DbCreator's unit tests also after a failed Cosmos DB suite (424-252)`). It is the last step of the vNext job and the only CI of those tests. It now has `if: ${{ !cancelled() }}`: it runs after a failed suite, and not when the run is cancelled or the job times out, which fails the run anyway. Its comment and the Cosmos DB row of `docs/github/workflows.md` say so. **Alternative not taken**: moving the step first. A failure of its own would then skip the three emulator suites, which have no other CI either, unless every suite got `!cancelled()` too. That would change how the whole job behaves, and the step's fast feedback is not worth it: a failure shows in the same run either way.
2. **The tests of the set `showcase` hard-coded its counts** (242 annotations, 153 configurations, 2 descendant-type schemas, 1 template, 398 created), so every change of the admin UI's showcase mock needed edits of two C# tests as well. Fixed in `test(platform): count the showcase set's documents from its folder in DbCreator's tests (424-252)` (the integration test) and `test(platform): check the showcase set's documents against its folder in DbCreator's unit tests (424-252)` (the unit test; both lived in one working copy, and the first commit's message already names it). The counts now come from the set's folder (`DataSetFolder.GetEntries`):
   - `BuiltInSetsTests.Showcase_IsTheInvoicingSuiteOfTheMocksShowcase` (unit) checks that every file of the folder reads as a document (`Files.Count` equals the entries), that each lies in the folder of its kind (`ViewArchiveNames.GetFolder(GetContent(kind))`), and that annotations and configurations are among them. The structural checks stay: the target, the project description, no dependency, no line file, no failure or ignored file, and every document and annotation with its ancestors in the set.
   - `BuiltInSetsTests.Showcase_SeedsWithoutFailures` (integration) checks that the total `Created` is the number of files and that the `Created` of each kind's summary is the number of files in that kind's folder. It also checks that annotations were created and keeps the check of the project's description.
3. **The set seeded a binding that does not parse** (fixed in `fix(platform): seed a showcase binding that parses, and check every binding of the sets (424-252)`). The binding was `@(northwind.adyen-merchant, primaryVault)` in `exe.northwind.payments.production`.
   - The mock (`app/mock/showcase/projects/invoicing-suite.ts`) now holds `@(northwind.adyenMerchant, primaryVault)`, with a comment: the binding language takes no hyphen in a path, and a Key Vault secret name takes no underscore. `KeyVaultBindingSource` joins the path with `--`, so the secret is `northwind--adyenMerchant`. `npx vitest run test/unit/mock/showcase-set.test.ts -u` regenerated the set, and only that configuration changed; the same file passes with `CI=true`.
   - A correction to the open point below: the source `primaryVault` was never a problem. An unregistered source resolves to nothing, and the string stays as stored (`BindingEvaluator`). Only the hyphen failed the read.
   - New unit test `BuiltInSetsTests.EverySetOfTheRepository_HasBindingsThatParse` (`DbCreator.UnitTests` now references `Binding.Language`). It checks every built-in set and the playground's folder. It reads every configuration, and every template too, since a template is merged into the effective configuration of its type (`CosmosConfigurationService`). It picks the strings the platform binds: as `ConfigurationBindingResolver` walks a document and `BindingExecutor` reads a string, that is every string starting with `@`, at any depth, except under the `$definition` of an object with a string `$binding` (the program of an object binding, passed through). Each such string must be within `BindingExpressionLimits.MaxLength` and must tokenize and parse with the platform's `Tokenizer` and `Parser`. It does not evaluate them, since the sources and functions are the platform's. A first assertion checks that the old text throws `BindingSyntaxException`. With the old file back in place, the test fails and names `showcase: configurations/exe.northwind.payments.production.conf.json at merchantId`.
   - Left as it is: other projects of the showcase mock also hold hyphenated paths, for example `@(velvet.adyen-live-api-key, primaryVault)` in `storefronts.ts`, and the tests of `white-label-app` and `finance-cloud` assert that shape. No set is written from them, so the platform never reads them; only the mock renders them. If one becomes a set, the new test reports its bindings.
