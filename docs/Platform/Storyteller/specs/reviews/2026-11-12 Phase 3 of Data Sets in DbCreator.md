# Phase 3 of Data Sets in DbCreator

## Overview

Phase 3 of the spec [Data Sets in DbCreator](../2026-11-12%20Data%20Sets%20in%20DbCreator.md) (424-252) covers the library part of section 3 in DbCreator (`src/Platform/Storyteller/DbCreator/src/DataSets/`): the set manifest, `annotations.jsonl` with generator lines, the folder reader and the content hash, the catalog of built-in and `--path` sets, the target and owner, the provisioning of the target through `IAccessService` and `IViewService`, the seed record, the seeder `DataSetSeeder` on the importer of phase 1 and the bulk writer of phase 2, and `AddDbCreator`. The core data moved too (3.9, set `core`), because both Cosmos fixtures depend on `CoreDbStructureBuilder.BuildAsync()`. The unit tests of section 4.1 are the new project `DbCreator/test`. A second step added the commands (3.8), the set `large` and the Playground manifest (3.9), with their tests and a run against an emulator. The set `showcase` with the admin UI's showcase (3.11), Aspire (3.12), `DbCreator/testint` and the documentation (section 5) are later steps. It is the commits `feat(platform): seed data sets with DbCreator (424-252)`, `refactor(platform): seed the core annotations as the built-in set core (424-252)` and `test(platform): cover the data sets of DbCreator (424-252)`, then `feat(platform): seed and list data sets with the commands of DbCreator (424-252)`, `feat(platform): add the built-in data set large and the set of the playground (424-252)` and `test(platform): cover the commands of DbCreator (424-252)`, and after an independent review of the phase (see [Review findings](#review-findings)) `fix(platform): count the keys of earlier steps as active in a dry run of the bulk writer (424-252)`, `fix(platform): refuse a dotted organization and a set beyond the limits before a seed writes (424-252)`, `fix(platform): seed the lines above an annotation file before the file and carry a dry run over the sets (424-252)` and `test(platform): cover the exit code 4 of the root command of DbCreator (424-252)`. The sections below describe the final state.

## What Was Done

### 3.1 The set and its manifest

- `DataSetManifest.cs`: the record of `set.json` (`Name`, `Version`, `Description`, `Organization`, `Project`, `View`, `ProjectDescription`, `ViewDescription`, `DependsOn`) and `Read(IFileSystem, folder)`, with System.Text.Json: member names in any case, `JsonUnmappedMemberHandling.Disallow`, comments and trailing commas allowed. `Name` defaults to the folder name, `Version` to 1; the target names are trimmed (blank is none), `DependsOn` trimmed and distinct.
- **Additions:** the name must pass `NameRules.IsValidName` (2 to 63 lower-case letters, digits or hyphens), because it is a segment of the record's id and an argument of the command; `Version` must be 1 or more; an empty name in `DependsOn` is refused. Every problem, a missing `set.json` included, is a `DataSetException` with the path (`DataSetException.cs`: the wrong input of a seed, exit 2 in the command).
- `DataSet.cs` (`Manifest`, full `Folder`, `Source`) and `DataSetSource.cs` (`BuiltIn`, `Path`).

### 3.2 `annotations.jsonl` and generators

- `DataSetAnnotationLinesReader.cs`: `Read(IFileSystem, folder, target)` (null without the file; `File.OpenText`, so a BOM is fine) and `Read(TextReader, target, source)`. Blank lines and lines starting with `//` (after trimming) are skipped. Each line goes through `ViewAnnotationDocument.Parse` and the annotation through `ViewAnnotationDocument.TryRead` with the target's `FullKey`, so numbers keep their text and dates stay strings, and the `AnnotationKey` member stays in the document, which `TryRead` checks against the key as in a file.
- A line with `$count` (and `$start`, default 1; both matched in any case and removed) is a generator: per index, `Generate(document, index)` replaces `{n}` with the index and `{0…0}` with the index padded to that width (wider when the index is) in every string value at any depth (`Title`, `Labels`, `Values`, the key). Member names are not substituted. A line without `$count` is literal.
- The results are `DataSetAnnotationLine` (`Line`, `Key`, `Annotation` or `ErrorCode` and `Message`) in `DataSetAnnotationLines` (`Annotations`, `Lines`, `GeneratorLines`). Codes: `InvalidDocument` for a line that is not a JSON object, has no `AnnotationKey`, or a `$count` that is not a whole number of 1 or more (`$start`: 0 or more, `$start` without `$count`); `InvalidKey` for a key that does not parse (the type code in any case is lowered as in a file name; empty segments are refused); otherwise the codes of `TryRead` (`InvalidDocument`, `InvalidAnnotation`), per generated annotation.
- **Decision:** the limit of 200 000 annotations per set is checked over all lines before any line is expanded (a failed line counts as one), so an oversized generator costs nothing; beyond it `DataSetException` names the file and the line. `CountAnnotations(IFileSystem, folder)` runs the same parse and check without expanding anything (0 without the file), for the plan of a seed (3.8).
- `DataSetContent.cs`: `Read(IFileSystem, folder, target)` gives the documents and the lines, and `WithoutDuplicates` fails with `DuplicateFile` a line whose key an annotation file holds (any annotation file, a failed one too: `The file '…' already holds the annotation …`) or an earlier line holds (`Line N of annotations.jsonl already holds the annotation …`), as the reader does with a second file of one key.

### 3.3 The folder reader, the hash and the catalog

- `DataSetFolder.cs`:
  - `GetFiles(IFileSystem, folder)`: every file below the folder as `DataSetFile` (path with `/`, full path), in ordinal order; a path that `ViewArchiveNames.IsSkippedPath` skips is not entered.
  - `GetEntries`: the files as `ViewArchiveEntry` (length from `FileInfo`, `Open` through the file system), without `set.json` and `annotations.jsonl` at the root, so they are not counted as ignored (a nested `set.json` is, like any other non-document).
  - `ReadDocuments`: `ViewArchiveReader.Read(entries, ReaderOptions)`, with `ReaderOptions` sized for sets: `MaxArchiveEntries` 1 000 000, `MaxExtractedBytes` 2 GiB, `MaxDocumentBytes` the 2 MB default.
  - `Validate`: the same limits from the number and the declared lengths of the files, without opening one, through the new `ViewArchiveReader.Validate(IReadOnlyCollection<ViewArchiveEntry>, ViewTransferOptions)` in Backend.Core (the entries counterpart of the zip's `Validate`, the same `Inspect`, so no rule is copied). Both turn an `InvalidInputException` of the reader into a `DataSetException`.
  - `ComputeHash`: SHA-256 (lower-case hex) over, per file in path order, the UTF-8 path, a NUL byte and the SHA-256 of the content. **Decision:** the content goes in as its own hash rather than its bytes, so no path and content can run into each other. Text files count with CRLF made LF (`NormalizeLineEnds`); a file is binary, and stays as it is, with a NUL byte among its first 8 000 bytes, Git's test, so a checkout with `core.autocrlf` and one without hash alike. Every file that is not skipped counts: the manifest, `annotations.jsonl`, and ignored files such as a README.
- `DataSetCatalog.cs` (singleton): `DataSetCatalog(IFileSystem, string? baseDirectory = null)`, the built-in folder `data-sets` below `baseDirectory ?? AppContext.BaseDirectory` (the container uses the default; tests give their own). `GetSets(paths)`: the built-in sets (sub-folders with `set.json`, hidden ones left out, in ordinal order; none when the folder is missing), then per `--path` folder in the given order (resolved with `Path.GetFullPath`): the folder itself when it has `set.json`, otherwise each sub-folder with one. A missing folder, a folder without any set and a name found twice are `DataSetException`s. `Resolve(sets, names)` (static): a depth-first walk over `DependsOn`, every set after its dependencies and once, the names in their order; a cycle names its path (`a -> b -> a`), an unknown name or dependency lists the catalog.
- `DbCreator.csproj`: `<None Update="data-sets\**\*" CopyToOutputDirectory="PreserveNewest" />`. The sets reach the output, the tool package (`tools/net10.0/any/data-sets/…`, checked with `dotnet pack`) and the output of the projects that reference DbCreator (both Cosmos suites and `DbCreator/test`).

### 3.4 The target

- `DataSetTarget.cs` (`Organization`, `Project`, `View`, `IsDefaultView`, `ProjectKey`): `Resolve(sets, organization, project, view)` takes the given names first (blank is none), otherwise the values of the named sets' manifests, which must agree (a set without one does not disagree; dependencies do not count); the view defaults to `default`. A missing organization or project, or manifests that disagree, are `DataSetException`s that name the option to give.
- `EnsureNames(isNewOrganization)`: `NameRules.EnsureOrganizationName` for a new organization and for any organization with a dot, `EnsureProjectName` always, `EnsureViewName` unless the view is `default`; an `InvalidInputException` becomes a `DataSetException`. A dotted name is the key of a project, never an organization, which is also how `CreateAccessPointAsync` checks it: `apt.42dotnet.main` reads as an existing access point, so without the dot rule `--organization 42dotnet.main` passed as an existing organization. The plan calls it with `isNewOrganization: false` (the project, the view and a dotted organization), the provisioning again after reading the access points and before any write.

### 3.5 The owner and the target's creation

- `DataSetOwner.cs`: `Resolve(ownerId, BaseAccountOptions)`: the given id, or `baseAccount:id` (the legacy default without one); an id with `:` must be `UserIdentity.IsEntraAccountId`, as `HasValidAccountId` checks the base account. The base account gets `Constants.BASE_ACCOUNT_USER_NAME` and `BASE_ACCOUNT_NAME`, another id is its own user name and name.
- `DataSetProvisioner.cs` (a class of its own, so the seeder stays about the sets) and `DataSetProvisioning.cs` (`IsAccountCreated`, `IsOrganizationCreated`, `IsProjectCreated`, `IsViewRegistered`; in a dry run: would be). `ProvisionAsync(target, owner, projectDescription, viewDescription, dryRun)`:
  1. reads `apt.{org}` and `apt.{org}.{project}`, then `EnsureNames`;
  2. **refinement of the spec:** a missing project in an existing organization whose Owner is not the owner is refused with a `DataSetException` before anything is written (no takeover); an existing project is used as it is, its access unchanged, whoever owns it;
  3. creates the owner's account when missing (`CreateAccountAsync`, `AccountExists` caught), first, so the project's membership is mirrored into it;
  4. creates the organization and the project when the project is missing (`CreateAccessPointAsync` with the owner and the description; `AccessPointExists` caught, an `AccessDeniedException` of a race and an `InvalidInputException` become a `DataSetException`);
  5. registers a view other than `default` when `GetViewsAsync(…, discover: false)` does not list it as registered (`CreateViewAsync` with the description and `AuditActor.System`, `ViewExists` caught, an `InvalidInputException` becomes a `DataSetException`). Reading first lets a dry run tell.
- The `InvalidInputException`s are a safety net behind `EnsureNames`: whatever the access model or the view registry refuses ends as wrong input (exit 2), not as the crash of `Program` (exit 1).
- **Decision:** the account is ensured even when the project exists. The descriptions come from the first named set that has one, then from the dependencies: a dependency such as `core` is not what the project is about.

### 3.6 The seed record

- `DataSetSeedRecord.cs`: the stored item itself: `Organization`, `PartitionKey` (`ViewEntity.GetPartitionKey(project)`, `{project}.meta`), `id` `seed.{view}.{set}`, `Set`, `View`, `Version`, `Hash`, `Seeded` (an `AuditStamp` of `AuditActor.System`) and the counts `Documents`, `Annotations`, `Created`, `Updated`, `Unchanged`, `Skipped`, `Warnings` (files and lines together). No `ViewName`, `ProjectName` or `AnnotationType`.
- `IDataSetSeedRecordStore.cs` and `CosmosDataSetSeedRecordStore.cs`: a point read (`ReadItemAsync`, 404 is null) and an upsert in the organization's partition, both with the client's serializer.
- What else reads `{project}.meta` (grep of `.meta`, `GetPartitionKey(project)` and the project-wide queries): the view registry reads it with `STARTSWITH(c.id, 'view.')`; view discovery needs `ViewName`; the project-wide queries of annotations need `ProjectName`, `ViewName` or `AnnotationType`; the key/value queries need `.kv.` in the partition key. None sees the record. **Note:** the configuration listings of a view query by id prefix (`{view}.cnf.`, `{view}.cfv.`) over the project's partitions, so a record of a view named `cnf` or `cfv` would match the listing of a view named `seed` (`seed.cnf.{set}`). It takes both view names in one project; the id is the spec's, so it stays.

### 3.7 Seeding one set

- `DataSetSeeder.cs` (`IFileSystem`, `DataSetCatalog`, `DataSetProvisioner`, `IViewImporter`, `IAnnotationBulkWriter`, `IDataSetSeedRecordStore`, `IOptions<BaseAccountOptions>`, `TimeProvider`, `ILogger<DataSetSeeder>`; no console output):
  - `SeedAsync(DataSetSeedRequest)`: the catalog with the request's `Paths`; the named sets, or without names the sets of the folders (none at all is a `DataSetException`); `Resolve`; the target from the named sets; the owner; `ProvisionAsync`; then every set in dependency order. **Addition:** a set that depends on a set with failures is not seeded (`FailedDependency`), since its annotations would hang on what is missing. Returns `DataSetRunResult` (`Target`, `Owner`, `Provisioning`, `Sets`, `IsDryRun`, `HasFailures`). The containers must exist; the command calls `EnsureContainersAsync` first.
  - **A dry run over several sets:** a dry run stores nothing, so the run keeps one overlay of what its sets would write, and each set's overlay starts from it: the active (and re-created) annotations, the schemas and the configurations of the sets before it, not their failures (a set that depends on a failed set is not seeded at all, and an independent set gets what the real run gives it). So the dry run of a set whose configuration breaks a schema of its dependency fails as the real run does. A real run gives every set a new overlay: the store has what the sets before it wrote.
  - `SeedSetAsync(set, target, DataSetSeedOptions)`: computes the hash and reads the record; same version and hash without `Again` is `IsAlreadySeeded` and nothing else is read. Otherwise `DataSetContent.Read`, `ViewImportOptions { Actor = AuditActor.System, Existing = Skip, Force, DryRun }` and one `ViewImportOverlay` for the set:
    1. a line of `annotations.jsonl` that could not be read is `Failed`, and its key joins `overlay.FailedAnnotations` (unless it is a `DuplicateFile`) before the first file is imported, so a file below it is `DependencyFailed` instead of creating the key with defaults;
    2. **the annotations in rounds** (`GetRounds`, a deviation from the spec's "files, then lines"): a file comes after the lines that are its ancestors, a line after the files that are its ancestors; ancestors of the same source share a round, since the importer and the bulk writer both take ancestors first. Each round imports its annotation files through `IViewImporter`, then sends its lines (`WriteLinesAsync`). Both a file import and the bulk writer create a missing ancestor with defaults, and `Skip` then keeps the defaults: with files first, a line `rst.payments` with a title above a file `unt.payments.ledger` was created empty by the file and then skipped for good (`Skipped DocumentExists`, the set recorded). A set without a line above a file has one round, files then lines, as before; the chain line, file, line, file of the four depths gives at most three rounds;
    3. per round, `WriteLinesAsync`: in depth order, a line whose key or an ancestor is in `FailedAnnotations` is `Skipped DependencyFailed` with the importer's words (`The ancestor(s) … failed in this import.`) and joins it, without being sent; the rest go in line order to `CreateMissingAnnotationsAsync` (`AnnotationBulkOptions { DryRun, Progress, DryRunActiveKeys }`); a `Failed` or `DependencyFailed` result joins `FailedAnnotations`; in a dry run the `Created` keys and `AncestorsCreated` join `ActiveAnnotations`, and `DryRunActiveKeys` gives the writer the overlay's active keys, so the files of the dry run (and the sets before it) count as stored for the writer as they do for the importer. The progress of a later round counts on from what the earlier rounds committed (`OffsetProgress`); the ancestors created and the relation updates add up over the rounds;
    4. the schemas, templates and configurations through `IViewImporter` with the same overlay;
    5. the record, unless a dry run or any `Failed` outcome.
  - `AnnotationBulkOptions.DryRunActiveKeys` (Backend.Core, an addition to phase 2): in a dry run, the keys earlier steps of the same dry run made active without storing them. The writer (`CosmosAnnotationService.Bulk.cs`) treats such an ancestor as active, as `ImportAnnotationAsync` treats the overlay: it is not created with defaults, gives no `AncestorCreated` warning and no `AnnotationDeleted` skip, and a parent among them counts as one relation update (the real run replaces its arrays once). The input keys themselves are read from the store, as in the importer. A real run ignores the keys: it reads what the earlier steps wrote, and a key that is not stored must be created rather than assumed.
  - `DataSetSeedOptions.cs` (`DryRun`, `Force`, `Again`, `AnnotationProgress`) and `DataSetSeedRequest.cs` (`Sets`, `Paths`, `Organization`, `Project`, `View`, `Owner`, `Options`).
- The result, `DataSetSeedResult.cs`: `Set`, `Hash`, `IsAlreadySeeded`, `FailedDependency`, `Documents` (a `ViewImportTally` over the files: `Summary` with the ignored files, `Summaries` per kind), `Lines` (`DataSetLinesResult.cs`: `Lines`, `GeneratorLines`, `Annotations`, their `Summary` from a `ViewImportTally` that keeps no items, `AncestorsCreated`, `RelationUpdates`), `Items`, `IsRecorded`, `Elapsed`, `IsSeeded`, `HasFailures`, `Failures`. **Decision:** `Items` (`DataSetSeedItem.cs`: `Path`, `Line` for `annotations.jsonl`, `Kind`, `AnnotationType`, `AnnotationKey`, `Outcome`, `ErrorCode`, `Message`, `Warnings`) lists every outcome but `Created` and `Unchanged`, files and lines alike: the items of a large set would otherwise be every created annotation; the counts are in the tallies.

### 3.8 Commands

- **The root** (`Commands/InitDbCommand.cs`) keeps its behaviour and gets `[Subcommand(typeof(SeedCommand), typeof(SetsCommand))]`: the check of `baseAccount:id`, then `BuildAsync()` (the layout check, the containers, the access, the set `core`), then a summary of the core seed (`DataSetOutput.WriteSummary`: a line per set, seeded with its counts and time or seeded already, and its failures), then the review as before. A run with failures exits `4` without the review; a `DatabaseLayoutException` exits `3` (the message moved to `DataSetOutput.WriteLayoutProblems`, shared with `seed`), a `DataSetException` `2`. `BuildAsync` no longer prints the line of the core seed: the command does.
- **`seed`** (`Commands/SeedCommand.cs`, a plain `IAsyncCommand`, no prompt): the argument `sets` (any number) and the options `--path` (repeatable), `--organization`, `--project`, `--view`, `--owner`, `--dry-run`, `--force`, `--again`. `CreateRequest()` maps them to a `DataSetSeedRequest` (blank or missing values stay null, so the manifests decide). `OnExecuteAsync`:
  1. `DataSetSeeder.Plan(request)` (**new**, see below), so wrong input (an unknown set, a manifest, a cycle, a missing or bad target name, a dotted organization, an invalid owner id, a missing `--path` folder, a set beyond the limits) exits `2` before the database is touched, not after the layout check;
  2. the plan's line (the sets in seed order, the target, the owner), and with `--dry-run` a note that nothing is written;
  3. `CoreDbStructureBuilder.EnsureContainersAsync()`, the layout check and the containers without the access and `core` (split out in the first step). **Decision:** also in a dry run: the containers are the tool's structure, not data of a set, and a dry run against a new database would otherwise fail on its first read; the help of `--dry-run` says so;
  4. `DataSetSeeder.SeedAsync(plan, options)` with `AnnotationProgress = DataSetOutput.AnnotationProgress`, then `DataSetOutput.WriteRun` and `ExitCodes.Of(run)`.
- **`sets`** (`Commands/SetsCommand.cs`): `--path` (repeatable); `DataSetCatalog.GetSets(paths)`, then per set `DataSetOverview.Read` (**new**, `DataSets/DataSetOverview.cs`: the document files per kind with those that cannot be read, the ignored files, and `annotations.jsonl` read as for a seed, with `WithoutDuplicates`; a set without a target of its own is read with its name as organization and project, which only names the annotations). It prints the name, version and source (`built-in` or `--path`), the description, the default target (`<organization>/<project>` and a hint where the manifest names none), the dependencies (a name not in the catalog is marked), the documents per kind, the lines, generators and annotations of `annotations.jsonl` (and how many cannot be read), and the folder. It reads the files only; a `DataSetException` exits `2`.
- **`DataSetSeeder.Plan(DataSetSeedRequest)`** returns a `DataSetSeedPlan` (`Sets` in seed order, `Named`, `Target`, `Owner`, `ProjectDescription`, `ViewDescription`): the first half of the former `SeedAsync(request)`, which now is `SeedAsync(Plan(request), request.Options)`. **Addition:** the plan checks the names of the project, the view and a dotted organization already (`EnsureNames(isNewOrganization: false)`); any other organization's name is checked by the provisioning once it knows the organization is new. It also checks every planned set, dependencies included, against the limits that reading it would hit later: `DataSetFolder.Validate` (the reader's limits, from the lengths) and `DataSetAnnotationLinesReader.CountAnnotations` (the 200 000 annotations, without expanding a generator). Before, these came from `DataSetContent.Read` in the seed of the set, after the target was provisioned and the sets before it were seeded and recorded, and the command printed only the error. The documents are still read once, when the set is seeded; for `large` the check parses its 49 lines. `SeedAsync(DataSetSeedPlan, DataSetSeedOptions)` provisions the target and seeds the sets as before.
- **`DataSetOutput`** (`Commands/DataSetOutput.cs`, static, `Colorful.Console` like the rest of the tool). Per set: a header with the version and source; seeded already (with the hint `--again`) or not seeded because a dependency failed; otherwise a line per kind with documents (`created, updated, unchanged, skipped, failed, with warnings`), the line of `annotations.jsonl` (lines, generators, annotations and their counts) with the ancestors the bulk writer created and the relation arrays it updated, the ignored files, the warnings of the documents by code (those of the lines are counted only: their tally keeps no items), the failures (path, or `annotations.jsonl line N (key)`, code, message; at most `MaxListedFailures` = 20, then `… and N more`), the other listed outcomes by outcome and code (`Not created: 1 Skipped DependencyFailed`), and the time with whether the set was recorded. After the sets: what the target got (`Created the organization 'acme' and the project 'acme.billing'.`, `Would create …` in a dry run, or that the project exists and is used as it is), the failed sets, and `Done in …` or, in a dry run, `nothing was written`. **Decision:** the provisioning runs first but is printed after the sets, since the result comes at the end and the progress lines of the sets come before it. `AnnotationProgress` prints a line per executed plan of the bulk writer (`… 2,506 annotations of annotations.jsonl written`); the writer reports from the seed's own flow, so no synchronization or redraw is needed.
- **Exit codes** (`ExitCodes.cs`): `ERROR_SEED_FAILED = 4` and `ExitCodes.Of(DataSetRunResult)`: `4` when any set has failures (a `Failed` outcome, or `FailedDependency`), `0` otherwise, also for a set seeded already and with warnings or skipped items. A dry run that would fail exits `4` as well, so `seed --dry-run` can check a set (with the overlay carried over the sets and the bulk writer given the dry run's active keys, its failures are those of the real run; one difference stays, see the last point of [Review findings](#review-findings)). `2` covers every `DataSetException`; `DataSetFolder.ReadDocuments` now turns an `InvalidInputException` of the reader's limits into one too (it crashed before).
- **`Program.Main`** catches `CommandParsingException` after `UnrecognizedCommandParsingException`, like `sform`: a missing value or a single value given twice prints the message and exits `-1` instead of the crash message (it logs the command name only). The comment on `ValidateOnBuild` is updated (the commands resolve the builder, the review, the sets and the services of the seed) and moved above the builder chain, which also removes the one `SA1515` warning DbCreator had.

### 3.9 The built-in sets

- `core` (`DbCreator/src/data-sets/core/`): `set.json` (target `42dotnet` / `main` / `default`, a description) and exactly what `Data.CreateCoreAnnotations` wrote: the annotation files `rst.storyteller`, `rst.supervisor`, `rst.scheduler`, `sbt.42`, `cnt.42.system`, `usg.42.{storyteller,supervisor,scheduler}`, `exe.42.{storyteller,supervisor,scheduler}.system` (each `{}`, as the old entities had no editable members) and `configurations/cnt.42.system.conf.json` (`{ "IsSystem": true, "Number": 42, "Text": "system" }`). The relation arrays are no longer written by hand: the creates maintain them.
- `CoreDbStructureBuilder` (constructor now with `DataSetSeeder`): `EnsureContainersAsync()` (new, public, returns `core`) holds the layout check (`DatabaseLayoutException` before any write, as before) and the containers; `BuildAsync()` calls it, seeds the access as before (`Data.SeedAccountAccessAsync`, out of scope), then seeds `CORE_SET` (`"core"`) through `SeedAsync` and returns the `DataSetRunResult` (it returned `Task` before; `await` callers are unchanged). It prints nothing about the seed: the root command prints the summary (`DataSetOutput.WriteSummary`, 3.8). So the core annotations get audit items, a second run reads the record and changes nothing, and a soft-deleted core annotation stays deleted.
- `Backend.CosmosDb/src/Data.cs`: `CreateCoreAnnotations` and its `UpsertAsync` are removed; `Create.cs` is deleted (a grep of the repository found no other user).
- `large` (`DbCreator/src/data-sets/large/`): `set.json` and `annotations.jsonl`, no document files.
  - **Target** `acme` / `billing` / `default`: the scope of the mock's large dataset (`scopeSeed` gives `acme/billing/default` its 500 subjects), so the admin UI against a seeded platform shows the organization, project and view of `npm run dev:mock -- --large`. It keeps 16 000 annotations out of `42dotnet`, which every root run seeds, and away from the organizations of the automation tests (`ui-tests`, `cli-tests`). The names pass `NameRules`. `ProjectDescription` names the set.
  - **Content**: 17 literal lines (the responsibilities `invoicing`, `payments`, `reporting`, `notifications`, `archiving`, `dunning` with titles, descriptions and labels, and their 11 units `pdf`, `email`, `card`, `sepa`, `csv`, `xlsx`, `sms`, `email`, `push`, `s3`, `letter` with `UnitType` `file`, `message`, `event` or `time` and a `UnitDefinition`) and 32 generator lines of `$count` 500 with keys `customer-{000}`: the subjects (`Title` `Customer {n}`, the label `generated`, `Values.customerNumber` `C-{00000}`), the contexts `prod` and `staging`, a usage of each responsibility, an execution per usage and context, a unit of execution per unit in `prod`. That is 6 + 11 + 500 × (1 + 2 + 6 + 12 + 11) = **16 017** annotations (the spec says about 16 000).
  - **Deviation from the mock:** generators cannot draw, so the mock's random choices (the contexts `eu`, `us`, `test`, a usage with p = 0.7, a unit of execution with p = 0.5, labels, statuses, the orphaned unit of execution) are left out; every subject gets everything. No relation array grows with the set: a subject lists 2 contexts and 6 responsibilities, a context 6 responsibilities, a usage 2 contexts, an execution and a responsibility at most 3 units; nothing lists the subjects. Every ancestor is a line of the set, so the bulk writer creates none on the way.
- `Playground/data/set.json`: `playground`, target `42dotnet` / `main` / `default`, a description, no `DependsOn` (it needs nothing of `core`). `2sInitDb seed --path src/Platform/Storyteller/Playground/data` seeds it; `sform story import` of the folder counts the manifest as an ignored file.
- `showcase`: a later step (3.11).

### 3.10 DI

### Review findings

Independent reviewers read section 3 of the spec against the commits of this phase, and reproduced some findings on an emulator. Each finding was checked against the code; the fixes were then run against an emulator (the second table above, whose "before" outcomes are those the reviewers reproduced or the code gave).

Fixed:

1. **A line of `annotations.jsonl` above an annotation file was created with defaults by the file and then skipped for good** (medium). The files went first; the import of `unt.payments.ledger` created `rst.payments` with defaults, the bulk writer then found it active and different (`Skipped DocumentExists`), and the set was recorded. The same happened to a fixed line whose earlier version could not be read. Fixed by the rounds and by failing an unreadable line before the files (3.7); the alternative of refusing such a set was not taken, since lines for the simple annotations and files for the detailed ones below them is a natural way to write a set.
2. **The dry run did not see what the earlier steps and sets would create** (low, reported twice: once for the sets of a run, once for a set that mixes files and lines). The bulk writer read only the store, and every set started from an empty overlay. Fixed by `AnnotationBulkOptions.DryRunActiveKeys` and by carrying what the sets would write over a dry run (3.7). **Deviation from the suggestion** of one overlay shared by every set: the failures are not carried, because a set that is not a dependent of the failed set would get `Skipped DependencyFailed` from another set's failure, which is no `Failed` outcome of its own, so it would be recorded without the annotations that hang on the failed key; a real run seeds them (with the ancestor's defaults). Carrying happens in a dry run only: a real run reads the store.
3. **A dotted `--organization` that matches a project crashed the real run** (exit 1, after the owner's account; the dry run passed; reported twice, low and medium). Fixed in `EnsureNames` (3.4) with the rule of `CreateAccessPointAsync`, so the plan refuses it (exit 2), and by the provisioner's safety net for `InvalidInputException` (3.5).
4. **The 200 000 annotations and the reader's limits were checked only in the seed of the set** (low, reported twice), after the provisioning and the sets before it, and the command printed only the error. Fixed by the plan's check of every planned set (3.8). The alternative of reporting such a set as failed was not needed: nothing is left that the plan cannot check.
5. **No test of the root's exit 4 or of the provisioner's errors** (low): `InitDbCommandTests.Root_AFailedDocumentOfTheSetCore_ExitsWithFourWithoutTheReview` and `DataSetProvisionerTests` (see the tests above).
6. **The review said that `BuildAsync` prints the line of the core seed** (low): corrected in 3.9; the root command prints it.

Rejected:

- **"Section 3 is not complete: the set `showcase`, its Vitest snapshot test and workflow trigger (3.9, 3.11) and the Aspire resource `db-seed` (3.12) are missing"** (low). Not a defect of what this phase delivers: the spec is delivered in steps, and these were planned as a later step together with `DbCreator/testint`, the CI of 4.3 and the documentation of section 5, as this review says in its overview and under "Not in this phase". No change.

Left as it is: the `Skip` decision of a configuration reads the stored configuration (`ImportConfigurationAsync`), so when two sets of one dry run configure the same annotation differently, the later one is reported `Created` in the dry run and `Skipped DocumentExists` in the real run. Neither is a failure, so the exit code is the same; it would take a dry-run layer of stored configurations in the importer, beyond this change.
