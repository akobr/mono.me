# Phase C of Key-Value Pairs in Data Sets

## Overview

Phase C of the spec [Key/Value Pairs in Data Sets of DbCreator](../2026-11-15%20Key-Value%20Pairs%20in%20Data%20Sets%20of%20DbCreator.md) (424-265) covers section 7, the pairs of the set `showcase` written from the admin UI's mock, the set `exhibit` brought in line now that its pairs are seeded, and section 9, the documentation. It is two commits: `feat(platform): give the showcase data set the key/value pairs of the mock (424-265)` and `docs(platform): document the key/value pairs of DbCreator's data sets (424-265)`. Phases A and B delivered the seed of the pairs and its tests (see their reviews).

## What Was Done

### 7. The showcase set

- **`ui.admin/src/app/mock/showcase/key-values.ts`**: the scope `fabrikam/invoicing-suite/default` gets eleven pairs: the SMTP host, sender (two versions) and password (`Standard`, two versions), the PDF renderer, the Peppol participant id and a reference to its API key (`kv://fabrikam-prod/peppol-api-key`), the Adyen merchant account and HMAC key (`Standard`), the dunning limit (two versions), the feature flags (JSON, two versions), and a pair deleted 20 days ago (`legacy.ftpHost`). Every key is camel case, because the set goes through the platform's key rule; the other scopes of the mock keep their hyphenated keys, which the mock never checks. A comment says that the `Standard` values are demo values.
- **`ui.admin/src/test/unit/mock/showcase-set.test.ts`**: `keyValuesDocument()` builds the `2s.key-values.v1` document from `showcaseKeyValues` (the current version of every pair that is not deleted, `{ Key, Protection, Value, ContentType? }`, ordered by key with an ordinal comparison, as the export orders), and `setFiles()` adds it as `key-values.json`, so it is a file snapshot like the documents and the stale check covers it. A new test checks both levels, the key rule (`keyPattern` of the mock, the platform's pattern), a value per pair, and that the deleted pair stays out. The header comment names the pairs.
- **`DbCreator/src/data-sets/showcase/key-values.json`** (generated by `npx vitest run test/unit/mock/showcase-set.test.ts -u`): 10 pairs, 8 `Public` (one of them the reference) and 2 `Standard`.
- **The set's configurations** bind no pair, as planned: the resolved reads of seeded pairs are checked with `exhibit` and a test set (phase B).
- **`DbCreator/test` `BuiltInSetsTests.Showcase_IsTheInvoicingSuiteOfTheMocksShowcase`** checks that the set has pairs of both levels, ordered by key; `testint` seeds it with the vault (phase B).

### The set `exhibit`

- `set.json`: the description says that the `Standard` pair needs a Standard vault, instead of "seeded once 424-265 is done". The hash of the set changes with it, so a target seeded before reads the set again and adds its pairs.
- `README.md`: the content table counts the 20 pairs (18 public, a reference, one `Standard`); the seed section explains the vault (with the command against the Aspire host's Lowkey Vault) and keeps `sform story kv import` for a project seeded or imported without the pairs.

### 9. Documentation

- **`docs/Platform/Storyteller/data-sets.md`**: the introduction and the code list name `key-values.json`, `DataSetKeyValues`, `DataSetKeyValueSeeder`, the Standard vault of `Startup`, the key/value import and the spec; the folder of a set shows the file; ignored files name a nested `key-values.json`; "What a set cannot carry" drops the pairs and names what of them a set cannot carry. A new section **key-values.json**: an example, the place and the reading rules, the rules of every item, the refusal with its message, **the levels** (a table, the project policy), **the vault** (the two variables, the roles, Production with its credentials, Debug, Aspire, the first Standard key), and **secrets in the repository** (demo and test values only, references for real secrets). The seed record gets `KeyValues`; a changed or deleted pair in the table of what a seed does and in the paragraph after it; **Seeding a set** gets step 6 with the decision table, the refusals, the failures of the vault, the race and the audit and usage notes; the outcomes, the dry run, the configuration of the commands, the plan, the output of `seed` and `sets`, the exit codes `2` and `4`, the built-in sets (`showcase` with its pairs, `exhibit` as a row and a section), the showcase's pairs, adding a set, Aspire with an example command, and the tests.
- **`docs/Platform/Storyteller/key-values.md`**: a paragraph under Import and export on the seed of a set's pairs.
- **`docs/Platform/Aspire.Host/local-development.md`**: the `db-seed` row names the pairs and the vault, and `exhibit` among the other sets. **`docs/Platform/development.md`**: the sets table has the pairs of `showcase` and the set `exhibit`, and a paragraph tells how to give a command-line seed the vault.
- **`src/Platform/ui.admin/README.md`**: the showcase set's `key-values.json`, its rules, and the pairs file among what regenerates the set.
- **`docs/github/workflows.md`**: `DbCreator/testint` in the Cosmos DB workflow also starts Lowkey Vault. The workflow itself needs no change: its runners have Docker, which the Cosmos DB emulators already need.
- **`CLAUDE.md`**: the DbCreator line names `key-values.json`, its rules and the set `exhibit`.
