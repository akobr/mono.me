# TypeScript SDK and API Extensions for the Administration UI

## Problem

The planned [Administration UI for 2S Platform](../../ui.admin/specs/2026-10-09%20Administration%20UI%20for%202S%20Platform.md) needs two things from Storyteller:

1. **A TypeScript SDK.** The old openapi-generator SDK (`src/Platform/sdk.typescript`) was removed in `ff0b479`. A new one is generated from `open.api.v0.8.89.json` and lives in `src/Platform/Storyteller/sdk.typescript/src/sdk.typescript.esproj`. The original request named NSwag, the tool that produces the C# `Sdk.NSwag`. On 2026-10-09 the TypeScript generator was changed to **Orval**, because the UI uses TanStack Query and Orval also generates the query composables, Zod schemas and MSW mocks (section 1). The C# SDK stays on NSwag.
2. **API changes.** A browser admin tool cannot work around several gaps in today's REST API:
   - members cannot be listed with names;
   - there are no invitations;
   - views, configurations, schemas and templates cannot be listed;
   - authorization failures look like authentication failures (`401`);
   - revoking access is broken;
   - a failed JSON Patch `test` returns `500`.

## Current State

- **OpenAPI.** `src/Platform/Storyteller/sdk.typescript/open.api.v0.8.89.json` and `Sdk.NSwag/open.api.v0.8.89.json` (untracked) describe 72 operations with the tags Access, Annotations, Configurations, Schemas and Templates. The server is `http://localhost:7071/api`.
- **NSwag.** 14.6.3 is installed globally. The C# SDK is generated by the command in `Sdk.NSwag/README.md` (`openapi2csclient`, `MultipleClientsFromFirstTagAndOperationId`, `{controller}ApiClient`).
- **NSwag TypeScript trial.** A trial run of `openapi2tsclient` (Fetch template, `typeStyle: Interface`, `enumStyle: StringLiteral`) on v0.8.89 produced about 6,500 lines with five clients: `AccessApiClient`, `AnnotationsApiClient`, `ConfigurationsApiClient`, `SchemasApiClient` and `TemplatesApiClient`. Derived annotation types are interfaces that extend `Annotation`, and enums are string-literal unions. Two problems showed up:
  - `GetCertificateAuthority` returns `application/x-pem-file`, but the generated code runs `JSON.parse` on it, so the call always throws.
  - The diff operations take `format=unified` (`text/plain`), which the generated code would also `JSON.parse`.

  Whatever generator is used, these two operations need a fetch layer that parses by content type. The Orval fetcher in section 1.4 does that.
- **Access** (`Api.Functions/src/V1/AccessHttp.cs`, `Backend.CosmosDb/src/Accessing/CosmosAccessService.cs`):
  - `GrantPermissionAsync` (lines 202-268) can only raise a role. If the target already has the same or a higher role, it returns `false`.
  - `RevokePermissionAsync` (lines 270+) checks `if (creator.AccessMap.TryGetValue(model.AccessPointKey, out _)) throw …`. The condition is inverted, so a legitimate administrator always fails. A caller with **no** membership passes the check, and nothing verifies the caller's role. That last part is a **security defect**.
  - `AccessPoint.AccessMap` holds account IDs and roles only. There is no endpoint that resolves names.
  - `CreateAccount` requires `Organization` and `Project`.
  - `HttpRequestDataExtensions.CheckAccessToAsync` (lines 90-120) throws `SecurityTokenException` when the role is too low. `ExceptionHandlingMiddleware` maps that to `401`, the same as an invalid token.
  - Domain errors (`InvalidOperationException`) become `500` with the full exception, including the stack trace, in `ErrorResponse.Error`.
- **Views** exist only as id prefixes (`{view}.…`) on annotation, configuration, template and schema documents in the organization container (`org.{organization}`).
- **Configuration items** have ids `{view}.cnf.{annotationKey}` in partitions `{project}.sbt.{subject}` and `{project}.rst.{responsibility}` ([inheritance.md](../inheritance.md)). Schema items are `{view}.cfs.{t|a|d}…` in partition `{project}.schema` ([definitions.md](../definitions.md)). Template items are `{view}.<template prefix>.{annotationType}` (`CosmosConfigurationTemplateService.cs:286-298`).
- **JSON Patch.** `JsonExtensions.ApplyPatch` (`Backend.CosmosDb/src/JsonExtensions.cs:107-127`) throws `InvalidOperationException("JSON Patch operation failed: …")`, which becomes `500`.
- **CORS.** Allowed origins are set in `local.settings.json` (`CORS: *`) for local work. Deployed Function Apps need the admin origin.

## Proposed Changes

### 1. TypeScript SDK (`src/Platform/Storyteller/sdk.typescript`)

**Generator: Orval v8** (decided 2026-10-09; the C# SDK stays on NSwag). The SDK is not just typed fetch calls. It also produces the **TanStack Query for Vue** composables and query keys the admin UI uses, the **Zod 4** schemas for forms and editor validation, and the **MSW** handlers with Faker data for tests. All four come from one OpenAPI document in one run, so they cannot drift apart.

| Generator | Why not chosen |
| --- | --- |
| NSwag `openapi2tsclient` | Class clients only. No query composables, Zod or mocks. Mishandles non-JSON responses (see Current State). |
| Hey API (`@hey-api/openapi-ts`) | Good framework-agnostic SDK and TanStack Query plugin, but still pre-1.0 with breaking releases (0.97, April 2026). No shipped MSW plugin. |
| openapi-typescript + openapi-fetch | Types and fetch only. Query layer and mocks would be hand-written. |

- `npm run generate` runs `orval --config orval.config.ts`, then `scripts/set-version.mjs`, which sets `package.json` `version` from `info.version` (major.minor.patch). A newer spec is passed with `SPEC=../open.api.v0.9.0.json npm run generate`.

- The `client` and `vueQuery` targets both emit request functions. The duplication is generated, so it costs nothing, and it keeps the root entry free of Vue and TanStack imports.
- Check every option name against the Orval v8 docs at implementation time: `includeHttpResponseReturnType`, `shouldExportQueryKey`, and the mock `baseUrl`. Orval v8 requires Node 22.18 or later.

#### 1.4 Fetcher (`lib/fetcher.ts`, the Orval mutator)

```ts
export interface StorytellerConfig {
  baseUrl: string                                     // e.g. https://host/api
  getAccessToken?: () => Promise<string | undefined>  // bearer for user tokens
  onUnauthorized?: () => void                         // called after a 401 survives one token refresh
  fetch?: typeof globalThis.fetch                     // tests / custom transport
  headers?: Record<string, string>                    // e.g. X-Client: 2s-admin/0.1.0
}

export function configureStoryteller(config: StorytellerConfig): void

export async function storytellerFetch<T>(url: string, init: RequestInit): Promise<T>
```

`storytellerFetch` does the following:
1. Prefixes `baseUrl` to the relative path that Orval generates (`/v1/...`).
2. Adds `Authorization: Bearer <token>` when `getAccessToken` returns one. The token is never logged and never copied into errors.
3. Merges `headers`, and keeps `signal` for cancellation.
4. On `401`, asks for a token once more and retries once. If that also fails, it calls `onUnauthorized` and throws.
5. On any other non-2xx, reads the body. JSON bodies become `ErrorResponse` or `SchemaValidationErrorResponse`. It then throws `StorytellerError`.
6. Returns `undefined` for `204` or an empty body, and `JSON.parse`s `application/json` and `application/*+json`. **Every other content type is returned as text.** This fixes `GetCertificateAuthority` (`application/x-pem-file`) and the diff endpoints with `format=unified` (`text/plain`), which the NSwag trial broke.
7. Turns network failures (`TypeError`) into `StorytellerError` with `status: 0`.

The configuration is module-level, because the admin UI talks to one API. A consumer that needs several base URLs can pass a full URL per call through `options`, or a later version can add a factory for several fetchers.

### 2. API extensions

All new endpoints follow the existing conventions: `[Function]`, `[OpenApiOperation]` with tag `Access`, `Annotations`, `Configurations`, `Schemas` or `Templates`, both bearer security attributes, `Definitions.Routes`, and `Scopes`. Unless stated otherwise, they require `User.Impersonation` and the listed account role.

#### E1. Authorization correctness

1. **Fix `RevokePermissionAsync`.** Mirror `GrantPermissionAsync`:

   ```csharp
   if (!creator.AccessMap.TryGetValue(model.AccessPointKey, out var creatorRole)
       || creatorRole < AccountRole.Administrator
       || (accountRole == AccountRole.Owner && creatorRole != AccountRole.Owner))
   {
       throw new AccessDeniedException($"The creator '{model.CreatedById}' can't revoke this permission.");
   }
   ```

   Also: refuse to remove the last `Owner` of an access point, and add unit tests for the creator role, the missing membership, and the last owner.
2. **`403` for authorization failures.**
   - Add `AccessDeniedException` (in `Backend.Core`, next to the other domain exceptions) and use it in `CheckAccessToAsync` when the account role is too low, and in the access service rules.
   - `ExceptionHandlingMiddleware` maps it to `403` with `ErrorResponse { Message, ErrorCode = "AccessDenied" }`, without exception details.
   - `SecurityTokenException` keeps meaning `401`. Machine checks keep throwing `SecurityTokenException` (no change for machines).
3. **Domain error mapping.** `NotFoundException` → `404` and `ConflictException` → `409`, both with `ErrorResponse` and no `Error` (stack trace). Use them in the new code and in grant and revoke. Existing `InvalidOperationException` sites are left alone except in `CosmosAccessService`.
4. OpenAPI: add `403` responses to every operation that calls `CheckAccessTo*Async`.

#### E2. Members

| Method | Route | Role | Body / result |
| --- | --- | --- | --- |
| GET | `v1/access/points/{key}/members` | Administrator on `{key}` | `AccessPointMember[]` |
| PUT | `v1/access/points/{key}/members/{accountId}` | Administrator (Owner to set or unset `Owner`) | `{ Role }` → `AccessPointMember` |
| DELETE | `v1/access/points/{key}/members/{accountId}` | Administrator, or the member themselves (leave) | `204` |

```csharp
public sealed record AccessPointMember
{
    public required string AccountId { get; init; }
    public string? UserName { get; init; }   // email / preferred_username
    public string? Name { get; init; }
    public required AccountRole Role { get; init; }
}
public sealed record MemberRoleUpdate { public required AccountRole Role { get; init; } }
```

- `IAccessService` gains `GetMembersAsync(pointKey)`, `SetMemberRoleAsync(pointKey, accountId, role, actorId)` and `RemoveMemberAsync(pointKey, accountId, actorId)`.
- **Cosmos:**
  - Read the access point, then read the accounts with `SELECT c.id, c.UserName, c.Name FROM c WHERE ARRAY_CONTAINS(@ids, c.id)` in the main partition.
  - Update the access point `AccessMap` and the account `AccessMap`, the same way as grant. Use `ReplaceItemAsync` with `IfMatchEtag` on both documents and retry once on `412`.
- **Rules:**
  - `Role` must not be `None`.
  - Only an `Owner` may set `Owner` or change an `Owner`.
  - The last `Owner` cannot be demoted or removed (`409`, `ErrorCode = "LastOwner"`).
  - Administrators cannot change their own role (`409`, `ErrorCode = "SelfRoleChange"`).
- `GrantUserAccess` and `RevokeUserAccess` stay for compatibility, and the SDK marks them as deprecated in a doc comment. The `sform` CLI keeps using them.

#### E3. Invitations

**Model** (core container, main partition, id `inv.{id}`, TTL 30 days after the invitation ends):

```csharp
public enum InvitationStatus { Pending, Accepted, Declined, Revoked, Expired }

public sealed record Invitation
{
    public required string Id { get; init; }                 // ULID
    public required string AccessPointKey { get; init; }
    public required string Email { get; init; }              // normalized lower-case
    public required AccountRole Role { get; init; }
    public required InvitationStatus Status { get; init; }   // Expired computed on read when ExpiresAt < now
    public required string InvitedById { get; init; }
    public string? InvitedByName { get; init; }
    public required DateTimeOffset CreatedAt { get; init; }
    public required DateTimeOffset ExpiresAt { get; init; }
    public string? AcceptedById { get; init; }
    public DateTimeOffset? RespondedAt { get; init; }
    public string? ExternalInvitationId { get; init; }       // WorkOS invitation id
}
public sealed record InvitationCreate { public required string Email { get; init; } public required AccountRole Role { get; init; } public int? ExpiresInDays { get; init; } }
```

**Endpoints:**

| Method | Route | Who | Notes |
| --- | --- | --- | --- |
| GET | `v1/access/points/{key}/invitations` | Administrator | Pending and recent invitations |
| POST | `v1/access/points/{key}/invitations` | Administrator (Owner for `Owner`) | One per email. `409 InvitationExists` when a pending one exists. Default `ExpiresInDays` 7, max 30. |
| POST | `v1/access/points/{key}/invitations/{id}/resend` | Administrator | Re-sends the email and extends the expiry |
| DELETE | `v1/access/points/{key}/invitations/{id}` | Administrator | Status `Revoked`; revokes the WorkOS invitation |
| GET | `v1/access/invitations/mine` | Any signed-in user | Pending invitations whose `Email` equals the caller's email claim |
| POST | `v1/access/invitations/{id}/accept` | Invitee | Email must match. Creates the account if missing (E4). Grants `Role` with the inviter as `CreatedById` but without re-checking the inviter's current role; the invitation was authorized when it was created. Returns `Account`. |
| POST | `v1/access/invitations/{id}/decline` | Invitee | Status `Declined` |

**Email claim:** the canonical `preferred_username`, which comes from AuthKit's JWT template `email` or Entra's `preferred_username`/`upn`. Acceptance is refused (`403`, `ErrorCode = "EmailNotVerified"`) when the provider says the email is unverified. For AuthKit, add `email_verified` to the JWT template and to the claim normalizer. When the claim is missing, treat the email as verified only if `Auth:AuthKit:RequireVerifiedEmail` is `false`.

**Sending the email** (`IInvitationSender`, in `Backend.Core`):
- `AuthKitInvitationSender` (in `Access.AuthKit`) calls `POST https://api.workos.com/user_management/invitations { email, expires_in_days, inviter_user_id }` with the management key. This is an application-level invitation with no WorkOS organization. WorkOS sends the email, and its link goes to the admin UI's accept URL configured in the WorkOS dashboard. Resend and revoke call the matching WorkOS endpoints.
- `NoopInvitationSender` (Entra or Keycloak, or no management key): nothing is sent. The UI shows **Copy link** (`{adminUrl}/invitations?highlight={id}`).
- WorkOS invitations to the application can be accepted with any email. That is why Storyteller always matches the **Storyteller** invitation's email against the signed-in user. The WorkOS token only opens sign-up when AuthKit sign-up is disabled.

#### E4. Account without an initial project

`AccountCreate.Organization` and `AccountCreate.Project` become optional. When both are absent, `CreateAccountAsync` stores the account with an empty `AccessMap`. When only one is present, it returns `400`. Invitation acceptance (E3) uses the same path.

| GET | `v1/{organization}/{project}/views` | Reader | `View[]`, always including `default` |
| POST | `v1/{organization}/{project}/views` | Administrator | `ViewCreate { Name, Description? }` → `View` (`409 ViewExists`) |
| PUT | `v1/{organization}/{project}/views/{view}` | Administrator | `{ Description }` → `View` |

```csharp
public sealed record View
{
    public required string Name { get; init; }
    public string? Description { get; init; }
    public DateTimeOffset? CreatedAt { get; init; }
    public string? CreatedBy { get; init; }
    public bool IsDefault { get; init; }   // Name == Constants.DefaultViewName
    public bool IsRegistered { get; init; } // false = discovered from data only
}
```

- **Storage:** the organization container, partition `{project}.meta`, id `view.{name}`.
- **Listing:** registered views ∪ `default`. With `?discover=true` (Administrator), it also runs `SELECT DISTINCT VALUE c.ViewName FROM c WHERE STARTSWITH(c.PartitionKey, @projectPrefix) AND IS_DEFINED(c.ViewName)` in the organization container, cross-partition, and returns unregistered views with `IsRegistered = false`. The UI offers to register them.
- Writes to an unregistered view are **not** blocked. Views stay implicit for the API and CLI, so this is backward compatible.
- Deleting and copying views are out of scope.

#### E6. Configuration listing

`GET v1/{organization}/{project}/{view}/configurations?annotationType=&keyPrefix=&continuationToken=` (Reader) → `ConfigurationsResponse`:

```csharp
public sealed record ConfigurationSummary
{
    public required string AnnotationKey { get; init; }
    public required AnnotationType AnnotationType { get; init; }
    public required long Version { get; init; }
    public string? Author { get; init; }
    public string? Hash { get; init; }              // CalculatedContentHash
    public DateTimeOffset? UpdatedAt { get; init; } // _ts
    public bool HasContent { get; init; }           // own Content is a non-empty object
}
public sealed record ConfigurationsResponse { public required IReadOnlyList<ConfigurationSummary> Configurations { get; init; } public string? ContinuationToken { get; init; } public int Count { get; init; } }
```

The query is a projection without `Content` or `CalculatedContent`, cross-partition within the organization container. It filters on `STARTSWITH(c.PartitionKey, '{project}.')` and `STARTSWITH(c.id, '{view}.cnf.')`, with `MaxItemCount = 1000`.

#### E7. Schema listing

`GET v1/{organization}/{project}/{view}/configuration-schemas` (Reader) → `ConfigurationSchemaSummary[]`:

```csharp
public enum ConfigurationSchemaKind { Type, Annotation, DescendantType }
public sealed record ConfigurationSchemaSummary
{
    public required ConfigurationSchemaKind Kind { get; init; }
    public AnnotationType? AnnotationType { get; init; }   // Type, DescendantType
    public string? AnnotationKey { get; init; }            // Annotation, DescendantType
    public required long Version { get; init; }
    public string? Author { get; init; }
    public DateTimeOffset? UpdatedAt { get; init; }
}
```

The query is single-partition (`{project}.schema`), filtered on `STARTSWITH(c.id, '{view}.cfs.')`, as a projection.

#### E8. Template listing

`GET v1/{organization}/{project}/{view}/templates` (Reader) → `ConfigurationTemplateSummary[] { AnnotationType, Version, Author, UpdatedAt }`. It reads the template items of the view in their partition with a projection. This replaces seven `GetTemplate` calls.

#### E9. Labels (deferred)

Not implemented in this plan. Views are expected to hold 5,000 to 20,000 annotations, and the admin UI derives label suggestions from its client catalog. If views grow past about 20,000 annotations, the endpoint would be `GET v1/{organization}/{project}/{view}/labels?prefix=` (Reader) → `LabelUsage[] { Label, Count }`. It would aggregate with `SELECT l AS Label, COUNT(1) AS Count FROM c JOIN l IN c.Labels … GROUP BY l`, cross-partition and project-prefixed.

#### E10. Annotation search (deferred)

Not implemented in this plan, for the same reason as E9. If it is needed later: `GET v1/{organization}/{project}/{view}/annotations/search?q=&type=&label=&status=&continuationToken=` (Reader) → `AnnotationsResponse`.
- `q` is a case-insensitive substring over `Name`, `AnnotationKey`, `Title` and `Description` (`CONTAINS(…, @q, true)`).
- `type` takes type codes, comma-separated.
- `label` uses `ARRAY_CONTAINS`.
- `status` is computed from `IsDisabled`, `ValidFrom`, `ExpiresAt` and `GetCurrentDateTime()`.

#### E11. Name validation

`CreateAccount`, `CreateAccessPoint`, `ViewCreate` and invitation keys validate names:
- They must match `^[a-z0-9][a-z0-9-]{1,62}$`, so no dots, because `.` is the key separator.
- Reserved organization names: `access`, `auth`, `login`, `callback`, `onboarding`, `invitations`, `account`, `orgs`, `unsupported`.
- Reserved project and view names: `access`, `views`, `members`, `invitations`, `machines`, `certificates`, `settings`.

Failures return `400` with `ErrorCode = "InvalidName"`. Existing documents are not migrated. Names that already exist stay readable, but no new ones can be created with them.

#### E12. CORS and deployment

- Document in `docs/Platform/Storyteller/authentication.md`: the deployed Function App's CORS allowed origins must include the admin UI origin. No credentials, because bearer tokens are used.
- `local.settings.json` keeps `*`.
- The anonymous `GET v1/auth/configuration` must stay reachable cross-origin.

#### E13. JSON Patch errors

`JsonExtensions.ApplyPatch` throws `JsonPatchException` (new) with `Kind = Invalid | TestFailed | PathNotFound`. `ExceptionHandlingMiddleware` maps it as follows:
- `TestFailed` → **`412 Precondition Failed`**, `ErrorCode = "PatchTestFailed"`.
- `Invalid` and `PathNotFound` → `400`, `ErrorCode = "PatchInvalid"`.

This covers both configurations and templates. OpenAPI: add `412` to `PatchConfiguration` and `PatchTemplate`. The admin UI uses `test` operations for optimistic concurrency.

## Decisions

1. The TypeScript SDK is generated by **Orval v8**, not NSwag (decided 2026-10-09). It has four targets from one spec: plain fetch functions, TanStack Query for Vue composables, Zod 4 schemas, and MSW mocks. Auth and content-type handling live in one hand-written mutator (`storytellerFetch`). The C# SDK stays on NSwag.
2. The root entry has no runtime dependencies, and each subpath (`./vue-query`, `./zod`, `./msw`) has only optional peers. The package ships ESM with types, keeps the generated code committed, and is consumed through `file:` by `ui.admin`.
3. Members get dedicated endpoints with "set exact role" semantics. Grant and revoke are kept for the CLI.
4. Invitations are Storyteller documents. WorkOS only delivers the email. Acceptance matches the verified email of the signed-in user.
5. Views become registered, but stay implicit for writes, so the change is backward compatible.
6. Authorization failures return `403`. `401` is reserved for authentication.
7. All extensions except E9 and E10 are delivered before the admin UI work starts (decided 2026-10-09). E9 and E10 are deferred, because views are expected to hold 5,000 to 20,000 annotations.
8. Deployed environments use a custom AuthKit domain, and the WorkOS invitation email links to the admin UI on its own domain.

## Open questions

1. Should `sform` get `member` and `invite` commands in the same release, or in a follow-up? (Assumed: follow-up.)
2. Should invitations to an **organization** grant anything on its projects? (Assumed: no. Organization and project roles stay independent, as today.)
3. Is `email_verified` available in the WorkOS JWT template for this environment? If not, use the fallback described in E3 (`RequireVerifiedEmail=false`, or a profile lookup).

## Out of scope

- Deleting or renaming organizations, projects and views. Copying views.
- Publishing the SDK to npmjs.
- Labels endpoint and server-side annotation search (E9 and E10, deferred).
- Entra ID or Keycloak invitation email delivery.
- Removing stack traces from `500` responses globally. Recommended as a follow-up. This spec removes them only from the new `4xx` mappings.
