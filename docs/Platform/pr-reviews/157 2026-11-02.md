# Review of PR #157: [fix(platform): no discard prompt after deleting a configuration's own content (424-157)](https://github.com/akobr/mono.me/pull/157)

Reviewer: Harry · Review date: 2026-11-02

**Verdict: approve-ready.** The PR is small (`ConfigurationEditor.vue`, the `CodeEditorStub` test helper, one new Vitest case, spec and spec review; +84/−4). The root cause is right: after `remove()` set `original` and `draft` to `undefined`, the `DocumentEditor` rendered `draft ?? {}` and CodeMirror echoed `{}` back, so `"{}" !== "null"` kept the editor dirty. The two-part fix (reset both refs to the same `{}`, and treat "nothing stored" as "nothing to discard") is sound. Making the stub echo like CodeMirror, so the test actually fails on the old code, is the most valuable part of the PR. The points below are follow-ups, not blockers.

**CI at review time:** "Lint, type-check, test, build" was still running (mergeable state `unstable`). I read the diff against the full `ConfigurationEditor.vue`, `useConfiguration.ts` (how `noOwn`/`missing` are derived) and `useUnsavedChanges.ts` (the guard, `beforeunload` and the title dot), but did not run it.

## Blocking

None.

## Important

1. **The `noOwn || missing` gate also drops edits silently when someone else deletes the content (behaviour change; decide on purpose).** `dirty` (ConfigurationEditor.vue L61–64) is now `false` whenever the own query 404s, whatever caused it. So if a user is mid-edit and another admin deletes the own content (or the annotation), the next `refetchOnWindowFocus` of the effective query moves `version` to 0, the own query 404s, and the route guard, the `beforeunload` prompt and the title dot all switch off. Worse, if the user then clicks **Create empty**, the own-content watch (L68–77) now sees `!dirty` and overwrites `draft` with `{}`. Before this PR the edit stayed in `draft`, and a later save went through the 412 / `PatchTestFailed` path into the conflict dialog, where the user could still overwrite with their version. The spec review mentions the first half (no prompt) but not the overwrite on re-create.
   *Fix (pick one):* (a) accept it and add a sentence to the spec review covering the re-create case; or (b) scope the gate to the user's own delete, for example a `deletedOwn` flag set in `remove()` and cleared when own content loads again, and keep `dirty` honest otherwise. Option (b) keeps the original fix and restores the old safety for concurrent deletes. Either way, a test for "someone else deleted it while I was editing" would pin the chosen behaviour.

2. **The `{}` reset is the only thing protecting the short window before the 404 arrives.** `invalidateConfiguration` (L233) waits for the effective refetch, but the own query's key includes `version` (`useConfiguration.ts`), so the request for version 0 starts only after that, as a new query. Until it 404s, `noOwn` is `false`, and `dirty` compares the editor's echo with `{}`. In JSON/YAML mode the echo is `{}`, so this is fine. In **Form** mode (`SchemaForm v-model="draft"`, L315–324), JSON Forms may write schema defaults into `draft` on mount, which would make the editor dirty for that window (title dot flicker, and a navigation started in that moment would prompt). The spec relies on the `noOwn` gate for exactly this case, so it's likely benign, but it isn't tested.
   *Fix:* add a variant of the new test that uses a configuration with a schema (Form mode), or note in the spec review that only JSON mode is covered.

## Nits

3. **The stub echoes more than CodeMirror does** (test/helpers.ts L18–22). The `watch` re-emits every `modelValue` change, including the one that comes back after the stub's own `input` emit. Real CodeMirror only reports a change when the document text actually changes, and a well-behaved `CodeEditor` doesn't dispatch when the incoming value equals the current doc. Today this means one extra, harmless `update:modelValue` per simulated keystroke in all tests that use the stub (the full suite passing shows it's harmless). Remembering the last emitted text and skipping an echo of that same value would match the real component more closely and avoid surprises in future tests that count emits.
4. **The test only checks `hasUnsavedChanges()`.** The bug was reported as the **Discard changes?** prompt and the "● " title mark. Two cheap assertions would cover the user-visible symptoms directly: `document.title` doesn't start with `● `, and a `router.push` away resolves without a `[role="dialog"]` appearing.
5. **Global state in `useUnsavedChanges`.** `dirtySources` is a module-level `Set`, and the new test (like its neighbours) calls `view.host.unmount()` only at the end. If an assertion fails earlier, the editor stays registered and later `hasUnsavedChanges()` checks in the file can fail for the wrong reason. An `afterEach` unmount (or `try/finally`) would keep failures local.
6. **Non-null assertions on lookups in the test** (`.find(...)!` for **Delete own**, the dialog input and the **Delete** button, new test L178–190). If the label changes, the test fails with a `TypeError` instead of a clear message. `expect(button).toBeDefined()` before using it reads better when it breaks.
7. **Brief editable empty editor after delete.** Because `draft` is now `{}` and not `undefined`, `LoadingState v-if="own.isPending.value && draft === undefined"` (L314) no longer shows during the refetch. The user briefly sees an empty `{}` editor (Save disabled) before **No configuration yet**. This is cosmetic, but `own.isPending.value && (draft === undefined || version === 0)` or a local `deleting` flag would hide it.
8. **`original = {}` is not what's stored.** After the delete, the editor's base claims an empty document exists. It is harmless because the editor is hidden as soon as `noOwn` is true, but the code comment at L229 could say so ("placeholder until the 404 hides the editor") so nobody later builds a patch against it.

## Good

- The diagnosis in the PR and spec is precise: it names the exact echo (`DocumentEditor` re-serializes, CodeMirror reports it, `{}` vs `null`) and why the existing watch can't repair it (the own query 404s, so it never fires).
- Fixing the test double, not just the component, is the right call. Without it the regression test passed on the broken code. Saying so in the spec review ("deviation from the plan") is good practice.
- The scope is tight: the sibling bugs in `SchemaDetail.vue` and `TemplateDetail.vue` are named and tracked separately, and the `DiscardIfShownAsync` workarounds on `feat/424-152` ([#155](https://github.com/akobr/mono.me/pull/155)) are left for after the merge, with the follow-up written in the PR body.
- The code comments carry the issue key, which matches the repo convention (`424-67` in `useUnsavedChanges.ts`) and explains why the two-part condition exists.
