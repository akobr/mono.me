# Review of PR #195: [feat(platform): seed named data sets with DbCreator (424-252)](https://github.com/akobr/mono.me/pull/195)

Reviewer: Harry · Review date: 2026-11-12

**Verdict: approve-ready after a short discussion.** Nothing blocks the merge. Two points are worth settling first: the bulk writer retries the whole procedure on a throttle, and the CLI never passes a cancellation token, so the cancellation code in the new seed path is never used. The design holds up. The import passes move out of the transfer job behind `IViewImporter`, and the transfer job keeps its constructor and its behaviour. The bulk writer returns the same outcomes as a sequential `Skip` import, and it is built to be re-run: transactional batches per partition carry each annotation with its audit item, parents get an ETag-guarded replace, and the `BulkCommits` bookkeeping makes a retry treat its own earlier commits correctly. Test coverage is unusually thorough (21 Cosmos tests for the writer alone, including purge or delete between attempts and a cancel-then-resume test).

**CI at review time (head `61ff04e`):** "Classic emulator" and "Lint, type-check, test, build" passed. "vNext emulator" (which runs the new DbCreator unit and integration suites) and "Playwright (mocked API)" were still running. CodeRabbit skipped the PR because it has too many files (546 files, about 414 of them data-set documents). I read the diff of every non-data file, with the bulk writer, seeder, provisioner, lines reader, folder/hash, record store, commands and DI in full, and compared them with the base `CosmosAnnotationService`, `BatchPlan`, `ViewAnnotationDocument` and `IAsyncCommand`. I did not run the tests myself.

## Blocking

None.

## Important

1. **A throttle re-runs the whole bulk procedure, which costs the most request units at the worst moment.** In `CosmosAnnotationService.Bulk.cs`, `WithBulkRetriesAsync` (≈L139–159) catches a 429 that outlasted the SDK's own retries, waits for `RetryAfter`, and then calls `CreateMissingCoreAsync` again. That call re-reads the full closure with `ReadNodesAsync`, which for `large` means 16k+ items in about 17 ReadMany calls, then reloads the audits and re-decides every key. On a low-RU container (a 400 RU/s dev or prod account shared with the API) a throttle near the end of a big set can therefore cause more throttling, until `BulkMaxAttempts = 5` is used up and the run crashes with exit code 1, not 4. Suggestion: retry the failed *batch* inside `BatchPlan.ExecuteBatchAsync` on 429, honouring `response.RetryAfter` (the value is already captured in `CosmosRequestFailedException`). Keep the whole-procedure rerun for 409/412 only, where re-reading is actually needed. A smaller alternative is to lower `MaxParallelBatches` after a throttle.
2. **The CLI never passes a cancellation token.** `IAsyncCommand.OnExecuteAsync()` takes no `CancellationToken` (`src/Libraries/CLI/Toolkit/src/IAsyncCommand.cs`), so `SeedCommand.OnExecuteAsync` (L76–100) calls `_seeder.Plan`/`SeedAsync` without one. All the new plumbing (`BatchPlan.ExecuteAsync(ct)`, `ReadNodesAsync(ct)`, `[EnumeratorCancellation]` in `ViewImporter`) is therefore unused in the real tool, and Ctrl+C during a 40–100 s `large` seed just kills the process. Resuming is safe by design, so this is not data loss, but the PR text promises cancellation. Suggestion: McMaster also binds `OnExecuteAsync(CancellationToken)` by convention, so add that overload to `SeedCommand` (and `InitDbCommand`), or add a token-taking variant to `IAsyncCommand` with a default implementation, and pass it down. Then print "stopped, run again to complete" on `OperationCanceledException` and return `WARNING_ABORTED` (40), which already exists.
3. **A whole set is held in memory and sent in one bulk call per round.** `DataSetContent.Read` → `DataSetAnnotationLinesReader.Read` (L75–100) expands every generator line into `Annotation` objects up front (up to `MaxAnnotations = 200_000`). `WriteLinesAsync` then passes the whole round in one `CreateMissingAnnotationsAsync` call, which keeps the closure's nodes, the `creates` list and the stored-entity dictionary for every key. `MaxUnitsPerPlan` only limits the serialized streams. That is fine at 16k, but at the advertised 200k it means several hundred MB, plus a full re-read on every retry (see 1). Suggestion: either lower the limit to what has been measured (e.g. 50k), or have the seeder send the lines of a round in slices of a few thousand. Ancestors-first order is already guaranteed by sorting on depth, and a slice boundary only needs the overlay. Separately, please align the numbers: the PR body says "about 15 500" for `large` and `set.json` says 16 017.
4. **Seeding into an existing project skips the ownership check (needs discussion).** `DataSetProvisioner.ProvisionAsync` (L45–56) refuses only a *new* project in an organization the owner does not own. When the project exists, the seed writes annotations, schemas and configurations into it as `System`, whoever the owner is. For a tool with direct DB access that may be the intended rule ("an existing project is used as it is"). But cookbook step 16.2 now runs seeds against production, so a typo in `--organization/--project` lands in someone's real project without any warning. Consider asking for `--force` (or a new `--existing-project`) when the target project exists and `owner` has no role in it. At minimum, print the existing project's owners in `WritePlan`/`WriteRun`.

## Nits

- `DataSetProvisioner.cs` L107–128: `isViewRegistered` means "registered by this run" (it starts as `!views.Any(...)`). Calling it `isViewCreated` / `registersView` would read correctly; `DataSetProvisioning`'s field could follow.
- `DataSetProvisioner`: none of the `IAccessService`/`IViewService` calls take the token. It cannot be passed today, but a `ThrowIfCancellationRequested()` between the steps (as at L58) would at least stop early.
- `EntryPoint.cs` (CosmosDb) L146–148: `AddSingleton<IAnnotationBulkWriter, CosmosAnnotationService>()` creates a second instance. The comment explains why that is safe today. Registering `CosmosAnnotationService` once and forwarding both interfaces (`AddSingleton<IAnnotationBulkWriter>(sp => (CosmosAnnotationService)sp.GetRequiredService<IAnnotationService>())`, or a concrete registration) would keep it safe if the service ever gains a cache.
- `ViewTransferService` ctor: it builds `new ViewImporter(..., logger)` with `ILogger<ViewTransferService>` while DI also registers `IViewImporter`. That is intentional and commented, but it means the transfer job and DbCreator never share a decorator or logger category. Injecting `IViewImporter` with a fallback ctor would be cleaner once the callers can change.
- `CosmosAnnotationService.Bulk.cs` L181–184: a key that does not parse throws `InvalidInputException` for the whole call, while every other bad input fails per item. The seeder can't hit it (the lines reader parses keys first), but for a public interface a per-item `InvalidKey` failure would be more consistent. `ErrorCodes.DuplicateFile` for a duplicate *key* in a list is also a slightly odd name to reuse.
- `DataSetAnnotationLinesReader.Parse`: a generator line whose `AnnotationKey` has no `{n}`/`{0…0}` placeholder expands to `$count` copies of one key, i.e. `$count - 1` duplicate failures and a failed set. Refusing it at parse time with a clear message would be friendlier. Also, with a huge `$start`, `line.First + line.Count` (L92) can overflow and silently expand to nothing. A `checked` sum or an upper bound on `$start` closes that.
- `DataSetSeedRecord.GetId` → `seed.{view}.{set}`: if a set name (it comes from `set.json`/folder) may contain `.`, `view=a.b,set=c` and `view=a,set=b.c` collide. Restrict set names in `DataSetManifest` validation or use a separator that names cannot contain.
- `DataSetFolder.Collect`: `EnumerateDirectories` follows directory symlinks, so a symlink cycle under a `--path` folder recurses forever. That is unlikely for our own sets; skipping reparse points is a one-liner.
- `CoreDbStructureBuilder.BuildAsync`: the access is written before `seeder.SeedAsync` plans `core`, so a broken built-in `core/set.json` would leave a half-initialized DB despite the "wrong input before anything is written" rule. Calling `seeder.Plan(...)` before the access step keeps that promise.
- `AppHost.cs`: `db-seed` doesn't `WaitFor(dbCreator)`. That's fine since it ensures the containers itself, but if both are started at once they race on `EnsureOrganizationsContainerAsync`. That is harmless, just noisy.
- The record skips a set by version + hash only, so `--force` alone does nothing on a recorded set (`--again` is required). A short line in `data-sets.md` or the `--force` help text would save a confused run.

## Good

- The `IsKept`/`StateOf` logic in `CreateMissingCoreAsync` is subtle and correct. A key committed by an earlier attempt that still reads active is decided as it was before this call and not written again. A key purged in between is written again, and one deleted in between blocks its descendants. All three cases have their own emulator tests.
- Relations are computed set-wise (`AddBulkRelations`) and written last with `IfMatchEtag`, and `CompleteRelationsAsync` repairs parents left out by an interrupted file import. This closes a real gap that neither create nor import repaired before.
- `GetRounds` correctly orders lines and files across sources, so neither path creates the other's annotation with defaults and then keeps those defaults under `Skip`.
- Wrong input is refused before the database is touched (`Plan` validates every set's limits without expanding generators), the exit codes are clear (`4` for document failures), and the dry run threads an overlay through sets and rounds so its numbers match a real run.
- `DataSetFolder.ComputeHash` normalizes CRLF using Git's binary heuristic, so a Windows checkout doesn't re-seed everything. The `showcase` set is generated from the admin UI mock with a snapshot test, so the two cannot drift.
- `core` now goes through the services, so it gets audit items and is no longer reset on every run, which fixes a long-standing wart.
