## Important

1. **Phases 4–5 skipped on `main`. Confirm they ran from the branch** (`prod.bicepparam` lines 82–83).
   With `mcpAppExists = true`, `modules/mcp-existing.bicep` reads `prod-2s-mcp-ca` as `existing` to take its image and custom domains (lines 11–16). `main.bicep` line 338 then uses that image instead of `mcpInitialImage`. If phase 4 (`az deployment sub create` with `e6f879c`'s values, `mcpAppExists = false`) has **not** run yet, the next run of `main.bicep` fails with `ResourceNotFound` on the Container App. And if the phase 5 DNS records (`mcp.2s` CNAME, `asuid.mcp.2s` TXT) are missing, the custom-domain binding fails with `InvalidCustomHostNameValidation`.
   The runbook also says: *"Each change of `parameters/prod.bicepparam` goes to `main` through a pull request before its run."* That rule exists because `main.bicep` owns the API's app settings. Running phase 4 from the branch is fine here, because the branch had nothing that `main` lacked. But it does break the documented order.
   *Suggested fix:* either (a) say in the PR description that phase 4 ran from `e6f879c`, phase 5's records resolve, and phase 4's checks passed (401 with `resource_metadata`, API restarted cleanly), then merge and run phase 6's what-if/create from `main`; or (b) if phase 4 hasn't run, split the PR: merge `e6f879c` alone (phase 4), add DNS, then a second PR with `aea61b4` (phase 6).

2. **The pending deployment of run 45056694971.** Runbook phase 3 says to *reject* that deployment while the Container App doesn't exist. It has been waiting since 19:43 CET. If the app exists now, approving it is harmless: it deploys the same `20ef5b5` image by digest. If it doesn't, approving it fails the run. Either way, decide on it deliberately so it isn't approved by accident or left to time out.

3. **Follow-ups after the merge** (runbook, not this diff):
   - Phase 6: the what-if must show only `+ customDomains` on `prod-2s-mcp-ca` (same image) and the new `managedCertificates/mcp-2s-42for-net`, and nothing for the API's app settings. `create` can take up to 20 minutes for the certificate.
   - Phase 4's "restrict the exchange application" step: `New-TokenExchangeApplication.ps1 -McpIdentityName prod-2s-mcp-mi`. Without it, any identity in the tenant can get tokens for `api://2399e89b-…`. The API pins the object id anyway, so this is defence in depth.
   - Phase 7 (WorkOS production resource indicator, non-default) and phase 8 (`AZURE_MCP_APP_NAME` on `prod.42.Platform`) are still needed before the workflow can deploy on its own.
