## Important

1. **A definitive failure keeps a watch alive forever, silently.** `DescendantPollingSource.PollAsync` (lines 132–157) turns every `StorytellerConfigurationException` into `DescendantBatch.Failed`, and `StorytellerCatalog.WatchAsync` (lines 145–150) only throws it when the interval is zero. So `WatchAsync(StorytellerTarget.UnitsOf("rst.typo"))` never yields and never ends: it logs the 404 from `DoesNotExist` as a warning every 30 s for the life of the process. The same holds for a 403 `AnnotationRestricted` on the list and a 401. `ListAsync` throws all of these, so the two members disagree on the most common mistake a caller makes. This is deliberate and tested (`AnAncestorThatDoesNotExist_FailsThePoll_Definitively`, `AMachineRestrictedBelowTheAncestor_FailsThePoll_SayingWhatListingNeeds`), and it mirrors `WatchExecutionsAsync`, but I'd reconsider it for the new API. Suggested fix: when the *first* poll fails with a non-transient exception (`!exception.IsTransient`), throw it from the enumeration as the zero-interval case does; keep retrying transient failures and failures after a completed poll. If you prefer to keep the behaviour, say in the `WatchAsync` doc comment that a wrong target looks like an empty one.

2. **What happens to held descendants when the ancestor itself is deleted?** `CheckAncestorAsync` (lines 168–182) runs only until the first complete poll. If, after that, the platform answers the list of a deleted ancestor with a 404 rather than an empty page, every later poll fails, `DiffAsync` never runs, and the held descendants are never reported `Removed`. The consumer keeps acting on annotations whose parent is gone. Please confirm what `GET …/annotations/{key}/{descendants}` returns for a soft-deleted ancestor. If it is a 404, treat a missing ancestor after a completed poll as "everything held is removed" (confirm each with a point read, which already yields `Missing`/`Deleted`), and add a test next to `AHeldDescendantThatLeavesTheList_IsRemoved_WithTheReasonOfItsRead`.

3. **The two informers are now near copies.** `DescendantPollingSource` repeats `PollingSubscriptionSource` almost line for line: the `ReadAsync` loop with the cancel-while-failing handling (lines 48–83), `LimitAsync` (also a third copy in `StorytellerCatalog`, lines 159–171), `ReasonOf`, `PointRead`, the "Failed poll" logging, and `StorytellerCatalog.WatchAsync` mirrors `SubscriptionCatalog.WatchAsync`. `ListPaging` was the right first step. Suggested fix, here or in a follow-up: a small `PollLoop.RunAsync<TBatch>(Func<CancellationToken, Task<TBatch>> poll, …)` for the interval/jitter/cancellation loop, a shared `ConcurrencyLimit.RunAsync`, and one `RemovalReasons.Of(annotation, includeInactive, now)`. A fix to the cancellation edge case would then land once instead of twice.

4. **The cost of a list grows as N+1 point reads.** `ListAsync` (lines 94–110) and the first poll of `WatchAsync` read the ancestor, every page, and then every descendant that passes the filters, at most 4 at once. For `ExecutionsOf("rst.…")` on a busy responsibility that is thousands of requests per call and per process start, and the filters run in the process, so they don't make it cheaper. The reasoning (list values are lossy) is sound and documented. I'd still state the cost in the `IStorytellerCatalog.ListAsync` comment and in `hosting.md`, and consider making `MaxConcurrentReads` an option, since 4 is a guess that suits neither a small worker nor a large one.

## Nits

1. **Keys that differ only in the type code's case collapse non-deterministically.** `ListPaging` dedupes by the raw `AnnotationKey`, but `DescendantPollingSource.Candidates` (lines 190–203) and `ListAsync` (lines 97–106) key by the normalized full key. If another client stored `EXE.a.b.c` next to `exe.a.b.c` (see the follow-up from PR #169), the candidate keeps whichever item came last, so its fingerprint can flip and raise a spurious `Changed` on each poll, and the point read only ever reads the lower-case one. Edge case; a debug log when a normalized key is seen twice would make it visible.

2. **`ListAsync` computes `scope.KeyOf(key)` twice** (lines 102 and 104). Compute it once before the `keys.Add`.

3. **Inconsistent parameter name in the type checks.** `GetAsync<T>` passes `nameof(TAnnotation)` and `Find<T>()` passes the literal `"TAnnotation"`. Both are the same string, but `nameof` everywhere keeps a rename safe.

4. **Filter names compare ordinally.** `StorytellerTarget.Matches` uses `StringComparison.Ordinal`. That's right if the platform treats names as case-sensitive. If it doesn't, `WithContext("Production")` silently matches nothing. Worth a word in the `With…` comments either way.

5. **Playground: units are listed once even with `--watch`.** `ExecutorCommand.WriteUnitsOfAsync` documents it, so this is a nit: a unit added while watching never shows. A `WatchAsync(StorytellerTarget.UnitsOf(...))` alongside the executions watch would be a nice demonstration of the new informer in the very tool meant to show it off.

6. **`SubscriptionCatalog.GetAsync` now goes through `CatalogReader.FindAsync`.** Same semantics as before (read with deleted ones, null when deleted or 404). Good refactor; mentioning it only so nobody is surprised by the diff there.

## Good

- `StorytellerTarget` refuses impossible combinations at construction with messages that say what *is* allowed ("the descendants of a unit are its units of execution"), and the `With…` filters refuse a name the ancestor already fixes. That turns a class of empty-list confusion into an immediate `ArgumentException`.
- `GetAsync<T>` rejects a key of the wrong type, and an application's own derived type, *before* any read, instead of an `InvalidCastException` afterwards (the review fix in `89f552ed`).
- The informer's diff is well thought through: reads that fail are values, not exceptions, so one bad read doesn't sink the poll; changes are applied only after all reads end, in a stable order (Removed, Changed, Added, each by key); a held annotation the list missed is confirmed by a point read before it's removed; and a candidate that reads inactive keeps its old fingerprint so the next poll retries it.
- Cancellation is handled precisely: a failure that surfaces after the token was cancelled ends the enumeration as an `OperationCanceledException` with the failure as inner, and `Task.WhenAll` makes sure no read is left unobserved.
- The freshness caveat (relation arrays don't move `Modified`, so a parent raises no event for a new child) is documented and has its own test (`ANewChild_RaisesNoChangeOfItsParent_ButAnAdditionOfTheChildren`). That's exactly the kind of surprise that's better written down than discovered.
- `AnnotationMapper` builds the snapshot type from the key and only trusts body members when the body's discriminator matches, so a mismatched body degrades to empty names rather than a wrong cast.
- `TryAddSingleton<IStorytellerCatalog>` is registered independently of `ISubscriptionCatalog`, so an application that replaced one still gets the other.
