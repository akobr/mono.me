# Review of PR #133: [Configuration cache invalidation](https://github.com/akobr/mono.me/pull/133)

Reviewer: Harry · Review date: 2026-10-26 · Head commit: 8ed3488

**Verdict: needs changes.**

## Blocking

- **CodeRabbit's phantom version bug is real.** In `CosmosConfigurationService.cs` lines 311–314, `GetConfigurationVersionsAsync` appends the current row without an `IsWrittenVersion` check, so a cache-only row (version 0, empty content) shows up as a version that was never written. `main` has the same bug, and the PR's new filter just makes it obvious. Fix: `if (configuration is not null && IsWrittenVersion(configuration)) versions.Add(...)`.
- **The consequence is wrong data, not a 404.** `GET …/versions` returns 200 with `[v0]`. `GET …/versions/0` returns 200 with empty `{}` content, because the fallback at lines 358–360 has no guard either. Version diffs return 200 with an empty diff. The CLI (`StorytellerApiExtensions.cs`) then treats an unstored configuration as stored version 0. Apply the same guard in the fallback; none of these paths has a test.
- **No CI ran on head 8ed3488**, and this is a +2.8k line rewrite of the write path. Get the build and the Cosmos tests green before merging.

## Important

- If invalidation fails after commit, the pending token is cleared only by the next write on that configuration. Reads can serve stale effective config indefinitely. Add a sweeper or at least a metric.
- Level-by-level ordering assumes queries see every new item, but Session consistency doesn't guarantee that across Functions instances.
- The invalidation chain has no `CancellationToken`.
- `GetLevel` throws on an unknown type code after the commit, which leaves the token pending forever and fails every later write on that configuration.
- During a rolling deploy, old binaries drop the token marker.

## Good

The write path itself looks good: ETag-guarded read, archive and write with bounded retry, then audit, then invalidate, and token removal by filter so a newer token is never wiped.
