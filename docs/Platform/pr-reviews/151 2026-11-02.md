# Review of PR #151: [build(deps): upgrade all NuGet packages and move to .NET 10 (424-143)](https://github.com/akobr/mono.me/pull/151)

Reviewer: Harry · Review date: 2026-11-02

**Verdict: approve-ready, with one thing to check before merging.** This is a large but careful upgrade: 63 files and 30 commits, with PR #60 merged in. The spec, the five phase reviews and the held-back table explain almost every decision. The code changes are small and correct: the Orleans 10.4 nullability fix, the dashboard swap, the Aspire 13.6 API moves, the TestableIO `RandomAccess`/`OpenHandle` members and the `Examples` clean-build target. Nothing is blocking. The main risk is what couldn't be verified: the Cosmos-backed tests and the AppHosts were never run on the new versions.

**CI at review time:** ".NET reference (ubuntu-latest)" and "TypeScript SDK" passed. ".NET reference (windows-latest)" and CodeRabbit were still running. "Build and Deploy Job" (the Static Web Apps deploy) failed; it is likely unrelated to a NuGet upgrade, but check its log before merging. I reviewed the diff and the surrounding code but did not build it locally.

## Important

1. **The Cosmos path is unverified** (`src/Platform/Aspire.Host/src/AppHost.cs` L19-30, `Backend.CosmosDb/test/Startup.cs` L44, `Access.Certificates/testint/CosmosFixture.cs` L29). This PR moves `Microsoft.Azure.Cosmos` to 3.63.3, Testcontainers to 4.16.0 and the AppHost to the vNext emulator through `RunAsEmulator`. Yet 515 Cosmos-backed tests fail on the validation machine (the same failures as the baseline), and the AppHost was "built, not started" according to the phase 5 review. The diagnosis behind removing the image override (13.6 always sets the resource up for vNext, with `/ready` on port 8080) sounds right. Still, run it once before merging: start the Platform AppHost, check that `cosmos` turns healthy and that `db-creator` seeds it, and run `Backend.CosmosDb.UnitTests` and `Access.Certificates.IntegrationTests` on a machine where the emulator container works, or on Windows against the local emulator. Also note that the tests still use the classic `azure-cosmos-emulator:latest` image while the AppHost now uses vNext. That's fine, since the Testcontainers module targets the classic image, but say so in `docs/Platform/Aspire.Host/local-development.md` so nobody "aligns" them later.
2. **The scaffolded `global.json` still rolls to the next major** (`src/Monorepo/Cli/src/Templates/GlobalJsonT4.tt` L5, and the generated `GlobalJsonT4.cs`). The repo itself moved to `rollForward: latestFeature` precisely so that a .NET 11 SDK isn't picked. The template now writes `10.0.401` together with `latestMajor`, so a new repo from `mrepo` builds with a .NET 11 SDK as soon as it's installed. Suggest writing `latestFeature` there too (or `latestMinor` if you want 10.x minors), so the template matches the policy this PR introduces.
3. **`UnregisterReminder` is still fire-and-forget** (`MessageActionPoolingGrain.cs` L90-96 and `VolumeActionPoolingGrain.cs` L90-96, in `ReceiveReminder`). The null guard is right for the new `IGrainReminder?` return type. But the unawaited `Task` means a failed unregister (for example a storage error in the reminder table) is unobserved, and the reminder survives: it reactivates the grain every `PoolingMaxInterval` only for it to find no receiver again. The phase 3 review says awaiting would change when the grain deactivates. In practice `GrainContext.Deactivate` only requests deactivation after the current turn, so `await _reminders.UnregisterReminder(...)` before it is safe and makes the failure visible (a log at the very least). This isn't new to this PR, but the lines were touched, so it's a cheap fix now or a follow-up.
4. **No tests for the new trace-library members** (`src/Libraries/Testing/System.IO.Abstractions.Trace`, which has no test project). `ReadonlyFile.OpenHandle` encodes a non-trivial rule: read only, no `DeleteOnClose`, `Open`, or `OpenOrCreate` only when the file exists. A wrong condition there writes to or deletes a real file through a "read-only" file system, which was exactly the bug the final review caught. A small xUnit project with a temp-dir test per refused combination, plus one happy path for `DiagnosticRandomAccess` that delegates and traces, would lock this in.

## Nits

1. **Silent writes vs. throwing handles** (`Parts/ReadonlyRandomAccess.cs` L61-90). `OpenHandle` throws `NotSupportedException` for anything that isn't a read, but `ReadonlyRandomAccess.Write`/`SetLength` silently do nothing. That matches how `ReadonlyFile` drops stream writes, so it's defensible, but a caller holding a handle from elsewhere gets no signal. Either throw there too, or add a line to the class comment saying that dropped writes are the intended contract.
2. **Inconsistent tracing of buffers** (`Parts/DiagnosticRandomAccess.cs` L39-60 and L78-83). The sync `Read` traces `buffer.Length`, but `ReadAsync` traces the whole `Memory<byte>`, and `Write` copies the span with `ToArray()` on every call. The copy is fine for a diagnostics wrapper, but pick one rule, either the length or the content, for reads in both overloads.
3. **Hardcoded intermediate path** (`src/Crumble/Playground/Examples/src/Examples.csproj` L32). The `UpToDateCheckInput` hardcodes `obj\$(Configuration)\$(TargetFramework)\42.Crumble.Playground.Examples.Crumble.dll`, so it breaks silently if `Examples.Crumble` changes its `AssemblyName` or the repo moves to `UseArtifactsOutput`. Adding a comment pointing at the `AssemblyName` in `Examples.Crumble.csproj` is enough. The target itself (`AfterTargets="ResolveProjectReferences"`, with `Remove` before `Include`) is the right fix for the clean-build `CS0246`.
4. **The dashboard is mapped without auth** (`src/Crumble/Playground/Orleans.Silo/src/Program.cs` L22). It's fine for a playground silo, but if this `Program.cs` is ever copied as a template, `MapOrleansDashboard(...)` exposes grain and silo internals. Consider chaining `.RequireAuthorization()` behind a dev-only check, or adding a one-line comment.
5. **The Pkcs pin needs a removal trigger** (`src/Platform/Storyteller/Api.Web/src/Api.Web.csproj` L24-25). The comment explains why the pin exists, but not when to drop it. Add "remove once `Microsoft.Identity.Web.TokenCache` itself brings 10.0.13 or newer" so the direct reference doesn't outlive its reason.
6. **StyleCop 1.3 adds new warnings** that this PR leaves in place. Leaving them for a style pass is reasonable; please file it as a Linear issue so it doesn't get lost (it's only in the follow-up list of the phase 5 review).

## Good

- The nested `src/Crumble/SourceGenerator.Orleans/Directory.Packages.props` that keeps the generator on Roslyn 5.3 while the tools take 5.9 is exactly right, and the comment explains the compiler-load rule. This is the easiest thing to break in an upgrade like this.
- `global.json` with `latestFeature` and `allowPrerelease: false` finally stops .NET 11 previews from being picked. Choosing 10.0.401 as the minimum, because the Playwright image ships it, is well reasoned.
- Removing the `NU1510` in-box references and the unused `NuGet.*` references of c0ded0c, and pointing Scheduler and Supervisor at the custom `OpenApi.Core`, clears every audit warning at its source instead of just pinning versions.
- In `ExplicitStartupExtensions` the switch to named arguments and `KnownResourceCommands.StartCommand`, plus copying `Visibility` and `ValidateArguments`, guards against the next constructor reshuffle and against the renamed start command.
- The held-back table gives a concrete reason for every package that stays behind (BrowserStack's Playwright ceiling, App Insights 3.x in the Functions worker, the FluentAssertions license, MSBuild 18.10 being `net11.0`-only, Sentry 7 being only an RC).
- The PR description tells developers what changes locally (SDK 10.0.401+, the recreated `cosmos` container that has to be seeded again).
