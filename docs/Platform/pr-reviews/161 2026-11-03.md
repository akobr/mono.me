# Review of PR #161: [🐛 fix(platform): show No access to a Reader on the Machines page (424-164)](https://github.com/akobr/mono.me/pull/161)

Reviewer: Harry · Review date: 2026-11-03

**Verdict: approve-ready; one point worth a short discussion, the rest are nits.** The diagnosis is right: the API rule (machine list and machine need `Contributor`) is unchanged and correct in Release; a Debug API (`DEV_AUTH`) skips user role checks, so the admin UI, which only showed No access on a 403, listed machines to a Reader. The fix gates both machine queries on `useCan('machines')` and renders a synthetic 403 (`roleRequiredError`) instead, and adds a clean, test-only way (`UserRoleChecks.Enforce()`) to run the Release role check inside a Debug test flow. Code is small, well-commented and consistent with the repo's style.

**CI at review time:** "Lint, type-check, test, build", "Build and Deploy Job" and CodeRabbit were still in progress on `2fcd87d6`. I read the code at the PR head in context (session store, `useRole`, `HttpRequestDataExtensions`, the test doubles). A local `dotnet test` of `Api.Functions` on the box failed to build on an unrelated pre-existing error (`OpenApiConfigurationOptions.NamingStrategy` CS0115, in a file this PR does not touch; likely a package restore issue on the box), so I did not run the tests myself.

## Blocking

None.

## Important

1. **The root cause stays for every other route a Debug API serves to a lower role** (needs a short discussion, not a change in this PR). The UI now duplicates one server rule for one screen; any other screen that relies on the API's 403 (anything `Contributor`+ that reads data) will show the same symptom against a local stack, and each will need its own client-side gate. Since `UserRoleChecks` already exists, consider a follow-up that lets the local stack opt in to role checks too (e.g. a `DevAuth:EnforceUserRoles` setting read once at startup and OR'ed into `AreSkipped`), so local manual testing like ACC-MCH-08 matches Release without per-page UI code. Keep the UI gate either way; it saves a pointless request.

## Nits

- `machines.vue` / `[id].vue` Retry: `session.loadAccount(true)` gives no visible feedback while the account reloads (the No access state just stays until the new `AccessMap` lands). Showing `LoadingState` while `session.accountStatus === 'loading'` would make the click feel acknowledged. A failed reload is already covered: `DefaultLayout.vue` swaps in "Your account could not be loaded" on `accountStatus === 'error'`, so no real error gets hidden behind No access. A unit test for "Retry while the account endpoint answers 500" would pin that path.
- `UserRoleChecks.cs`: `Scope` restores `previous` unconditionally, so out-of-order disposal of nested scopes restores the wrong value. Fine for tests using `using`; a one-line comment ("dispose in LIFO order") is enough. In Release, `Enforce()` could return a static no-op instance instead of allocating; trivial.
- `UserRoleChecks.cs`: it is a test hook living in the production assembly. It is `internal`, has no effect in Release and nothing in `src` calls `Enforce()`, so I'm fine with it; worth a quick analyzer/grep guard or a note in `access.md` that `Enforce` is only for tests (the class comment already says so).
- `MachineHttpTests.cs` new theory: it sends `ContributorRequest()` for `None` and `Reader` too; the role actually comes from `RecordingAccess.Role`. Rename the helper to something neutral (`UserRequest()`) or add a comment, so the denied cases don't read as a Contributor being refused.
- `machines.vue` / `[id].vue`: the template gate uses `context.projectKey` while the query `enabled` uses `context.project`. They are set together today, but using one of them in both places would make the "only while the context has the project" rule easier to see.
- `errors.ts` `roleRequiredError`: `noAccess` is built once per component with a constant role, which is right; just note that if `capabilityRoles.machines` ever becomes dynamic it must move into a `computed`.

## Good

- The diagnosis and PR description are excellent: it separates the API rule (unchanged) from the Debug-build behaviour and says plainly that ACC-MCH-08 wasn't re-run locally.
- `AsyncLocal` scoping is the right tool for parallel xUnit tests, and `Enforce_InOneFlow_ReachesItsChildrenButNotAnotherFlow` actually proves that a flow started before the enforcement is unaffected while a child flow inherits it.
- The new theory asserts both the exception message and the mapped `403 AccessDenied` response, and that no machine is read on the denied path, in every build.
- Gating the queries with `enabled` (not just hiding the table) means no data reaches the client at all, and `useHashScroll` was updated so `#shared-certificates`/`#trusted-issuers` don't wait on a query that never runs.
- The Owner "no flash on the way out" test guards a subtle regression the author's own review caught.
