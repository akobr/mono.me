## Important

1. **On Windows a custom `code --wait` is resolved to `code.cmd`, then started in a way that cannot run a batch file.** `OpenFileInEditorAsync` looks up a custom command with `PATHEXT` and then puts that path in `ProcessStartInfo.FileName` with `UseShellExecute = false` (`src/Platform/Cli/src/Services/EditorService.cs:158-175`). `FindExecutable` is tested to return `code.cmd` when the VS Code `bin` folder has the extensionless script and the `.cmd` (`EditorServiceTests.cs:171-181`), and the docs say that is how `code --wait` starts (`docs/42for.net/cli/sform.md:316`). `CreateProcess` (what `UseShellExecute = false` uses) starts only images, not `.cmd` / `.bat`; the usual result is a `Win32Exception` such as “%1 is not a valid Win32 application.” `IsEditorAvailable` still reports the editor as found, so `sform account settings editor custom --command "code --wait"` saves without a warning, and the next `config edit` fails. `$EDITOR=code --wait` hits the same start failure and then falls back to the picker, which is kinder, but a saved custom command does not. The built-in `vscode` type already does the thing that works: `cmd.exe /c code --wait "…"`. Suggested fix: if the resolved path ends with `.cmd` or `.bat` (or, simpler, every custom command on Windows), start `cmd.exe` with `/c` and the command line, keep `UseShellExecute = false` and `CreateNoWindow = false` so a terminal editor still uses this console. Add a test that `OpenFileInEditorAsync` — not only `FindExecutable` — builds that start info; the edit tests currently override `OpenFileInEditorAsync` and never start a process.

2. **A dangling settings symlink is replaced by a regular file, instead of creating the file it points to.** `Load` treats a link whose target is not there yet as no settings, and the comment says “the first change creates the file it points to” (`UserSettingsStore.cs:53-54`). The in-repo review repeats that (`docs/Platform/Cli/specs/reviews/2026-11-08 sform account settings and User Preferences File.md`, deviations). `GetWritePath` only follows a link when `file.Exists` is true *and* `ResolveLinkTarget(returnFinalTarget: true)` returns a target (`UserSettingsStore.cs:320-336`). A dangling symlink has `Exists == false` on `File`/`FileInfo`, and `ResolveLinkTarget(returnFinalTarget: true)` cannot walk to a file that is not there, so both checks fail. `Write` then does `File.Move(temporaryPath, FilePath, overwrite: true)` onto the symlink path itself (`UserSettingsStore.cs:351-360`), which replaces the link inode with a regular `sform.settings.json`. The usual dotfiles setup — `ln -s ~/dotfiles/sform.settings.json ~/.42for.net/sform.settings.json` before the file exists in the repo — therefore loses the link on the first `set` / `editor` / `account set`. A link whose target already exists is written through correctly. Suggested fix: if `FileInfo.LinkTarget` is set, write to the immediate target path (`ResolveLinkTarget(returnFinalTarget: false)` still describes a missing file) and create its parent directory if needed; do not require `Exists`. Add a test that a write through a dangling link leaves the link in place and creates the target.

## Nits

- The settings table in `docs/42for.net/cli/sform.md` (line 295) says the editor is used by `story config edit`. On this branch the callers are `config edit`, `config patch`, `template edit` and the schema edit commands (`ConfigEditCommand`, `ConfigPatchCommand`, `TemplateEditCommand`, `SchemaOperations`), which is what `UserSettingDefinitions` already says. `story config edit` is not a command.
- There is no store test that a write through an *existing* link keeps the link. The load side of a missing target is mocked (`UserSettingsStoreTests.ALinkToAMissingFile_LoadsAsEmpty`); `GetWritePath` is not covered.

## Good

- The store is careful in the ways that matter for a file people will edit by hand and that must survive `dotnet tool update`: comments and dates stay as written on read, unknown properties are kept, a section or property is matched in any case and rewritten in camelCase in its place, a legacy file that holds more than its section is copied but not deleted, and a failed write deletes the temporary file and leaves the original alone.
- The lock retries only while another holder is plausible (Windows 32/33, flock 11/35, or `UnauthorizedAccessException` while the lock file still exists) and fails at once for a read-only or full disk, instead of waiting five seconds and blaming another `sform` run.
- Configuration loads only known, valid properties, so a hand-written `"editorType": "notepad"` cannot break every edit command, and a damaged file or a missing `HOME` warns on stderr and gives no settings — including no stale legacy values the new file had already replaced.
- `sform account settings` shows the value the commands actually use. A custom type without a command is “(ask on first use)”, a leftover `editor.command` is marked unused, `STORYTELLER_PROJECT` without a view uses the default view, an invalid project variable is called out, and a machine sign-in never displays `house.main` from the file. `--path` and `--json` write UTF-8 on stdout and `--path` still works when the file is damaged.
- `account set -p payments` (no dot) is refused before the account call, with a clear message, instead of throwing in the split. `register` and `access-point create` treat a failed save as a warning after the account already exists.
- An editor that cannot be started is reported instead of crashing `Process.Start`; `$VISUAL`/`$EDITOR` that cannot be started fall through to the picker. A command of quotes alone (`""`) is refused up front. Quoted executable paths work.
