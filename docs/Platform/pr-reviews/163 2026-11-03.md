# Review of PR #163: [🐛 fix(platform): end slow requests of the admin UI with an error, and connect the local API over IPv4 (424-166)](https://github.com/akobr/mono.me/pull/163)

Reviewer: Harry · Review date: 2026-11-03

**Verdict: needs changes (small).** The design is sound and carefully done: every SDK request now ends (30 s reads, 120 s writes, 10 min transfers), a timeout is its own `StorytellerError` kind instead of a network failure, the catalog stops flooding the browser's six connections, and the local Cosmos DB and Key Vault emulators are reached over IPv4 first so the API stops hanging on `localhost` → `::1`. I found no correctness bug in the core paths. What holds it back is that the branch currently conflicts with `main`, and two behaviours deserve a decision before merge: a production assembly now ships a public "accept any certificate" handler, and only the configuration save handles the "timed out, but maybe applied" case.

The only check is CodeRabbit, which finished "neutral" because it hit its rate limit, so nobody else has reviewed this yet. No build/test workflow ran on the head commit. ## Blocking

## Important

1. **`EmulatorHttpHandler` is a public type in `Backend.Core` that accepts any server certificate** (`src/Platform/Storyteller/Backend.Core/src/EmulatorHttpHandler.cs`, the `RemoteCertificateValidationCallback = (_, _, _, _) => true` in the factory). Today it is only wired up for emulator endpoints, but nothing stops a later caller from using it against a real host. Make it `internal` (with `InternalsVisibleTo` for `Backend.CosmosDb`, `KeyValues.Azure.KeyVault` and the tests), or keep it public but only skip validation when the target host is a loopback address (`IPAddress.IsLoopback` on the resolved addresses, or `localhost`/`127.0.0.1`/`::1`), and fail otherwise. That keeps the emulator path working and makes misuse impossible rather than merely unlikely.
2. **Only the configuration save resolves an ambiguous write after a timeout.** `ConfigurationEditor.vue` (`settleTimedOutSave`) is careful: it reads the content back and only reports success when it matches what was sent. The other writes that now get a 120 s limit (template save and delete, a key-value "Set new value", Bulk create, restore, subtree delete and purge, the schema writes) show their usual "not saved" failure, and the user docs in this PR say "A change that runs out of time shows the error of that change (for example "The template was not saved"), and you make it again." That's the wrong advice when the API may still be applying the write. Template patches carry `test` guards (a repeat gets a 412), Bulk create skips existing keys and delete is idempotent, so most repeats are harmless, but a repeated "Set new value" would add a second version. At minimum, show the timeout's own wording on those failures ("The API did not answer in time; the change may have been saved. Reload before trying again.") and change that sentence in the docs. A read-back for the template save, like the configuration's, would be the complete fix.
3. **Any failure inside `read` is now reported as "API not reachable"** (`sdk.typescript/src/lib/fetcher.ts`, `perform` → `failure`). `perform` now wraps `read(response)` in `race(...)` and sends every non-`StorytellerError` through `failure`, whose last branch is status 0, "The Storyteller API is not reachable", and `isTransientError` treats that as retryable. Before this PR the body was parsed outside `storytellerRequest`, so a `SyntaxError` from a 200 with a non-JSON body (an HTML page from a proxy or a captive portal) or a bug in `readValue` propagated as it was. Now it looks like a network blip and a poller retries it forever. Keep the mapping for what the deadline and the transport throw (the attempt's signal aborted, an `AbortError`/`TimeoutError`, a `TypeError` from the body stream), and rethrow anything else unchanged, the same way `send` already keeps a failing token provider's own error. A test with a 200 and the body `<html>` would pin it.
4. **`AutomationDataTests.PurgeAutomationData` and test ordering** (`UI.Admin.AutomationTests`). The comment says the `[Serial]` purge runs "after the other tests", but TUnit's `[Serial]`/`NotInParallel` only prevents parallelism; it doesn't order the test last. If it runs first it can delete data from an earlier run that is still being read by a parallel session on the same target, and if it runs in the middle it competes with the run's own requests. The safety guards (opt-in `Maintenance:Purge`, never against the mock, the generated-name regex, excluding the current run's slug, `OlderThanHours >= 1`) make actual damage unlikely, so this is about honest documentation: either use an explicit ordering mechanism (`[DependsOn]`, or run purge as a separate filtered invocation), or correct the comment and the docs to say it can run at any point but only touches older runs.

## Nits

- `EmulatorHttpHandler` connect: the candidates are tried one after another inside one `ConnectTimeout` (15 s). A firewalled IPv4 that drops packets would use the whole budget before IPv6 gets a turn. Fine for local emulators; a per-attempt slice (or a comment) would make the intent explicit.
- `ContainerRepositoryProvider`: the `GetOrAdd` with a static lambda and state is the right fix for the race. `_clientProvider.Client` is still evaluated on every call, cache hit or not; reading it inside the factory avoids that. The new test is a smoke test (as the PR says); a concurrent `Parallel.For` asserting one instance per container would actually pin the race fix.
- `StorytellerApi.cs` (automation tests): the `renewed` flag never resets, so an instance renews its token at most once in its lifetime; fine for one test session, worth a comment if instances live longer. The `SemaphoreSlim` is not disposed.
- `StorytellerApi.cs`: the scrubbing of the Playwright call log (it contains the `Authorization` header) from exception messages is important. A small unit test that feeds a fake `PlaywrightException` message with a bearer token and asserts it's gone would keep it from regressing.
- `RequiresPurgeAttribute`: when `LoadedSettings` is null the test is not skipped. That's fine because the session then fails earlier anyway, but a one-line comment saying so saves the next reader the trace.
- `stores/catalog.ts` `pageTypes`: `progress.lists` counts settled lists, including the ones another list's timeout stopped, so the strip can briefly show "7 of 7 types" just before the error. Cosmetic.
- `catalog.ts`: after a timeout of one type list there's no `getAnnotations` fallback by design (it would wait again). Reasonable, but on a cold-starting deployed API the first page now shows an error after 30 s where it used to eventually load. The README says so; consider mentioning it in the PR description's risk section as well, since it's a user-visible change.
- `fetcher.ts` `limitOf`: a negative or `NaN` limit means "no deadline" by design (the comment says so), but silently; a config typo like `timeoutMs: -30_000` would quietly bring back endless requests. A `RangeError` in `configureStoryteller` for a negative or non-finite value would catch it.
- The PR description lists the still-broken `Access/AuthKitSignIn.cs:53` ("Continue" vs "Continue with email"). Worth a Linear issue so it doesn't get lost after merge.

## Good

- The SDK deadline is implemented without `AbortSignal.any`/`AbortSignal.timeout`, so it works in every runtime the SDK supports, and the timer is `unref`'d so Node processes don't hang, and clamped to 2^31−1 ms so a huge limit doesn't fire at once. The first abort wins, so a caller abort is never reported as a timeout and vice versa, and a caller's own `AbortSignal.timeout` is correctly classified as a transient timeout rather than an abort.
- The deadline covers the token lookup, the 401 retry and the body read, which is what "every request ends" should mean; a late response from a transport that ignores the signal is discarded and its body cancelled. Errors are told apart by name, so a `DOMException` from another realm (jsdom, a polyfilled fetch) is still classified right.
- `settleTimedOutSave` in the configuration editor is exactly the right shape: read back, compare by content (`sameJson`), only claim success when it matches, keep the draft otherwise, and explain why re-sending could double-apply `add` operations.
- The catalog changes fix real UX traps: no more endless "Loading configurations…" when the summaries fail, a failed refresh keeps the shown catalog with a compact Retry, and a failed first load no longer leaves a partial `ready` map that would mark ancestors as missing.
- Sentry gets timeouts under their own fingerprint, so they don't merge with network failures, and still without messages or bodies.
- On the .NET side the emulator handler disposes the socket on failure, rethrows cancellation, keeps `Host`/SNI intact, and the clients share it correctly: Cosmos gets a new `HttpClient(handler, disposeHandler: false)` per factory call with the handler disposed after the client, and Key Vault uses one process-wide `Lazy<SocketsHttpHandler>`, so `CustomerKeyProvider` no longer builds a connection pool per call.
- The purge test's guards are thorough: opt-in only, always skipped on the mock, only generated `at-` roots of earlier runs, an age cutoff, 404 treated as done and 409 (restored meanwhile) skipped.
- The spec and the review of each of the three phases explain each decision, which made this large PR much easier to review.
