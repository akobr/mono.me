# Review of PR #190: [fix(platform): the WorkOS API's per-client issuer without the custom AuthKit domain](https://github.com/akobr/mono.me/pull/190)

Reviewer: Harry · Review date: 2026-11-11

**Verdict: approve-ready.** I found nothing blocking. Two points are worth a small hardening change or a follow-up. The diagnosis is sound: the admin UI (authkit-js) and `sform` get their tokens from `api.workos.com/user_management/authenticate`, and WorkOS stamps those tokens with `iss = https://api.workos.com/user_management/<client id>`, not the environment's `….authkit.app` domain. The JWKS the API already uses (`AuthKitOptions.GetJwksUri()` gives `https://api.workos.com/sso/jwks/{ClientId}`) is keyed by the same client id. So signature validation was never the problem, and only `Auth__AuthKit__Issuer` has to change, which matches the reported what-if. The infrastructure change is small and correct. `authKitCustomDomain` already existed in `main.bicep` (default `true`) and was used only for the admin UI outputs. It now reaches `functions.bicep` again, and `prod.bicepparam` already sets it to `false`.

**CI at review time:** "Bicep build and lint, PSScriptAnalyzer" and CodeRabbit were still running on `42e75e4`. The PR says `az bicep build` of `main.bicep` passes locally. I read the Bicep at the PR head in context, along with `AuthKitOptions`, `AuthKitBearerTokenValidator`, `AuthKitTokenSource` and `AuthKitUserSubjectTokenValidator`.

## Blocking

None.

## Important

1. **An empty `authKitClientId` now silently produces a broken issuer.** See `src/Platform/Deployment/modules/functions.bicep:78` and `main.bicep:50`, where it defaults to `''`. With `authKitCustomDomain = false` and no client id, the issuer becomes `https://api.workos.com/user_management/`. Every user token then fails with a 401 that looks just like #188, and `Auth__AuthKit__ClientId` is left out too (line 122), so the JWKS URL is `…/sso/jwks/` as well. Prod sets the client id, so this isn't a bug today, but it is an easy way to misconfigure a new environment. Suggested fix: fail fast in one of these places:
   - in Bicep, guard it, e.g. `var authKitIssuer = authKitCustomDomain ? … : (empty(authKitClientId) ? fail('authKitClientId is required without a custom AuthKit domain') : '…')` (the `fail()` function needs a recent Bicep version), or at least document the dependency in the `authKitCustomDomain` `@description`.
   - or in the API, at startup: refuse an `Issuer` that ends in `/user_management/` or `/user_management`, or check that it ends with `ClientId`. `AuthKitBearerTokenValidator` already throws on an empty issuer (line 41), so a similar check fits there.

2. **The issuer is now per client, but the API accepts exactly one.** `AuthKitTokenSource.IssuerMatches` does an exact match against the single `Auth:AuthKit:Issuer`. The docs (cookbook step 13.2, `decisions.md`) plan for every later 42for.net product to be **its own application** in the same environment, with a shared `aud`. Without the custom domain, tokens from another application (and from the CLI device flow, if it ever uses a different client id than `2S Platform`) carry a different `iss` and get a 401. They pass the signature check but fail the issuer check. That's fine for now. To avoid a second #188, please do one of these:
   - add a sentence to `decisions.md` "Open points" saying a second application's users need the custom domain or a second accepted issuer.
   - or confirm here that the CLI's device flow uses the same client id as the admin UI. The docs now say it gets the same `user_management` issuer.

## Nits

- `src/Platform/Storyteller/Backend.Core/src/Accessing/AuthKitOptions.cs:7-8` (not in the diff): the default `Issuer = "https://api.workos.com/"` and the comment "Or the custom auth domain" are now misleading, because the real WorkOS API issuer is `…/user_management/<ClientId>`. As a follow-up, consider deriving the default from `ClientId` when `Issuer` is empty, the way `GetJwksUri()` does. Bicep could then even drop the hard-coded URL.
- `functions.bicep:73-78`: the custom-domain branch (`https://${authKitDomain}`) is still unverified, as the PR says (424-247). A `// TODO(424-247)` next to the ternary would keep that visible in the code, not only in the docs.
- `cookbook-azure-production.md` §8.3: the commented "with it" line sets two variables on one line. That's valid shell, but two lines would make the copy-paste switch harder to get wrong.
- In `AuthKitBearerTokenValidator.cs:76` and `:64` the comments still describe the authkit.app/custom-domain world ("with a custom auth domain an M2M token can share this issuer"). They are still accurate, and the new issuer actually separates user tokens from M2M tokens even more cleanly. No change needed, but worth a glance when 424-247 lands.

## Good

- The PR checked a real production token instead of trusting the OpenID metadata. The previous assumption (the `issuer` of `/.well-known/openid-configuration`) is exactly what broke.
- The change is minimal: one ternary plus wiring an existing parameter, and the deploy diff is limited to a single app setting.
- The docs are updated consistently everywhere the old assumption appeared (cookbook, runbook, decisions, Storyteller `authentication.md`, the `prod.bicepparam` comment), with the date the token was checked.
