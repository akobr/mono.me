## Important

1. **Check that the vNext digest is the multi-arch index, not the amd64 manifest.** `Backend.CosmosDb/test/CosmosTestEmulator.cs` L44–45 pin `vnext-EN20261019@sha256:db53613d…`. If that digest is the platform-specific amd64 manifest (which is what `docker inspect` RepoDigests or a local pull can give you), arm64 machines such as Apple Silicon would run vNext under emulation or fail to pull. Until now they got the native arm64 image. Classic is x64-only anyway. Check with `docker buildx imagetools inspect mcr.microsoft.com/cosmosdb/linux/azure-cosmos-emulator:vnext-EN20261019@sha256:db53613d…`: it should list a manifest per platform. If it doesn't, pin the index digest of build 20261019.1.
2. **The package-update block is a single host name.** `CosmosTestEmulator.cs` `BuildVNext` (`.WithExtraHost("packages.microsoft.com", "127.0.0.1")`) only works while every tdnf repo of the pinned image resolves through that host. That is true today and was verified locally (PostgreSQL stayed at 16.15). But this is the one guard against cause B, and its failure mode is the old flaky 500 about a minute in. Consider a cheap tripwire in the vNext fixture, at start or in `DisposeAsync`: `ExecAsync(["rpm", "-q", "postgresql16"])` (or whatever the package is named) that logs, or fails, when the version is not the image's own. Then a broken block shows up as a clear signal rather than a flaky test. Optional, but cheap.
3. **The repo docs and the `mrepo` template still show `setVersionVariables: true`.** The root `version.json` change is right. Code search finds no reader of `GitBuildVersion*` or `NBGV_*` in workflows or code. But `docs/Monorepo/versioning.md` (the "Global version settings" sample) and `src/Monorepo/Cli/src/Templates/RootVersionJsonT4.tt` / `.cs` still recommend `true`. The PR lists the template as a follow-up, which is fine. Please also add the doc sample to that follow-up (or fix it here, since it is one line), so the docs and the repo's own root file don't contradict each other.

## Nits

1. `LowkeyVaultTestContainer.cs` L32–37: the `HttpClientHandler` is never disposed. That is harmless for one handler per test process, but a short comment saying the handler lives as long as the container (Testcontainers keeps it for every probe) would stop someone from "fixing" it with a `using`, which would break the retries.
2. `LowkeyVaultTestContainer` and `CosmosTestEmulator` live in `_42.Platform.Storyteller.Backend.CosmosDb.UnitTests` but are now compiled into three other test assemblies. That is why `CosmosFixture.cs` and `LowkeyVaultFixture.cs` need a `using` of another project's test namespace. A neutral namespace such as `_42.Platform.Storyteller.Testing`, or a small shared folder for linked test helpers, would read better. This matches the existing `OrganizationQueryGuard` link pattern, so leave it if you prefer consistency.
3. `.github/workflows/Platform.Storyteller.CosmosDb.yml`, classic `if: ${{ inputs.classic || !inputs.vnext_runs }}`: a caller that passes `vnext_runs: ''` gets the classic job even with `classic: false`. That is an unlikely edge case, and the comment explains the PR-has-no-inputs trick well. A `github.event_name == 'pull_request'` check isn't usable here (as noted, a called workflow sees its caller's event), so this is fine as is.
4. The matrix `fromJSON(inputs.vnext_runs == '10' && '[…]' || inputs.vnext_runs == '5' && '[…]' || '[1]')` silently falls back to one job for any other `workflow_call` value (for example `'3'`). Mention "other values run one job" in the `workflow_call` input description.
5. The PR was opened as `fix(platform)` and is now titled `ci(platform)`. The changes are tests, CI and `version.json`, so `ci`/`test` fits better. Just make sure the squash commit uses the final title.

## Good

- **Pinning tag and digest together** (`tag@sha256:…`) keeps it readable and immutable, and the comment says exactly what to re-check when the pin moves (that the package update stays off).
- **The `/ping` readiness wait** fixes the reuse/restart blind spot for all three Lowkey Vault users at once. Testcontainers appends it after the module's log wait, so first starts and restarts both pass through it. The evidence (0.3 s "ready" vs 4.4 s with `/ping`, and the second test failing after about 6 s, which is the SDK retry budget) is convincing.
- **The class fixture for `KeyValueEndToEndTests`** removes the per-test start/stop churn that caused A, and it keeps its own reuse label so it can't stop another suite's vault.
- **One linked `CosmosTestEmulator`** removes the drifted copy in `Access.Certificates/testint`. That copy would not have received the digest pin or the update block. The only differences were the namespace and the new pin/block lines, so no behavior is lost.
- **Changing the Testcontainers reuse hash** (extra host and env) means old poisoned containers are not picked up again, and `development.md` documents removing them.
- **`vnext_runs`** is a nice reusable way to prove a fix is steady, and keeping the single job named `vNext emulator` preserves any required-check name.
