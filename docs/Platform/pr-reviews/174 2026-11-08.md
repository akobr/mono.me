# Review of PR #174: [🐛 fix(platform): add ETags, If-Match and a merge PATCH to annotation writes (424-210)](https://github.com/akobr/mono.me/pull/174)

Reviewer: Harry · Review date: 2026-11-08

**Verdict: approve-ready.** The PR changes 361 files (+27,835/−759) in 17 commits and is not a draft; most of the line count is regenerated SDK code and two copies of the 0.10.30 OpenAPI spec. The real change is about 6,000 lines: strong `ETag`s on annotation reads and writes, `If-Match` / `If-None-Match` on `POST`/`PUT` checked on every retry attempt, a new `PATCH …/annotations/{key}` that takes a JSON Merge Patch or a JSON Patch and re-applies it to fresh state on each attempt, and the CLI (`sform story set`) and MCP `set_annotation` moved off their unprotected read-merge-write. The concurrency design is sound: the condition is checked against the very item the batch replaces under its Cosmos `_etag`, so a write in between fails the batch and the retry fails the condition instead of overwriting. The fail-safe default interface method (a service that cannot check a condition throws rather than writing unconditionally) is a nice touch. Tests are thorough, including Cosmos tests that interleave competing writes with the storage interceptor. Nothing is blocking; the points below are hardening.

**CI at review time:** on `1ae1430b`, `.NET reference` (ubuntu and windows), `TypeScript SDK` and `Build and Deploy Job` passed; `Lint, type-check, test, build` and CodeRabbit were still running, and `Close Pull Request Job` was skipped. ## Blocking

None.

## Important

1. **A JSON Patch can build a document far larger than any write can store.** `AnnotationPatch.MaxDocumentWeight` is 16 Mi characters (`Backend.Core/src/Annotating/AnnotationPatch.cs:18`), while a full write's body is capped at 4 MiB (`RequestBodyLimits.Annotation`) and a Cosmos item at 2 MB. A small patch with a few `copy` ops can pass `CheckGrowth`, get serialized (several times across up to three retry attempts), and then fail in `BatchPlan.ExecuteBatchAsync` with a `CosmosException` 413, which is not one of the mapped statuses (`BatchPlan.cs:140-149`) and so most likely surfaces as a 500. Suggested fix: cap the weight at the full-write body limit (or a bit under the Cosmos item limit), and map a batch 413 to a 400/413 `ErrorResponse` (for example `ErrorCodes.BodyTooLarge`) so an oversized `POST` gets the same treatment.

2. **The commit callbacks rely on an implicit "one `BatchOperation` = one batch operation" invariant.** `BatchPlan.ExecuteBatchAsync` (`Backend.CosmosDb/src/Annotating/BatchPlan.cs:132`) pairs `operations[index]` with `response[index]` and stops silently at `index < response.Count`. Today every `Apply` adds exactly one operation (I checked `AnnotationAuditStore.Write` and the relation updates), but if a future `Apply` adds two, the target's marker would quietly become the `_etag` of a neighbouring item (an audit or a parent), and every conditional write after it would answer a false 412. Suggested fix: assert `response.Count == operations.Count` and throw (or at least log and skip the callbacks) when it does not hold, and document the invariant on `BatchOperation`.

3. **Child creates and deletes move the parent's `ETag`, so `If-Match` on a parent is fragile.** The relation arrays live on the parent item, so the tag changes whenever a child is created or deleted, which the `AnnotationEntityTag` description says honestly. For `sform story set --replace` and any SDK user doing read, edit, `If-Match` write on a busy parent (for example a responsibility whose units are being created), that means spurious 412s and exit code 2 for changes the user never touched. That is safe but noisy. It is worth a sentence in `annotation-lifecycle.md` recommending `PATCH` (no `If-Match`) for editing content of parents, and a follow-up issue if relation arrays ever move out of the item.

4. **`sform story set --replace` silently drops to an unconditional write when the read has no `ETag`.** `StorytellerSetCommand.ReplaceAsync` (`Cli/src/Commands/Storyteller/StorytellerSetCommand.cs:326`) sets `ifMatch = stored.ETag`, and when a proxy strips the header (or the server is older than 0.10.30) the replace goes out with no condition, which is exactly the lost-update the PR fixes. Suggested fix: when the read returned 200 without a tag, either refuse with a clear message or print a warning that the replace is unprotected.

5. **The generated `.NET` `SetAnnotationAsync` signature is a breaking change.** In `ApiSdk.g.cs`, `body` lost its default and `if_Match` / `if_None_Match` were inserted before `cancellationToken`, so a caller passing the token positionally no longer compiles and compiled consumers break at runtime. The generated `PatchAnnotationAsync(AnnotationMergePatch)` also cannot clear a member, because every property is `NullValueHandling.Ignore`. Suggested fix: call out the signature change in the SDK README or changelog and bump the package version accordingly, and note on the generated `PatchAnnotationAsync` that clearing a member needs `PatchAnnotationVersionedAsync` with a `JObject` or `AnnotationJsonPatch`.

## Nits

- `AnnotationPatch.CheckGrowth` calls `GetSegments(operation.From)` twice on one line (`AnnotationPatch.cs:294`); compute it once.
- `CosmosAnnotationService.KeepETag` (`CosmosAnnotationService.cs:516`) duplicates `BatchOperation.KeepingETag`; use one.
- `AnnotationEntityTags.ToHeader` compares to `Binding.BindingDependency.Absent` (`AnnotationEntityTags.cs:53`), which couples the HTTP tag helper to a binding sentinel. A named `MarkedRead.HasMarker` or a constant on `AnnotationWriteResult` would read better.
- The JSON Patch weight never decreases on `replace` / `remove` / `move`, so a long patch that repeatedly replaces a large value can hit the limit spuriously. That is conservative and fine, but worth a comment in the docs next to the limit.
- `GetAnnotation` now answers an `ETag`, but annotation reads do not honour `If-None-Match` (no 304). That is not needed for this PR; just mention it under "Not in this PR" so nobody assumes conditional reads work.
- `PUT` deliberately answers no `ETag` (RFC 9110 §9.3.4), while `POST` with the same normalizing body does. That is defensible, but a client then needs a re-read after `PUT` to continue with `If-Match`; the SDK helpers use `POST`, so a sentence in the API description would help.
- The same 19,808-line spec is committed twice (`Sdk.NSwag/open.api.v0.10.30.json` and `sdk.typescript/open.api.v0.10.30.json`, byte-identical), and the TypeScript copy of 0.10.15 was moved rather than kept. This follows the repo's habit, but a single shared spec location would cut churn.
- The Cosmos suite had to run class by class because the Linux emulator crashed under the full run. That is not caused by this PR, but a tracking issue for the emulator stability would help, since the new conditional-write tests are exactly the ones you want running in CI.

## Good

- Conditions are re-checked per attempt against the item the batch replaces, with the `committed` marker so a write that already landed in an earlier wave does not fail its own condition. That is subtle and correct.
- The PATCH ordering follows RFC 9110 §13.2.1: 404 for missing or deleted first, then `If-Match`, then the patch. `If-None-Match` on PATCH is refused with a clear 400.
- A malformed condition header is a 400 rather than ignored, so an intended conditional write never turns unconditional.
- The custom RFC 6902 applier handles `~1` before `~0` correctly (with a test for `~01`), rejects moves into a descendant, deep-clones values so the parsed patch is never attached to a document, and walks depth iteratively.
- The CLI and MCP flows (patch first, create with `If-None-Match: *`, bounded rounds, no silent re-create of a key deleted after the lookup) close the race from [#169](https://github.com/akobr/mono.me/pull/169) cleanly.
- The CORS section in `authentication.md` is honest that a cross-origin browser cannot read the `ETag` without `Access-Control-Expose-Headers`, and it points to `PATCH` as the way around it.
