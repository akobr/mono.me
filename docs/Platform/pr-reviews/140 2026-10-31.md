# Review of PR #140: [Typed annotation name queries filter every list, bounded and with 400s (424-97)](https://github.com/akobr/mono.me/pull/140)

Reviewer: Harry · Review date: 2026-10-31

**Verdict: approve-ready, with a few follow-ups worth tracking.** `fix/424-97` into `main`, not a draft. CI ("Build and Deploy") and CodeRabbit were still running at review time; nothing is blocking.

The fix is right. Before, `Condition<T>` was typed over the entity and its `Against` was never set, so the Cosmos service applied only the responsibility conditions. The cast to the entity type threw, which caused the `rst` 500, and every other typed filter was silently dropped. Now `Against` comes from the model type, `CompileConditions<T>()` ANDs the conditions, and the service filters the mapped page in memory. The Api.Web descendants conditions (`AnnotationsController.cs` ~L310–370), which were also being dropped, now really filter.

## Important

1. **Api.Web still answers 500 for a bad pattern.** `NameQuery.Parse` and `IsMatch` throw `InvalidInputException`, and Api.Web has no mapping for it. There are now more ways to hit it: the length cap, unsupported constructs, the timeout and the budget. Add a small exception filter that maps it to 400 with its `ErrorCode`, like Functions' `ErrorResponseMapping`, or track it as an explicit follow-up.
2. **Every filter runs in memory**, even ones Cosmos could run (`CosmosAnnotationService.cs` ~L650 and L758). Read cost is unchanged, since those filters were never applied before. But an exact name on a parameter that isn't the partition key scans across partitions and can return many empty pages that still carry continuation tokens. Push exact and contains down to Cosmos and keep only patterns in memory. A follow-up issue is enough.
3. **`NameQuery` is public but holds per-request state.** `_spentTicks` accumulates for the instance's lifetime, and `ToCondition` captures `this`. If anyone caches a parsed query, the budget stays used up and every later request gets a 400. Document it as one per request, or move the budget into a context created by each `CompileConditions` call.
4. **The timing tests may be brittle.** `IsMatch_StateHeavyPatternOverAPage_RunsOutOfTheBudget` (`NameQueryTests.cs` ~L1001) depends on a slow fallback in today's regex engine, and the wall-clock limits (`< 1s` and `< 5s`) can flake on a busy CI agent. Test the budget with a fake slow matcher or a tiny `MatchBudget`.

## Nits

- The budget is wall-clock, so a GC pause during a match counts against it. Add a comment.
- The "not supported" message repeats the user's pattern but the other errors don't. Leave the input out everywhere.
- Functions uses `nameQuery` while Api.Web uses `contextNameQuery` (`AnnotationsController.cs` L166/L188). Line them up.
- `AddNameQuery` is duplicated in `AnnotationsHttp.cs` and `AnnotationsController.cs`. Make it an extension on `List<ICondition>`.
- Stray blank line in `AnnotationsController.cs` (~L496).
- `Condition<TEntity>` became `Condition<TAnnotation>` and lost its `Against` setter, which only matters if Backend.Core ships as a package.

## Good

14 copies of the three-branch parsing became one `NameQuery`, removing about 340 lines. The non-backtracking engine plus the 63-character names, 50 ms timeout and 250 ms budget is solid defense in depth. The test matrix is excellent, and `%` alone now matches every name.
