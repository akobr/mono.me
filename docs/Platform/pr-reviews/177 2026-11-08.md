## Important

1. **Four of the five labels don't exist in the repo, and two overlap with existing ones.** The repo's labels are the GitHub defaults (`bug`, `documentation`, `duplicate`, `enhancement`, `good first issue`, `help wanted`, `invalid`, `question`, `wontfix`). `api`, `feature`, `backend` and `frontend` are new. With `auto_apply_labels: true` they will either be created on first use with a default colour and no description, or fail to apply, depending on how CodeRabbit adds them. `feature` also duplicates the existing `enhancement`. Suggested fix: create the four labels (with colours and descriptions) before merging, and either rename the rule to `enhancement` or delete `enhancement` so there is only one "new feature" label.

2. **`bug` and `feature` depend only on "the original issue in Linear", which CodeRabbit may not find.** The rules say "Determined based on the original issue in Linear" (`.coderabbit.yaml:11-14`), with no fallback. Nothing in this file configures the Linear knowledge base (`knowledge_base.linear`), so it relies on the Linear integration being connected in the CodeRabbit app. The PR titles here reference work as `(424-218)`, which is not the usual `TEAM-123` Linear key, so automatic linking may not pick it up. The titles already carry the type reliably through gitmoji and conventional-commit prefixes (`✨ feat`, `🐛 fix`, `🚸 fix`, `♻️ refactor`). Suggested fix: make the title the primary signal and Linear the secondary one, for example: `The PR title starts with "🐛 fix"/"🚸 fix" (or another fix type), or the linked Linear issue is a bug.` and the same for `✨ feat` / `feature`.

## Nits

- Labeling is closed-world: when `labeling_instructions` is set, CodeRabbit suggests only from that list. A large share of PRs here are docs, refactors and chores (this one included), and they will get at most `backend`/`frontend`. Consider adding `documentation` (docs-only or docs-mostly changes, e.g. under `docs/`) and maybe `refactor`/`chore` from the title prefix.
- `backend` and `frontend` would be more consistent with path hints, since this is a monorepo. For example: backend for `src/Platform/**` services, APIs and Orleans grains; frontend for the admin UI and the static site. Note the rule puts the CLI under frontend, while `src/Platform/Cli` is C#, so expect both labels on many CLI PRs; that's fine if intended, but say so in the instruction.
- Typo in the `frontend` instruction: `web interface,mobile` is missing a space after the comma.
- `api` instruction reads a bit awkwardly; something like `The PR changes the payload or contract of an existing endpoint, or adds a new endpoint.` is clearer for the model.
- `unit_tests.enabled: true` and `fix_ci.enabled: true` are already the schema defaults. Keeping them explicit is fine for documentation; just know they don't change behaviour. `simplify: true` does (its default is off).
- `early_access: true` opts every review into features CodeRabbit hasn't stabilised yet. Fine for a personal repo; worth remembering if review behaviour changes without a config change.
- `issue_enrichment.auto_enrich: true` makes CodeRabbit comment on every new issue with related code and a complexity estimate. The repo has 9 open GitHub issues and tracks most work in Linear, so this is low-noise, but it's a behaviour change worth a line in a PR description.
- The PR has no description. A short one listing what was turned on and off would help when someone later wonders why CodeRabbit started labelling PRs or posting on issues.

## Good
