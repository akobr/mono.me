# Review of PR #184: [test(platform): run the key-value paging test on the classic emulator only (424-230)](https://github.com/akobr/mono.me/pull/184)

Reviewer: Harry · Review date: 2026-11-10

**Verdict: needs discussion. The PR is mostly overtaken by its base branch and conflicts with it.** It's a small, test-and-docs-only bot fix for the failed vNext run of [#182](https://github.com/akobr/mono.me/pull/182), with no production code touched. But `feat/424-230` already got the same fix in `b06a3927` ("run the key/value paging test only on emulators that keep the page size") after this branch was cut from `a60ef40a`. GitHub reports the PR as `dirty` (merge conflicts), and the two commits give **different root causes** for the same failure.

Scope I read: the PR description, the diff against both the merge base (`a60ef40a`) and the current base tip (`b06a3927`), `CosmosKeyValueService.ListAsync`/`BuildListingQuery` and the other ordered listings in the same file, the `Listing_Pages` test in context, both `CosmosTestEmulator` classes, and the PR's comments. CI: only CodeRabbit, which skipped because the author is a bot. The Storyteller Cosmos DB workflow hasn't run on this head.

## Blocking

None in the code itself. The test change is correct and identical to what's already on the base.

## Important

1. **The PR duplicates `b06a3927` and conflicts with it.** Both add `[Trait(Emulator, Classic)]` and `Assert.SkipUnless(Context.Emulator.IsLikeTheService, …)` to `Listing_Pages` (`Backend.CosmosDb/test/CosmosKeyValueServiceTests.cs` around L414). The conflicts are in that comment and in `SkipReasonOnVNext` (`Backend.CosmosDb/test/CosmosTestEmulator.cs` around L57). What this PR still adds is documentation only: the workflow header, `local-development.md`, the probe cookbook, and the `VNext` enum comment. I'd suggest either closing it and porting those doc lines onto the base, or rebasing it onto `b06a3927` so it carries only the doc delta. Merged as is, a rebase would also undo base content, such as section 8 of the review findings and the `Access.Certificates` skip reason. The diff against the current base shows those as deletions.

2. **The two diagnoses disagree, and the docs should state the combined one.**
   - `b06a3927` (review findings §8) says the cause is the client OS. A Linux SDK gets the query plan from the gateway and receives 1,050 items with no continuation, while from Windows the same emulator pages at 1,000.
   - This PR says vNext ignores `MaxItemCount` on **any** `ORDER BY` query. Its probe shows that unordered queries page correctly on Linux.
   - Each observation narrows the other, so the likely truth is that vNext ignores the page size for `ORDER BY` queries when the query plan comes from the gateway, which is the non-Windows SDK path.
   - Fix: write the condition once in a single place, such as the `CosmosTestEmulator` comment or the review findings, and link to it. This matters most in `docs/Platform/Aspire.Host/local-development.md` (L42). As written, it tells a Windows developer on the Aspire host that ordered listings come back in one page, which `b06a3927` says isn't true there.

3. **Check the other ordered, paged listings.** `CosmosKeyValueService.cs` has two more `ORDER BY` queries with `MaxItemCount = CosmosConstants.MaxItemCountPerPage` (around L1044 and L1054, plus `ORDER BY c.Version` at L297). If a vNext test pages any of them past 1,000 items, it'll fail the same way. Today none seems to, since 777 of 777 passed, but the trait reason should cover them by name so the next failure isn't diagnosed a third time.

## Nits

- The new comment in `Listing_Pages` starts in lower case (`// the vNext emulator ignores…`), unlike the surrounding comments, and it drops the pinned image tag (`vnext-EN20261019`) that the base comment kept. The tag is what tells a future reader when to re-check.
- `IsLikeTheService` has a comment saying "Request charges, indexing policies and container settings behave as in Azure". Add paging there too, so the property and the trait comment list the same things.

## Good

- The diagnosis is careful and reproducible: a throwaway probe with a table of ordered vs. unordered queries, checked with the hierarchical key and with a plain `/PartitionKey` container. That rules out the shared container as the cause.
- The test and its assertions are unchanged. It's moved to the classic job rather than weakened, which is the right call for an emulator gap.
- The verification covers both CI job commands and the `Access.Certificates` integration suite that the failed run skipped.
