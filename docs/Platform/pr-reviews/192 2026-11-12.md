## Important

- **Set up the environment before you merge, and delete `ui-admin` only after a green deploy.** The deploy job (`.github/workflows/ui-admin.yml` L127) runs on the first push to `main` that touches the paths, and this PR's own merge is one. If `prod.42.Platform` doesn't exist yet, GitHub auto-creates it for the job **with no required reviewer and no branch policy**. The job then fails in "Environment configuration" (no `VITE_API_BASE_URL`), so it fails closed, but an unprotected production environment is left behind until the script runs. Run `Set-GitHubEnvironment.ps1` (runbook §10) first, or confirm in Settings → Environments that it already has the reviewer, the `main` policy, the variables and the secret. Also confirm that the token's Static Web App (the Bicep one, `staticWebAppName`) is the app that should serve the admin domain. If the old `AZURE_STATIC_WEB_APPS_API_TOKEN_UI_ADMIN` pointed at a hand-made SWA, this PR silently moves the target.
- **The protected environment now also holds the Azure identity, so keep `id-token` out of this workflow.** `prod.42.Platform` also carries `AZURE_CLIENT_ID`/`AZURE_TENANT_ID`/`AZURE_SUBSCRIPTION_ID`, and the deployment app has a federated credential for `environment:prod.42.Platform` (`New-DeploymentApplication.ps1` L54). The deploy job runs `npm ci` and two builds (L139–L143), so third-party install scripts execute inside that environment. Today that's safe, because the workflow has `permissions: contents: read` and no `id-token: write`, so it can't mint an OIDC token. Add a short comment at the top-level `permissions` saying that `id-token: write` must never be added here. Optionally, separately from this PR: build `dist/` in a job with no environment, upload it as an artifact, and let the deploy job only download it, write the config and upload. Then no npm code runs with the SWA token or next to the identity.

## Nits

- **The error messages now name variables that the script doesn't read.** `build/environment-config.ts` L72–L73 and L80–L81 say `VITE_API_BASE_URL`, `VITE_SENTRY_DSN`, …, but the script reads `API_BASE_URL`, `SENTRY_DSN`, … (`EnvironmentVariables`, L6–L17). That's also how cookbook §16.3 (manual deploy, ~L551) sets them. Someone deploying by hand who gets `VITE_SENTRY_DSN must be an absolute https URL.` will look for the wrong variable. (The old `UI_ADMIN_*` names had the same mismatch.) Name both, e.g. `SENTRY_DSN (GitHub variable VITE_SENTRY_DSN)`. Or, more simply, have the step and `EnvironmentVariables` use the `VITE_*` names, which would also line up with the local fallback in `app/boot/app-config.ts` L51–L64. The tests only match substrings, so either way is cheap.
- **A stale doc outside the diff:** `src/Platform/Deployment/README.md` L139 still says the script "creates `production`". It creates `prod.42.Platform`. Worth fixing in this PR, since it's the doc the new README table points to.
- **The older specs/reviews** (`docs/Platform/ui.admin/specs/...2026-10-19 Sentry and PostHog...md` L52/L172/L207, the reviews L71/L102, Phase H review L117/L150) still mention `ui-admin`/`UI_ADMIN_*`. They're historical records, so leaving them is fine. Just don't let anyone treat them as setup instructions.
- **Concurrency (existing behavior):** `cancel-in-progress: true` on the group `ui-admin-${{ github.ref }}` also applies to `main`. With a required reviewer, a later push cancels a deploy that's waiting for approval (fine), but it can also cancel an upload that's already running. Consider `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.

## Good

- It fixes a real gap: the job referenced an environment, variables and a secret that no setup script or cookbook step creates. Now there's one source of truth (`Set-GitHubEnvironment.ps1` and cookbook step 15).
- The `VITE_*` names match the local `.env.*` names and the `VITE_*` fallback in `app/boot/app-config.ts`, so the same name means the same setting everywhere.
- The variable updates are idempotent and empty values are skipped (script L51–L56). `VITE_AUTH_LOCAL_STORAGE_SESSION` is lower-cased to `true`/`false` (L124), which matches the `=== 'true'` check in `environment-config.ts`.
- The README table, the error messages and the tests changed together, and the stated validation (`vitest run test/unit/build`, 34 passed) covers every touched assertion.
