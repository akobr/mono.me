# Review of PR #196: [feat(platform): add the demo data set exhibit of Acme Corp and Globex](https://github.com/akobr/mono.me/pull/196)

Reviewer: Harry · Review date: 2026-11-15

The only thing that needs to change is the repo's own checklist for a new built-in set ([data-sets.md → Adding a set](https://github.com/akobr/mono.me/blob/main/docs/Platform/Storyteller/data-sets.md#adding-a-set), step 5). CodeRabbit passed with no actionable comments, but its walkthrough only covers `playground.md`, so it did not really review the data set. There are no other reviews or comments. ## Blocking

1. **There is no shape test or seed test for `exhibit`, and the seed path has never run.** `data-sets.md` → *Adding a set*, step 5, asks for a test of the set's shape in `DbCreator/test/DataSets/BuiltInSetsTests.cs` and a seed into its own organization in `DbCreator/testint/BuiltInSetsTests.cs`. The `core`, `large`, `showcase` and playground sets all have both. This PR adds neither, and the description says a real `seed exhibit` was not run. The only seed-like run used `sform story import` from the old `Playground/demo/` location, through the API instead of `DataSetSeeder` → `IViewImporter`. Today only `EveryBuiltInSet_ReadsWithoutFailures` and the binding parse test cover the set.
   *Fix:* add `Exhibit_IsTheDemoOfAcmeAndGlobex` (unit). It should check the target `fourth-wall/toons-and-tyrants/default`, `IgnoredFiles == 3`, the per-kind counts (30/11/3/30), `ErrorCode == null` everywhere, and the ancestor check that `Showcase_` already does. Also add `Exhibit_SeedsWithoutFailures` (integration), modelled on `Showcase_SeedsWithoutFailures`. Then add `exhibit` to the Tests table in `data-sets.md`.

## Important

2. **The JSON-e templates make every resolved read of a Department, Application and AppUsage volatile, so they lose the cheap 304 path.** `ConfigurationBindingResolver` calls `MarkVolatile("JSON-e can read the clock.")` for every `jsone` envelope it evaluates. `ConfigurationHttp` then tags the response by its body instead of by its inputs. The three templates apply to whole types (`cnt`, `usg`, `exe`), so this affects 21 of the 30 annotations. That includes the reads where the template takes the `else: {}` branch (Globex AppUsages, Acme Departments and Applications). For a demo set this hides one of the platform's showcase features, cheap 304s for bound configurations. *Suggestion:* decide whether that is acceptable, and if so say so in the README's "Things to try". Otherwise, gate per Company with `jlogic` where only values are needed, and keep JSON-e for the one deliberate clock example (`usg.globex.social` `countdown`, `$fromNow`, `configurations/usg.globex.social.conf.json` ≈L35).
3. **Gated templates still add an empty key to the other Company's configurations.** `templates/cnt.template.json` L31, `exe.template.json` L45 and `usg.template.json` L27 all use `"else": {}`. The envelope sits under a fixed key, so for example every Acme Department resolves with `"cypressCreek": {}`, and every Globex AppUsage with `"toonSafety": {}`. That contradicts the PR's "a template serves only Acme or only Globex". *Fix:* if the merge cannot drop the key, say so in the README, or rename the keys to something neutral. If the import accepts a root `$binding` in a template, make the whole template a root envelope whose `then` returns `{ "cypressCreek": … }`.
4. **The bindings inside template `$definition`s are only checked at runtime.** `EverySetOfTheRepository_HasBindingsThatParse` skips `$definition` on purpose. That leaves `@globex.hammock.vendorsUrl` (cnt L23), `@[https://@acme.boomdesk.host/@acme.boomdesk.apiVersion/incidents]` and `@public(acme.safety.hotline)` (exe L41–42), and `@[https://@globex.lair.host/audit/${solution.acronym}]` (usg L20) unchecked. The resolver walks a JSON-e result again, but a failure in an emitted string is reported "at the path of the stored envelope … with a fixed message", which makes it hard to debug. The usg one is the riskiest: JSON-e's `${…}` interpolation runs first, so the final string depends on the acronym value. *Fix:* the unit test from #1 can render each template with the set's annotation values and parse every `@` string the render emits. Otherwise, add a resolved read of one AppUsage per Company to the integration test.
5. **Built-in sets docs.** `docs/Platform/Storyteller/data-sets.md` → *The built-in sets* lists `core`, `large`, `showcase` and the playground, but not `exhibit`. Add a short subsection that links the README and mentions the ignored files and the key/value dependency (the `422` on resolved reads until `sform story kv import`).

## Nits

6. **`project-settings.json` L47: `"dateFormat": "yyyy-mm-dd"`.** In .NET (and in most JS date libraries), `mm` means minutes. The server format of 424-266 doesn't exist yet, so this file sets a precedent. Use `yyyy-MM-dd`, or state which token dialect it uses. The file also uses camelCase keys while `set.json` and `key-values.json` use PascalCase. Worth aligning with whatever 424-266 decides.
7. **`key-values.json` ≈L89 (`globex.lairforce.escrowPin`).** This is the only item without `ContentType`. Confirm that `2s.key-values.v1` makes it optional for `Standard` pairs. Otherwise add `text/plain` for consistency. A committed value for a `Standard` (vault-backed) pair is fine as an obvious joke, but the README could say it must never be used as a pattern for real values.
8. **README: changing it re-reads the seed.** README L15 correctly notes that README and `project-settings.json` are part of the set's hash, so a doc typo fix makes the next seed of a seeded target re-read the set (with `Skip`). That's cheap at this size, but the hash could later exclude `*.md` at the set root. That would be a separate PR.
9. **Small inconsistencies.** The `exe.acme.hr.*` and `exe.acme.crm.tunnel-painting` configurations bind `appVersion` inconsistently: some do and some don't. The `seats` math differs on purpose (`+1`, `+3`, `*2`). That's fine for a demo, but one sentence in the README's "Things to try" would stop readers from treating it as data drift.
10. **The spec still names `Playground/demo/`.** This is acknowledged as historical, but add a one-line "moved to `DbCreator/src/data-sets/exhibit/` (see review 2026-11-15)" note at the top of the spec. Readers land on the spec from the README link first.

## Good

- The set is internally consistent: no orphan configurations, no missing ancestors, and every template field reference resolves against the right Company or Department.
- It covers the binding surface well: `@key`, `@public`, `@(…, public)`, `@secret`, `@[…]`, `@{…}` with nested `@annotation`/`@config`, a jlogic envelope with a bound `$context`, and a JSON-e `$fromNow`. The composition example (`physics.gravityDelayMs` from the Department, read through `@config` on the JobInstance) is a good teaching case.
- Schemas show all three kinds, and they rely on the merged-schema model correctly. For example, `rst.crm` uses `additionalProperties: false` with only `crm`, which works because `rst` provides `solution`, `telemetry` and `features` in `MergedContent`.
- The README's relative link to the spec resolves (7 levels up), and the `set.json` target follows the "a target of its own" rule.
