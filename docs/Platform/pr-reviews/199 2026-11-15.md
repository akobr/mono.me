# Review of PR #199: [fix(platform): refuse WorkOS impersonation tokens and log changed user names (424-262)](https://github.com/akobr/mono.me/pull/199)

Reviewer: Harry · Review date: 2026-11-15

**Verdict: approve-ready.** The refusal is small and fails closed. It checks the payload, not the claim set, which is the right call, and the tests that pin the IdentityModel behaviour are unusually thorough. The user-name check is log-only and costs no extra reads. I found nothing blocking. Below are two operational points worth a decision before an alert is wired to the new Warnings, and a few nits.

**CI at review time (head `b95d88d`):** "Lint, type-check, test, build", "Classic emulator", "vNext emulator" and CodeRabbit were still running. There were no reviews yet and one CodeRabbit comment. The author reports these local results: Access.AuthKit 203, Api.Functions 3093, Backend.Core 1402 and Access.Federation 474, all passing. They also ran a mutation check: with the refusal turned off, 15 AuthKit tests and 3 of the 4 middleware tests fail.

## Why I think it is correct

- **Order of checks** (`AuthKitBearerTokenValidator.cs` L78–109). The order is: signature and lifetime, then `sub` starts with `user_`, then `act`. So an invalid or expired token is never logged as an impersonation. An M2M token with `act` still goes to the machine validator as before. Returning `null` gives a 401 because no machine validator accepts `user_`. The middleware tests confirm this, including with a machine validator that shares the issuer.
- **Payload, not claims** (`AuthKitTokenSource.cs` L75). `TryGetPayloadValue<object>("act")` catches `[]`, `null`, scalars, and a duplicate whose last value is `[]`. The claims-based `UserSubjectTokenRules.HasActor` would miss these. `Source_ActClaims_DoNotShowAnEmptyArray` pins the IdentityModel 8.23 quirk, so a package bump that changes it will show up as a test failure. A token that isn't a `JsonWebToken` is refused (`token is not JsonWebToken || …`), so this fails closed.
- **Exchange parity.** `AuthKitUserSubjectTokenValidator` now uses the same payload check, so the token-exchange path can't be used to get around the bearer refusal.
- **Log hygiene.** `DescribeActor` logs only `act.sub` or a plain-string `act`, never the JSON. Values are cut to 256 characters and control characters are replaced (`Sanitize`, L159). Tests cover the length cut and a `\n` in the value.
- **User name read the same way as registration.** `AccountUserNameCheck.UserNameClaimTypes` is now the single source for `HttpRequestDataExtensions.UniqueNameClaimTypes`. `GetUserName` matches `GetClaim` exactly: the first claim present wins, even if it's blank. The exchange passes the *normalized* claims (`NormalizeUser` maps `email` to `preferred_username`), so both channels compare the same thing.
- **Delegated requests are skipped correctly** (`AccessHttp.cs` L77). The middleware replaces `name`/`preferred_username` with the stored values for a delegated token, so comparing them would be meaningless.

## Important

1. **The Warning repeats forever after a legitimate email change** (`AccountUserNameCheck.cs` L41–93, `AccessHttp.cs` L79). Nothing refreshes `Account.UserName` (that's out of scope). So once a person changes their email, every `GET v1/access/account` call (the UI calls it on every load) and every exchange logs the elevated-account Warning again, indefinitely. An App Insights alert on that message would become noise within weeks and then get muted, which defeats the point. Options:
   - Alert on *distinct* `AccountId` + `TokenUserName` per window, and say so in the runbook.
   - Or log the elevated message once per account and new name per process lifetime, using a small bounded `MemoryCache`. This matches the existing `_exchanges` replay counter pattern.
   - At minimum, add a note in `authentication.md` → "Changed user names" that the only way to acknowledge a legitimate change is to update `Account.UserName` by hand, until the refresh lands.
2. **Blind spot: deployments without a JWT template.** Registration falls back to `IUserProfileResolver` when the token has no user name (`GetIdentityProfileAsync`). In that setup `GetUserName` returns `null` and the check is silently inert, which is exactly where the email-swap path stays open. `authentication.md` does say "a token without a user name gives no evidence", but it doesn't connect that to deployments without a template. I'd say there explicitly that the check depends on the JWT template with `email`, or log a one-time Information line when the claims carry no user name.

## Nits

- **Log volume of the refusal** (`AuthKitBearerTokenValidator.cs` L102). One Warning per request of an impersonated session. That's fine as a signal, but it's per request. Consider `LoggerMessage` source-gen (`[LoggerMessage(EventId = …)]`) for both new Warnings. A stable `EventId` is also a much sturdier alert match than message text, which the PR explicitly relies on ("its own message … so an alert can match it").
- **Unsanitized user names in `AccountUserNameCheck`.** `StoredUserName` and `TokenUserName` go to the log as-is, while `DescribeActor` sanitizes. The values are signed claims and structured logging won't be split by them, but sharing `Sanitize` (moved to a small shared helper) would make the two consistent and cap the length.
- **Exchange check runs before the replay limit** (`UserTokenExchangeService.cs` L139 vs L143). A replayed subject token logs the change again on every refused attempt. This is harmless, but moving it after step 5 logs only exchanges that actually issue a token. Keep it where it is if the intent is evidence of attempts too; either way, a short comment would help.
- **`account.AccessMap ?? new Dictionary<…>()`** (L62) allocates on each mismatch. `?? Enumerable.Empty<KeyValuePair<…>>()` or a pattern match avoids it. This is trivial.
- **`CapturingLogger`** is duplicated in `Access.AuthKit/test` and `Backend.Core/test`. If there's a shared test-utilities project, move it there; if not, leave it.
- **Pre-existing:** `AccessHttp.GetAccount` L72 logs every call at Warning (`"GET api/access/account call with accountId"`). It's unrelated to this PR, but it now sits next to a Warning that is meant to be alertable. Dropping it to Debug would make the new signal easier to find.
- **Constructor change.** `ILogger<AuthKitBearerTokenValidator>` is now a required parameter of both public constructors. DI is unaffected and all in-repo call sites are updated. It's only a source break for out-of-repo callers, which I don't expect exist.

## Tests

The coverage is strong: 13 `act` shapes, near-misses (`ACT`, `"act "`, `may_act`), a JSON-escaped `\u0061ct`, no log for invalid or expired tokens and non-user tokens, and real-middleware 401 tests. One gap: `AccountUserNameCheckTests` should have a case with more than `MaxLoggedAccessPoints` elevated entries (to check the "and N more" text), if it doesn't already. A case where `preferred_username` is blank but `upn` is present would document the "first present wins, even blank" behaviour that intentionally matches registration.

## Good

The review notes and spec are linked, the scope is clearly fenced ("Not in this PR"), and comments explain *why* (the IdentityModel quirk, why there's no log for invalid tokens). The trust-boundary write-up in `decisions.md` plus the runbook and cookbook checks turn a code fix into an operable control.
