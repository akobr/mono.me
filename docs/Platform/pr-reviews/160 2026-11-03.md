## Important

1. **The test resources wait only for the Vite process, not for a ready admin UI or API** (`AppHost.cs` L118 and L125). `ui-admin` has no health check, so `WaitFor` releases as soon as the process is Running, which can be before Vite listens on 5173; and `ui-admin` only references `api-functions` without waiting for it (nor for Cosmos and the key vault behind it). Started right after the AppHost comes up, a run can hit the target check's `ERR_CONNECTION_REFUSED` or fail on API calls. Suggested fix: add `.WithHttpHealthCheck("/")` on `ui-admin` (so `WaitFor` means "serving") and `.WaitFor(apiFunctions)` on both test resources.
2. **The automation-tests doc doesn't mention the Aspire route** (`docs/Platform/UI.Admin.AutomationTests/automation-tests.md`, the `dev` profile lines 33 and 82 say "`npm run dev` or Aspire" only for the UI). This doc is the repo's single source for running the suite; please add a short paragraph on the two dashboard resources, what each one runs, that the Playwright 1.63 browsers must be installed first (`playwright.ps1 install chromium`), and that the pool passwords come from the test project's user secrets. Otherwise the first click on `ui-tests-elementary` on a fresh machine ends in "Executable doesn't exist".

## Nits

3. **`ui-tests-all` runs `DisposableProject` tests against the local environment** (`AppHost.cs`, `ui-tests-all` args). Those create projects that stay in the organization (`DisposableProjectAttribute.cs`), so every run grows the local Cosmos data. If that's not intended, add `--treenode-filter "/**[Category!=DisposableProject]"`, or say in the comment above the resources that it's deliberate.
4. **Starting both resources at once** shares the pool users and the same `bin/.../TestResults` folder. Artifacts are per run id so they won't clash, but two processes drawing from the same pool can sign the same user in twice. A line in the comment ("run one at a time") is enough.
5. **Use `[GeneratedRegex]` for `AuthKitContinue`** (`AuthKitSignIn.cs` L29). The project already uses source-generated regexes (for example `BrowserTimeZone()` in `AnnotationBulkCreateTests.cs`); a `[GeneratedRegex("^Continue( with email)?$")] internal static partial Regex AuthKitContinue();` plus a `using System.Text.RegularExpressions;` replaces the fully qualified type and matches the convention. The class would need to become `partial`.
6. **The hosted-page sign-in in `PlatformTest.ACC.cs` L83 now reaches into `Access.AuthKitSignIn`** for the regex. Fine for now; if a third caller appears, a small `AuthKitLocators` helper would keep the AuthKit page's labels ("Email", "Password", "Sign in", the Continue regex) in one place instead of only one of the four.
7. **The group resource is a placeholder that always reports Running** (`AppHost.cs` L105–112 and L131). That works and is excluded from the manifest, which is right. Consider `KnownResourceStates.NotStarted` or a neutral custom state so the dashboard doesn't show a green "Running" for something that runs nothing.
8. **The weakened ANN-BLK-01 assertion** (`AnnotationBulkCreateTests.cs` L32) is correct, since `Or` with mutually exclusive grid and empty state can't trip strict mode. But on a populated deployed target a grid that fails to render would now pass if the empty state showed instead. If you want to keep the stronger check there, branch on the profile or assert the grid after the bulk create, when the view is known to be non-empty (the later `annotations.Item(key)` check already covers that indirectly, so this is optional).

## Good

- Keeping both test resources `WithExplicitStart()` and under one parent group keeps the dashboard tidy and never runs browsers on AppHost start.
- `UITESTS_PROFILE` plus `--test-parameter` is exactly the layering the settings loader documents, so nothing new is invented in the AppHost.
- The regex is anchored, so it won't accidentally match "Continue with Google" or other social buttons on the same page.
