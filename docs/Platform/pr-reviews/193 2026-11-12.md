## Important

- **The new convention contradicts its own examples, so tighten it before it becomes the rule.** `docs/github/naming-convention.md` L9 defines the dotted path as "its path under `src/` with `/` replaced by `.`", and L20 picks "the narrowest workspace or project". Two of the new names don't follow that:
  - `Platform.Cli.UnitTests` (L33, L46): there is no `src/Platform/Cli.UnitTests`. The CLI's tests live in `src/Platform/Cli/test`, and this workflow also runs the self and coverage checks of `Cli.AutomationTests`. So the name is neither a real path nor the narrowest scope.
  - `Platform.Storyteller.CosmosDb` (L50): there is no `Storyteller/CosmosDb`. The suites are `Backend.CosmosDb/test` and `Access.Certificates/testint`.

  Fix: either rename them to the area plus a suffix (`Platform.Cli-checks`, `Platform.Storyteller-cosmosdb`), or loosen L9 and L33 to say the dotted path may name a *logical* project or test kind, not only a folder. Also, `Platform.Storyteller-conformance` vs. `src/Platform/Storyteller/conformance` (a real folder, so by L20 it would be `Platform.Storyteller.Conformance`) is defensible as area + suffix, because the suite spans several projects. Say that explicitly as the rule for cross-project suites. Otherwise the next workflow author will guess, and renames are expensive (new run history).

## Nits

- **Concurrency groups still use the old names:** `cli-checks-${{ github.ref }}` (`Platform.Cli.UnitTests.yml`), `platform-deployment-checks-…` (`Platform.Deployment.yml`), `ui-admin-…` (`Platform.UI.Admin.yml` L24) and the others. This is harmless, but this PR is the cheapest moment to align them with the file names, because run history restarts anyway. For the reusable ones, keep the "caller's context" reasoning in the comment of `Platform.Storyteller-conformance.yml`.
- **`run-name:` strings keep the old human names:** "CLI automation (…)", "Admin UI automation (…)", "Release the Storyteller configuration action…". That's fine if it's intentional (a readable run title), but say so in `naming-convention.md`, or switch them to e.g. `Platform.Cli.AutomationTests (${{ … }})` so the Actions list stays uniform.
- **Line endings in `Docs.42for.net.yml`:** the file went from CRLF to LF, which is why its diff is a full-file rewrite (similarity 95%) and blame on it is lost. That's fine as a one-off. Consider a `.gitattributes` rule `*.yml text eol=lf` so it doesn't flip back.
- **`Docs.42for.net.yml` doesn't run on this PR.** Its path filters (L8, L14) cover only `docs/42for.net/**`, so the renamed docs workflow isn't exercised until the next docs change. Every other workflow lists its own file in its path filters. Add `.github/workflows/Docs.42for.net.yml` for consistency. Also note that the Azure portal of the SWA `victorious-cliff-019dda503` still records the old workflow path. If the portal's deployment source is ever reconfigured, it may try to recreate or delete `azure-static-web-apps-victorious-cliff-019dda503.yml`.
- **The link text in `src/Platform/GitHubAction/README.md` L188** still reads "Storyteller action release", while the link now points to `Platform.GitHubAction-release.yml`. Use the new workflow name so it matches the Actions list.
- **CLAUDE.md has the same workflows twice:** the CI/CD section still lists every workflow in long form, next to the new link to `docs/github/workflows.md`. Two lists will drift apart. Consider keeping only the link plus the convention summary, since the instruction already says to keep `workflows.md` up to date.
- **`docs/github/workflows.md` L3 says "All push and pull request triggers use path filters".** That's true today. It would read better as a rule ("must use"), if that's the intent.

## Good

- This is a clean, mechanical rename. Every in-repo reference (path filters, `uses:`, the self-grep, READMEs, `testsettings.ci.json`, `write-environment-config.ts`, cookbook, conformance and automation docs) was updated together, and the historical specs were deliberately left alone.
- The environment convention (`<stage>.42.<dotted-path>`) matches what `New-DeploymentApplication.ps1` and `Set-GitHubEnvironment.ps1` already create (`prod.42.Platform`). The doc's notes on renaming environments (recreate secrets and policies, update the federated subject) are accurate and save a painful surprise.
- `workflows.md` is a genuinely useful overview: trigger, purpose and gating for each workflow in one table.
