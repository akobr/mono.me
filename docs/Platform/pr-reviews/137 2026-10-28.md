# Review of PR #137: [Hosting, subscription informer and Aspire packages for .NET (424-91)](https://github.com/akobr/mono.me/pull/137)

Reviewer: Harry · Review date: 2026-10-28

**Verdict: needs changes.** Solid, careful work, but it has one status bug, a token-handling trap and a packaging risk to fix first. It's stacked on #135 (base `feat/424-96`), so #135 has to land first; the diff was reviewed against that base.

## Blocking

1. **A deleted usage reports as Active.** In `StorytellerExecutionContext.cs`, `GetSubscriptionStatus` (about lines 70–94) reads ancestors without deleted ones. A usage deleted after the key was read ends up in neither `Ancestors` nor `Unreadable`, so for an exe or uxe key the method returns Active and a worker keeps running a removed tenant. Read ancestors with `includeDeleted: true`, or return Deleted or Unknown on a 404. Add a test for "usage deleted after the key".

## Important

2. **The continuation token isn't URL-safe.** `ContinuationToken.ToString()` (`ContinuationToken.cs:28`) now uses standard base64 with `+`, `/` and `=`. `RequestProcessModel.cs:16` discards the `TryParse` result, so a client that doesn't URL-encode the token gets page 1 again and pages forever. Use base64url and return 400 on an unparseable or unknown token.
3. **The informer can die permanently.** In `SubscriptionsService.ExecuteAsync` (about lines 269–310), any exception other than a stop ends the loop and nothing restarts it, so a bug in a listener or mapper kills subscriptions for the life of the process. Restart under supervision with jittered backoff, and expose an `IHealthCheck`.
4. **Hosting depends on Configuration's internals.** `Hosting.csproj:29` uses a `ProjectReference`, which packs as a `>=` dependency, so a newer Configuration alone can break Hosting at runtime with MissingMethod or TypeLoad errors. Pin an exact version when packing, or move the shared pieces behind a small public surface.
5. **Watcher channels are unbounded.** `SubscriptionsService.cs:147` uses `Channel.CreateUnbounded`, so a slow `WatchAsync` consumer grows memory on every poll. Bound it, coalesce per key, or drop and resync.
6. **No real CI signal.** CodeRabbit skipped the PR because it isn't against the default branch, and no build or test checks ran. The Cosmos emulator paging tests don't appear to have been run either.
7. **Who-am-I failures aren't backed off.** In `ExecutionContextService`, a failed first read isn't cached, so every `GetAsync` starts a new read. With a wrong key on a hot path like middleware, that's one request per call.

## Nits

- `PollingSubscriptionSource.DiffAsync` creates every task up front. Use `Parallel.ForEachAsync` or a bounded pipeline.
- Document the cost of one conditional GET per subscription per interval.
- The `WaitUntilReadyOnStart` timeout uses the system clock instead of `TimeProvider`.
- The Aspire resource starts in `Running`, so `WaitFor(storyteller)` waits for nothing.
- `WatchExecutionsAsync` swallows poll failures in continuous mode, so "no changes" looks the same as "broken".
- The long prose comments will be costly to keep in sync. Trim them to XML docs on the public API.

## Good

Stale-while-revalidate with numbered reads, bounded read concurrency with timeouts, removals confirmed with a point read, a repeated-token guard and `MaxPages`, no Cosmos error text leaked to clients, and broad tests (218 in Hosting, 164 in Aspire).
