## What changed

`src/Platform/Deployment/modules/mcp.bicep` (lines 191–224): the `probes` array of the `mcp` container is reordered from Startup, Readiness, Liveness to Liveness, Readiness, Startup. The PR says that is the order Azure stores them in. The aim is that what-if of `main.bicep` stops showing two probe "swaps" on `prod-2s-mcp-ca`, and that a run with no real change no longer writes a different template and creates a new revision.

I checked the diff value by value. Every probe keeps exactly the same settings:

| Probe | Port | initialDelay | period | timeout | failureThreshold |
|---|---|---|---|---|---|
| Liveness | tcp 8080 | – | 10 | 3 | 3 |
| Readiness | tcp 8080 | – | 5 | 3 | 3 |
| Startup | tcp 8080 | 1 | 3 | 3 | 10 |

The only real change is the order. The Startup comment ("Up to 30 seconds…", 1 + 10 × 3 s) moved with its probe. The new block comment explains why the order matters.

## Blocking

None.

## Important

None. Runtime behaviour does not change: Container Apps evaluates probes by `type`, not by their position in the array.

## Nits / follow-ups

1. **Confirm that what-if is clean, not just quieter** (`mcp.bicep`:194–224). ARM what-if compares arrays by position. The reorder should remove the "swaps", but Azure can also fill in defaults that the template omits, such as `successThreshold: 1` or `initialDelaySeconds` on Liveness and Readiness. If those still appear as `- successThreshold` lines after this change, the template still differs and a run may still create a revision. Suggested fix: run `az deployment group what-if` against prod after the merge. If defaults still show up, set them explicitly (`successThreshold: 1`, plus whatever `initialDelaySeconds` Azure reports for Liveness and Readiness). Mention the outcome in 424-287.
2. **Order is now a hidden invariant.** The comment states it, which is good. A future edit that adds or reorders a probe would quietly bring the noise back. Optional: add a short note where container-app conventions are documented (for example `docs/Platform/Deployment/runbook-mcp-server.md`), so the API's container app follows the same order if it ever gets probes in Bicep.
3. **Comment wording** (line 192): "In the order Azure stores them (…), so a run that changes nothing writes the same template" reads a little elliptical. Consider: "They are listed in the order Azure stores them (…), so that a run that changes nothing writes the same template…"

## Good

- The change is minimal and stays inside the scope of the issue. The values are untouched, so the risk is very low.
- The comment records *why* the order matters, which a future reader would otherwise not guess.
- The PR description is precise and cites the what-if output that motivated the change.
