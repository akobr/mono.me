# Review of PR #187: [feat(platform): restore a previous version of a configuration, template or schema (424-221)](https://github.com/akobr/mono.me/pull/187)

Reviewer: Harry · Review date: 2026-11-10

**Verdict: approve-ready, with a few important follow-ups.** The restore is built the right way: one server-side operation per document kind, the same ETag-guarded retry loop as the writes, history kept, "unchanged" detected by content equality, and the write helpers (`TryCreateVersionAsync`, `TryWriteNextVersionAsync`, `TryWriteVersionAsync`, `CheckComplianceAsync`) extracted so restore and write cannot drift apart. I found no correctness blocker. The things worth acting on are an inconsistency in how the schema restore re-checks compliance, mixed integer widths on the new public model, and the audit enum change that breaks older NSwag clients.

Scope I read: the PR description, the backend diff in full (`CosmosConfigurationService(.Restore)`, `CosmosConfigurationSchemaService(.Restore)`, `CosmosConfigurationTemplateService`, the mappings and entities), the surrounding write paths and version listings in context, the three HTTP handlers and their access checks compared with the existing writes, the MCP tools, the CLI restore plumbing, and the names of the new backend and HTTP tests. The regenerated SDKs (`ApiSdk.g.cs`, Orval output) and the admin UI I only skimmed. CI at review time: only CodeRabbit was reported, still in progress, so I couldn't confirm a green build.

## Blocking

None.

## Important

1. **The schema restore runs the compliance check on every retry; the write runs it once.** `CosmosConfigurationSchemaService.Restore.cs`, `RestoreAsync` calls `CheckComplianceAsync(...)` inside the `for` loop without a guard. The write path in `CosmosConfigurationSchemaService.cs` (around L474) wraps the same call in `if (!isChecked)`. For a type schema the check scans every stored configuration of the type in the view, so a contended restore can do that up to four times. Either guard it with an `isChecked` flag like the write, or, if re-checking per attempt is intentional (other layers may have changed), say so in a comment and do the same in the write. Pick one behavior for both.

2. **Mixed integer widths on the new public surface.** The route takes `uint version`, `ConfigurationVersion.RestoredFrom` is `uint?`, the entities store `ulong? RestoredFrom` (mapped back with `(uint?)` casts in `SchemaMappings`/`TemplateMappings`/`ConfigurationMappings`), and `VersionRestoreResult.FromVersion`/`Version` are `ulong`. The MCP `revert_schema` takes `int version`. It works today, but the OpenAPI contract now shows `int64` for `FromVersion` and `int32` for `RestoredFrom` describing the same concept. Settle on one width (the existing `ConfigurationVersion.Version` is `uint`, so `uint` everywhere in the public models is the least surprising) before the SDKs are published at `0.10.34`.

3. **Adding `ConfigurationRestored` to `AnnotationAuditAction` breaks older .NET SDK clients.** The PR calls this out (NSwag's `StringEnumConverter` throws on an unknown value), and it isn't just a compatibility footnote: any deployed consumer on SDK 0.10.33 or older that reads an annotation history will start failing once one restore happens. I'd suggest (a) stating it in the SDK changelog or release notes as a breaking read change, and (b) for the future, generating the NSwag client with a tolerant enum converter, or exposing audit actions as strings with known values, so new actions stop being breaking. Not a blocker if all consumers are in this repo and ship together, which seems to be the case.

4. **Missing backend tests for template and schema concurrency.** `CosmosConfigurationRestoreTests` has `Restore_RetriesAConcurrentChange_AndGivesUpAfterThreeMore`, but `CosmosTemplateRestoreTests` and `CosmosSchemaRestoreTests` don't cover the retry path or the `TemplateConcurrencyException`/`SchemaConcurrencyException` throw. The HTTP tests only cover the mapping to 409. Since the schema retry is where item 1 lives, one test there would pin the chosen behavior.

## Nits

- `SchemaTools.RevertSchema` (`Mcp/src/Tools/SchemaTools.cs`): `var (type, annotationKey) = (target.AnnotationType!, target.Key!);` suppresses nullability for values that really are null at the Type or Annotation level. They are only used in the branches where they're set, so it's correct, but reading them inside each switch arm (or using `?? throw`) keeps the analyzer honest.
- `revert_schema` and `revert_configuration` take `int version`; a negative value goes to the API and fails as a route mismatch rather than with a clear message. A small guard, as `VersionRestoreConsole.ValidateVersionToRestore` does for the CLI, would make the MCP error readable.
- `EnsureAnnotationRestorableAsync` and the configuration restore's `AnnotationItemStore.ReadStateAsync` check run once before the loop, so a delete of the annotation that lands between the check and the write isn't seen. The normal writes have the same window, so this is consistent; just worth a comment.
- The `VersionRestoreResult.Restored` and `Unchanged` factories are identical apart from the outcome; a single private constructor helper would do. Purely cosmetic.
- `RestoreConfigurationVersion` in `ConfigurationHttp.cs` doesn't catch `InvalidOperationException` the way the PUT and PATCH handlers do. As far as I can see the restore path never throws it (no patch processing), so this is fine, but a short comment would stop someone from "fixing" the asymmetry later.

## Good

- Validation happens before any write, so a schema rejection can't leave an orphaned history item. That matches the write path's invariant.
- The configuration restore treats an archive at or above the current version as a leftover and answers `VersionNotFound`, exactly as `GetConfigurationVersionsAsync` hides it, so the list and the restore agree on what a "version" is.
- The archived document is read once and the row re-read per attempt. That's correct, since archives are immutable, and it's cheap.
- `RestoredFrom` is carried through `ToHistory` for all three kinds and cleared by any ordinary write, so the history stays truthful.
- The template restore completes a pending invalidation even on the unchanged path, which is a nice touch for crash recovery.
- The access checks mirror the existing writes exactly (annotation-scoped for configuration and annotation/descendant schemas, project-scoped for type schemas and templates, with the same machine scopes).
- Exit code 42 for "nothing changed" reuses the existing `ExitCodes.WARNING_NO_WORK_NEEDED`.
- The deviations from the issue (409 for schema violations, no `If-Match`/412) are documented and consistent with the existing writes.
