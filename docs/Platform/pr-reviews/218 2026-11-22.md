# Review of PR #218: [fix(platform): attribute, block and narrow the MCP clients of the user token exchange (424-302)](https://github.com/akobr/mono.me/pull/218)

Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready once CI is green.** I found nothing blocking. The security design holds up: deny is checked before the account is read, trust is matched exactly while deny ignores case, ReadOnly refuses by HTTP method before any role check, and the default for untrusted clients is fail-safe (`ReadOnly` + `NoSecretReveal`). There are a few important points, mostly about brittle coupling and behaviour changes that should be written down. At review time, "Lint, type-check, test, build", "vNext emulator" and CodeRabbit were still running. Unit tests, the .NET reference builds, the Classic emulator, the TypeScript SDK and the Bicep lint had passed.

Scope: 405 files, +26,784 / −757. About 320 of the files (~23k lines) are the regenerated OpenAPI document and the NSwag/Orval SDKs. I spot-checked those but did not review them line by line. The review covers the hand-written source in Access.Federation, Backend.Core, Api.Functions, Mcp and ui.admin, plus the Bicep files, their tests and the docs.

## Blocking

None.

## Important

1. **The MCP server spots "client blocked" and "no account" by matching the exact human-readable `error_description`.** See `Mcp/src/Authentication/StorytellerTokenExchangeProvider.cs` (`ReadAnswer`, ~l.300–316). `StorytellerSignInRefusedException.ClientBlockedMessage` must equal `UserTokenExchangeResult.ClientBlockedDescription` character for character, across two projects. If anyone edits the wording on the API side, the MCP server quietly falls back to the misleading "check SubjectAudiences" warning.
   *Fix:* return a machine-readable reason, for example a non-standard `reason: "client_blocked" | "no_account"` member next to the existing `restrictions` member, and branch on that. At the very least, add a test that pins the two strings as equal, if none exists yet.

2. **`HasSamePolicy` now compares the client lists, which is a start-time breaking change.** See `Backend.Core/src/Accessing/TokenExchangeOptionsValidator.cs` (~l.253–259). Today two actors can share a `SubjectAudience` while their `AllowedClientIds` differ. After this PR, that configuration stops the API at start. The reason is sound: the client lists now decide the restrictions. Prod has a single actor, so nothing breaks there.
   *Fix:* add a line to `decisions.md` or the release notes, and add a validator test for "same audience, different AllowedClientIds → failure" if it is not covered yet.

3. **`IsRecordableClientId` refuses the exchange outright for some ids that used to work.** See `Backend.Core/src/Accessing/UserSubjectTokenRules.cs` (l.54–62). Any client id with a space, a non-ASCII character or more than 256 characters is now refused (`invalid_grant`), not just left unrecorded. Entra GUIDs, AuthKit `client_01…` ids and CIMD URLs all fit. A Keycloak client id with a space or a non-ASCII character would now be locked out of the exchange.
   *Fix:* if refusing is the intent, say so in `authentication.md` under the Keycloak notes. The alternative is to store a hashed or escaped form for logs and audit and still accept the token. Refusing is the safer default and I'm fine with it, as long as it is documented.

4. **`ToolListFilter` is now always registered, so every `tools/list` triggers a token exchange.** See `Mcp/src/Hosting/McpHostExtensions.cs` (l.52–54) and `Mcp/src/Tools/ToolListFilter.cs`.
   - Before, with `Mcp:SecretTools:Enabled = false`, a `tools/list` cost nothing on the API.
   - Now the first list of a session runs the exchange and can wait up to 5 s on a cold API. The result is cached, and that wait comes out of the person's replay budget for the subject token.
   - This is needed for the ReadOnly hiding, so it is not wrong.
   *Fix (optional):* make `TokenWait` configurable (`Mcp:ToolList:TokenWaitSeconds`), and mention the extra exchange in `runbook-mcp-server.md`, so a slow first `tools/list` is not mistaken for a fault.

## Nits

- **The ReadOnly gate trusts `ReadOnlyHint`.** See `Mcp/src/Tools/ReadOnlyToolSet.cs`. A tool marked `ReadOnly = true` that calls a POST outside `ReadOnlyOperations` passes the MCP call filter and then fails at the API with 403 `ActorReadOnly`. Nothing unsafe happens, because the API is the gate, but the person gets a confusing result. A catalog test that maps each read-only tool to the SDK operations it calls would catch this. That may be too much work, so it is nice-to-have.
- **`GetStatusCode` can log the wrong status.** See `Api.Functions/src/Security/BearerAuthenticationMiddleware.cs` (~l.163–172). It maps an `ObjectResult` with a null `StatusCode` to 200. That is right for `OkObjectResult`-style results. For a `ProblemDetails` value, ASP.NET Core writes the status from `ProblemDetails.Status`, so the request line could say 200 for a 4xx. It only affects logs, but a `ProblemDetails { Status: { } s }` arm would fix it.
- **No warning for trust that can never apply.** See `Access.Federation/src/TokenExchangeActorNotice.cs` (`LogActor`). When `AllowedClientIds` is non-empty, any entry of `TrustedClientIds` that is not also in `AllowedClientIds` is dead config. A start-time warning for it would be cheap and fits the purpose of the notice.
- **Tokens without a client cannot be denied by `DeniedClientIds`.** They get `UntrustedClientRestrictions`, and only a non-empty `AllowedClientIds` refuses them. The spec covers this. One sentence in the runbook's "Cut off one client" section would stop an operator from looking for a way to deny "(none)".
- **Deny and trust lists are read at start.** `DeniedClientIds` and `TrustedClientIds` are read from `IOptions`, so they take effect when the app restarts. On Functions, changing an app setting restarts the app, so the kill switch is effectively immediate after a deployment. Worth stating explicitly in the runbook, which already hints at it.
- **`DelegationLogScope` is opened again in each `catch`.** See `ExceptionHandlingMiddleware`. It is correct and has a good comment. A small helper or one `using` around a local function would cut the repetition.
- **`TryGetSubjectClientId` returns `false` for an empty string claim**, which ends up as a 401. That is the right behaviour. A one-line test for `subject_client_id: ""` would pin it, if it isn't already among the new validation tests.

## Good

- **Deny comes first and leaks nothing.** The deny check runs before the account lookup, and the refusal is a generic `invalid_grant` with a clear description.
- **Case rules are justified.** `IsTrustedClient` matches ordinally, `IsDeniedClient` ignores case, and the comments explain why: a trust list must never widen, a deny list may.
- **Live tokens follow the current settings.** They are judged against the actor's restrictions of now for their client. A token issued before `subject_client_id` existed counts as untrusted, so removing trust or adding a restriction takes effect at once, and it fails safe.
- **New write routes are refused by default.** `ActorRestrictionMiddleware` decides by method and function name, both set by the host and impossible to spoof. The catalog test (`EveryFunction_ThatTakesAChangingMethod_IsRefused_UnlessItOnlyReads`) and the `ReadOnlyOperations` existence test keep it that way. I checked both allow-listed POSTs, `FindDeletedAnnotations` and `ExportKeyValues`, and both only read. All three secret MCP tools only call GET endpoints, so keeping them in `ReadOnlyToolSet` is consistent.
- **Fail-open vs fail-closed is well separated in `ToolListFilter`.** ReadOnly hiding fails open, secrets fail closed, the wait is cut but the shared exchange keeps going, and the call filter plus the API remain the real gate.
- **`Forget` only removes the token that was refused.** It does a compare-and-remove, so a fresh token another call already got stays in the cache. A step-up 401 is excluded, so it does not burn the replay limit.
- **The Bicep fails a deployment instead of breaking the API at start.** Blank client ids fail the deployment, `@allowed` is set on the restriction array, and each list is written only when it has entries. The full `appsettings` replacement also removes stale indices.
- **Thorough tests across every layer**, including Cosmos serialization of `ViaClient` and the manifest key encoding (base64url after `@` keeps the parts apart).

## Notes

- As the PR says, the OpenAPI document and SDKs were generated at version 0.10.58. Merging any of #212–#217 first means exporting the document and regenerating both SDKs again.
- Whether AuthKit puts the CIMD URL in `client_id` is still unverified. With an empty trusted list that fails safe, but it blocks any real use of `TrustedClientIds`. Track it explicitly in 424-302 or a follow-up.
