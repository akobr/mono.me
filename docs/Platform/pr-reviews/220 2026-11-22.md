Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready once CI is green, plus one product point to settle (item 1).** Nothing is blocking. The backend is careful where it matters. Accept and dismiss are ETag-guarded with a bounded retry. An item above the caller's role answers 404. The push is idempotent and can never fail a job. ## Important

1. **The toaster auto-dismisses a shared item and stamps it as the person's own dismissal.** See `ui.admin/src/app/components/transfer/TransferToaster.vue` l.91–100 and `queries/inbox.ts` l.75–90. Item state is shared per view ("open for everybody who sees it"), not tracked per reader. So when the tab that started an export shows its toast, the item becomes **Dismissed by \<person\>** for every other Administrator too, and the `Closed` stamp records a click that never happened. This is Decision 1 in the PR, and it is defensible for a job the person started themselves. But it mixes "I have seen it" with "this is handled for the team", and it will look wrong once 424-8 pushes actions and messages that matter to several people.
   *Fix / discuss:* keep it, but limit it to items whose `CreatedBy` is the current user and only to `Notification`, so the rule can't leak to other kinds later. Say in `inbox.md` that such a dismissal is automatic. Or, if per-reader "seen" state is the long-term model, open a follow-up now rather than baking the shared-dismissal semantics into the UI.

2. **A misconfigured `ViewInbox:RetentionDays` silently disables every failure notification.** See `Backend.Core/src/Notifying/ViewInboxEntryPoint.cs` l.13–17 and `ViewInboxPublisher.cs` l.29–31, l.60. The options are validated lazily on purpose (per the comment). The first push without `ExpiresAt` (every failed export or import, see `ViewTransferNotifications.cs` l.45, l.75) then throws `OptionsValidationException`. `ViewTransferService.NotifyAsync` (l.489–512) catches it and logs a warning, so nothing fails visibly.
   *Fix:* add `.ValidateOnStart()`, so a bad setting fails the deployment rather than quietly dropping notifications. If the host must start anyway, log the push failure at `Error` when it is an `OptionsValidationException`.

3. **Changed cleanup when `FailAsync` itself fails (Decision 6).** See `Backend.Core/src/Transferring/ViewTransferService.cs` l.250–259 and l.442–481. The archive is now deleted only when `FailAsync` returns `true`. `FailAsync` also returns `false` when its own read or replace throws (l.477–481). In that case the job stays `Running`, the queue message completes (the exception was swallowed), and a partial archive of an export now stays in storage until `PurgeExpiredAsync`. Before this PR it was deleted. This is not a data leak, as long as the download route only serves `Succeeded` exports, but it is a regression in cleanup that the PR description doesn't mention.
   *Fix:* make `FailAsync` return a tri-state (`Failed`, `AlreadyEnded`, `Unknown`), and keep deleting on `Unknown`. Or add a test that pins the new behaviour and note it in `export-import.md`.

4. **Idempotency depends on `CreatedAt`, not on the key alone.** See `Backend.Core/src/Notifying/ViewInboxIds.cs` l.22–30 and `ViewInboxPush.cs` l.35–38. The id is `time + sha256(key)`, so two pushes with the same `Key` but different `CreatedAt` create two items. For transfers that's fine, because `CompletedAt` is written once. But the "keyed pushes give one item per event" contract is easy to misuse for the next producer (424-8), for example by passing `now`.
   *Fix:* make the XML doc on `ViewInboxPush.Key` explicit: "the same Key **and** CreatedAt". Consider a guard test in `ViewInboxPublisherTests` showing that a different `CreatedAt` produces a second item, so the behaviour is deliberate and visible.

## Nits

- **`ViewInboxService` takes the handlers at construction, and it's a singleton.** See `ViewInboxService.cs` l.19–37 and `ViewInboxEntryPoint.cs` l.21. A scoped `IViewInboxActionHandler` becomes a captive dependency, and the duplicate-handler exception surfaces on the first request instead of at startup. Document "handlers are singletons". Optionally resolve the service once at startup, or add a registration test for duplicates (the `ViewInboxRegistrationTests` already exist).
- **`AcceptAsync` returns the unsaved item when `SaveJobAsync` loses its replace.** See `ViewInboxService.cs` l.290–322. The caller then gets `Job` set although it is not stored. That's fine as best effort, but the 200 response then differs from the next `GET`. A comment on the route's OpenAPI description, or returning `saved?.Item ?? item`, would make it explicit.
- **`Cut` can split a surrogate pair.** See `ViewInboxPublisher.cs` l.150–153: `text[..(length - 1)]` on a title or an export error that contains emoji or other astral characters can leave a lone high surrogate, which then fails to serialise in some clients. Step back one char when `char.IsHighSurrogate(text[length - 2])`.
- **`state` accepts numeric values.** `KeyValueRequests.ParseEnum` (l.231–238) passes `Enum.TryParse` + `IsDefined`, so `?state=1` means Done. This is harmless and consistent with the other routes. Mention it only if the OpenAPI description should say "names only".
- **The Done tab sorts by creation, not by close time.** See `CosmosViewInboxStore.cs` l.131 (`ORDER BY c.id DESC`). An old item dismissed a minute ago lands deep in Done. That's acceptable for now, but users will probably expect "recently handled first".
- **Load more is reset by the 20 s poll whenever the first page changes.** See `inbox.vue` l.76–85. This is intended and commented, but a new arriving item collapses the extra pages a person had just loaded. Consider keeping `more` when the new first page still contains the old last id.
- **Naming: `canRead = useCan('edit')`** (`inbox.vue` l.38). The gate is Contributor, which is "edit" in `useCan` terms, so `canUseInbox` would read better.
- **`dismissJobItem` only looks at the first 50 open items** (`queries/inbox.ts` l.63–66). That's fine because the job's item is the newest, but pass the job id and filter on the server if an inbox ever routinely holds more than 50 open items.
- **Generated churn.** Every generated TS model changes its version header (≈300 one-line diffs). If the generator can drop the version from per-file headers, future PRs would be much easier to review.

## Good

- **Concurrency done right.** `CloseAsync` (`ViewInboxService.cs` l.218–255) replaces under `IfMatchEtag`, re-reads on a lost replace, turns "already closed" into a clean 409 `InboxItemClosed`, and bounds retries at 3. Accept claims the item *before* running the handler and runs the handler with `CancellationToken.None`, so a disconnected caller can't leave an accepted item without its work. A failing handler re-opens the item, best effort and logged.
- **Authorization is in the right layer.** `GetUserRoleInProjectAsync` checks the minimal role and returns the role, and the service uses that role for filtering (`IsVisible`, `GetVisibleRoles`). An item above the caller's role answers 404, not 403, so its existence doesn't leak. Machines are refused by `EnsureUser`. The keyset token is versioned, validated (`DecodeToken` l.49–79) and never reaches Cosmos unchecked, and ids are regex-checked before a point read.
- **The Cosmos design is solid.** There's one logical partition per view inbox, all queries are parameterised, `TOP @take` + `ORDER BY c.id DESC` does keyset paging on the time-ordered id, and the TTL is "what is left" on every write, so an accept never extends an item's life. The `Project`/`View` predicates and `ViewInboxIsolationTests` cover the dotted-name partition collision (`a.inbox` + `b` vs `a` + `inbox.b`).
- **The push can never hurt a job.** `NotifyAsync` swallows and logs, ignores the invocation token, and is called on every path that observes an end, including redelivery and the poison queue, with the keyed id making repeats free.
- **Admin UI:** a shared query key between the sidebar and the page (no double polling), polling that stops on error, a dot rather than a count so the link text and existing automation stay stable, `aria-describedby` for the mark, a confirmation before Accept, per-row busy state, and `ph-no-capture` on rows that show people.
- **Tests and process:** dedicated unit tests for the ids, the publisher, the service, registration, the HTTP layer and the notifications, plus emulator tests for the store and its isolation. The spec and its three phase reviews were committed alongside, with the decisions and known limits stated plainly in the PR description.
