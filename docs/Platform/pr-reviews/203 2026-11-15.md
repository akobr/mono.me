# Review of PR #203: [feat(platform): require a recent sign-in for secrets, roles and machine credentials (424-264)](https://github.com/akobr/mono.me/pull/203)

Reviewer: Harry · Review date: 2026-11-15

**Verdict: approve-ready. Nothing is blocking, but please fix or ticket the important items below.** The design is sound. The bearer middleware judges `auth_time` once per request and stores the result as `SignInRecency`. Machines are never judged, and an `act` impersonation never counts as recent. Secret rights are withheld, not refused, so public key/values and resolved reads keep working. The RFC 9470 challenge and `Details.MaxAge` in the body suit cross-origin browsers. The ETag letter `u` keeps caches correct after a new sign-in. The PR is large (467 files, about 28k lines added), but about 21k lines are the OpenAPI `0.10.40` snapshot and generated SDK code. The hand-written backend change is small and focused.

**CI at review time (head `cd3aac5`):** .NET reference (Windows and Ubuntu), TypeScript SDK, CLI and Bicep/PSScriptAnalyzer are green. The admin UI lint/test/build job and both emulator jobs were still running. "Build and Deploy Job" failed because the Static Web App already has its maximum number of staging environments. That is an infrastructure quota, not this change: remove an old preview environment and re-run it.

## Blocking

None.

## Important

1. **The fallback for a missing judgement ignores `Auth:StepUp:Enabled`.** In `src/Platform/Storyteller/Api.Functions/src/Security/HttpRequestDataExtensions.cs` around line 222, `GetSignInRecency` returns `Stale(DefaultMaxAge)` in Release whenever the `SignInRecency` item is missing. Users can reach a handler without the bearer middleware storing it: `BearerAuthenticationMiddleware.Invoke` skips when `CachedClaims` is already set (line 42), and `GetClaims` falls back to `request.Identities` (line 89). For those users the step-up applies even when it is turned off (Entra ID, Keycloak, or the `'false'` escape hatch). The window it reports is also the default, not the configured one. *Fix:* in the fallback, resolve `IOptions<StepUpOptions>` and the provider and call `SignInRecency.Evaluate(@this.GetClaims(), …)`, or move the judgement into `GetSignInRecency` with lazy caching so every path agrees. Add a test where a user request has no item and the step-up is disabled.

2. **Restore and purge relabel every `AccessDenied` item as `StepUpRequired`.** `KeyValueRequests.cs` `WithStepUpOutcomes` (around line 56) rewrites any `Forbidden` + `AccessDenied` item whenever the write right was withheld by the step-up. In `CosmosKeyValueService.ToFailure` (line 676), any `AccessDeniedException` thrown while an item is processed becomes `Forbidden` with its own error code, not only the secret checks (lines 1163 and 1187). An item refused for another reason, now or after a future policy check, would tell the user to sign in again, and the second attempt would still fail. *Fix:* have the service mark secret refusals with their own code or flag, for example a `SecretWriteWithheld` reason, and relabel only those. At the least, add a test that pins down that only the secret branches produce `AccessDenied` in restore and purge.

3. **The step-up runs before the authorization a new sign-in cannot fix.** The `EnsureRecentSignIn` doc comment says it is "called after the refusals a new sign-in cannot fix". Several handlers call it before the role check, which lives in the service:
   - `MembersHttp.RemoveMember` (line 116), where `CosmosAccessService.RemoveMemberAsync` decides whether the caller is an administrator,
   - `AccessHttp.PostGrantPermission` and `PostRevokePermission` (around lines 302 and 340),
   - `KeyValuePolicyHttp.AddRecipient` and `UpdateRecipient` (lines 237 and 280), which call it before `GetCallerAsync`.

   A stale non-admin is sent through a full re-sign-in only to get a 403 afterwards. The admin UI's loop guard does not catch this, because the sign-in did move. *Fix:* move the guard after the caller's role is known, for example after `GetCallerAsync` in the recipient handlers. For the access-service calls, either check the role up front in the handler or pass a "needs recent sign-in" predicate into the service so it throws `StepUpRequiredException` after its own checks. If you keep the current order deliberately, correct the comment.

4. **`Enabled: true` under Entra ID quietly locks out every user.** `StepUpOptions.IsEnabledFor` honours an explicit `true` for any provider, but Entra ID access tokens carry no `auth_time`. Every secret operation and role change would then answer 401, and no new sign-in fixes it. `StepUpOptionsValidator` cannot see the provider, so it does not catch this. *Fix:* inject `IOptions<UserAuthenticationOptions>` into the validator and fail `ValidateOnStart`, or at least log a startup warning, when `Enabled == true` and the provider is `AzureAd`.

## Nits

- `KeyValuePolicyHttp.UpdateRecipient` (line 280) is guarded for every update, including a rename or `IsEnabled = false`, which give no access. The comment says only re-enabling matters, so guard only when `update.IsEnabled == true`.
- `Mcp/src/Tools/ApiErrors.cs`: an empty line was added before the first `using` (line 1), and a double blank line before `DefaultMessage` (around line 155). `StepUpRequiredMessage` (line 50) lists secrets, machine credentials and federation rules but not role or member changes, which the API also guards.
- `StepUpRequiredException.Describe` and `Sdk.StepUp.DescribeWindow` both turn a window into words, and the CLI and MCP call the SDK version. One implementation, or a shared test vector, would keep the API's message and the clients' text from drifting apart.
- `ui.admin` `useStepUp.ts` line 68: `Math.max(authTime, returned.returnedAt)` mixes the browser clock with the provider's `auth_time`. It is only a client hint, since the API decides, but on a client clock that runs ahead it can hide a stale sign-in until the API's 401. Prefer `authTime` alone once `signedInSince` holds.
- TypeScript SDK `fetcher.ts` `failOnStepUp`: if `onStepUpRequired` throws, its error replaces the `StorytellerError`. Wrap the call in `try`/`catch` so callers always get the step-up error.
- `BearerAuthenticationMiddleware.JudgeSignIn` (line 312) resolves three services on every user request. It is cheap, but these could be resolved once, since the middleware is a singleton and `IOptions` and `TimeProvider` are singletons too.

## Good

- Secret rights are withheld rather than every key/value route being gated. A public pair or version needs no new sign-in, because `UnderSecretReadRuleAsync` and `UnderSecretWriteRuleAsync` apply the step-up only once the service refuses a secret.
- The precedence is clear and tested: mTLS for machines, the actor's `NoSecretReveal` before the step-up for users, and one `ReadWithheldReason` instead of two competing headers.
- The challenge header is protected: guards sit outside the `try` blocks whose mapping would drop `WWW-Authenticate`, and each place says so in a comment.
- `StorytellerTokenValidator` copies `auth_time` only as a non-negative integer, so the MCP token exchange keeps the original sign-in time and does not reset it.
- The configuration is strict: a whole-seconds check, bounds from 1 minute to 24 hours, and an error message that explains the "600 is 600 days" trap. Bicep emits the settings only when they are set.
- Test coverage is strong: `StepUpAuthenticationTests` (338 lines), `StepUpOptionsTests`, `SecretRightsTests`, MCP `StepUpToolTests`, the CLI `StepUpTests`, and Playwright for the UI flow. The rollout notes are honest: deploy the admin UI first, expect conflicts with `fix/424-262`, and turn on MFA in WorkOS.
