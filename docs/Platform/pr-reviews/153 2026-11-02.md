# Review of PR #153: [chore(platform): user pool and local default target for the UI automation tests](https://github.com/akobr/mono.me/pull/153)

Reviewer: Harry · Review date: 2026-11-02

**Verdict: needs changes.** The PR is small (one file, +14/−5), but both changes interact badly with how the settings layers merge. .NET configuration merges arrays index by index rather than replacing them, and the validator requires a password for every pool entry under AuthKit. As a result, the live CI workflow can no longer configure a valid pool, and a plain local run fails instead of skipping.

**CI at review time:** only CodeRabbit was reported, and it was still running. No workflow runs the suite on pull requests. I reviewed the diff against the settings loader, validator, user pool, workflow and docs, but did not run it.

## Blocking

1. **The live CI run fails validation because slots 6 and 7 have no password.** `testsettings.json` L42–51 now commits 8 pool users. `.github/workflows/ui-admin-automation.yml` L271–289 only fills slots `0…5` (`UITESTS_Users__Pool__<n>__Email/Password/Roles`). The `ConfigurationBuilder` in `UiAutomationSettingsLoader` (L43–55) merges `Users:Pool` by index, so CI gets its six users in slots 0–5 plus the committed `ui-test-reader-1/2` in slots 6–7 with no password. `SettingsValidator` (L210–212) then reports `Users:Pool:6:Password is required by the sign-in flow AuthKit` and the same for slot 7, and the whole run errors. This also happens when the CI variables point at exactly these eight users, because the workflow has no seventh or eighth slot.
   *Fix:* pick one source of truth. Either extend the workflow to 8 slots (secrets `UITESTS_USER_6/7_PASSWORD`, plus the vars and the `for index in …` loop), or keep `Pool: []` in the base file and put the eight users in a profile such as `testsettings.authkit-automation.json` that CI and local runs opt into. With the first option, the workflow's e-mail and role vars become redundant for these users and could be dropped. Either way, update the docs table (`automation-tests.md` L217, "n = 0…5").

2. **A plain `dotnet run` now fails instead of skipping.** `BaseUrl` now defaults to `http://localhost:5173` (L6), so `IsConfigured` is true, full validation runs, and with no user secrets all 8 pool entries fail the password check. This breaks the documented zero-config behaviour: `automation-tests.md` L28 says "Target:BaseUrl empty, the committed default … every test is skipped … exits 0". The README (L11) has `# skipped without Target:BaseUrl`, and the troubleshooting row at L261 says the same. The PR description says "a run without a target still skips all tests". That's only true when someone explicitly sets `BaseUrl` to empty, which no one does by default now.
   *Fix:* keep `BaseUrl: ""` in the base file and move the localhost default into a `local`/`dev` profile (`UITESTS_PROFILE=dev`). The mock profile already works this way for `:5174`. If you prefer the new default, update L28, L43 ("empty"), README L11 and L261, and say in the PR that a fresh clone now needs the passwords or an explicit empty `BaseUrl`.

## Important

3. **The mock profile's pool silently grows from 4 to 8.** `testsettings.mock.json` sets 4 placeholder users. Merged by index, slots 0–3 become `mock-user-n` but inherit `DisplayName` "Auto Owner1…Admin2" from the base file, and slots 4–7 are the real `ui-test-contributor/reader` users with the Contributor and Reader roles. Its comment ("Each stands for Ada Lovelace, the Owner…") is no longer true, and a future test that requires a `Reader` would lease a user on mock while Ada (an Owner) is signed in, so it would pass or fail for the wrong reason. This affects the `use_mock_ui` CI path too. *Fix:* this goes away with the profile approach in point 1. Otherwise, document the merge rule and give the mock file 8 entries, or add a loader option that replaces arrays.

4. **CI slots inherit the committed display names and roles.** When `UITESTS_USER_n_ROLES` is empty, slot `n` keeps the committed role (for example slot 2 stays `Administrator` whatever the CI user really is). A CI user with fewer roles than the base entry would also keep the extra ones. `PlatformTargetCheck` (L111) reports these roles in its "no access" message, so a mismatch makes the diagnosis misleading. *Fix:* same as point 1, so CI and the base file don't share indices.

## Nits

5. The comment at L40–41 says the roles are "in the target's organization and project". It's worth adding that the passwords are indexed by position, so reordering the list moves every user's secret onto another account.
6. Publishing the test accounts' e-mails in a public repo is acceptable since they aren't secrets. Still, it gives anyone an easy target for lockout attempts on AuthKit. Consider rate-limit and lockout settings, or keep the e-mails in the CI vars and local files as before.
7. The new comment at L4 is clearer than the old one, but it should say what happens when the dev server isn't running: the navigation timeout, not a skip.

## Good

- Moving the pool's shape (e-mail, display name, roles) into the repo while keeping secrets out is the right direction, and two users per role leaves room for the parallelism checks (`MaxParallelTests × 2 ≤ pool`).
- The password-key hint in the comment (`Users:Pool:<n>:Password` / `UITESTS_Users__Pool__<n>__Password`) matches the validator's error text.
