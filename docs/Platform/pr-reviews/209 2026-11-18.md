# Review of PR #209: [🔒️ feat(platform): accept only the 2S AuthKit audiences in the API (424-239)](https://github.com/akobr/mono.me/pull/209)

Reviewer: Harry · Review date: 2026-11-18

**Verdict: approve-ready.** The change is small and well contained. `AuthKitOptions.GetAudiences()` is now the single rule. The list takes precedence over the single `Audience`, and blanks are filtered, trimmed and de-duplicated. `AuthKitTokenSource` takes a collection that maps empty to null ("aud not checked"). The machine validator and the exchange's additional issuers keep their behavior exactly. `prod.bicepparam` sets no list, so production behavior doesn't change with this merge. I found nothing blocking. Two design points are worth deciding before the production release that fills the list.

**CI at head `1176789`:** *vNext emulator*, *Classic emulator*, *Bicep build and lint, PSScriptAnalyzer* and *CodeRabbit* were all still running when I reviewed. There are no human reviews or comments yet.

## Blocking

None.

## Important

1. **Nothing enforces that the shared template `aud` leaves the list.** The whole protection rests on `Audiences` not containing an audience that every WorkOS application gets. The runbook's production order adds the new audience *next to* the old one (`https://2s.42for.net`) and drops the old one later. If that last step is forgotten, every other application's token passes again, and nothing reports it. `AuthKitOptions.Audience` stays configured for a rollback and is by definition the template's shared value. So a cheap guard exists: when `GetAudiences()` comes from the list and still contains `Audience` (compared like the handler, ordinal and without a trailing `/`), log a startup **warning** in `AuthKitBearerTokenValidator`'s constructor (`Access.AuthKit/src/AuthKitBearerTokenValidator.cs` ~L53). It should be a warning, not a failure, because the transition step needs that state for a while. Better still, add a health or telemetry signal so it shows up in Sentry. Please also add a test for it.
2. **The `client_id` allow-list as defense in depth.** The PR says this is conditional on the staging findings. Still, the PR's own key finding (one issuer, one key pair and one template for all applications in the environment) means the audience is now the *only* separator. A WorkOS-side template edit that reintroduces a shared `aud` can't be seen from the API. The token already carries `client_id` (the new tests sign it). Checking it against an allowed set of 2S client ids, defaulting to the list when it's configured, would be a few lines in `AuthKitBearerTokenValidator`. It would make the staging outcome matter less. I'd make it part of the production release rather than optional. *(Needs discussion, not a blocker for this PR.)*

## Nits

1. `Backend.Core/src/Accessing/AuthKitOptions.cs` L62: list entries are trimmed, but the single `Audience` is returned "as configured", untrimmed. That keeps the earlier behavior, but the rule is inconsistent: a stray space in `Auth__AuthKit__Audience` gives a silent 401 for everyone. `TokenExchangeOptionsValidator` already trims it (L340). Suggest `[Audience.Trim()]`.
2. `Backend.Core/src/Accessing/TokenExchangeOptionsValidator.cs` L333–342: when the list is empty, `GetAudiences()` already returns `Audience`, so it's added twice. It's harmless because the check uses `Any`, but `.Distinct()` or a `HashSet` would make the intent clearer.
3. `Backend.Core/src/Accessing/UserAuthenticationOptionsValidator.cs` L51: `options.Audiences.Any(...)` assumes a non-null array. The binder keeps the `[]` default, but options built in code (tests, `PostConfigure`) can set `null`. `options.Audiences is { Length: > 0 } list && list.Any(...)`, or `?? []` in `GetAudiences()` (L51), costs nothing.
4. `Deployment/modules/functions.bicep` L139–143: a blank or whitespace item in `authKitAudiences` deploys fine and then fails at start in `UserAuthenticationOptionsValidator`, which takes the Function app down until the next deploy. Fail-fast is the right policy at runtime. Catching it at deploy time would be cheaper, for example with a check in the deployment script or a `build-params` lint next to the existing Bicep job.
5. `Api.Functions/test/AuthKitAudienceAuthenticationTests.cs`: `KeySet()` is built twice per context (L~122–123). One instance shared by both stubs reads more simply. It's purely cosmetic.

## Good

- A clear precedence rule in one place (`GetAudiences`), used by both the bearer check and the exchange's collision check, so the two can't drift apart.
- `AuthKitTokenSource` normalizes an empty collection to `null`, so a configured `[]` can't turn into "`ValidateAudience = true` with no valid audiences" (which would reject everything).
- The exchange validator still reserves the single `Audience` while the list overrides it. That's correct, because it's the template audience every application receives.
- The validator now reports all AuthKit failures together, and a blank `Audiences__n` fails instead of being silently dropped.
- The Bicep `appsettings` resource is a full replace. Shrinking the list on a rollback therefore removes the stale `Auth__AuthKit__Audiences__<n>` keys, and keeping `Auth__AuthKit__Audience` makes rolling back to an older build safe.
- Strong tests: real signed tokens through the real middleware with a shared issuer and keys, the "shared template `aud`" case, the "not taken as a machine" assertion, Release-path validation, binding from `:0`/`:1`, and a mutation check of the precedence rule.
- The no-`401`-window production order in the runbook is well thought out.
