# Review of PR #217: [feat(platform): write annotation changes from the admin UI as a PATCH of only the change (424-225)](https://github.com/akobr/mono.me/pull/217)

Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready once CI is green.** Nothing blocks. There is one important point about the mock (the `withDb` race is fixed only for `PATCH`) and a few nits. At review time, "Lint, type-check, test, build" and CodeRabbit were still running, and "Build and Deploy Job" had passed.

The PR changes only the admin UI (Vue/TS), its MSW mock and the docs. I checked the client against the server contract in `docs/Platform/Storyteller/annotation-lifecycle.md` ("Merge writes (PATCH)"). The editable document always has every member present, with `Labels` as `[]` and `Values` as `{}` when they are empty. That makes `replace /Title` on an unset member valid, and it makes `add /Labels/-` and the `test /Labels` guard work on an annotation with no labels. The client's assumptions hold.

## Blocking

None.

## Important

1. **The mock still races for every write handler except `PATCH`.** See `src/Platform/ui.admin/src/app/mock/annotation-handlers.ts`.
   - The new `withDb` comment says correctly that a handler that awaits after `loadDb()` can overwrite a concurrent write. Only the new `PATCH` handler (l.817–818) reads its body before `withDb`.
   - These handlers still `await request.json()` or `request.text()` inside `withDb`: `POST …/annotations/:key` (l.795/801), the bulk `POST …/annotations` (l.561/567), `…/annotations/simple` (l.589/598), `deleted/lookup` (l.697/702) and `deleted/restore` (l.713/718).
   - The bulk delete and restore paths run four requests at a time (`deleteConcurrency`). A create or restore that overlaps a bulk patch can still lose a write in the mock, which makes e2e runs flaky.
   - **Fix:** apply the same pattern everywhere. Either read the body first and call `withDb(...)(info)`, or give `withDb` a variant that parses the body before `loadDb()`. Then no handler awaits between load and save.

2. **Two concurrent editors can still lose a change to the same member, with no warning.** The form sends `PATCH` without `If-Match`. The PR acknowledges this ("the browser can't read `ETag` across origins"), so it is a follow-up, not a blocker.
   - **Fix:** expose `ETag` in the API's CORS policy (`Access-Control-Expose-Headers: ETag`). The form could then send `If-Match` and reuse the `ConflictDialog` pattern that configurations already have.

3. **"Create new" and the path after ancestors are restored still `POST` without `If-None-Match: *`.** See `AnnotationCreateDialog.vue` l.168.
   - If someone creates the key between the deleted-key lookup and the save, the dialog overwrites it whole, which is the lost-update class this PR removes elsewhere. The docs now state this explicitly.
   - **Fix (follow-up):** send `If-None-Match: *` and map `412` to "the key was created or restored meanwhile".

## Nits

- **`forms/annotation-patch.ts` l.181–188, JSON Patch fallback.** A changed value name is set whole (`add /Values/<name>`), so a concurrent change inside that same value is lost. This only happens when the change sets a JSON `null`. The docs say so, which is fine. A one-line comment at the `add` would help the next reader.
- **`useAnnotationActions.ts` l.187, `patchLabels`.** When the re-read copy needs no change, it goes into the catalog, but `invalidateAnnotation` is not called, so an open detail query can keep its stale labels. Call `invalidateAnnotation(queryClient, target, key)` there too, or return `current` and let the caller handle both cases alike.
- **`useAnnotationActions.ts` `patchMany`.** A key that answers `404` is reported as "not saved", together with real failures. A separate count ("2 were deleted meanwhile") would be clearer to the user, since those rows also disappear from the list.
- **`mock/annotation-patch.ts` l.223.** `applyOperation(result, operation, true, true, true, index)` passes `banPrototypeModifications = true`. A JSON Patch on `/Values/__proto__` therefore throws in the mock, but the .NET API accepts it. The client goes out of its way to support a value named `__proto__` (`setOwn`, and reading `values` instead of Zod's output), so the mock should match. Pass `false`; the document is a fresh `structuredClone`, so it is safe.
- **`AnnotationForm.vue` l.144–147.** Saving diffs the raw form `values` rather than the schema output, which is the right choice for `__proto__`. But it means any future Zod `transform` on a member is silently bypassed. The schema check still runs, and `editableOf` repeats the trimming. Add a short comment on `annotationFormSchema` saying that transforms there do not affect the PATCH body.
- **`mock/annotation-handlers.ts` `updateAnnotation`.** It uses `new Date()` twice, while `storeAnnotation` uses one `now`. Take `now` as a parameter so that `Created` and `Modified` match on the fallback path and in tests.

## Good

- `toAnnotationPatch` is careful and well thought out:
  - it compares dates as instants, as the API does;
  - it diffs `Values` recursively, so a concurrent change of another value name survives;
  - it detects when a merge patch can't express a JSON `null` and falls back to JSON Patch;
  - it uses `add null` + `remove`, so removing a name that was deleted meanwhile doesn't fail;
  - it escapes JSON Pointers per RFC 6901 and handles `__proto__` with `defineProperty`.
- The label actions are correct under concurrency:
  - each patch is guarded by a `test` of the labels it was built from;
  - removals go from the highest index down;
  - a stale catalog copy is guarded with the `test` alone;
  - a `412` gets at most three attempts, each after a re-read with `includeInactive`.
- Bulk runs pin their target view (`catalogHolds`), so switching views mid-run can no longer write into the wrong catalog.
- `reset(..., { force: true })` and `setDocument` fix a real bug: in the JSON/YAML modes, a removed value name used to come back on the next save.
- Restore-and-update now patches only the title, plus the time zone when the record has none. If that patch fails, the user sees an honest "restored, but not updated".
- The mock `PATCH` follows the API's order of checks and error codes closely. Test coverage is strong: 73 new unit tests (patch builder, mock handler, bulk actions, form against the mock, restore) and an e2e flow that checks the request bodies and that a concurrent title change survives.
