## Important

1. **The PR duplicates `be3f0637` and conflicts with the base.** The conflicts are in the test's comment (L160), the `VNext` enum comment (L18–21), the trait comment (L35) and `SkipReasonOnVNext` (L59), in both `Backend.CosmosDb/test/CosmosTestEmulator.cs` and `Access.Certificates/testint/CosmosTestEmulator.cs`. What the PR still adds is its sharper explanation, the two doc lines (`local-development.md`, the probe cookbook) and section 9 of the #182 review findings. I'd close it and port those onto the base, or rebase it onto `be3f0637` so it carries only that delta.
2. **The two branches disagree about the vNext emulator, and a conflict resolution has to pick a side.**
   - Container settings: `221b5de7` on the base says vNext "stores and applies replaced container settings (TTL, indexing policy)". The PR keeps the older "replacing container settings does nothing" and "does not apply container settings" in the skip reason. Taking the PR's side would silently revert `221b5de7`. Someone needs to confirm which is true for `vnext-EN20261019` before resolving.
   - Expiry: the base says vNext "does not expire items in time" and lists "TTL expiry" under the classic trait. The PR's probe shows reads return 404 right at the 3 s TTL, and only the id is freed late (about 0.95 s). The PR's wording is the accurate one and should win. Keep "TTL expiry" in the trait comment either way, since `HistoryVersion_ExpiresAfterTheVersionRetention` still relies on it.
3. **"`SetAsync` is correct as written" is shown on the classic emulator, not on Azure (needs discussion, not this PR).** The create path of `SetAsync` (`Backend.CosmosDb/src/KeyValues/CosmosKeyValueService.cs` around L180–190) treats 409 as "created concurrently" and retries. The jittered `BackOffAsync` (L664, `Random.Shared.Next(10, 40 * attempt)`) gives about 0.6 s in total over `MaxRetries = 8` (L29). Azure removes expired items in a background task that can lag under load. I haven't verified whether Azure answers 409 for an id whose item is expired but not yet purged. If it does, a user recreating a just-expired key would get the same `ConflictException` (surfaced as busy) in production. It's worth a one-off probe against a real account. If it reproduces, give the "read 404, create 409" case its own handling, such as a longer back-off for that case only, rather than reusing the contention retry.

## Nits

- The test comment hard-codes the image tag `vnext-EN20261019`. That's good for traceability, but the workflow and `AppHost` pin the image elsewhere. A pointer to where the tag is pinned would keep the comment from going stale on the next bump.
- The `VNext` comment now packs four limitations into one sentence ("the id of an expired item taken for about a second…"). A short bullet list there would read better and make the next addition a cleaner diff.
- `HistoryVersion_ExpiresAfterTheVersionRetention` still says "the vNext emulator does not expire the version items within a minute". With the probe showing a 3 s expiry for a per-item `ttl`, either that comment is about the container default TTL (say so) or it's stale.

## Good

- A careful root-cause write-up with a reproducible probe on both emulators and both key layouts. It rules out the shared-container change and explains the flakiness precisely: the 2 s poll lands the recreate at the edge of the roughly 1 s window.
- The fix is the right one: no production retry tuning to hide an emulator quirk, and the test keeps running on every PR in the classic job.
- Verification covers both CI filter commands and the `Access.Certificates` integration suite.
