## Important

1. **Add a build-time stop next to the run-time one.** The guard is unverified on the deployed Flex Consumption app (the PR says so). It also depends on which `WEBSITE_*`/`LEGION_*` variables the *worker* process actually inherits there. On a VM, plain Docker or ACI it falls back to the environment name only. A cheap defence in depth is an MSBuild target in `Api.Functions.csproj` that fails `dotnet publish` of a DEV_AUTH build:
   ```xml
   <Target Name="RefuseDevAuthPublish" BeforeTargets="PrepareForPublish"
           Condition="$(DefineConstants.Contains('DEV_AUTH')) and '$(AllowDevAuthPublish)' != 'true'">
     <Error Text="DEV_AUTH: a Debug build of the Storyteller API must not be published. Use -c Release." />
   </Target>
   ```
   This also covers the stale `Dockerfile` (`--build-arg BUILD_CONFIGURATION=Debug`) and any host where the variables are missing. It is independent of the follow-up check on the Function App, which should still happen once (e.g. a one-off Debug zip to a staging slot, expecting the `DEV_AUTH:` line in the host log).

2. **`EntryPoint_OfADebugBuildOutsideDevelopment_RefusesToStart` resolves the environment by hand.** In `DevelopmentAuthenticationGuardTests.cs` (the skip condition), the test guesses the worker's precedence as `ASPNETCORE_ENVIRONMENT ?? AZURE_FUNCTIONS_ENVIRONMENT`. If a developer's shell or IDE sets a variable the worker reads differently, the skip and the real host disagree. For example, `ASPNETCORE_ENVIRONMENT=Production` with `AZURE_FUNCTIONS_ENVIRONMENT=Development`, or a test runner that injects one. Then the entry point actually builds and runs `host.RunAsync()` inside the test process. It throws something other than `DEV_AUTH:`, or worse, waits on the gRPC host. Suggested fix: derive the skip from the same pipeline. Build a throwaway `new HostBuilder().ConfigureFunctionsWebApplication()` whose `ConfigureServices` captures `context.HostingEnvironment.EnvironmentName` and throws a sentinel. Or drop the reflection entry-point call and assert the wiring with a source-level check (Program.cs calls `DevelopmentAuthenticationGuard.Ensure` first in `ConfigureServices`). Running `Program` in-process also calls `ProcessDefaults.Apply()` and mutates `AppContext` for the whole test run. That is harmless today, since the value is the same, but it is a hidden coupling.

3. **The isolation suite proves the API against a model of the store.** `TenantWorld`'s access service is "an exact, case-sensitive key … with no inheritance from the organization". Case variants and dotted values of B are refused *because* the fake treats them as distinct keys. If `CosmosAccessService` ever normalises keys differently (lower-casing, trimming, prefix matching), these 817 cases stay green while production diverges. Tie the fake to the real semantics. Run the same key table (`KeysOfB`/`RoutesOfB`) against the real access service in the Backend.CosmosDb isolation suite, or extract a shared contract test that both the fake and the Cosmos implementation must pass.

4. **The vendored `.nupkg` files: add source mapping and a hash check.** Vendoring is a reasonable answer to the "decision for you" item, and the README documents provenance and SHA-256 well. Two cheap hardening steps:
   - Add `<packageSourceMapping>` to `nuget.config`. Map `Microsoft.Azure.Functions.Worker.Extensions.OpenApi` and `Microsoft.Azure.WebJobs.Extensions.OpenApi.Core` to `Vendored packages` only, and `*` to NuGet.org (and `Local packages` as needed). Then no other feed can satisfy those IDs, and the vendored source cannot accidentally satisfy anything else.
   - Add a step to the new workflow that runs `sha256sum -c` against the README's table, or a small `.packages/SHA256SUMS`. Then a replaced binary fails CI instead of being trusted silently.

## Nits

- **`TenantIsolationHttpTests` control check:** `control.Reached.Count > 0 || control.Status < 500` accepts a 400/404 from A as "past the gate". A harness mis-binding (a wrong route value or body) could make the control "pass" while the B request is refused for the same unrelated reason. Consider requiring `Reached.Count > 0` for the `Api` gate, with an explicit allow-list of functions that legitimately answer on their own.
- **`TenantPipeline.InvokeAsync`** uses only `trigger.Methods![0]`. That is fine as long as every function has one verb. A guard assertion in `TenantRoutesTests` (`Methods.Length == 1`) would make that assumption explicit.
- **`TripwireServiceProvider.IsService`** calls `GetService`, which can construct platform classes via `ActivatorUtilities` just to answer "is it a service". Answering structurally avoids the side effect (interface, known types, `_42.` concrete class).
- **`IOptions<T>` in the tripwire provider** uses `Activator.CreateInstance(T)`, which throws for options types without a parameterless constructor. It fails loudly, so it is fine, but the message will be a reflection error. Wrap it with the function name.
- **`BearerValidationMode.DecodeWithoutValidation`** is still a process-wide static guarded by `[Collection]`. The new 800+-case suite now serialises with the other bearer tests (run time), and any class outside the collection that reads the flag in Debug can still race. As a follow-up, make it `AsyncLocal`-scoped like `UserRoleChecks.Enforce()`.
- **`KUBERNETES_SERVICE_HOST`** also refuses local Kubernetes dev (kind, Docker Desktop k8s). That is intended, but worth one line in `development.md`'s troubleshooting row next to the env-name advice.
- **Workflow `paths`** are duplicated between `pull_request` and `push`. YAML anchors aren't supported by Actions, so it is acceptable. Just keep the two lists in sync, or note it in the header comment.

## Good

- The guard's message never echoes a variable's value, starts with a searchable `DEV_AUTH:` prefix, and tells the operator what to do. It is tested for exactly that.
- The decision function takes the build as a parameter, so both branches are covered in both CI legs. The `fail-fast: false` matrix makes the Release leg (the one that matters) report independently.
- The tripwire design (`DispatchProxy` + `AsyncLocal` recorder) detects any service reached *before* the gate, without per-handler mocks. A new constructor dependency needs no harness change. The mutation results quoted in the PR (248 / 273 / 6 failing cases) show the suite actually bites.
- `TenantRoutesTests` makes classification of every new HTTP function mandatory. That is the right long-term guard for a single shared container.
- Docs are updated consistently (cookbook, runbook, development troubleshooting, Deployment README), and the scope cuts (424-241, the deployed-app check, `testint`/`Dockerfile`) are stated explicitly.
