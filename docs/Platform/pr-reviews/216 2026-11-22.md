# Review of PR #216: [feat(platform): read-only Modeling for Readers in the admin UI (424-272)](https://github.com/akobr/mono.me/pull/216)

Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready once the Playwright run is green. Nothing blocks, there is one test-coverage point worth a follow-up, and the rest are nits.** This PR changes only the admin UI (plus docs and UI automation tests). The question that matters for a Reader feature is whether the server enforces read-only, and it does. I checked every endpoint the Modeling tabs call, at the PR head and independent of the UI:

- `ConfigurationSchemaHttp` (`Set*`/`Delete*` for the type, annotation and descendant-type schemas), `ConfigurationSchemaHttp.Restore` (the three `Restore*SchemaVersion`), `TemplateHttp` (`SetTemplate`, `PatchTemplate`, `DeleteTemplate`, `RestoreTemplateVersion`) and `AnnotationsHttp.Deleted.RestoreAnnotations` all require `AccountRole.Contributor`.
- `AnnotationsHttp.Deleted.PurgeAnnotation` requires `Administrator` through `CheckUserAccessToProjectAsync`, so it is user-only.
- The reads (lists, documents, versions, diffs, deleted, history, combined schema) require `Reader`.

The UI's `canEdit` gates are therefore cosmetic, as they should be. A Reader who crafts a request still gets a 403. Non-members never reach Modeling either: `router/guards/context.ts` redirects when `roleRank(accessMap["{org}.{project}"])` is 0, so dropping the page-level lock in `modeling.vue` does not open anything to the `None` role.

**CI at review time (`524af137`):** "Lint, type-check, test, build" and "Build and Deploy Job" were green, while "Playwright (mocked API)" and CodeRabbit were still running. The PR had no comments or reviews yet. I read the changed files at the head together with `SchemaDetail.vue`, `TemplateDetail.vue`, `modeling/deleted.vue`, `modeling/schemas.vue`, `modeling/compare.vue`, `VersionsView.vue`, `VersionTimeline.vue`, `AnnotationHistory.vue`, `DeletedAnnotationBanner.vue`, `AuditActorLink.vue`, `DocumentEditor.vue`, `useRole.ts`, `utils/navigation.ts`, `utils/modeling.ts` and the Storyteller HTTP functions listed above.

## Important

1. **The live-target Reader test (MOD-TAB-03) can pass without checking anything read-only.** In `UI.Admin.AutomationTests/src/Tests/Modeling/ModelingTabsTests.cs` (`Modeling_Reader_BrowsesReadOnly`), the template check branches on `templates.NoTemplate.IsVisibleAsync()`, and the Deleted row check branches on `deleted.NothingDeleted.IsVisibleAsync()`. Both branches are deterministic, because `OpenAsync` and `WaitForListAsync` wait for a final state, so the test is not flaky. On a deployed Reader project without an `exe` template and without deletions, though, the only read-only assertions left are "no New schema" and "no Create template". The test also never opens a schema detail, so the new **Read-only** badge, the missing footer and the "No schema" empty state of `SchemaDetail.vue` are covered only by Vitest and the mocked Playwright suite, never against a real API.
   *Suggested fix:* open a type schema in MOD-TAB-03 (one that exists on every target, or accept either state as the template branch does) and assert `Read-only`, the absence of Save/Revert/Delete and a non-editable document. Also log or `Assert.Inconclusive`-style mark the branches that were skipped, so a run on an empty target is not read as full coverage. Testiny 42 could note which branches need seeded data.

## Nits

- **"Locked" now always means "read-only".** `CommandPalette.vue` L76 lists `item.tabs` for locked entries too, and `navigation.ts` drops `lockedHint`, so `NavigationEntry` can no longer express "visible but closed". That is right today, because the only entry with tabs is Modeling and every `editRole` entry is browsable read-only. If a closed-with-tabs entry ever returns, its tabs would leak into the palette. A one-line invariant on `editRole` in `NavigationEntry` ("the page must be browsable below this role; hide it with `minRole` otherwise") would stop that from regressing silently.
- **Deleted shows names to exhibition visitors.** The **By** column (`AuditActorLink`) and the raw JSON in the detail slideover (`modeling/deleted.vue` L364, `JSON.stringify(detail)`) now reach Readers. The API already returns this to Readers, so nothing new is exposed. Still, `access.md`'s "Names in the versions" bullet could also mention the Deleted list's **By**, since a delete by hand in the exhibition now shows its author to every visitor.
- **`modeling/deleted.vue` L225** gates the bulk toolbar on `canEdit && selected.size > 0`. With the checkboxes hidden (L280, L299), `selected` cannot fill for a Reader, so the extra `canEdit` is defensive only. That is fine, but a short comment such as "a selection kept across a role change" would explain why it is there.
- **`SchemaDetail.vue` L212–217**: the "No schema" description ("…so it validates nothing") is accurate for a type schema. For an annotation-specific or descendant-type target it could say *what* it would apply to, as `api.description` already does above it. This is wording only.
- **Committed review doc** (`docs/Platform/ui.admin/specs/reviews/2026-11-22 Read-only Modeling for Readers.md`, last bullet) records that the review agents "ran out of usage" and the checks were done by hand. That is useful in the PR thread, but it is noise in a permanent spec review. Consider rephrasing it as what was verified and how.
- **PR description:** the one failing Playwright test (`theme.spec.ts` › dark › accent, `rgb(0, 0, 0)` under load) is unrelated, but it is a known flake. A tracking issue would keep it from being re-explained on every PR.

## Good

- **Server-side authorization was already right, and the PR's docs say so accurately.** `access.md` now states that the UI's create/edit/delete/restore need `Contributor` "as in the API" and **Delete permanently** needs `Administrator`. That matches the attributes in the code.
- **Every write path a Reader can reach is gated:**
  - Schema and template footers and `⌘S`: `canEdit && canSave` and `canEdit && dirty`.
  - The editors: `DocumentEditor :readonly="!canEdit"`.
  - **New schema**: `schemas.vue` L76.
  - **Create template** in the template's empty state.
  - Version restore: `VersionsView.restorable` requires `canEdit`.
  - The deleted banner's Restore: `DeletedAnnotationBanner` `#actions` under `canEdit`.
  - The row menu (`deleted.vue` L172–200): only **Show details** below Contributor, **Delete permanently** only under `canPurge`.
- **Compare views is read-only by construction.** It only calls `getConfiguration`/`getConfigurationViewDiff` and renders a `DiffEditor`, so opening it to Readers (and the **Compare** button on `views.vue` L121) is safe.
- **The "No schema" empty state for Readers** (`SchemaDetail.vue` L212) avoids showing a starter document that only a Contributor could save. `useUnsavedChanges(dirty)` cannot trip for a Reader, because the editor is read-only and a format switch does not emit `update:modelValue`.
- **Simplifications.** `modeling.vue` shrinks to a bare `<RouterView />`, and `CombinedSchemaView`/`ConfigurationComposition` drop their `useCan('edit')` link gates. That removes code rather than adding conditions.
- **Thorough tests:**
  - Vitest covers Reader vs Contributor for the schema and template details (including `⌘S` sending nothing), the new `deleted.test.ts` (no selection, menu with only **Show details**, a detail without Restore), Compare, the composition and schema links, and navigation (the Reader's four tabs, no `lockedHint`).
  - The C# page objects follow the repo's patterns: `GeneratedRegex` locators, waits bounded by `ApiTimeoutMs`, and an error state that throws with its text.
- **The docs are thorough and consistent across files:** `admin-ui.md`, `access.md`, `export-import.md`, the README test lists and `test-cases.md`.
