# Review of PR #194: [feat(platform): report the API's errors to Sentry (424-248)](https://github.com/akobr/mono.me/pull/194)

Reviewer: Harry · Review date: 2026-11-12

**Verdict: approve-ready, with two small hardening changes I'd make before the DSN is committed.** The PR adds 2,910 lines and removes 19, across 37 files. The work is careful. Sentry is off without a valid DSN. The privacy settings are applied in `PostConfigure`, after any other configuration. Every invocation gets its own scope. A per-instance throttle limits the volume. A leak test sends secrets through the real SDK and inspects the serialized envelopes. I checked the main SDK assumptions against the Sentry 6.12.1 sources, and they hold:

- `SentryEventHelper.DoBeforeSend` **drops** the event when `BeforeSend` throws. So the "regex timeout never sends an unfiltered event" claim in `SentryScrubber.cs` is correct.
- `Scope.AddBreadcrumb` also drops the breadcrumb when `BeforeBreadcrumb` throws.
- `SentryLogger` puts `{OriginalFormat}` into `SentryMessage.Message`, so the throttle's signature uses the template rather than the formatted text, as intended.

Nothing deploys until `sentryDsn` is set, so the risk of merging is low.

CI: when I reviewed it, the .NET reference builds (ubuntu and windows), the CLI tests, the TypeScript SDK and Bicep lint had passed. The Cosmos emulator jobs (classic and vNext) and CodeRabbit were still running. `mergeable_state` was `unstable`.

## Important

- **The diagnostics middleware can take the API down if it throws.** `SentryScopeMiddleware` (L27–53) runs *before* `ExceptionHandlingMiddleware`. It calls `FunctionTransactionNames.Get` (L31), which builds a `Lazy<FrozenDictionary>` by reflecting over `assembly.GetTypes()` and `RoutePatternFactory.Parse` (`FunctionTransactionNames.cs` L16–17, L56–91). `Lazy<T>` in the default `ExecutionAndPublication` mode **caches the exception**. So one `ReflectionTypeLoadException`, or a route template the parser rejects, would make every later invocation fail with a raw worker error and no 500 body. Today the test over `All` catches this at build time, but the PR's own rule is that an optional diagnostics setting must not stop the API. Fix: in the middleware, wrap the name computation (and the `ConfigureScope`) in `try/catch` and fall back to `context.FunctionDefinition.Name`. Optionally, build the map eagerly in `AddErrorReporting` so a failure turns Sentry off with a warning, like a malformed DSN does.
- **The volume cap is per *process*, not per instance-day, so it isn't a hard ceiling.** `SentryEventThrottle` keeps its state in memory (L19–29). On Flex Consumption, instances are recycled, scaled out and moved. Each new process starts with fresh counters and an empty signature map, so the same error is sent again by every new instance. The "at most 400 a day on 10 instances" math in `error-reporting.md` (L76 of the diff) assumes stable instances. Spike protection helps, but it reacts late. Fix: also set a **rate limit on the `2s-api` client key** in Sentry (Project settings → Client Keys → Rate limit, e.g. 100 per hour). Add that to "Before it reports" and to the runbook's "Adding the API's Sentry project" step. That gives a global cap that no process restart can reset. The in-process throttle then stays as the first line of defence for deduplication.
- **The tests don't go through the real host wiring.** `ErrorReportingHarness` calls `AddErrorReporting` on a bare `ServiceCollection`. `Program.cs` adds two more things it doesn't cover: the condition that registers the middleware (L28–31), and the ordering, where `SentryScopeMiddleware` must come before `ExceptionHandlingMiddleware`. The real worker's logging pipeline is also different, because the Application Insights worker service adds its own filter rules. Add one smoke test that builds the host via `ConfigureFunctionsWebApplication` with the fake DSN. It should assert that `IHub` resolves, that a `SentryLoggerProvider` is in the `ILoggerFactory`, and that an `_42.*` Information entry is not filtered before it reaches Sentry. Without a DSN, it should assert that no Sentry service is registered.

## Nits

- **The comment on timeouts in `ExceptionHandlingMiddleware`** (the new `catch` branch) says "a timeout's cancellation (another token) stays an error". That is true for an app-level CTS such as a Cosmos timeout. For the host's `functionTimeout`, the host sends `InvocationCancel`, which cancels **the same** `FunctionContext.CancellationToken`, so a host timeout ends up as a Warning. That matches `error-reporting.md` ("Sentry doesn't see … timeouts"), but the comment reads as if it were otherwise. Reword it to "a timeout of our own (another token) stays an error; the host's timeout cancels the invocation's token". Also check that `context.CancellationToken` is actually signaled for functions that don't bind a `CancellationToken` parameter (older worker versions only created the CTS when one was bound). Otherwise client disconnects there remain Errors.
- **"Values never leave the API" is best-effort, not a guarantee.** `SentryLogger` adds `exception_message` to breadcrumb data, and the new Warning parse failures (`ConfigurationHttp`, `TemplateHttp`, `ConfigurationSchemaHttp`) are `_42.*` entries, so they become breadcrumbs. Third-party parse exceptions can quote input values (JSON Patch libraries typically say "The value '…' is invalid for target location"). `ScrubText` only removes values that *look* secret. Fix: in `ScrubBreadcrumb` (L108–119), drop `exception_message` from the data of entries in the client-parse categories, or from all breadcrumbs. Alternatively, soften the wording in the PR and the docs.
- **The entropy rule misses hex secrets.** With `TokenEntropy = 4.2` (`SentryScrubber.cs` L21), a hex string can never pass, because log₂16 = 4. That is intended for GUIDs and SHAs, but it also lets 32- to 64-character hex keys through, e.g. some HMAC or webhook secrets. A 32-character random base64 run also lands below 4.2 now and then. Consider a length-scaled threshold, e.g. `min(4.2, 0.8 * log2(len))`, or an explicit rule for hex runs of 48 or more characters that aren't GUID-shaped.
- **The throttle records an event before it's scrubbed** (`ErrorReportingEntryPoint.cs` L103–114). If `ScrubEvent` throws (a regex timeout), the event is dropped. But its signature's `LastSent` was already updated, so that error stays silent for `RepeatInterval`. Fix: catch the failure in `BeforeSend` and send a minimal event (exception type plus transaction, no texts), or roll back the signature.
- **`GetSignature`** (`SentryEventThrottle.cs` L109–127) uses `GetBaseException().TargetSite`. For async code, that is the state machine's `MoveNext`, whose declaring type is `<Method>d__N`. That's fine for grouping, but the name shifts whenever the compiler renumbers it after an edit, so after a deploy the same error counts as new once. That is acceptable. A short comment would help.
- **`ScrubBreadcrumb`** passes `breadcrumb.Type!` and `ScrubText(...)!`. The comment explains why, but `breadcrumb.Message ?? string.Empty` would avoid the null-forgiving operator.
- **`ErrorReportingWarnings`** exposes `Messages` only for tests. `internal` (with `InternalsVisibleTo`) would keep the class's surface minimal.

## Good

- The privacy-relevant options are set in `PostConfigure`, after the tests' `configure`. They include `SendDefaultPii`, `ServerName`, `DisableSentryHttpMessageHandler`, `CaptureFailedRequests` and no tracing, sessions or logs. The tags are reduced to an allow-list of one, and the contexts to an allow-list.
- Breadcrumbs are kept only inside an invocation (`AsyncLocal` plus `PushScope` and a fresh trace). That avoids cross-tenant breadcrumbs leaking through the root scope, which is the classic failure of Sentry in shared hosts.
- A malformed DSN or volume setting degrades to a warning that names the key, never the value. `IsValidDsn` mirrors `Dsn.Parse`, so the host can't throw during startup.
- The transaction is the route template, normalized from the constraints, so events group by route and the names of organizations and projects stay out of the transaction.
- The deduplication of the rethrown queue exception is tested: the same instance is sent once.
- The 400s from parse failures are now Warnings instead of errors. The leak test with 24 secrets runs through the real SDK and a recording transport. The Bicep change follows the existing `empty(...) ? {} : {...}` pattern.
