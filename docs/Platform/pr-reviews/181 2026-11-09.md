# Review of PR #181: [feat(platform): turn off machine credential kinds per deployment (424-232)](https://github.com/akobr/mono.me/pull/181)

Reviewer: Harry · Review date: 2026-11-09

**Verdict: approve-ready.** The change sits in the one place every consumer already goes through (`MachineAuthenticationPolicies.Resolve` / `Validate`), it's reversible, and startup validation catches the obvious misconfigurations. Nothing blocks it. There is one configuration trap worth fixing before production relies on it, and two behaviours worth a deliberate decision.

**Scope:** one commit (`6ce707a3`), 11 files, +321/−7. It adds the `MachineAuth:DisabledCredentialKinds` setting, filters it in `Resolve`, refuses it in `Validate`, adds `ValidateOptions` plus an `IValidateOptions` validator with `ValidateOnStart`, 12 tests, and docs (spec, spec review, `authentication.md`).

**CI and comments at review time:** on `6ce707a3` the only check was CodeRabbit, still in progress. The single conversation comment is CodeRabbit's summary. There are no review comments.

**My verification (Linux, .NET 10 on the box, PR head):** `Backend.Core.UnitTests` passed 1,367/1,367 and `Access.Certificates.UnitTests` passed 121/121. I also ran a small binder check (see the first Important finding).

## Consumers checked

Every policy consumer resolves through `Resolve`, so the filter reaches all of them:

- `PolicyAwareMachineAccessService.CreateMachineAccessAsync:45`
- `SharedCertificateService.IssueAsync:37`
- `MachineAuthenticationMiddleware:195`, which also covers certificate renewal, because `PostRenewCertificate` needs an authenticated machine
- `MachineCredentialPolicy:26`
- `FederatedTokenExchangeService:86`
- `AccessHttp` GET `:605` and PUT `:652`

`CosmosMachineAuthenticationPolicyStore` caches the *stored* policy and `Resolve` runs per call, so a cached entry can't leak a turned-off kind. `TestCertificateHelper.DefaultOptions` is `=> new()`, so the tests that mutate `DisabledCredentialKinds` don't share state.

## Blocking

None.

## Important

1. **A scalar app setting silently turns nothing off.** The binder only fills an array from indexed children. I checked with `Microsoft.Extensions.Configuration.Binder` 10.0: `MachineAuth__DisabledCredentialKinds=Certificate,CertificateAndApiKey` and even `=Certificate` both bind to `[]`, with no error. In Azure App Settings that is the natural way to write it, and the startup validator can't see the mistake because it only gets the bound options. The spec mentions the `__0` form, but `authentication.md` shows only the JSON array.
   *Fix:* in `AddCertificateMachineAccess` (`Access.Certificates/src/EntryPoint.cs:30`), fail when `section.GetSection("DisabledCredentialKinds").Value` is non-null, meaning a scalar was given. Alternatively, accept a comma-separated scalar with a `PostConfigure`. Also add the `MachineAuth__DisabledCredentialKinds__0=Certificate` form to `authentication.md`, plus a test for the scalar case.

2. **The fallback can widen a project's policy.** In `MachineAuthenticationPolicies.cs:15-18`, a stored policy that enables only turned-off kinds (for example certificate-only) resolves to `DefaultCredentialKind` (`ApiKey`). Contributors of that project can then create API-key machines, which the project's Administrator never allowed. This is documented and tested (`Resolve_APolicyWithOnlyTurnedOffKinds_EnablesTheDeploymentDefault`), and it doesn't matter on a fresh Azure database. If the setting is ever applied to an environment with real projects, though, it quietly weakens the posture those projects chose.
   *Decide deliberately:* keep the fallback (and say in the spec that it's a conscious trade-off), or log a warning when it kicks in. The stricter option is a resolved policy that enables nothing, but that needs `Resolve`'s non-empty contract relaxed and every consumer checked.

3. **"Reversible" holds only until an Administrator saves the policy.** GET returns the effective policy without the turned-off kinds, and PUT refuses them. So any save from the admin UI (GET, edit, PUT) overwrites the stored `Certificate`/`CertificateAndApiKey`, and they won't come back when the setting is emptied. A stored default of `Certificate` is replaced the same way.
   *Fix:* either qualify the sentence in `authentication.md:919` and in the spec ("…until the policy is saved again"), or have PUT carry the stored turned-off kinds over. For example, merge `stored.EnabledCredentialKinds.Where(options.IsTurnedOff)` into the normalized policy before `SetAsync` in `AccessHttp.cs:651`. The second option keeps the promise but makes PUT less literal, so I'd lean toward the doc fix.

4. **Creation blames the project, not the deployment.** Creating a turned-off kind answers "The credential kind Certificate is not enabled in the project org1.proj1." (asserted in `PolicyAwareCredentialKindTests.cs:237`). The PR deliberately relies on the API's `400` message in the admin UI, so this is exactly the text an Administrator will see. They'll look at the project's policy, which may well list the kind as stored, and won't find the cause. Shared certificates have the same problem.
   *Fix:* in `PolicyAwareMachineAccessService.CreateMachineAccessAsync` (around `:48`) and `SharedCertificateService.IssueAsync` (around `:40`), check `_options.Value.IsTurnedOff(kind)` first and throw `MachineAccessNotSupportedException` with "…is turned off in this deployment." The error code and status stay the same; only the message changes.

5. **The sign-in refusal of existing machines isn't tested.** The PR and docs claim it, and the code path is right (`MachineAuthenticationMiddleware.cs:195-197`), but none of the 12 tests exercises it.
   *Fix:* add one middleware test, a `CertificateAndApiKey` machine on a project that enables it, with the kind turned off, expecting `401`. Optionally add a GET `machine-authentication` test showing the filtered kinds.

## Nits

- **Reset still works for a turned-off `CertificateAndApiKey` machine.** `PolicyAwareMachineAccessService.ResetMachineAccessAsync:119-128` resets its API key and hands out a key for a machine that can't sign in. It's harmless and consistent with how reset ignores project-disabled kinds, but the spec says these machines "can't be … used". A turned-off check there would give a clearer `400`.
- **Registration lives in an odd place.** The validator is registered in `Access.Certificates/src/EntryPoint.cs`, while the options type and `FederationOptionsRegistration` (the same `TryAddEnumerable` + `ValidateOnStart` pattern) live in `Backend.Core`. A `MachineAuthenticationOptionsRegistration` next to it would keep both option sets together and let other hosts reuse it.
- **The OpenAPI 400 description is stale.** The `PUT` 400 description (`AccessHttp.cs:615`) no longer lists every reason. It's acknowledged in the spec review, and fine to leave until the next SDK regeneration, but worth a tracking note.
- **A restart is needed to apply a change.** The options are read through `IOptions<>`, not `IOptionsMonitor<>`, so changing the setting needs a restart. Mention it in the `authentication.md` paragraph so nobody expects a live toggle.
- **`Validate` reports only the first turned-off kind.** That matches the "unknown kind" message style, so it's fine. Listing all of them (`string.Join(", ", turnedOff)`) would save a round trip in the admin UI.
- **`IsTurnedOff` scans a 0–2 element array.** That's perfectly fine; no `HashSet` needed.

## Good

- **One choke point.** Filtering in `Resolve` means no consumer had to change, and the consumer list in the spec is accurate.
- **The array default avoids a binder trap.** The `[]` default on an array property (`MachineAuthenticationOptions.cs:15`) sidesteps the configuration binder appending to a non-empty default list, which a `List<>` with defaults would hit.
- **Startup validation is sensible.** It catches an unknown numeric kind and the default kind being turned off. The test goes through the real `AddCertificateMachineAccess` registration rather than calling the validator directly, which proves the wiring.
- **Stored data is untouched,** so rollback is a configuration change, subject to Important #3.
