## Important

1. **A timeout while recording the key can fail a write that already succeeded.** `CosmosKeyValueService.RecordStandardKeyAsync` (~L1564-1578) catches `Exception ... when (exception is not OperationCanceledException)`, but no token is passed down, so any `OperationCanceledException` here is not a caller cancellation. Azure.Core throws `TaskCanceledException` when a Key Vault call exceeds its network timeout, and the Cosmos SDK can surface `CosmosOperationCanceledException` too. In `SetAsync` the call sits after `CreateItemAsync` and `RecordWriteAsync`, inside a `try` that only handles `CosmosException` 409, so the caller gets a 500 for a value that is stored, versioned and audited; a client retry then sees an unchanged value or a version conflict. That contradicts the PR's own promise ("a failed record never fails the write"). Fix: catch every exception here (log it as a warning), or keep the filter only for a real token (`when (!cancellationToken.IsCancellationRequested)`) once a token is threaded through. A unit test with a provider whose `GetKeyInfoAsync` throws `TaskCanceledException` would pin it.

2. **The maintenance's conflict merge can now erase a freshly recorded Standard key.** Pre-existing code, but this PR adds a new writer of `Standard` on the data path of every instance. `CosmosKeyValueMaintenanceService.SaveAsync` (~L330-345) handles `PolicyVersionMismatch` with `latest with { Standard = policy.Standard, Hsm = ..., Byok = ..., Rewrap = ... }`, and `RewrapAsync` (~L263) builds its final save from the cached `GetAsync`. On the timer's instance, a cached copy without `Standard` (for example an HSM or BYOK project that is re-wrapping) conflicts with the policy a write just recorded, and the retry overlays `Standard = null`. It heals at the next hourly check thanks to `standardMissing`, but Settings loses the key and **Rotate now** in the meantime. Fix: in the conflict path only overlay members the caller actually changed (for `RewrapAsync` that is just `Rewrap`), or never overlay a null `Standard`/`Hsm.Key` onto a non-null one.

## Nits

- `IKeyValuePolicyStore.GetCurrentAsync` (`IKeyValuePolicyStore.cs` L105-106) is a default interface method that falls back to `GetAsync`. Any future caching store that forgets to override it silently loses the guarantee the policy endpoints now rely on. Making it abstract (and updating the fakes) is safer, since there is only one real implementation.
- `CosmosKeyValuePolicyStore.GetCurrentAsync` unconditionally overwrites the cache with what it read, so a read that started before a concurrent `SetAsync` on the same instance can put the older copy back for up to 60 s. It self-heals (a stale copy without `Standard` triggers another `GetCurrentAsync` on the next Standard write), so only worth a comment.
- `RestoreAsync` of a deleted Standard key does not record the key, while create/update/protect/import do. For projects whose Standard secrets predate this fix that is one more path that could have healed them; either add it or mention it next to the "Not done" backfill note.
- The first Standard write now pays a Key Vault `GetKeyInfoAsync` plus a Cosmos read and replace on the request path. Fine for a once-per-project event, but a short note in `key-values.md` (or a debug log with the duration) would help if someone later chases first-write latency.
- `policy.Modified` is overwritten with the `System` actor by the record, so Settings no longer shows which Administrator last changed the policy. It is documented as intended; just confirming that is the behaviour you want for the "last modified" line in the UI.
- `ui.admin/src/app/queries/invalidation.ts` (~L137-143): the policy path is built by hand next to `invalidateKeyValuePolicy`, which builds `/v1/${org}/${project}/key-values` separately. A small `policyPath(org, project)` helper shared by both would keep them from drifting. Also, while `Standard` is not allowed at all the policy is invalidated after every write; harmless, but `policy.AllowedProtections.includes('Standard')` in the condition would make the intent exact.
- `KeyValuePolicyTests.ConcurrentFirstStandardSecrets_RecordTheKeyOnce`: with eight writers and three attempts each, the test relies on losers seeing the key on their re-read. That holds, but if the store ever stops removing the cache entry on conflict it would get flaky; asserting no warning was logged would make the test fail loudly instead.

## Good

- The record is cheap once the key is known (it keys off the policy the write already read) and is idempotent across instances.
- `CheckKeysAsync`'s `standardMissing` bypass is narrow (allowed level, configured provider, no key yet) and the test proves it falls back to the interval right after.
- Tests cover create, update, import (including dry run), protect, the eight-writer race, no access point, the stale second instance, and a real Lowkey Vault end-to-end check that the envelope uses the recorded version. The mutation checks in the PR body are a nice touch.
- Living docs, spec and branch review are all updated and consistent with the code.
