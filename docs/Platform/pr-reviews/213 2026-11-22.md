# Review of PR #213: [fix(platform): end an MCP tool call after 200 seconds, before the Container Apps ingress drops it (424-301)](https://github.com/akobr/mono.me/pull/213)

Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready.** The fix is right and small. `StorytellerCallFilter` links a 200 s deadline on the host's `TimeProvider` to the caller's token. It passes the linked token to the exchange and to `next`, and it keeps testing the *caller's* token in the exception filters. So a deadline becomes an unfinished call, and the client's own cancellation stays a cancellation. I checked the arithmetic: a replica start of at most ~31 s (startup probe) plus 200 s is 231 s, below the 240 s idle timeout of the ingress. And 200 s is below the 230 s of the Functions front end. The new `IOException` / `ApiException` → `IOException` mapping closes a real gap for the one-time credentials of `create_machine` / `reset_machine`. Nothing below blocks the merge. The two Important items are design points to decide on.

**CI at head `0365725`:** *Unit tests* and *Bicep build and lint, PSScriptAnalyzer* passed. *Classic emulator*, *vNext emulator* and *CodeRabbit* were still running. *Container image* and *Deploy* were skipped. The only comment so far is CodeRabbit's in-progress placeholder. No human reviews.

## Important

1. **A hung GET can no longer be retried inside a tool call.** See `McpHostExtensions.cs:21` and `:152-153`. `AttemptTimeout` = `TotalRequestTimeout` = `ToolCallTimeout`, and the attempt starts after the exchange. So the tool's deadline always fires before the attempt timeout. A GET that hangs uses the whole budget, and the standard handler's retry (3×, exponential) never runs for a timeout. It only runs for fast 5xx or transport errors. This isn't a regression, because it was the same with 5 minutes. But now that the outer deadline guards the whole call, nothing forces the per-attempt timeout to equal it.
   *Suggestion:* keep `TotalRequestTimeout = ToolCallTimeout`. Give safe methods a shorter attempt (for example 60 s) so that a stalled read gets a second try within the 200 s. Writes keep one long attempt: unsafe methods aren't retried anyway, so their attempt timeout could stay at `ToolCallTimeout`. A per-method attempt timeout needs `options.AttemptTimeout.TimeoutGenerator` keyed on the request method. Otherwise, write down in the comment at `:125-129` that GET retries cover only fast failures. Either way works, but it should be a conscious choice.

2. **The deadline starts at the filter, not when the request arrives.** See `StorytellerCallFilter.cs:61`. The 40 s margin has to cover the start of a replica, the JWT bearer handler's first fetch of OIDC metadata/JWKS on a cold replica, the MCP session setup, and writing the result. The startup probe alone allows ~31 s, which leaves ~9 s for everything before the filter on a worst-case cold start. That margin is probably enough, but it isn't measured.
   *Suggestion:* either anchor the deadline on the request's start, or lower the deadline a little (for example to 180 s) and cite the probe in the constant's comment. To anchor it, capture a `TimeProvider` timestamp in a tiny middleware before authentication, put it in `HttpContext.Items`, and subtract the elapsed time from `ToolCallTimeout`. A follow-up issue is fine. The `HostDefaultsTests` assertion (`≤ 240 − 40`) encodes the assumption but doesn't verify it.

## Nits

- **`IsUnfinishedCall` treats any `IOException` as a transport failure** (`StorytellerCallFilter.cs:151`). The comment says that's safe because "no tool reads a file", but that is an invariant nobody enforces. A future tool that reads a file, or a `FileNotFoundException` from some helper, would quietly become "it may have completed". *Suggestion:* match `HttpIOException`, or an `IOException` whose `InnerException` is a `SocketException`. That is exactly the two shapes `SocketsHttpHandler` produces, and the tests already build both. Apply the same narrowing in `FindBrokenBody` (`:160`).
- **Misclassification near the deadline** (`:101`). A genuine transport failure at ~199.9 s, followed by the deadline firing before the `deadline.IsCancellationRequested` check, is reported as the deadline message. Both messages say "may have completed", so this is harmless. One comment line would save the next reader from wondering about it.
- **The exchange's own timeout ignores `TimeProvider`.** See `StorytellerTokenExchangeProvider.cs:232` (pre-existing): `new CancellationTokenSource(_exchangeTimeout)` runs on the system clock, while the provider already takes `_timeProvider` for its cache. Now that the deadline and the resilience handler run on the host's `TimeProvider`, use `new CancellationTokenSource(_exchangeTimeout, _timeProvider)` for consistency and so the exchange can be tested with `FakeTimeProvider`.
- **Missing test: the caller cancels during a tool call.** The new linked token is where a regression would hide. Add a test where the client cancels during a tool call, assert the result is *not* `ToolCallTimeoutMessage` or `UnfinishedCallMessage`, and assert no "stopped at the deadline" log. A test for a deadline that fires during the exchange (→ `StorytellerSignInUnavailableException`) would also pin the documented behaviour, even though it can't happen while `ExchangeTimeout` is 30 s.
- **The `{Seconds}` log value** (`:104-107`) is a `double` (`200`). It's fine, but `(int)ToolCallTimeout.TotalSeconds` keeps structured logs integer-typed.
- **`ToolCallDeadlineTests`**: `cancelled` is a captured `bool` written by the handler and read after `await`. It's correct thanks to the await's memory barrier, but `TaskCompletionSource<bool>` would match the `arrived` pattern and read more clearly.

## Good

- The linked-token design is minimal and correct: there's one place for the deadline, and the caller-versus-deadline distinction is kept by testing the original token in the `when` filters.
- The tests use `FakeTimeProvider` end to end, and `McpTestHost` swaps the host's `TimeProvider`, which the resilience handler picks up too. The tests are deterministic, with no real waiting. The "a second before the deadline" test and the two-calls-that-each-fit test cover the edges that matter. The hand-run mutation checks in the description are a nice touch.
- `BrokenBodyStream` reproduces the real failure: a 200 status, a partial body, then `HttpIOException` or a reset. It shows that the one-time-credentials path now answers "may have completed" instead of a generic SDK error, and still logs only the exception type, never the body.
- `LostCredentials` is factored into a shared constant. The deadline message tells the assistant what to do: check a write with the matching read, and retry a read with a narrower request.
- The docs (`mcp.md`, the runbook, `decisions.md`, the `mcp.bicep` comment) now correctly describe 240 s as an *idle* timeout and record why premium ingress isn't used. The "Left for later" section is honest about the synchronous body read that the deadline can't stop.
