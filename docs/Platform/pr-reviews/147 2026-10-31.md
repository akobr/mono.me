# Review of PR #147: [🐛 fix(platform): keep the routes of the Functions API apart with route constraints (424-128)](https://github.com/akobr/mono.me/pull/147)

Reviewer: Harry · Review date: 2026-10-31

**Verdict: approve-ready.** The diagnosis is right: the Functions host maps HTTP routes in function-name order into a legacy `RouteCollection` and takes the first match, so `SetAnnotation` (`…/annotations/{key}`) shadowed `SetAnnotationsSimple` (`…/annotations/simple`), `GetAnnotation` shadowed `GetDeletedAnnotations`, and `GetKeyValues` shadowed `GetKeyValueUsage`. Making same-method routes mutually exclusive with inline `regex` constraints (`Api.Functions/src/Definitions.cs`, `Routes.Constraints`) is the correct fix for that host: it doesn't depend on names, keeps the public URLs, the OpenAPI paths and the SDKs unchanged, and is verified both by a model of the dispatcher (`RouteDispatchTests`) and against a real local host (per the PR's self-review). At `320d3502` CI had no reported statuses yet and CodeRabbit was still processing. Locally `Api.Functions` doesn't build on my box because of the unrelated `OpenApiConfigurationOptions.NamingStrategy` override error (same as on PR #146), so I couldn't run the unit tests; the new `testint` project builds cleanly. I rely on CI and the author's reported 2680/2680.

## Important

1. **Check production data for the two reserved names before deploying.** `NameRules` only guards new names (`Backend.CosmosDb/src/Annotating/CosmosViewService.cs:54`, `Accessing/CosmosAccessService.cs:173`), and `usage` became a reserved view name on 2026-10-13, after views could already be created. With this PR, `GET v1/{o}/{p}/usage/key-values` of a legacy view named `usage` returns the project's usage report instead of the view's list (documented in `key-values.md`). Likewise, an organization named `access` created before `NameRules` (2026-10-10) would lose its `views` and `bindings` routes to `Constraints.Organization`. Both are very likely empty sets, but a one-off Cosmos query (views with `name = "usage"`, organizations with `name = "access"`) turns "likely" into "known". If any exist, rename them rather than adding more routing rules.
2. **The descendants values now live in three places.** `Constraints.Descendants` (`Definitions.cs:20`), the `switch` in `GetDescendants` (`V1/AnnotationsHttp.cs:268` and the checks at 215-246), and two hard-coded test lists (`RouteDispatchTests.DescendantsConstraint_TakesTheValuesOfGetDescendants`, `AnnotationsHttpTests.Descendants_ReadsTheValuesOfTheRouteConstraint`). The comments say "keep both lists the same", but nothing enforces it: add a seventh value to the switch and forget the constraint, and the host answers `404` while every test still passes. Suggest one `static readonly string[] DescendantsValues` (or a small `DescendantsKind` map) next to the switch, and a test that every entry is accepted by the constraint and that the constraint's alternation equals `string.Join('|', DescendantsValues)`. The constraint has to stay a `const` string for the attribute, so the test is the binding link.
3. **The behaviour change for clients is a real contract change; record it in the OpenAPI text or the changelog.** `GET/PUT/POST/DELETE …/annotations/{key}` with a dotless key, `…/{key}/bogus`, and `configuration-schema/{key}…` with a dotless key now get the host's bodyless `404` instead of a JSON `400`. The docs cover it (`annotation-lifecycle.md`, `definitions.md`), and the reasoning for not adding a `404` operation response is fair, but SDK users who branch on `400 InvalidKey` (the generated `ApiException<ErrorResponse>`) will now see a plain `ApiException` with `404`. A line in the release notes of the next SDK version is enough.

## Nits

1. **Opt-in integration tests report as passed, not skipped** (`testint/HostRoutingTests.cs:101` and its siblings). It matches `Mcp/testint`, so it's consistent, but a CI summary of "4 passed" is misleading. When the repo moves to xunit v3, `Assert.Skip(...)` (or `Skip.If` from `Xunit.SkippableFact` today) would show the truth.
2. **`HostTestSettings.CreateClient` creates a new `HttpClient` per test** (`HostTestSettings.cs:40`). Harmless for four tests; a shared static client with a timeout (`Timeout = TimeSpan.FromSeconds(30)`) would avoid a hung test against a stuck local host.
3. **The mock's invalid-JSON message** (`ui.admin/src/app/mock/annotation-handlers.ts:574`): a syntactically broken body ends up as `body = undefined` and answers `"… (at $)."`, while the API's `ReadJsonBodyAsync` takes the path from the `JsonException` (`V1/RequestBodyExtensions.cs:55`) and usually omits it or names the real position. Fine for a mock; mention it in the comment so nobody asserts on that text.
4. **`CrosswisePaths` skips multi-part segments and different lengths** (`RouteDispatchTests.cs:215-244`). No route has optional, catch-all or complex segments today, so the pair test is complete for now; a one-line assertion that no route template has optional/catch-all parameters would make that assumption fail loudly if one is added.
5. **Regex constraints are case-insensitive** (`RegexRouteConstraint` uses `IgnoreCase | CultureInvariant`), so `USAGE` and `ACCESS` are excluded too. That's the desired behaviour here; the docs mention it only for `{descendants}`. Optional to say it once in the `Constraints` comment.

## Good

- Root cause is traced to the host's actual code path (`FunctionMetadataManager` ordering, `WebJobsRouteBuilder`, the open host issue #9876) rather than guessed, and the fix is the minimal one that makes order irrelevant.
- The unanchored `\.` key constraint is a good choice: it only separates keys from literals and leaves semantic validation to `AnnotationKey.TryParse`, so dotted-but-invalid keys still get a proper `400 InvalidKey`.
- `RouteDispatchTests` is the standout: it resolves constraints with the real `AddRouting()` resolver (a missing constraint fails), tests exact single matches, every route with samples, and every same-method pair crosswise. It found the 12 extra overlaps (views/bindings vs. access points, schema `type` routes) that the spec had parked, and they were fixed in the same branch.
- Moving the `usage` exclusion from the base `KeyValues` constant to a dedicated `List` route keeps legacy `usage` views working for everything except the list, and the `RouteTableTests` prefix fix (`RouteTableTests.cs:287`) is the right adjustment.
- Every `{key}` function now answers `InvalidKey` consistently, with one theory covering the `{key}` functions.
- `OpenApiExportTests.Document_Paths_HaveNoRouteConstraints` pins that the constraints never leak into the document or the SDKs.
- The Admin UI mock now mirrors the API's `400`s instead of a fake `500`, and the false "literal segments win" comments are gone from code, mock and docs.
