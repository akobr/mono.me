# Review of PR #188: [chore(platform): first production deployment: region, credit period, AuthKit stopgap and ids](https://github.com/akobr/mono.me/pull/188)

Reviewer: Harry · Review date: 2026-11-11

**Verdict: approve-ready after one fix (needs changes, small).** This is mostly infrastructure parameters and docs that are already deployed. The Bicep is clean, and the admin UI opt-in is well fenced: it's off by default, a set hostname wins, and it's tested on both the build side and the boot side. The one real problem is that the GitHub-environment script writes the new switch under a variable name the deploy workflow never reads. The script already did this for the existing `VITE_*` names, so the opt-in will not reach the CI deployment as described. I also have two important points: the stopgap's effect on AuthKit-domain-issued tokens, and stale variables.

What I read: the PR description, the full diff (20 files), and these files in context at the head commit: `ui-admin.yml`, `Set-GitHubEnvironment.ps1`, `modules/functions.bicep`, `main.bicep`, `boot/auth.ts`, `boot/app-config.ts`, `build/environment-config.ts` and its tests, plus `docs/Platform/Storyteller/authentication.md` for the issuer and AuthKit-domain rules. CI at review time: "Bicep build and lint, PSScriptAnalyzer" passed (only two runner deprecation notices: Node 20 actions and the `ubuntu-latest` → Ubuntu 26 move). "Lint, type-check, test, build" for the UI and CodeRabbit were still in progress. The PR had no comments yet.

## Blocking

1. **`Set-GitHubEnvironment.ps1` and `ui-admin.yml` don't share variable names, so `AUTH_LOCAL_STORAGE_SESSION` never reaches the CI build.** The script (L118–124) writes `VITE_AUTH_LOCAL_STORAGE_SESSION`, `VITE_AUTH_API_HOSTNAME`, … into the GitHub environment `production` (the default `-Environment`). The deploy job of `ui-admin.yml` (L127, L149–156) runs in the environment `ui-admin` and reads `vars.UI_ADMIN_AUTH_LOCAL_STORAGE_SESSION`, `vars.UI_ADMIN_AUTH_API_HOSTNAME`, …. The secret names differ too: the script writes `AZURE_STATIC_WEB_APPS_API_TOKEN` and the workflow reads `AZURE_STATIC_WEB_APPS_API_TOKEN_UI_ADMIN`. The mismatch is older than this PR, but this PR builds the production admin UI on that path. As things stand, the first push to `main` after the merge runs `write-environment-config.ts` with no hostname and no opt-in, so it throws, or it deploys whatever was set by hand. **Fix:** make the script write the names the workflow reads (`UI_ADMIN_*` in the `ui-admin` environment, and the `_UI_ADMIN` secret), or change the workflow to match. Then fix the README tables (`ui.admin/README.md` L171+, `Deployment/README.md`) so they name one set of names. If the variables were set by hand for phase 11.3, it's still worth fixing now, before the next run of the script adds a second, unused set.

## Important

2. **Without the custom domain, the API advertises an AuthKit domain whose tokens it rejects.** `authKitDomainSetting` (`functions.bicep` L123) now sets `Auth__AuthKit__AuthKitDomain = https://palatial-omen-84.authkit.app`, while `Auth__AuthKit__Issuer` is `https://api.workos.com/` (L79/L93). `authentication.md` says (around L244–250) that a set `AuthKitDomain` turns on the OpenAPI authorization-code and client-credentials flows at `{AuthKitDomain}/oauth2/...`. It also says that tokens from those endpoints are issued by the AuthKit domain and accepted only when `Issuer`/`JwksUri` point there. So during the stopgap, Swagger UI's "Authorize" (and M2M, once `MachineOrganizationId` is set) gets tokens that come back as `401`. With the custom domain, issuer and domain coincide, which is why this didn't come up before. **Suggested fix:** state the limitation in the decisions section "Without the custom AuthKit domain" and in runbook phase 12. An alternative is to keep `Auth__AuthKit__AuthKitDomain` out while `authKitCustomDomain = false` (only if the admin UI and `sform` don't need it from discovery; check that first). Don't turn on M2M until the custom domain exists.

3. **Stale variables can silently override the stopgap.** `Set-GitHubVariable` skips empty values ("left as it is", L47–53), and `authApiHostname` is now `''` without a custom domain. If an older run of the script, or a manual step, has already set `…AUTH_API_HOSTNAME=auth.42for.net`, it stays. `environmentConfig` then lets the hostname win over the opt-in (`environment-config.ts` L761, by design). The UI would then try to use a domain that doesn't exist, and sign-in breaks. Going back the other way has the same problem: the script can't clear a value. **Suggested fix:** in the script, delete the variable (`gh variable delete … --env …`) when the output is empty, or at least print a warning for this one. Also add a runbook check that the environment has no hostname variable while the stopgap is on.

4. **The `localStorage` refresh token: keep the exposure small while it lasts.** The decision and the docs explain this well and it's a conscious trade-off. Since any XSS now reads a long-lived refresh token, the page should load as little third-party script as possible during the stopgap: Sentry and PostHog are both configured. Please confirm that the CSP `script-src` stays `'self'`-only (no PostHog toolbar or remote loading). I would also add a short "remove the opt-in" item to 424-247 itself, not only to the runbook. Also, `app-config.ts` L60 ORs the build-time `VITE_AUTH_LOCAL_STORAGE_SESSION` with the file. Every other field uses "file ?? env". As written, an env opt-in baked into the bundle can't be turned off by `app-config.json`. Using `file.authLocalStorageSession ?? (env.VITE_AUTH_LOCAL_STORAGE_SESSION === 'true')` makes the file authoritative, which suits "one build serves every environment".

5. **The credit period depends on someone remembering a date.** Going back on 7 December needs a PR and three parameter edits. The `@minValue(0)` guard is good. Two cheap safety nets: add a `// TODO(2026-12-07)` next to each of the three values in `prod.bicepparam`, and lower the budget alert thresholds (or add an actual-cost alert at the old 5 USD) so a forgotten always-ready instance shows up in Cost Management alerts and not only in the bill.

## Nits

- `functions.bicep` L79: with `authKitCustomDomain = true` and an empty `authKitDomain`, the issuer becomes `https://`. A guard (`fail()` or an assertion such as `!authKitCustomDomain || !empty(authKitDomain)`) catches that at what-if time instead of as a `401` storm.
- `main.bicep` L445–447: the outputs `authApiHostname` and `authLocalStorageSession` are derived from the same flag, which is good. Consider also outputting `authKitIssuer`, so phase 12 can compare it with a decoded token's `iss` instead of re-deriving it.
- `staticWebAppLocation` is now set both as the `main.bicep` default and in `prod.bicepparam`. One place is enough, preferably the parameter file, with the default kept neutral. Changing a default to a US region is a bit surprising for a template whose other defaults are European.
- Decision 5: worth saying explicitly that SWA metadata in East US 2 is outside the Sweden data-residency claim (no customer data, but a reviewer will ask).
- `42.mono.slnx`: the empty `<Folder Name="/Libraries/Platform/" />` is something VS writes for nesting, so it's harmless. The new `/Platform/AutomationTests/` folder is a nice tidy-up.
- `auth.test.ts`: the "refuses to start" case duplicates the `sessionStorage` setup that `authKitService` already does. A small `seedAuthConfiguration(appConfig)` helper would remove the copy. Also consider one test for "local host + opt-in + no hostname still uses devMode with no `apiHostname`", to pin that localhost behavior is unchanged.
- The load testing plan is solid. Small points: secret parameters that reference Key Vault need the load-test identity to have Key Vault Secrets User at the secret scope, so plan for two role assignments. Also, the `X-Load-Test` header will only be queryable in Application Insights if the API logs it; today it probably doesn't, so filter by the client IP or user agent instead, or add a telemetry initializer.

## Good

- The always-ready configuration uses the right Flex group name (`http`) and collapses to `[]` at 0, so the what-if diff is minimal when it's switched back.
- `Auth__AuthKit__AuthKitDomain` is now left out when it's empty instead of being written as `https://`. That's a real robustness gain.
- The stopgap has three fences (opt-in flag, hostname wins, CSP narrowed to `api.workos.com`), and both the build and boot paths have tests for it.
- The docs explain why switching later loses no data (`sub` is per environment, not per domain), and the "Adding the custom AuthKit domain" runbook has concrete what-if expectations and checks.
