# Review of PR #144: [🐛 fix(platform): audit secret version reads and diffs as reveals (424-101)](https://github.com/akobr/mono.me/pull/144)

Reviewer: Harry · Review date: 2026-10-31

**Verdict: approve-ready.** The fix closes the gap the ticket describes. A secret version read with `reveal` and every secret version a diff compares now write a `Reveal` event and count one `reveals`, on both the catalog path and the history path. The events carry the stored key, so the exact-match audit query finds them. Nothing is recorded when a read fails or delivers no plaintext. The service change is small and sits on the existing `RecordRevealAsync`, the model, OpenAPI document and SDKs are unchanged, and the tests pin the important edges. CI (`Lint, type-check, test, build` and CodeRabbit) was still running on `75774fe5` when I reviewed.

## Blocking

None.

## Important

1. **The same reveal now gets two different details depending on the route.** The pair read writes `Detail` empty (`CosmosKeyValueService.cs:120`), while `GetVersionAsync` on the current version writes `version {n}` (`:332`). The MCP `reveal_key_value` still sends a current-version reveal through the pair (`SecretTools.cs:41-46`), so the admin UI and MCP describe one action differently. That is harmless for `--operation reveal`, and `key-values.md` documents it, but anyone filtering by `Detail` will be surprised. Once this API is deployed everywhere the MCP server talks to, drop the pair workaround so MCP uses the version route. The PR already lists that as a follow-up, so please open the ticket now so it doesn't get lost.
2. **A diff can leave a half-written audit record.** `GetVersionChangesAsync` (`:368-377`) awaits the two `RecordRevealAsync` calls one after the other, after both sides were already decrypted. If the second audit write fails (a Cosmos 429 or timeout), the caller gets a 500 and no diff, but the first event and both `reveals` increments are already recorded. Failing closed and over-reporting is the right direction for an audit trail, so this isn't blocking. Still, say so in the spec, or write both events in one transactional batch (they share the `{project}.audit` partition) if `IKeyValueAuditLog` can take one.
3. **`reads.api` is still not counted on the version and diff routes.** `GetAsync` counts it (`:116`) and `GetVersionAsync` and `GetVersionChangesAsync` don't, so the `reads` priced item undercounts the versions panel and `sform story kv diff`. It's listed under "Left for later". Fixing it changes billing input, so give it its own ticket rather than folding it into something else.

## Nits

1. **The return type of `GetVersionTextAsync` is hard to read.** `(string Text, string? Key, KeyValueProtection? Protection)?` (`:779`) is a nullable tuple with nullable members, and the call site needs a property pattern to get back what was stored. A small `private sealed record VersionText(string Text, string? Key, KeyValueProtection? Protection)` with a static `Empty` for version 0 would read better, and `from.Protection?.IsSecret() == true` would replace the patterns at `:369` and `:374`.
2. **The diff detail uses the order of the request.** `diff 2..1` and `diff 1..2` are separate details for the same pair of versions. That's fine and arguably more honest, but `key-values.md` could say the detail keeps the requested order.
3. **The usage test reads the day from `DateTime.UtcNow`** (`Usage_CountsRevealsOfSecretVersionsAndDiffs`) while the service stamps through `TimeProvider`. A run that crosses midnight UTC would split the counters across two days. Other tests in the file probably do the same, so this only matters if they ever get flaky. Reading the day from the injected `TimeProvider` would fix it.
4. **The new MCP comment** ("an API from before the audit of its version route still records that reveal", `SecretTools.cs:41`) is accurate but hard to parse. Something like "Reveal the current version through the pair so that older APIs, which don't audit the version route, still record it" would be clearer.
5. **The mock is good.** It only records events after both sides resolved, and `new Set([from, to])` gives the dedupe for `2..2`. A short comment that version 0 is skipped because it has no entry would help the next reader.

## Good

- Recording the stored key (`catalog.Key` or `item.Key`) and not the casing of the request is the right call, and a mutation-tested assertion pins it (`"the stored key is recorded, not the casing of the request"`).
- The audit is written only after both sides resolved, so an unknown version, a `Hyok` side or a caller without secret rights records nothing. The `RevealsAfter` helper makes those negative cases easy to read.
- Public sides, version 0, `reveal: false` and the public-to-secret protection change (`moved`) are all covered, which are the edges most likely to regress.
- `RecordRevealAsync` gets an optional detail instead of a new operation, so the CLI filter, the Audit tab and the SDKs work unchanged. That keeps the change free of breaking changes.
- The docs now say plainly which operations, `Reveal`, `Export` and `BindingRead`, make up "everyone who received a secret". That's a useful paragraph for whoever builds a compliance report on this.
