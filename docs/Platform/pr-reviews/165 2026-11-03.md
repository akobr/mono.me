# Review of PR #165: [feat(platform): move Storyteller NuGet packages into Libraries (424-169)](https://github.com/akobr/mono.me/pull/165)

Reviewer: Harry · Review date: 2026-11-03

**Verdict: needs discussion (one versioning decision, otherwise approve-ready).** This is a clean, pure move: 173 files, almost all 100% renames, no C# changes, assembly names, package ids, namespaces and `InternalsVisibleTo` untouched. Every `ProjectReference` in `src/**` resolves after the move (I checked all of them), the conformance embeds still point at `src/Platform/Storyteller/conformance`, the package readmes moved to where `ProjectStructurePath` now looks, and no living file outside the historical specs still names the old paths. The one open point is that the new shared `version.json` makes two packages go *down* in version, which the PR's own spec says must not happen.

Only CodeRabbit's auto-summary comment so far. ## Important

1. **Configuration and ConfigurationFormats go backwards in version.** `src/Libraries/Platform/Storyteller/version.json` uses `pathFilters: ["."]` without hierarchical versioning, so the height restarts from the move commit and every package in the workstead is `0.10.2-alpha`. Per the PR table that is a downgrade for `42.Platform.Storyteller.Configuration` (`0.10.4-alpha` → `0.10.2-alpha`) and `42.Platform.Storyteller.ConfigurationFormats` (`0.10.5-alpha` → `0.10.2-alpha`). The spec (`docs/Libraries/Platform/Storyteller/specs/2026-11-03 Move…md`, Versioning paragraph) states "The new version of each packable project must be greater than or equal to its pre-move version", and the Phase 1 review acknowledges the branch breaks that without saying why it is acceptable. I found none of these ids on nuget.org yet, so no public consumer is hurt today, but any local or dev feed, Aspire app host or CLI cache holding `0.10.4`/`0.10.5` will keep preferring those builds, and the next real release would be lower than what people have already tried. Fix: add `"versionHeightOffset": 3` to the workstead `version.json` (that puts the whole linked set at `0.10.5-alpha`, at or above every pre-move version), or, if you deliberately accept the reset because nothing was published, update the spec's acceptance line so the docs and the code agree.

2. **The shared version and the Hosting coupling pull in different directions.** `Hosting.csproj` says "Hosting uses internals of it, so both ship one version", and `Configuration.csproj` grants `InternalsVisibleTo` to `42.Platform.Storyteller.Hosting`. After this PR, Configuration versions with the Libraries workstead (`0.10.2-alpha`) while Hosting stays on the Platform hierarchy (`0.10.8-alpha`), so the "one version" promise in that comment is no longer even approximately true, and a consumer can update one without the other and hit a `MissingMethodException` on an internal. This was already loose before (per-directory heights differed), and Hosting is not released yet, so it is not a blocker, but it is worth deciding now: either move Hosting into the same workstead when it ships, or have Hosting's package depend on an exact Configuration version (`[x.y.z]`) at pack time, and fix the comment either way.

## Nits

- `.github/workflows/storyteller-conformance.yml` path filters cover `Configuration`, `ConfigurationFormats` and the workstead `version.json`, but not `Configuration.KeyVault` or `Aspire.Hosting`, and the job only runs the two formats/provider test projects. Pre-existing gap, but now that all four sit in one folder a single `src/Libraries/Platform/Storyteller/**` filter plus `dotnet test` for all four test projects would be simpler and would actually run the KeyVault (87) and Aspire (164) suites in CI.
- `storyteller-sdk-release.yml` still does not pack `Aspire.Hosting`, although it is one of the four "published" packages this PR moves. If it is meant to ship with the others, add it to the Libraries loop; if not, say so in the comment above the loop.
- With one linked version, a commit that touches only `Aspire.Hosting` (or only a test project) bumps the version of all four packages. That is the intended trade-off per the PR text; just note it in `docs/Platform/Storyteller/configuration-provider.md` or the package readmes so nobody reads a version bump as a Configuration change.
- `src/Libraries/Directory.Build.proj` traverses `**\*.*?proj`, so building Libraries now also builds `Sdk.NSwag` and `Abstractions.Annotations` from the product tree through references, and the "2S platform" `test` script in `mrepo.json` no longer runs these four test projects. Fine, but worth a line in `CLAUDE.md` so people know where to run them.
- The workstead `version.json` drops `hierarchicalVersion` that `src/Platform/version.json` uses, while the spec still describes the hierarchical body. The Phase 1 review explains the switch; the spec's "Proposed Changes" versioning text could get a one-line pointer to that review so a later reader does not follow the stale plan.
- The PR title uses `feat`, which `mrepo.json` maps to a minor bump. For a move with no behaviour change, `refactor` (patch) would describe it better, if release notes or version bumps are derived from commit types.
