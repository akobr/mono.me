# Review of PR #200: [feat(platform): seed key/value pairs with DbCreator's data sets (424-265)](https://github.com/akobr/mono.me/pull/200)

Reviewer: Harry · Review date: 2026-11-15

**Verdict: approve-ready.** There is one behaviour change worth deciding on before merge. The seeder is careful. It plans every chunk with the import's dry run, so it never updates or restores a pair, and refusals happen before the database is touched. It also handles an unreachable vault and a write that fails partway. The tests cover the decision table well, in both unit and Cosmos/Lowkey Vault suites. I found nothing blocking. The main point is that a Standard vault is now needed to seed `showcase` and `exhibit` at all, even when they are already seeded.

**CI at review time (head `3d06c36`):** "Classic emulator" passed. "vNext emulator", "Lint, type-check, test, build" and CodeRabbit were still running. There were no reviews yet and one CodeRabbit comment. The author reports these local results: DbCreator/test 184 passing, DbCreator/testint 25 passing (vNext + Lowkey Vault), and the admin UI typecheck, lint and `showcase-set.test.ts` passing.

## Why I think it is correct

- **Merge without its side effects** (`DataSetKeyValueSeeder.cs` L84–147). Each chunk runs a `Merge` dry run first. `Update` becomes `Skipped/KeyValueExists`, and a `Create` for a key in the deleted listing becomes `Skipped/KeyValueDeleted`. Only what is really missing is written. This matches `PlanImportItemAsync`, which plans a deleted key as `Create`. Doing it this way avoids a new import mode in shared code.
- **Refusal before any write.** `DataSetKeyValues.Read` checks every item: `KeyValueRules`, the level, a missing value, references and duplicates ignoring case. It lists up to 20 problems. `DataSetSeeder.Plan` (L94–97) runs it for every set, dependencies included, before provisioning. `KeyValueDocument.Format` defaults to the current format, so the comment at L96 holds.
- **Failure classification.** A `KeyValueImportInvalidException` fails the listed items, and the chunk is planned again without them. Storyteller, integrity, vault and auth errors, and an Azure.Core retry `AggregateException`, are pair failures (exit 4). A storage failure ends the run. After a write that fails partway, the active keys are listed again so stored pairs are not reported as failed (L364–378). Each of these has a test.
- **Hash and record.** `ComputeHash` already covers `key-values.json`, so a new or changed file seeds again. `DataSetSeedRecord.KeyValues` defaults to 0 for older records. `IKeyValueService` takes no `CancellationToken`, so the `ThrowIfCancellationRequested` between chunks is as good as it can get.
- **Aspire.** `db-seed` gets the same `keyVault.GetEndpoint("https")` as `api-functions` (AppHost L81–84 vs L90–92). That gives the same host in the key ids, so the API can decrypt seeded Standard pairs. This was finding 3 of the branch review.

## Blocking

None.

## Important

1. **A Standard vault is now required for any seed of `showcase`/`exhibit`, even an already-seeded one** (`DataSetSeeder.cs` L94–97 vs L392). `Plan` calls `EnsureSeedable` for every set and dependency before `SeedSetAsync` checks the record (`record.Hash == hash`). Both built-in sets now carry Standard pairs (`payments.adyen.hmacKey`, `smtp.password`, `globex.lairforce.escrowPin`). So:
   - `2sInitDb seed showcase` without `AzureKeyVaults__default` now exits 2 and seeds no documents, where it used to work. This hits the packaged tool against an environment without the vault's roles, and anyone running `dotnet run -- seed showcase` outside Aspire.
   - A repeat run on a target where the set is already recorded also exits 2, though it would write nothing.

   *Suggested fix:* pick one of these and document it in `data-sets.md`.
   - (a) Move the Standard check into `SeedSetAsync`, after the record check, but keep it before the first write of that set. The file-shape refusals can stay in `Plan`.
   - (b) Add a flag such as `--public-pairs-only`, which reports the Standard pairs as `Skipped` with a code like `ProtectionNotConfigured`.
   - (c) Keep the strict behaviour, but state in the docs and in the `sets` overview that these two built-in sets need a vault.
2. **The race between plan and write can overwrite a pair** (`DataSetKeyValueSeeder.cs` L328–356). If another writer creates the key between the dry run and the write, `Merge` writes the set's value over it and reports `Updated`. That breaks the "a seed never changes a pair" rule the docs promise, even though it is reported honestly. The window is small and seeds are usually the only writer, so this is not blocking. *Suggested fix:* say in `data-sets.md` that the guarantee assumes no concurrent writer. Or, as a follow-up, give the import a create-only option (for example `KeyValueImportOptions.IfNotExists`). That would remove both the race and the extra deleted-keys listing.
3. **The recovery listing can hide the original failure** (`DataSetKeyValueSeeder.cs` L370). If `GetKeysAsync(Active)` throws inside the `catch` (for example, Cosmos is also unhealthy), its exception replaces the vault failure and ends the run with exit 1. The original cause survives only in the warning log. *Suggested fix:* wrap the listing in a `try`/`catch`. When it fails, fail every missing pair with the original `Failed(exception)`, or rethrow an `AggregateException` of both.

## Nits

- `IsVaultRetryFailure` (L172) counts `OperationCanceledException` as a vault failure. That is correct today, because the import gives the vault no token. Add a comment that this must be revisited if `IKeyValueService` ever takes a `CancellationToken`, or user cancellation would be swallowed as `KeyEncryptionUnavailable`.
- `key-values.json` is read and validated twice per set, in `Plan` and in `DataSetContent.Read`, and up to 32 MB each time. A recorded set is fully read in `Plan` even though it is skipped. This is fine for a CLI. Caching the parsed `DataSetKeyValues` in the plan would remove the second read.
- `DataSetKeyValues.Validate` (L144–149) calls `KeyValueRules.Normalize(item.Key)` twice. Store it in a local.
- `DataSetKeyValuesResult` and `DataSetKeyValues.Levels` expose `IReadOnlyList<(KeyValueProtection Level, int Count)>`. Tuples are fine internally. If these results are ever serialized (a `--json` output), STJ drops tuple fields. A small `record struct LevelCount` would be safer.
- `DataSetSeedItem.Kind` went from `required` to nullable. I checked, and nothing outside `DataSetOutput` and the tests uses it, so this is fine. Consider an invariant comment or factory methods, such as "exactly one of `Kind` or `KeyValueKey`", so a future item cannot have neither.
- The demo secret `smtp.password = "Is-smtp-2026-09"` in the showcase looks plausibly real. Prefer an obviously fake value like `demo-smtp-password`, as the HMAC one is, so secret scanners and readers do not trip on it.
- With `KeyValues__Protection__Emulator=true`, `AddKeyVaultKeyProtection` also registers `CustomerKeyProvider`, so `IsConfigured(Byok)` returns true in Aspire. This does no harm, because Byok is refused when the file is read. Still, `IsConfigured` should probably only be asked about `SeedableLevels`.

## Good to note

- Clear exit-code semantics (2 = refused up front, 4 = a pair failed), documented in `ExitCodes.cs` and exercised by the command tests.
- `FakeKeyValueService` models the real plan, including deleted keys, the chunk limit and `WrittenBeforeException`. That keeps the unit tests honest without Cosmos.
- `ABindingToASeededPair_ResolvesInAResolvedRead` checks the end-to-end value: configurations bind the seeded pairs, and seeded writes run before the configurations.
- The docs clearly say sets carry demo and test values only, never real secrets.
