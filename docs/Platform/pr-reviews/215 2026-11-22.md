# Review of PR #215: [feat(platform): join or leave the exhibition after onboarding in the admin UI (424-271)](https://github.com/akobr/mono.me/pull/215)

Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready. Two points are worth a small follow-up, and the rest are nits.** The feature is small, well scoped and matches the API exactly. I checked the mock's DELETE against `CosmosAccessService.RemoveMemberAsync` and `MembersHttp.RemoveMember`. Any member may leave, leaving needs no step-up, removing someone else needs Administrator (and Owner to remove an Owner), and `LastOwner` always applies. The join reuses `POST v1/access/exhibition/join`, which already returns the account, so the client avoids a second read. The API and the SDKs are unchanged. The unit tests cover the paths that matter (`MemberNotFound` counted as left, a failed re-read falling back to `withoutMembership`, the snapshot of the dialog, a 404 kept vs another failure retried, and a 404 on join). The new Testiny cases 510–514 have automation tests.

## Important

1. **The leave invalidates the left project's queries while its page is still mounted.** In `composables/useLeaveProject.ts` (≈L57–61), `session.setAccount(fresh)` and then `void invalidateProject(queryClient, projectKey)` both run *before* `toOrganizations()`. Every active query of `[org]/[project]/settings.vue` that is not gated on a role (the project settings query, the project summaries and anything else `invalidateProject` touches) refetches as a non-member and can briefly get 403s, error states or toasts before the route changes. The cached data of a project the user can no longer read also stays in the cache until GC.
   *Suggested fix:* navigate first, then drop the cache: `await toOrganizations(); queryClient.removeQueries({ predicate: q => keyMentions(q, projectKey) })` (or whatever `invalidateProject` matches on). Removing is better than invalidating here, because nothing on `/orgs` needs those queries. If the flash cannot happen because every such query is silent and role-gated, add a short comment saying so and a unit test that asserts no project request after the leave.

2. **The "how to come back" text depends on an optional GET that can fail.** `settings.vue` passes `:exhibition="exhibition.isExhibition(context.projectKey)"`, and `useExhibition` only counts `isSuccess` data. While `GET /exhibition` is pending, has timed out (5 s) or has failed, a member of the exhibition who leaves is told *"To come back, you need a new invitation"*. That is wrong, and it may stop a user from rejoining. The snapshot in `ProjectLeave.open()` freezes whichever answer was there at the click.
   *Suggested fix:* for the *text*, use the last known data (`query.data.value`, even after a failed refetch) and keep `isSuccess` only for the *offer*. Alternatively, phrase the fallback neutrally when the exhibition is unknown.

## Nits

- **`settings.vue` now asks for the exhibition on every Settings page** (via `useExhibition()`) for every user, only to choose one sentence of the dialog. It is cached for 5 minutes, but a misconfigured deployment logs a Warning per request (`ExhibitionHttp.FindExhibitionAsync`). Consider making the query lazy (`enabled` only once the dialog opens), or accept it knowingly.
- **`settingsDirty` gated on `canManageSettings`** (settings.vue ≈L127). This fixes the prompt after a leave. As a side effect, an Administrator who is demoted while editing now loses the draft without a prompt. That is acceptable, but the comment could say so.
- **Order of checks in the mock DELETE** (`mock/access-handlers.ts` ≈L438–461). The real API runs `EnsureRecentSignIn` in the HTTP layer *before* the service, so the 401 step-up comes before 403/404/409 when someone else is removed. The mock checks the step-up last. This order is older than this PR, but the block is being reworked anyway, so moving `requireRecentSignIn()` to the top for `!leaving` would make the mock match the API.
- **`lastOwner` treats unknown members as "not last"** (`?? Infinity`), and that is documented. Note that `accessPoint` is `meta: { silent: true }`, so if it fails, the Owner gets the API's 409 toast instead of the disabled button. That is fine and covered by a test.
- **`ProjectLeave.confirm()` closes the dialog on failure too.** The toast explains the reason, so this is fine. Keeping the dialog open on `LastOwner` would show the reason next to the action, but that is optional.
- **`useJoinExhibition` returns from `catch` and relies on `finally`** to reset `joining`, which is correct. The success toast and `router.push` run after `finally`, so a guard that rejects the push leaves the user on `/orgs` with no card and no project link. This is unlikely, and the membership is still shown in the grid.
- **`projectPath` moved to `utils/memberships.ts`.** This is a good de-duplication. `roleLabel` and `ownerCount` in `utils/roles.ts` are good extractions too.
- **Exhibition keys are compared case-sensitively** (`${Organization}.${Project}` against the lower-cased access map). This is safe because `ExhibitionOptions.IsValid` requires valid, lower-case names. The JSDoc could mention it.

## Good

- The mock now encodes the API's rules for removing a member, including the Owner-only removal of an Owner with the `AccessDenied` code, with a comment that points to `RemoveMemberAsync`.
- The `MemberNotFound` path counts a leave as done, and the fallback to `withoutMembership` when `getAccount` fails means the UI never keeps a membership that is gone.
- `toOrganizations()` handles a navigation failure with a full load and `leaveWithoutPrompt()`, so the user is never stranded on a page they cannot read.
- `retryOnMount: cached => !isNotFound(cached.state.error)` is a neat way to stop vue-query from asking again for a 404 that is a real answer.
- The C# automation pages and tests (`OrganizationsPage.ACC.cs`, `ProjectSettingsPage.ACC.cs`, `MockApi.ORG.cs`, `MemberTests`, `OrganizationTests`) follow the repo's patterns: argument guards, exact locators, and `[MockOnly]` with a stated reason where a leave would be destructive on a deployed target.
- The "Decisions to confirm" are reasonable. Offering Leave to Administrators fills a real gap, and the API's `LastOwner` remains the authority.
