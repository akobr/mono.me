# Review of PR #156: [fix(platform): count the deleted annotations in the bulk delete toast (424-156)](https://github.com/akobr/mono.me/pull/156)

Reviewer: Harry · Review date: 2026-11-02

**Verdict: approve-ready.** The PR is small (`AnnotationBulkBar.vue`, a new Vitest file, spec and spec review; +216/−7). It correctly fixes the root cause: `deleteSelected()` read `props.keys` after `removeMany`, but by then the page's `selectedKeys` (filtered by `catalog.byKey`) had already dropped the deleted keys. Taking a snapshot before the `await` is the right fix, and the tests reproduce the real shrinking-prop behaviour. The points below are follow-ups, not blockers.

**CI at review time:** "Lint, type-check, test, build" and CodeRabbit were both still running. I reviewed the diff against `useAnnotationActions.removeMany`, the Annotations page (`pages/[org]/[project]/[view]/annotations.vue`) and the component in full, but did not run it.

## Blocking

None.

## Important

1. **When everything is deleted, `emit('clear')` is dropped and the stale selection survives (pre-existing, now more visible).** The page renders the bar with `v-if="selectedKeys.length && canEdit"` (annotations.vue L254). When every selected key is deleted, the bar unmounts during the `await actions.removeMany(keys)` call. Vue 3 ignores `emit` from an unmounted instance, so `emit('clear')` (AnnotationBulkBar.vue L61) never reaches `rowSelection = {}`. The deleted keys stay in the page memory's `selection`. They are hidden only because `selectedKeys` filters on `catalog.byKey`. After **Undo** restores them, they come back selected and the bulk bar reappears. The toasts still work after unmount, because `useToast` and `useDeletionToast` use global state, as the first test shows.
   *Fix:* clear the selection where it lives, not through the bar. For example, the page could drop selected keys that leave the catalog with a `watch` on `catalog.byKey`. Or the bar could clear before the `await` once the snapshot is taken (with the failed keys re-selected afterwards, see 3). Add a test that asserts `clear` was emitted, or that the selection is empty after a full delete.

2. **`deleteSelected()` has no `catch` (pre-existing).** Unlike `run()` (L29–40), an exception from `removeMany` becomes an unhandled rejection with no toast, and the dialog stays open. Possible causes are `scope()` throwing "No view is selected." or `invalidateDeleted` rejecting after the deletes. The `finally` resets `busy` and `deleting`, so the UI doesn't hang. However, the user gets no feedback, and some keys may already be deleted.
   *Fix:* add `catch (error) { toast.add({ title: 'The delete failed', description: errorMessage(error), color: 'error' }) }`, matching `run()`.

3. **A partial failure clears the failed keys from the selection as well.** In the one-of-two-failing case, the bar stays mounted and `emit('clear')` also deselects the key that couldn't be deleted. The warning toast lists it, but the user has to find and reselect it to retry. Consider keeping the failed keys selected (emit them, or let the page set `rowSelection` to `failed`). This is a UX choice, but it fits well with fixing point 1.

4. **The steady dialog count (spec item 2) has no test.** In all three tests, `removeMany` resolves within one `settle()`. As a result, nothing asserts that the dialog title stays at "Delete 3 annotations?" while the deletes are in flight. This is the only window where `deleteCount` differs from `props.keys.length`.
   *Fix:* give `removeMany` a deferred promise. Delete 3 keys, let one resolve, and assert `dialog.props('title')` and `confirmLabel` are unchanged and `loading` is true. Then resolve the rest.

## Nits

5. `annotations(value)` (L27) reads like a collection. A name like `countAnnotations` or `annotationCount` would make the template (`` `Delete ${annotations(deleteCount)}?` ``) easier to read. If i18n is ever planned, `Intl.PluralRules` together with the `Intl.NumberFormat` you already use is the natural next step.
6. `count` (formatted string, L23) and `deleteCount` (number, L24) differ in type but have similar names. Renaming `count` to `selectedLabel` would avoid mixing them up.
7. The singular description ("The annotation and its descendants…") departs from the spec's "The 1 annotation…". The spec review documents this and the wording is better, but the spec's Proposed Changes still say otherwise. Consider updating the spec so the two match.
8. `useDeletionToast` ("N annotations restored / were not restored") and the Deleted page still have the plural problem. The spec review notes this as out of scope, so it's worth opening a small Linear follow-up.
9. Test helper `confirmDelete` computes the expected title from `selection.value`, so it repeats the component's plural logic. Using literal expected titles per test would be stricter.

## Good

- The root-cause analysis in the PR and spec is precise and correct (catalog removal → computed `selectedKeys` → shrinking prop → possible unmount). The code comments at L18 and L43 explain why the snapshot exists, so nobody "simplifies" it away later.
- The test models the real coupling: the mocked `removeMany` shrinks the reactive selection between awaits, and the bar is mounted conditionally as on the page. It fails on the old code and passes with the fix.
- The confirm button stays "Delete N", and the "N selected" label still follows the live selection, so the change is scoped tightly.
- The note about tightening ANN-CAT-02 to `2 annotations deleted` after #155 merges is a useful cross-PR follow-up. Keep track of it so it doesn't get lost.
