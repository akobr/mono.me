# Review of PR #166: [fix(platform): start the docked sidebar as the icon rail between lg and xl (424-168)](https://github.com/akobr/mono.me/pull/166)

Reviewer: Harry · Review date: 2026-11-04

**Verdict: approve-ready, with two small hardening suggestions.** The diagnosis is right and well documented: `useResizable` (`@nuxt/ui` 4.11.3) reads `isCollapsed` from storage first (`storageData.value?.collapsed ?? defaultStorageValue.collapsed`) and only copies a stored `true` into the model, so a stored `false` beat the width-based start and left the model and the screen apart, which is also why the first `[` did nothing. Reading a stored "expanded" as "no choice" and writing it back unchanged is a minimal, contained fix. Moving the start into module state in `useSidebar.ts` correctly fixes the logo/bare-route remount. I checked `useResizable.js` and `useStorage` (`@vueuse/core` 14.x) on the box: `storageOptions` is passed straight through to `useStorage`, `listenToStorageChanges` and `serializer` are honoured, and the setup read is wrapped in `try/catch` with `onError`, so the behaviour the comments describe holds.

## Important

1. **A first-ever narrow start still stores the rail; `writeDefaults: false` removes that cheaply.** `src/Platform/ui.admin/src/app/layouts/DefaultLayout.vue:20-27`. With nothing stored, `useStorage` writes its defaults on the first read (`writeDefaults` is `true` by default), and `useResizable` builds those defaults from the model, which is now `true` below 1280 px. So a browser whose first visit is at 1100 px stores `{"size":16,"collapsed":true}`, and every later start at 1440 px opens as the rail. That is the first case in the PR's "known limits". Adding `writeDefaults: false` to `sidebarStorage` keeps nothing in storage until the user actually toggles or resizes (with no stored value, `useStorage` returns the defaults without writing them, so `isCollapsed` still follows the start). It does not cover the "shrink an open page" path, because that write comes from the `wide` watcher through the model, but it closes the most common way a fresh user gets the rail on a wide screen. Add a unit case: nothing stored, mount at 1024 px, expect `localStorage.getItem(storageKey)` to be `null`.

2. **The fix depends on undocumented `@nuxt/ui` internals while the range is `^4.11.3`.** `src/Platform/ui.admin/src/package.json:50`. The PR's own review notes this (`useResizable.js:34`, `storageOptions` typed `Record<string, any>`). The unit tests will catch a regression, but only after an upgrade lands; a caret range means a fresh `npm install` or a lockfile refresh can pull a minor release that changes `useResizable`. Either pin `@nuxt/ui` to `~4.11.3` (patch only) with a comment pointing at `DefaultLayout.vue`, or add a short note next to `sidebarStorage` that the unit file `docked-sidebar.test.ts` guards this and must pass before a `@nuxt/ui` bump. Low effort, avoids a silent return of the bug.

## Nits

1. **`serializer.read` trusts the stored shape.** `DefaultLayout.vue:21-24`. A stored `null`, an array, or a hand-edited value makes `stored.collapsed` throw. `useStorage` catches it and logs via `onError`, so nothing breaks, but you get a console error on every start until something overwrites it. A one-line guard keeps it quiet: `if (!stored || typeof stored !== 'object') return {}`.

2. **Module-scope watcher and media query in `useSidebar.ts:8-10`.** Fine for a single SPA page (it is never disposed, and that is intended), but note it lives outside any effect scope, so under Vite HMR of this file each reload adds another `matchMedia` listener in dev. Harmless; a short `// intentionally app-lifetime` in the comment would stop someone from "fixing" it into the composable later.

3. **Unit test teardown resets to `false`, not to the module start.** `test/unit/components/docked-sidebar.test.ts:27-30`. `beforeEach` sets `true`, `afterEach` sets `false`, while at happy-dom's 1024 px the module starts at `true`. It is harmless inside this file (Vitest isolates files), but resetting to `!wide` (or simply `true`) in `afterEach` makes the intent match the comment above `beforeEach`.

4. **User docs only mention one way the rail is remembered.** `docs/42for.net/platform/admin-ui.md:319`. "If you collapse it in a wider window, it stays collapsed when you reload" is true, but a narrow first visit or a shrink also stores the rail (see Important 1). If you take `writeDefaults: false`, only the shrink case remains and the sentence is close enough; otherwise consider "Once collapsed, it stays collapsed through a reload until you expand it."

5. **E2E pin test types into the palette and clicks immediately.** `test/e2e/navigation.spec.ts:547-549`. The PR review says the filter-delay race was measured and rejected; fine, but `await expect(option).toBeVisible()` before `.click()` costs nothing and documents the wait.

## Good

- The spec and implementation review are unusually precise (line references into `useResizable.js` and `useStorage`), and the two deviations from the spec are justified with the concrete regressions they prevent (storage events dropping "expanded" in another window, the logo remount resetting the ref).
- `listenToStorageChanges: false` is the right call given that `serializer.read` also runs on storage events; the trade-off (windows no longer follow each other) is stated plainly.
- Tests hit the real failure paths: the unit tests fail without the storage options, and the e2e tests cover the new-tab, crossing-xl, logo, pin and reload flows, with mobile correctly skipped.
- No change to the stored format, so existing users' sizes are kept.
