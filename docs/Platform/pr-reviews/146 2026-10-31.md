# Review of PR #146: [🐛 fix(platform): answer unsupported machine access with MachineAccessNotSupported (424-102)](https://github.com/akobr/mono.me/pull/146)

Reviewer: Harry · Review date: 2026-10-31

**Verdict: approve-ready, with two points worth a short discussion.** Making `MachineAccessNotSupportedException` a `StorytellerException` with `ErrorCodes.MachineAccessNotSupported`, mapping it once in `ErrorResponseMapping` (`Api.Functions/src/ErrorHandling/ErrorResponseMapping.cs:22`), and having the four HTTP catches return the mapped body is the right shape: it follows the existing pattern, and a refusal that slips past a local catch now gets a coded `400` from the middleware instead of a `500`. Changing the base type away from `InvalidOperationException` is safe; none of the remaining `catch (InvalidOperationException)` sites sit on a machine access path. The reset of an `ApiKey` or `CertificateAndApiKey` record without a hash moves from `500` to `404`, and keeping `500` for a `ClientCredentials` provider that returns no secret is the correct call (a transient Keycloak failure must not look like a client error). When I reviewed `217205be`, both checks (CodeRabbit and "Lint, type-check, test, build") were still in progress. Locally, `Access.Certificates` `MachineResetTests` passed (7 of 7); `Api.Functions` did not build on my machine because of an unrelated `OpenApiConfigurationOptions.NamingStrategy` override error in a file this PR doesn't touch, so I couldn't run the HTTP tests and rely on CI for those.

## Blocking

None.

## Important

1. **Deployment misconfiguration now reads as a coded client error.** Several throws of `MachineAccessNotSupportedException` describe the server, not the request: AuthKit without `MachineOrganizationId` (`Access.AuthKit/src/AuthKitMachineAccessService.cs:38`), Entra ID without the service principal (`Access.AzureAd/src/AzureAdMachineAccessService.cs:63`), and `ClientCredentials` or `Federated` not configured (`Access.Certificates/src/PolicyAwareMachineAccessService.cs:145` and `:151`). They already answered `400` before this PR, so it's not a regression, but stamping them with `MachineAccessNotSupported` makes the contract official: a client will treat "this deployment is half configured" the same as "this kind can't be reset" and never page anyone. The repo already has `FeatureNotConfiguredException` (`501`). Suggest throwing that (it is sealed and takes its own error code) for the deployment-level cases, and keeping `MachineAccessNotSupported` for things the caller can change: the kind, the scope, the operation. If you'd rather keep this PR narrow, add it to "Left for later" in the spec.
2. **The new `404` names a machine that `GET` still lists.** The branch in `Backend.CosmosDb/src/Accessing/CosmosAccessService.cs:599-611` answers "not found" when the document exists but the hash doesn't. During a concurrent delete that's correct and matches the docs. In the "creation failed" case, though, the document can stay with no hash, so the list shows the machine, the reset says `404`, and the client has no hint what to do. A `DELETE` does clean it up (`DeleteMachineAccessAsync` deletes the hash idempotently, then the document), so two cheap options: add "delete it and create a new one" to the message, or give this case its own code (for example `MachineAccessIncomplete`) so the Admin UI can offer the delete. Longer term, the create compensation should remove the document too, so the orphan can't exist.
3. **Which kinds have an API key is now decided in two places.** The Cosmos branch tests `ApiKey or CertificateAndApiKey`, while the router in `PolicyAwareMachineAccessService` decides the same thing with its own `switch` (`_ =>` falls to the API key service). A new kind added to one and not the other will quietly get the wrong answer (a `500` or a wrong `404`). Suggest a single extension, `MachineCredentialKind.HasApiKey()`, in `Abstractions.Access`, used by both, with a small test that enumerates every enum value.

## Nits

1. **The SDKs aren't regenerated.** The PR says so, and the schema is unchanged, but `DeleteMachine` now declares a `400` with an `ErrorResponse` body. After the next NSwag regeneration (`Sdk.NSwag/src/ApiSdk.g.cs`), that `400` will surface as `ApiException<ErrorResponse>` instead of `ApiException`. The CLI's `WriteApiError` (`Cli/src/Output/KeyValueConsoleExtensions.cs:234`) handles both shapes, so nothing breaks; it's just worth regenerating in the same release so the typed body is there.
2. **No CLI test pins the code.** The docs say `sform machine reset` prints "Error code: MachineAccessNotSupported", which is true via `WriteApiError`, but `Cli/test/Commands/MachineListAndResetCommandTests.cs:133` only sends a `Message` body. Adding `ErrorCode` to that fake response and asserting the line would lock in the promise the docs make.
3. **`ToActionResult` returns a plain `ObjectResult` with `StatusCode = 400`,** not a `BadRequestObjectResult`. The tests already assert on the status code, so it's fine; just keep asserting status codes rather than result types in future tests.
4. **Wording.** The comments "no secret to reset" in `Cli/src/Commands/MachineAccess/MachineResetCommand.cs:45` and in `ui.admin`'s `machines.vue:214` are about `Federated` and still correct, but they now read differently from the new Certificate message. Optional alignment.
5. **Mixed scope.** The keyless reset `404` is a separate behaviour change from the error code. It's documented in the spec and the description, so acceptable, but it would have been easier to revert on its own as a separate commit range or PR.

## Good

- Small, well-scoped change that reuses the existing `StorytellerException` and `ErrorResponseMapping` machinery instead of inventing a new path.
- Local catches stay, so the expected refusals don't produce middleware warning logs, and the middleware mapping is a safety net rather than the primary path.
- Test coverage is thorough: all four HTTP routes, the mapping, the middleware, the OpenAPI theory over four routes, unit resets in `Access.Certificates`, and integration tests for the hash-cleared case for both kinds plus a `ClientCredentials` router without a secret. The integration test checking the ETag to prove nothing was written is a nice touch.
- The deviation from the CodeRabbit plan is argued well: a blanket `400` for a record without a hash would have hidden transient provider failures and contradicted the documented `404` for a reset racing a delete.
- Docs, OpenAPI descriptions, the Admin UI mocks and the MCP comment are all updated together, and `authentication.md` cleanly separates the uncoded `400`s from the coded ones.
