# Review of PR #183: [feat(platform): Bicep templates of the Azure production environment, cookbook steps 1-15 (424-231)](https://github.com/akobr/mono.me/pull/183)

Reviewer: Harry · Review date: 2026-11-09

**Verdict: approve-ready, with a few important fixes worth making before the first `create`.** Nothing deploys from this PR and the templates are careful: no secret is a parameter or an output, the Cosmos key goes from `listKeys()` straight into the vault, storage has shared keys off from the first write, basic publishing credentials are disabled, both irreversible resources are locked, role assignment names are stable `guid(...)` values with `principalType` set (so no replication race on the new identity), and the SWA token reaches GitHub through stdin. Nothing I found is blocking; the important items are about what a *second* run does to production.

Scope I read: every file under `src/Platform/Deployment/`, the `CLAUDE.md` row, the PR's own review doc, and the code that reads each app setting (`MachineAuthenticationOptions`, `FederationOptions`, `AuthKitOptions`, `KeyValueOptions`, `CosmosDbOptions`, `AzureStorageConnection`, the `AzureKeyVaults` entry points). I rebuilt both entry points and both parameter files with Bicep 0.49.2: no errors, no warnings, matching the description. CI: only CodeRabbit, still in progress when I looked; no workflow builds the Bicep.

## Blocking

None.

## Important

1. **A run from a shell without the later `PLATFORM_*` variables silently strips production app settings.** `prod.bicepparam:19-23` default `PLATFORM_AUTHKIT_CLIENT_ID`, `PLATFORM_BYOK_CLIENT_ID` and `PLATFORM_AUTHKIT_API_KEY_ENABLED` to empty/false, and `functions.bicep:196` owns the whole `appsettings` set. So after step 13, one `create` from a new terminal removes `Auth__AuthKit__ClientId` (every sign-in breaks) and `KeyValues__Protection__Byok__ClientId` (every BYOK project's secrets become unreadable). The README warns, but it's an easy mistake on a 5-step manual flow. (The deployment principal's role assignments are fine: incremental mode never deletes them.)
   *Fix:* these are public identifiers, not secrets. Once known, commit them as literals in `prod.bicepparam`, and keep variables only for the owner's personal values. If you want to keep them out of the repo, at least read them from the current site (`existing` + `list()` on `config/appsettings`) as the fallback instead of `''`, or fail the param file when a `PLATFORM_STEP` marker says step 13 is done.

2. **The budget's start date moves on every run.** `main.bicep:75` (`utcNow('yyyy-MM-01')`) rewrites `timePeriod.startDate` of an existing budget each month. Cost Management has historically refused changing the start date of an existing budget, so the first run in December may fail at the budget resource and with it the whole subscription deployment. I can't prove it without a subscription, so treat it as "verify with `what-if` + `create` in a later month". *Fix if it does fail:* pass the creation month as a fixed literal in `prod.bicepparam`, or move the budget into its own run-once deployment like `domains.bicep`.

3. **Nothing caps Cosmos DB throughput at the free tier.** The goal is "as cheap as the free tiers allow", but a budget only sends mail. `CosmosDbOptions.AutoscaleMaxThroughput` defaults to 1000 and DbCreator creates two containers; any mistake in the database/container throughput split goes past the free 1000 RU/s and is billed. *Fix:* add `capacity: { totalThroughputLimit: 1000 }` to `cosmos.bicep` (around line 20). DbCreator then fails loudly instead of billing quietly, and raising the cap later is a one-line, reversible change.

4. **The deployment identity gets more than it needs.** `access.bicep:54-70` grants Contributor on the whole resource group and Key Vault Secrets User on the whole vault. Contributor can `listKeys` on Cosmos (full data access, bypassing the vault), rewrite app settings (point `CosmosDb__Connection` anywhere) and delete the storage containers; Secrets User on the vault also reads `authkit-api-key` and any later secret. A compromised workflow on `main` gets all of that.
   *Fix:* Website Contributor scoped to the Function App (and the SWA if needed) for the code deploy, and Key Vault Secrets User scoped to the secret `cosmos-connection` (`scope: cosmosSecret`; secret-scoped role assignments are supported with RBAC vaults). Keep Storage Blob Data Contributor, but scope it to the `deployments` container. The spec's section 10 can still widen this when the pipeline runs `main.bicep`.

5. **No CI for the new folder.** Nothing runs `bicep build`/`lint` or PSScriptAnalyzer on PRs, so the strict `bicepconfig.json` only protects whoever remembers to run it. A small workflow with `paths: src/Platform/Deployment/**` that runs `az bicep build` on both entry points, `build-params` with dummy `PLATFORM_OWNER_*` values, and `Invoke-ScriptAnalyzer -Recurse scripts` would cover it; `what-if` can come with the deployment workflows.

## Nits

6. **`MachineAuth__DisabledCredentialKinds__*` (`functions.bicep` `disabledKindSettings`) isn't read by any code on this branch**: there's no such property on `MachineAuthenticationOptions`; it lives on `feat/claude/azure-deployment`. That's fine and fails closed (`IsCertificateHeaderFromClientAllowed=false` means no certificate machine can authenticate), but say in the README that the setting is inert until that branch merges, so nobody thinks certificate kinds are already off.
7. **`Set-GitHubEnvironment.ps1:117-119` doesn't check the token.** If `az staticwebapp secrets list` returns nothing, an empty secret is written (or `gh` fails with an unclear message). Throw on `[string]::IsNullOrWhiteSpace($token)` before `Set-GitHubSecret`.
8. **`Set-FederatedCredential` (`EntraApplications.psm1:77`) compares only issuer and subject.** A credential with the right name but a wrong audience is reported "up to date". Compare `audiences` too.
9. **`Initialize-Subscription.ps1:29-39`**: consider registering `Microsoft.AlertsManagement`; workspace-based Application Insights creates its smart-detection alert rule there, and an unregistered namespace has broken App Insights deployments elsewhere. Also, is `Microsoft.App` needed for Flex Consumption? If not, drop it.
10. **`prod.bicepparam:18`** repeats `authKitAudience = 'https://2s.42for.net'`, which is already the default derived from `trustDomain`. Keep one of them so they can't drift (the param file version is the better one, since it carries the "open point" comment).
11. **`functions.bicep:158`**: `siteConfig` could also set `scmMinTlsVersion: '1.2'` and `http20Enabled: true`; cheap hardening while basic auth is off anyway.
12. **First start of the Function App may race RBAC propagation.** The site is created right after its storage and vault roles; the host can log a few 403s (storage, Key Vault references) for a minute or two. Harmless, but worth one line in the README's checks so it isn't mistaken for a misconfiguration.
13. **Re-running `domains.bicep`** re-PUTs `Microsoft.Web/sites/certificates` (`domains.bicep:50`) while it's bound; if ARM refuses that, the README's "run it again only to rebind" needs "delete the binding first". Note it once the first run proves the managed certificate path.
14. **Key Vault reference without a version** (`CosmosDb__Connection`, `functions.bicep`): App Service refreshes it within 24 h, so a Cosmos key rotation needs a restart of the app after the next `main.bicep` run. Worth a sentence next to "the `cosmos-connection` secret is written from the account's current key".

## Good

- `naming.bicep` as an exported function plus types keeps both entry points on one convention, and adding `dev` really is one more param file.
- Leaving empty client ids out instead of writing `""` (checked against `CustomerKeyProvider`) is exactly right.
- Splitting `domains.bicep` out so normal runs never drop TLS, with the double binding through a module, is the clean way to do it in ARM.
- The app setting names match the options classes I checked (`MachineAuth`, `MachineAuth:Federation:PublicBaseUrl`, `Auth:AuthKit:*`, `KeyValues:Protection:*`, `AzureKeyVaults`, `AzureWebJobsStorage` with `accountName`/`clientId`).
- The scripts are idempotent, strict (`StrictMode`, `$PSNativeCommandUseErrorActionPreference`), and refuse the irreversible mistakes up front (a free tier already taken, duplicate app names, the wrong sign-in audience).
