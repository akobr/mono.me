## Important

1. **Every visitor is written into one shared document, and that document never shrinks.** `JoinAsync` (`src/Platform/Storyteller/Api.Functions/src/V1/ExhibitionHttp.cs` L205–219) calls `JoinAccessPointAsync`. That rewrites `apt.<org>.<project>` and adds one entry to its `AccessMap` per joiner. The write is a transactional batch in the single `access` logical partition (`CosmosAccessService.UpdateMembershipAsync`, L797–872). Nothing removes visitors, and AuthKit self-sign-up makes accounts cheap. As a result:
   - RU cost and latency of every join and every `GET v1/access/exhibition` grow with the visitor count. `FindExhibitionAsync` reads the full document and scans the map on every onboarding load (L133, L147).
   - The document will hit Cosmos DB's 2 MB item limit at some tens of thousands of joiners. After that, every join fails, and so does every other membership change on that project.
   - The owner's member list (`GetAccountProfilesAsync`, `ARRAY_CONTAINS(@ids, …)`) gets slow and costly.
   - Every newcomer contends on one ETag. The retries (3 here × 2 in the service, each reading two documents) soften this but don't remove it.

   **Suggested:** decide this now, because it is cheap before go-live. Options: (a) make exhibition read access implicit, e.g. a flag on the account or a per-account membership document, rather than a map entry on the project; (b) at least set a cap with a clear 409/503 and add a metric or alert on the document's size; (c) prune inactive visitors. If you accept it as a known limit, say so in `access.md` (section Exhibition) and the runbook.

2. **The hosting link in production copy points to a claude.ai share** (`ui.admin/src/app/utils/onboarding.ts` L75–78, `hostingLink`). This link backs a privacy statement ("Customer data stays in the EU"). The PR says nobody has checked the page against the copy. An AI chat share is third-party and mutable, its owner can delete it, and it is not a document you'd want customers to treat as authoritative. **Suggested:** link a first-party page (a sub-processors/EU-hosting page in the docs or on the site), or leave the link out until one exists.

3. **"Continue without the exhibition" after a join-only failure lands on `/orgs` with a bare account** (`composables/useOnboardingEnd.ts` L149–156, and L118–131 in `joinOnly`). From then on, `createAccount` refuses the user, because the account exists. Please confirm that `/orgs` lets an account with no memberships create its first organization and project via `POST v1/access/points`. If it does, add an e2e test for that path. If it doesn't, the user is stuck.

## Nits

- **A Warning on every request when misconfigured** (`src/Platform/Storyteller/Api.Functions/src/V1/ExhibitionHttp.cs` L137, L143, L149). Every newcomer to a misconfigured or not-yet-seeded deployment logs one, so App Insights will be noisy and the 0.15 GB/day Log Analytics cap gets used. Consider logging once per instance, or caching the result of `FindExhibitionAsync` for a short time. That cache would also save a point read per onboarding view.
- **A bare `catch` in `EnsureAccountAsync`** (L177). It also catches `OperationCanceledException` and then does an extra read. `catch (Exception ex) when (ex is not OperationCanceledException)` states the intent.
- **The cancellation token** reaches only the retry `Delay` (L109, L216). `IAccessService` takes no tokens, so this matches the repo, but a cancelled invocation still does every Cosmos call. Worth a follow-up on the interface.
- **The check and the join are separate steps.** `FindExhibitionAsync` checks "the owner is alone" and then `JoinAccessPointAsync` writes, without re-checking in the batch. Someone could become Administrator between the two. The window is tiny and the effect is one Reader join, so a comment is enough.
- **Optional constructor dependencies** (L44–56: `IOptions<ExhibitionOptions>? = null` etc.). `AddExhibition` always registers the options, so the defaults only serve tests. Making them required in production code would surface a wiring mistake instead of a silently disabled exhibition. Optional; this may already be a repo pattern.
- **Delegated actors can join** (`JoinExhibition_ThroughARestrictedActor_Joins`). This means a Storyteller user token or the MCP server can add the user to the exhibition. That's low-risk for Reader, but it is a choice: once the #199/#202/#203 safeguards land, confirm it fits the actor policy.
- **A Try again that can never succeed.** If the exhibition stops qualifying between the wizard's load and the join (it becomes 404), `join()` goes to `joinFailed` and *Try again* keeps hitting 404. You could map a 404 there straight to "continue without".
- **The `safeguardsLive = false` flag** (`utils/onboarding.ts` L32) has to be flipped by hand after a separate API release. A Linear follow-up would keep it from being forgotten.

## Good

- The exhibition is offered only when the configured account is the project's Owner and nobody else is Administrator or Owner. The comment at L121–125 explains clearly why owning is not the same as creating. Thoughtful threat modelling.
- The role and the key never come from the request. Machines get 403 in every build. Startup validation (`ValidateOnStart`, all three settings or none, messages that name settings and never their values) matches the Bicep "all three or none" union.
- The race where the account is created concurrently is handled carefully: if the read after a failed create also fails, the create's exception is the one that goes out. The join is idempotent, and the Cosmos test proves it with unchanged ETags.
- Strong tests: 21 API cases covering config states, retry/conflict codes, cancellation during the delay and Entra IDs, plus a Cosmos test of the bare-account state, broad unit and e2e coverage of the wizard, and accessibility work on focus handling.
- The project description is rendered as text, not `v-html`, so content controlled by the owner can't inject markup.
