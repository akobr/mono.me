# Review of PR #149: [🐛 fix(platform): read the relation arrays of annotations and answer an unreadable body with 400 (424-129)](https://github.com/akobr/mono.me/pull/149)

Reviewer: Harry · Review date: 2026-11-01

**Verdict: approve-ready.** The fix targets the real root cause (System.Text.Json can't create `IReadOnlySet<T>`), puts the converter on the models so every STJ consumer benefits, and is covered by a regression guard that fails if a new set property ships without it. Nothing blocking; one design point on the status code is worth a conscious decision.

Checked locally on `ce895d18`: `RelationNamesJsonTests` passes (109/109). `Api.Functions.Tests` doesn't build on my box because of an existing `OpenApiConfigurationOptions.NamingStrategy` error that also shows up on `main` there, so I relied on CI for the handler tests. At review time `.NET reference (ubuntu-latest)` and `TypeScript SDK` were green, and the Windows .NET job, the UI lint/test/build job and CodeRabbit were still running.

## Blocking

None.

## Important

1. **A model defect now answers 400, not 5xx** (`Api.Functions/src/V1/AnnotationsHttp.cs:976-986`, `DeserializeBody`). Turning `NotSupportedException` into a `JsonException` means a server bug (a model member STJ can't read) is reported to the client as *their* invalid body, and it drops out of any 5xx-based alerting or availability metric. The `LogError` softens that, and with the converter plus the reflection guard in place it should never fire. Still, the honest status is 500 with a sanitized message (no CLR types, no stack). Suggestion: catch `NotSupportedException` separately in `SetAnnotation`/`SetAnnotations` and return `500` with a fixed `ErrorResponse`, keeping the log. If you prefer to keep 400, say why in the doc comment (for example "the client can't succeed anyway") so nobody "fixes" it later.
2. **In the bulk create, the error log fires before the access check** (`AnnotationsHttp.cs:426-431`). `LogUnreadableMember` runs inside the element loop, before `CheckAccessToAnnotationsAsync`, so a caller without write access could produce `Error` log entries if a model defect ever came back. Today nothing triggers it, but moving the log to where `invalidElement` becomes the 400 (after the 403 decision) is free and keeps logs attacker-proof.

## Nits

- `RelationNamesJsonConverter.cs:12` is `internal`, so a source-generated `JsonSerializerContext` in another assembly can't reference it by type. The attribute still works there, so this is fine for now, and the PR already lists it as a follow-up. If an SDK or MCP context ever adds these models, making it `public` is the simple fix.
- `RelationNamesJsonTests.EverySetOfTheModels_HasTheConverter` compares `ConverterType.Name == "RelationNamesJsonConverter"` as a string. If `Abstractions.Annotations` has (or gets) `InternalsVisibleTo` for the test assembly, compare against `typeof(RelationNamesJsonConverter)` instead, so a rename is caught at compile time.
- The guard only matches `IReadOnlySet<string>`. A future `ISet<string>`, `IReadOnlySet<SomeKey>` or `IReadOnlyCollection<string>` with a set backing wouldn't be caught. Widening the check to any property whose type is an `IReadOnlySet<>` generic costs one line.
- `ui.admin/src/app/forms/annotation.schema.ts:118-120`: the comment says "the server ignores their values", but the server now type-checks them on `PUT`/`POST …/{key}`. "The server keeps its own values" is more precise.
- The converter quietly collapses `["prod","prod"]`. That's harmless because the server ignores the values, and it's documented in the PR, but the lifecycle doc line could say so too, for client authors who round-trip.

## Good

- The root-cause analysis is spot on, and fixing it at the model level (not with a per-handler `JsonSerializerOptions` converter) also fixes Api.Web, MCP and any other STJ reader for free.
- `throw new JsonException()` without a message is a deliberate, correct use of STJ's `AppendPathInformation`, so clients get `Path: $.ContextNames`, and the tests assert exactly that.
- `HandleNull => true` with null mapped to an empty set restores the non-nullable contract the models promise. The write side handles a null set and `WhenWritingNull` correctly, and both are tested.
- Ordinal comparer matches how the Cosmos mappings build their sets (`new HashSet<string>(...)`, default ordinal), so there's no case-folding drift.
- The tests are thorough without being flaky: every relation array times every wrong token, case-insensitive member names, members after the array, byte-identical output versus the serializer's own arrays, the 400 path in the handler, and the old 500 for a Usage without `SubjectKey`. The reflection guard is the best part, since it stops this class of bug from coming back.
- OpenAPI was verified unchanged, so no SDK regeneration was needed, and the "Left for later" list (the Api.Web body re-read, the unpaired-surrogate 500s, the stack trace in the second catch) is honest and well scoped.
