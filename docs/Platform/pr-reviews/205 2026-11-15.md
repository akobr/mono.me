## Important

1. **The restricted-ancestor check runs only when there are descendants.** `StorytellerCatalog.ListAsync(scope, …)` (`Hosting/src/Catalog/StorytellerCatalog.cs` ~L219–236) and `DescendantPollingSource.ReadAncestorsAsync` (`Hosting/src/Informer/DescendantPollingSource.cs` ~L185–196) read ancestors only for the listed or held descendants. `AncestorReader.ReadDistinctAsync` uses `known` only when a descendant's key reaches it. Take a machine that is not allowed to require active ancestors (restricted to the target, or below it). It gets an empty, successful `ListAsync`/`ListWithAncestorsAsync` while the target is empty, and a definitive 403 as soon as one descendant appears. A watch has the same problem: if its first poll is empty, it completes, and later the 403 is only logged as a warning every poll while new descendants are never added (`FindInactive` returns the undecided read). The test `ListWithAncestorsAsync_OfNoDescendants_ReadsNoOtherAncestor` pins exactly this. **Fix:** when `RequireActiveAncestors` is set, check the target's own read (`own`/`ancestor`) and the target's ancestor keys (`AncestorReader.KeysOf(scope.Ancestor)`) before the list, whatever the list returns. Then a configuration error fails the same way regardless of data. Add an empty-target test for list and for watch.

2. **The `SubjectTokenType` default differs between code and environment.** The environment path defaults a managed identity to `access_token` (`StorytellerCredentialVariables.ReadFederated`), and so does `FederatedTokenOptions.ForAzureManagedIdentity` (`Sdk.NSwag/src/Credentials/FederatedTokenOptions.cs` L48). Code that writes `new FederatedTokenOptions { ClientId = …, AzureManagedIdentity = new() { Resource = … } }` keeps the property default `jwt` (L36). That is a quiet difference, and if the server checks `subject_token_type` against the federation rule, the exchange is rejected. **Fix:** make the type depend on the source in `FederatedTokenCredential.Create`, for example a nullable `SubjectTokenType` that resolves to `access_token` for `AzureManagedIdentity` and `jwt` otherwise. Or document clearly that the factory is the supported way. Add a test for the object-initializer form.

3. **The managed identity call off Azure: retries, timeout and the shared circuit.** `RequestAzureManagedIdentityTokenAsync` (`TokenEndpointClient.cs` L117) goes through the same pipeline as the token endpoint (L55: *"one pipeline for both clients, so one circuit breaker"*). With the defaults (`MaxRetryAttempts = 3`, `AttemptTimeout = 5 s`), a developer box or a CI agent with `STORYTELLER_MANAGED_IDENTITY_RESOURCE` set but without IMDS tries to reach `169.254.169.254` for about 20+ s per token before it fails. Those failures also count toward the breaker, which then blocks the token endpoint for `BreakDuration`. The reverse also happens: a token endpoint that is down opens the circuit for IMDS. Azure.Identity probes IMDS with a short first attempt for this reason. On the other side, 5 s per attempt can be tight for a cold App Service MSI endpoint. **Suggestion:** give the managed identity request its own pipeline (its own breaker), with a short connect timeout for IMDS when `IDENTITY_ENDPOINT` is not set. Or at least say in the docs what an off-Azure process sees. Note also that IMDS `404/410` are `Unavailable` without a retry (L334), while Microsoft's IMDS guidance retries them (and 429/5xx) with backoff. That is fine at the caller's level, but say so in `authentication.md`.

4. **Read cost of `RequiringActiveAncestors()` in a watch.** Every poll re-reads every distinct ancestor of every held and listed descendant (`DescendantPollingSource` L185). For the main use case, a responsibility's executions across many subjects and contexts, that is O(subjects + contexts + usages + units) point reads every 30 s ± 10 % per watch. That is on top of the list, with at most 4 at once. That is correct, but it can put RU/latency pressure on the API and stretch a poll. **Suggestion:** document the cost in `hosting.md` next to the option. Consider a follow-up that skips an ancestor read when its list fingerprint (`Modified`) is unchanged, or that reads ancestors on a slower cadence than descendants.

## Nits

- **`GetEffectiveTimeZone()` returns the zone untrimmed** (`StorytellerExecutionContext.cs` L121; the mapper keeps it "as stored"). A stored `" Europe/Prague"` passed to `TimeZoneInfo.FindSystemTimeZoneById` fails. The test `TheEffectiveTimeZone_SkipsABlankOne_AndIsAsStored` shows this is on purpose. I'd still trim in the mapper, or say in the XML/comment that callers must trim.
- **Chain status and a missing ancestor.** `GetSubscriptionStatus(now, Chain)` leaves a missing ancestor (404, deleted between the key read and the ancestor read) out of `Chain`, so it can say `Active`. `AncestorReader.FindInactive`, which the lists and the watch use, treats the same ancestor as inactive (`Missing`). It is only a race, but the two "chain status" answers can disagree. Consider `Unknown` (or `Deleted`) when an ancestor read 404s in who am I.
- **A set `IDENTITY_ENDPOINT` without `IDENTITY_HEADER` and without `IMDS_ENDPOINT`** quietly falls back to IMDS (`AzureManagedIdentityEndpoint.cs` L56–62). That is usually a broken host or a copy-pasted env. A debug log, or a hint in the IMDS failure message, would save a support round-trip.
- **`IsOfTheHostNetwork`** (L105) also accepts `10/8`, `172.16/12` and `192.168/16` over `http`. That follows the documented deviation, and the variable is set by the platform, so the risk is low. Still, App Service and Container Apps use only loopback and link-local. If nothing needs RFC 1918, narrowing to loopback and link-local keeps the header off the wider VNet.
- **`FederatedTokenOptions.SubjectTokenPath`** went from `required string` to `string?`. That is binary-compatible, but consumers that read it get a new nullable warning, which breaks builds with warnings-as-errors. Mention it in the package release notes. The same goes for the new values in `StorytellerSubjectTokenSource` and the default interface members on `IStorytellerCatalog` (both additive, fine).
- **`FromFederatedTokenFile`** (`StorytellerCredential.cs` L52) now takes any source. Consider `[EditorBrowsable(Never)]` or `[Obsolete]` pointing to `FromFederatedToken`, so the misleading name fades out.
- **`CatalogDefaults`** uses `DateTimeOffset.UtcNow` (L41) and calls `GetAsync` one at a time. Both are documented and fine for test doubles. Just make sure no production decorator of `IStorytellerCatalog` relies on the defaults, or it silently loses restrictions and `TimeProvider`.
- **The provider-source fingerprint**: two different `SubjectTokenProvider`s of one machine share a cache identity. That is documented and harmless while the machine (client id) is the principal. Keep it in mind if a provider can ever pick a different principal.

## Good

- Everything is additive, with default interface implementations, so existing test doubles of `IStorytellerCatalog` compile, and the `ToString()` texts the fingerprint depends on are unchanged and pinned by tests.
- `AncestorReader` cleanly moves the ancestor logic out of `ExecutionContextService`, so who am I, the lists and the watch now share one rule. `Task.WhenAll` everywhere means no unobserved failures. A failure picked "first by key" makes the thrown error deterministic.
- Security of the managed identity request is well thought through: a separate client with no proxy (forced after the user callback), no redirects, the identity header never in messages, `UserInfo` refused, and `http` to a DNS name refused. `ProviderSource` maps exceptions carefully (caller cancellation vs. provider timeout) and never leaks the provider's message.
- `Interlocked.CompareExchange` for the lazy `Chain`, and one `Decide` routine, so `GetSubscriptionStatus` and `FindInactiveAnnotation` cannot disagree.
- Strong tests: +214 in Hosting and +120 in the SDK, including proxy, open-circuit, IMDS-updating and restricted-ancestor cases. The deviations from the spec are listed with reasons.
