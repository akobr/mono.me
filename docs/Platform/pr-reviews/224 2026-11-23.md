## Important

1. **The same identity bug is still in the Key Vault bindings.** See `src/Platform/Storyteller/Binding.Azure.KeyVault/src/EntryPoint.cs` L25–29. In production, `AddAzureKeyVaultBindings` still registers `new ChainedTokenCredential(new ManagedIdentityCredential(), new EnvironmentCredential())` for every `SecretClient`. `Api.Functions/src/Program.cs` L195–197 wires it up with the production environment. The Function App has only its user-assigned identity (`functions.bicep` L252–255). So a configuration binding that resolves a Key Vault secret will fail with the same *"Unable to load the proper Managed Identity"* error. The PR title promises "the Key Vault identity fix", so it should cover this path too.
   *Fix:* use `KeyVaultClients.CreateCredential(isProduction, configuration["AZURE_CLIENT_ID"])` there, or move `CreateCredential` and `GetManagedIdentityId` into a small shared helper. Then the two packages cannot drift apart again. `CustomerKeyProvider.cs` L244–246 and `McpActorCredential.cs` L97–103 already handle the user-assigned id correctly.

2. **A seed with options can quietly run with the defaults** (`src/Platform/Aspire.Host/src/DbSeedCommands.cs` L226–277). `StartWithAsync` puts the options into `PendingInvocation` and clears them in `finally`. That happens after the 2-minute `StartTimeout` (L29, L254), when the command is cancelled, or when the start fails. The arguments and environment callbacks only run when the process is actually launched. Both resources `WaitFor(cosmos)`, and the first start of the emulator (especially vNext) can take more than 2 minutes. If the launch comes after the options are cleared, `db-seed` runs `seed showcase`, maybe with `--owner`, and `db-creator` runs with the default base account. The dashboard reports only "did not start within 2 minutes". For a command whose options include `--force` and the owner of a new organization, running a different seed than the one you asked for is the wrong failure mode. It also writes data, because the dry run is lost too.
   *Fix:* consume the options when they are read. In the args/env callback, use `Interlocked.Exchange(ref _value, null)`, or set a "consumed" flag. Only clear them in `finally` if they were never consumed **and** the resource has really stopped waiting (FailedToStart, or a Stop). Another option: on timeout, do not clear. Instead, stop the resource (`KnownResourceCommands.StopCommand`) before you return the failure. That way a later launch cannot pick up the defaults.

3. **The wait predicate can match an old `FailedToStart`** (L258–262). The `StartTimeStamp` guard covers `Running`, `Finished` and `Exited`, but not `FailedToStart`. If the previous attempt failed to start and `ExecuteCommandAsync(Start)` returns before the snapshot moves to `Starting`, `WaitForResourceAsync` matches the stale state at once. Then the options are cleared before the launch (same result as item 2) and the command still returns **Success**.
   *Fix:* also require a new snapshot for `FailedToStart`. Compare the timestamp, or record the snapshot version before you start. Return `Failure` when the state you reach is `FailedToStart`.

4. **Relative `--path` is checked against a different directory than the one it runs in** (L95). `Directory.Exists(path)` resolves a relative path against the AppHost's working directory. DbCreator runs with its project directory as its working directory. So `data/` can pass validation and then fail in DbCreator, or the other way round.
   *Fix:* in `SeedAsync`, normalise it with `Path.GetFullPath(path)` (or relative to `builder.AppHostDirectory`) and pass the absolute path. Alternatively, say in the input's description that the path must be absolute.

## Nits

- `DbSeedCommands.cs` L153, `AppHost.cs` L58: **Create with options…** pre-fills the base account with the AuthKit staging user even when `seedStagingAccounts` is false. `WithSeedOptions` gets `defaultSeedOwner`, which respects that flag, but `WithCreateOptions` gets `authKitStagingOwner` with no condition. As a result, the dialog's defaults are not the same as the plain Start (legacy sub plus staging user as second owner). The docs describe this, so it may be intended. If not, pass `defaultSeedOwner` for consistency.
- `DbSeedCommands.cs` L234–243: the `IsBusy` check and `TrySet` are not atomic. This is harmless, because `TrySet` is the real guard and `UpdateState = IdleOnly` disables the button. A comment would help the next reader.
- `DbSeedCommands.cs` L281: `IsBusy` does not count `KnownResourceStates.Stopping`. Starting with options while a stop is still in progress will race.
- `DbSeedCommands.cs` L69: the data sets are discovered once, when the host is built. A set folder added while the host runs shows only after a restart. That is fine, but the spec should say so.
- `KeyVaultClients.cs` L39 and L53: `CreateCredential` and `GetManagedIdentityId` became `public` only for the tests. Consider making them `internal` with `InternalsVisibleTo` for the unit test assembly, so the package's public API does not grow.
- `KeyValueProtectionEntryPoint.cs` L13: `ManagedIdentityClientIdVariable` is a public const of this package, and it is the name the SDK already reads. Fine, but if item 1 is fixed through a shared helper, define it there once.
- `KeyVaultClientsTests.cs`: the identity assertions compare `ManagedIdentityId.ToString()`. They depend on how Azure.Identity 1.21 formats it. If that ever returns only the kind, `TrimsTheClientId` would pass without checking anything. A narrow check that is less brittle: give `CreateCredential` a `ManagedIdentityId` and test that, or wrap the id in your own record. Also, `using System;` is redundant with `ImplicitUsings`.
- `42.mono.slnx`: the new `KeyValues.Azure.KeyVault/test` entry is placed after `KeyValues.ClientEncryption/src`. Put it directly after `KeyValues.Azure.KeyVault/src` to keep the list sorted.
- `prod.bicepparam` L76–78: the production owner account id is now in the repo. It is not a secret, and other ids are already committed, so it is just worth noting. The comment "All three or none" is useful.

## Good

- The root cause analysis of 2S-API-3 is accurate. `functions.bicep` L126 already sets `AZURE_CLIENT_ID`, so the fix needs no infrastructure change. Treating a blank id as "system-assigned" and trimming it are sensible.
- Refusing the emulator in production is kept and now has a test.
- `PendingInvocation<T>` with `Interlocked.CompareExchange` is a tidy single-flight guard. Building the arguments as a list, with no shell string, rules out injection from the dialog.
- The validation (a set or a folder, an existing folder), `UpdateState = IdleOnly`, and logging the final command line make the commands easy to use and to debug.
- The docs (local-development, runbook, cookbook, decisions with its note on the rename, Deployment README) were all updated in the same PR.
