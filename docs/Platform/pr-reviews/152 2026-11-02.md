# Review of PR #152: [feat(platform): self-preparing admin UI under Aspire, and seed of the ui-tests organization](https://github.com/akobr/mono.me/pull/152)

Reviewer: Harry · Review date: 2026-11-02

**Verdict: needs changes, small ones and nothing blocking.** The idea is right and the diagnosis of the old `WithNpm(install: false)` is spot on. The prepare scripts are simple, dependency-free and stamp-driven, and the seed now merges instead of overwriting. Three things should change before merging: the Clean reinstall command crashes in exactly the broken state it exists for, its wait can hang, and the hardcoded staging AuthKit accounts are seeded into every database DbCreator touches. The rest are robustness and tidy-up points.

**CI at review time:** ".NET reference (ubuntu-latest)" and "TypeScript SDK" passed. ".NET reference (windows-latest)", "Lint, type-check, test, build" and CodeRabbit were still running. CodeRabbit had posted only its in-progress placeholder and there were no review comments. I reviewed the diff and the surrounding code but did not run the AppHost or DbCreator.

## Blocking

None.

## Important

1. **Clean reinstall throws when a stamp's folder is missing** (`src/Platform/Aspire.Host/src/UiAdminPreparation.cs` L74-77). `File.Delete` ignores a missing file but throws `DirectoryNotFoundException` when the parent folder doesn't exist (at least on Windows, the main dev machine here). That is exactly the state that sends someone to this command: `npm ci` failed and left no `node_modules`, or the tsup build failed after `clean: true` wiped `dist`. The command then fails with an unhandled exception and ui-admin stays stopped. Fix: delete only what exists, for example `var path = Path.Combine(platformDirectory, stamp); if (File.Exists(path)) File.Delete(path);`.

2. **`RunToCompletionAsync` can wait forever** (`UiAdminPreparation.cs` L94-116). The predicate needs `StartTimeStamp >= requestedAt - 1s`. A step that ends in `FailedToStart` (for example `node` not on `PATH`) may never get a `StartTimeStamp`, so the wait never completes, and the dashboard command spins until the AppHost stops. The comparison also mixes the AppHost clock with snapshot times and depends on a one-second tolerance. Suggestion: subscribe before issuing the start (`WatchAsync` or `WaitForResourceAsync` started first) and accept the first terminal state seen after a non-terminal one, or at least accept `FailedToStart` without a start time and add a generous timeout such as 15 minutes linked to the command token.

3. **The second `WithNpm` relies on Aspire internals** (`UiAdminPreparation.cs` L35-39). The comment is honest: it works because the installer "reads from the last annotation at start", and `.Last()` picks the installer resource from the annotation list. Neither is a documented contract, and [PR #151](https://github.com/akobr/mono.me/pull/151) moves Aspire from 13.1.2 to 13.6, so whichever merges second has to re-verify this by hand. Please pin it down: add a small AppHost test with `DistributedApplicationTestingBuilder` that asserts there is exactly one `ui-admin-installer`, that its args are `run prepare:local`, and that it waits for `ui-admin-sdk`. Alternatively, call `WithNpm(install: false)` and add your own `AddExecutable("ui-admin-installer", "npm", ..., "run", "prepare:local")` with `WaitForCompletion`, which avoids the internals entirely.

4. **Staging AuthKit accounts are seeded everywhere** (`src/Platform/Storyteller/DbCreator/src/Logic/SeedAccounts.cs`, `CoreDbStructureBuilder.cs` L27-41). `AuthKitOwner` and the eight `user_01M6C...` subs come from the AuthKit staging environment, yet DbCreator grants them Owner on `42dotnet` and `42dotnet.main` in whatever Cosmos account it points at. Today that is the local emulator, and I found no pipeline that runs DbCreator, but nothing stops someone from running it against a shared or cloud database. Then a personal staging identity and eight test logins with known emails become owners or members of real organizations. Gate it behind configuration, for example `Seed:AuthKitStaging` defaulting to off outside Development, or a `--seed-ui-tests` switch, and keep the ids in `appsettings.Development.json` rather than in code.

5. **The seed's read-modify-upsert can lose data** (`src/Platform/Storyteller/Backend.CosmosDb/src/Data.cs` L79-99). It reads the whole `AccountEntity` or `AccessPointEntity`, changes one map entry and upserts the whole document, with no ETag. Two consequences follow. A change made by the API between the read and the write is silently overwritten; the API's own writers (`CosmosKeyValuePolicyStore`, `CosmosKeyValueUsageStore`) use `IfMatchEtag` for exactly this reason. Any property on the stored document that isn't modelled on the entity is also dropped. The cleaner fix for existing documents is a patch, `PatchItemAsync(id, pk, [PatchOperation.Set($"/AccessMap/{accountId}", role)])` (and `/AccessMap/{key}` on the account), which is atomic and touches nothing else. Create the document only on 404. If you keep the upsert, pass `IfMatchEtag` from the read and retry once on 412.

## Nits

1. **One person, two names** (`SeedAccounts.cs` L13-17 vs `Constants.BASE_ACCOUNT_NAME`). `AuthKitOwner` uses `"Ales Kobr"`, while the base account uses `"Aleš Kobr"` with the same user name. When `BaseAccount:Id` is set to that AuthKit sub, as the docs suggest for AuthKit sign-in, the loop writes the same account twice and the name without the diacritic wins. Reuse `Constants.BASE_ACCOUNT_NAME`, and skip the second owner when its id equals the base account id (`owners.DistinctBy(o => o.Id)`).
2. **The seed resets profile fields** (`Data.cs` L86-88). Every run overwrites `UserName` and `Name` on existing accounts. Prefer keeping the stored values when the account already exists, which the patch approach from Important 5 does for free.
3. **Dead code.** `Data.CreateCoreAccess`, `Create.BaseAccount` and `Create.BaseAccessPoints` no longer have callers. Remove them, or point a comment at `SeedAccountAccessAsync`.
4. **Misleading parameter name.** `SeedAccounts.Roles(role, params string[] organizations)` also receives project keys (`42dotnet.main`, `ui-tests.automation`). Rename it to `accessPoints`, as `SeedAsync` already does.
5. **The UI script contradicts the README** (`src/Platform/ui.admin/src/build/prepare-local.mjs` L22-25). It exits with an error when the SDK build stamp is missing, even if the SDK was built with a plain `npm ci && npm run build`, which the README says still works. Either fall back to checking that `dist` exists and use its content hash as the SDK part of the stamp, or adjust the README to say the SDK has to be prepared with `prepare:local`.
6. **Concurrent Clean reinstall** (`UiAdminPreparation.cs` L51-53). The command is disabled only while ui-admin is `Starting`, so a second click during the minutes `npm ci` runs starts a second reinstall in the same folders. Guard it with a static `Interlocked` flag or `SemaphoreSlim(1)` and return `CommandResults.Failure("A clean reinstall is already running.")`.
7. **Prerelease Node versions** (both `prepare-local.mjs`, `versionNumber`). `'23.0.0-pre'.split('.').map(Number)` yields `NaN`, so the version check passes silently. Strip anything after `-` first, or use `process.versions.node` with a regex.
8. **`shell: true` with an args array** (both scripts, `run`). On Windows this triggers Node's DEP0190 warning on Node 24 and newer. The args are constants, so it's safe, but joining them into one command string, or spawning `npm.cmd` through `cmd /c`, keeps the output clean.
9. **Publish mode changed quietly** (`UiAdminPreparation.cs` L25-28, `AppHost.cs`). The old `WithNpm(install: false)` applied in every mode. Now publish mode returns before any `WithNpm`, so it falls back to `AddViteApp`'s default installer. That's probably what you want, but say so in the comment.
10. **Tests.** There are none for `SeedAccountAccessAsync`. `Backend.CosmosDb.UnitTests` already has a Cosmos fixture: one test that seeds twice, checks that a pre-existing member and the `KeyValues` and `MachineAuthentication` policies survive, and checks that the result is idempotent would cover the most important promise of this PR.

## What's good

- The root cause in the PR description (the installer was turned into a manual-start resource) is exactly right, and the fix keeps Aspire's own installer instead of fighting it.
- The SHA-256 stamps over the lockfile and the build inputs make the second start a no-op. Writing the build stamp after tsup's `clean: true` is the correct order, and the "only the SDK changed" path that reinstalls just `@42for.net` is a nice touch.
- The scripts are plain Node with no dependencies, so they work on a clean clone before anything is installed.
- The new resources run only in run mode, with `ExcludeFromManifest` and a parent relationship, so the dashboard stays tidy.
- The seed is now additive and idempotent, so running DbCreator again keeps members added through the UI. That's a real improvement over the old overwrite.
- The docs are thorough: CLAUDE.md, local development, both READMEs, plus a spec and its review.
