## Important

1. **The runbook's checks now fail in production.** `docs/Platform/Deployment/runbook-mcp-server.md` L253 expects "Scale to zero … no replica" after 10 idle minutes. L254 expects "Cost … 0 USD". With `mcpMinReplicas = 1`, both are wrong. Suggested fix: change the first check to "one replica (`mcpMinReplicas = 1`); none with 0", and the cost check to about 4–5 USD a month. L114 (phase 4 what-if: `minReplicas` 0) is history for the first creation, but a fresh run with today's `prod.bicepparam` would show 1. A short "(1 since 2026-11-22)" note avoids confusion.
2. **The cookbook's cost table no longer adds up.** `cookbook-azure-production.md` L718 now shows "about 4–5" USD, but the **Total** row at L719 still says "about 0–2 USD". It should be about 4–7 USD. L721 ("What raises it: … The budget of step 2 warns at 2.50 USD") should list the always-on MCP replica. The sentence about warnings at 2.50 USD only matches the 5 USD budget described in step 2 (L97). `prod.bicepparam` L65 actually sets `budgetAmount = 50`, so production won't start sending alerts, but the cookbook now says that 4–7 USD a month runs into its own 5 USD budget. Either update step 2 and L721 to the real 50 USD, or note the difference.
3. **Other stale "scale to zero" descriptions.**
   - `modules/mcp.bicep` L1–5, the file header: "scaled to zero between calls … inside the monthly free grant". Reword it to depend on `minReplicas`, the way the new comment at L232–233 already does.
   - `cookbook-azure-production.md` L622, the resource table: "0 to 3 replicas". It should say "`mcpMinReplicas` (1 in production) to 3".
   - L656, the manual `az containerapp create … --min-replicas 0`: fine as an alternative, but add a note or use `1` to match production.

## Nits

- `main.bicep` L355: the min-vs-max guard sits inline in the module's parameters. Every other MCP check (L182–195) is a `var` with `fail()` next to the parameters. A `var mcpMinReplicasChecked = mcpMinReplicas > mcpMaxReplicas ? fail(...) : mcpMinReplicas` there would match that style and keep the module block declarative. It behaves the same either way, and is evaluated only when `mcpEnabled` is true, which is fine.
- **The idle rate assumption.** The 4–5 USD figure assumes the replica is billed at the idle rate. Azure only does that when the replica uses less than 0.01 vCPU and less than 1,000 bytes/s of network. The TCP probes and a quiet ASP.NET Core host should stay under those limits, but background timers (token or JWKS refreshes, telemetry flushes) could push it toward the active rate. That still costs no more than about 14 USD, as the PR says. Worth checking in Cost Management a week after the deploy. The runbook's cost check (item 1) is a good place to note that.
- `mcp.bicep` L61: the new `minReplicas` parameter has a `@description`, but the existing `maxReplicas` next to it still has none. Add one for symmetry.
- The `@maxValue(10)` on `mcpMinReplicas` duplicates the max's limit. That's harmless, since the `fail()` already enforces min ≤ max, but it could just be the same range as `maxReplicas`.

## Good

- Default `0` keeps every environment except production unchanged. Only the production parameter file opts in, with a comment explaining why and how to go back.
- The cost math is right. 0.25 vCPU and 0.5 GiB over 30 days come to 648,000 vCPU-s and 1,296,000 GiB-s. Less the free grant, at the idle rates, that is about 1.4 + 2.8 ≈ 4.2 USD, and about 14 USD at the active vCPU rate.
- The deploy notes are precise: the expected what-if diff (`template.scale.minReplicas` 0 → 1), the new revision, and the warning not to run it during a `Platform.Storyteller.Mcp` deployment. The image is kept through `mcpAppExists`, so the run doesn't roll the image back.
- The fail-fast `fail()` check stops the run before anything is written, matching the template's existing approach to validation.
