# Review of PR #143: [🐛 fix(platform): bounded binding parser and value-free binding errors (424-99)](https://github.com/akobr/mono.me/pull/143)

Reviewer: Harry · Review date: 2026-10-31

**Verdict: approve-ready.** The fix does what the ticket asks. Nothing on the `@` string path can recurse without a bound any more, every failure of a binding's content now answers `422` with the path and no expression, and the messages and logs stay free of values. The follow-ups below are worth tracking, but none of them blocks the merge. CI had not reported any checks on `5498907c` when I reviewed.

## Blocking

None.

## Important

1. **The generic `500` path still serializes the whole exception into the body.** `ExceptionHandlingMiddleware.cs:56` writes `Error = exception`, so the body carries the stack trace and every inner message, and `:41` logs the full exception. This is pre-existing. It matters here because the PR's guarantee only holds while every failure in the binding pipeline is a `BindingException`. Anything else that escapes the evaluator, such as a Newtonsoft exception type outside the list in `JsonQuery.cs:104` (a `NullReferenceException` on some odd query, for example) or a source or function that throws a non-binding exception with a computed key in its message, lands on that path. Drop `Error` from the `500` body, or at least leave it out outside Development, and pin that with one test that throws a non-binding exception from a fake function.
2. **The regex timeout applies to one value, not to the whole read.** `JsonQuery.cs:26` limits one `=~` match to 200 ms, but a filter over N values can take N × 200 ms, and one stored document can hold many `@config(...)` strings. The PR's "Left for later" section already says this. I'd still open a ticket for one deadline per read (a `CancellationToken` or the `EvaluationMeter` deadline handed to the string executor), so the string path gets the same per-request bound the object path has.
3. **`EngineMessages.ForJsonE` lets every message through except the four it knows about** (`EngineMessages.cs:33-58`). I checked the vendored fork: it builds exactly 10 interpolated messages today, and the rest are either authored text (`JsonE.cs:246`, `JsonNodeExtensions.cs:51/54`) or already handled. One example is `object has no property "{segment}"` in `ValueAccessor.cs:220`, where an `ExpressionSegment` prints its type name and not the evaluated key. So it is correct now, but a future sync of the fork can quietly add a message that quotes a value. Add a guard test that counts the `Exception($"` sites under `Binding.JsonE/src` (or lists them) and fails when that set changes, so whoever syncs the fork has to revisit `EngineMessages`.

## Nits

1. **The JSONPath count checks also count characters inside quoted names.** `JsonQuery.cs:80` and `:85` refuse `$['a..b']` or `$['$price']`, and the `.`, `[` and `(` count also includes the dots of decimal literals in filters. That is a fine trade-off for safety, but give `binding.md` one sentence saying that quoted names count too, so an author who hits it isn't surprised.
2. **The middleware log no longer says anything about the cause** (`ExceptionHandlingMiddleware.cs:121`). Code and path are the right call for safety, but adding the innermost exception's type name (for example `JsonException` or `RegexMatchTimeoutException`) would make triage much easier without exposing a value.
3. **`Parser.Enter()` (`Parser.cs:77`) increments `_depth` before it throws, outside the `try`/`finally`,** so the counter stays off by one after a limit error. That's harmless because a parser instance is single-use, but moving the increment into the `try` (or decrementing before the throw) keeps the invariant obvious if someone reuses the parser later.
4. **The evaluator restarts `depth` at 1 for interpolation parts and math operands** (`BindingEvaluator.cs:245`, `:289`) and does not count math parentheses, while the parser counts both on one counter. The class doc says the parser is the real bound and the evaluator only guards hand-built ASTs, which is fine. A one-line comment at `:289` saying why the counter restarts would save the next reader a detour.
5. **`BindingExecutor.cs:103`**: `innerException: null` is the only call site that spells it out. Use the overload without an inner exception if there is one, or keep it for symmetry; either way is fine.

## Good

- `BindingExecutor` keeps the exception types now (limit, then evaluation) instead of flattening everything into `BindingException`. That fixes the real cause of the `500`, and the raw expression no longer appears in messages.
- `EvaluateChainAsync` walks the left spine in a loop and keeps the same evaluation order, which handles the 100,000-node chain without any stack tricks.
- Reporting failures inside emitted envelopes at the stored envelope's path, with a fixed message, closes a leak that is easy to miss. The `emitted` flag on `ObjectBindingEngine.Evaluate` also suppresses JSON-e text whose definition was computed.
- Good catches: `BigInteger` operands, `decimal.TryParse` for oversized literals, the `Enum.IsDefined` check after `Enum.TryParse` (numeric strings), the JSON Pointer escape error that now gives an offset and not the token, and the regex timeout (Newtonsoft has none by default).
- The tests are thorough. They cover the ticket's 40 KB and 10,000-level inputs, deep computed queries, exponential query shapes, every JSON-e message site, and end-to-end middleware tests with a capturing logger that check that neither the body nor the log holds the secret.
- The limits are kept in step with the MCP reader and pinned on both sides.
