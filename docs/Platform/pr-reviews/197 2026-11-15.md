Nothing that the old descriptions said was lost. The theory `Detail_KeepsWhatTheDescriptionSaid` pins the moved parts. The detail of `kv delete --permanent` ("every version") is still in the command's own description.

## Nits

1. **The out-of-scope commands are now easy to finish.** The description leaves `kv policy rotate`, `byok-setup`, `byok-verify` and the `kv recipients` changes out "pending a check against the API". I did that check: all six endpoints (`KeyValuePolicyHttp` lines ~115, 138, 165, 224, 264, 302) call `KeyValueAuthorization.CheckAdministratorAsync`. So each is Administrator-only and never a machine. They can take "(for administrators)" in a quick follow-up. Only `points grant`/`revoke` still needs a look. *Suggestion:* open a Linear follow-up so the note covers every Administrator-only command. The current test only checks the notes that exist. It does not check for missing ones.
2. **There are brittle spots in `RoleNoteTests`** (`src/Platform/Cli/test/Commands/RoleNoteTests.cs`):
   - `notes.ShouldBeGreaterThanOrEqualTo(13)` is a magic floor. A comment saying where 13 comes from (the 11 changed commands plus export/import) would help the next person who removes a note.
   - `ParentList_GivesTheCommandOneLine` indexes `lines[index + 1]` without a bounds check. If the command were ever the last line of its parent's help, the test would fail with `ArgumentOutOfRangeException` instead of a readable assertion. Use `index + 1 < lines.Count ? lines[index + 1] : string.Empty`.
   - `Help_StartsWithTheDescription_…` asserts that the line just before the detail starts with `-?|-h|--help`. That means it assumes McMaster always renders the help option last. That's true today, but a convention or an inherited option could change it. Asserting that the line before the detail is an option line (`^\s+-`) would be enough.
3. **`RoleInParentheses` uses `RegexOptions.IgnoreCase`.** It would also flag ordinary prose such as "(owner of the key)" or "(reader-only view)" in a future description. That may be what you want as a guard, but the failure message ("a role in parentheses") could confuse someone. Dropping `IgnoreCase` would match only the capitalised role names, which is the old style this test exists to catch.
4. **There is now one `internal const string HelpDetail` per command, each with the same two-line comment and the same final sentence pattern.** That's fine, and it's consistent with #171. If more of these appear, a small `RoleDetails.UserOnly("read the audit trail")` helper can't be used, because `ExtendedHelpText` needs a constant. So keeping it as is is the right call. I'm only noting this so nobody tries to "DRY" it later.
5. **`HelpTexts.Command<TRoot>` now matches aliases too (`Names.Contains`).** This is a small behaviour change for `TransferHelpTests`. It is harmless, but `Single` would throw if a sibling's alias ever matched another sibling's name. That's unlikely, and McMaster would reject it at build time anyway.

## Good

- Moving the long text to `ExtendedHelpText` keeps each parent list to one line per command. The narrow option column can no longer split "(for" / "administrators)."
- `NoNote_BreaksAcrossLines_InAnyHelp` renders the help of every command at 80 columns. That's a cheap, strong guard.
- The `HelpTexts` helpers moved out of `TransferHelpTests` cleanly, with no duplication left behind.
- The paragraph in `docs/42for.net/cli/sform.md` explains the "lowest role" convention and that an Owner can run what is for administrators. That was the one ambiguity of the new wording.
