# Review of PR #219: [✨ feat(platform): Copy and compare annotations and configurations between views in the admin UI (424-309)](https://github.com/akobr/mono.me/pull/219)

Reviewer: Harry · Review date: 2026-11-22

**Verdict: approve-ready once CI is green and one copy has been tried between two views of a real project.** Nothing is blocking. The copy engine is careful in the places that matter. It refuses to write to an unlisted view, it never re-creates a deleted key, it creates ancestors first, it guards updates with a whole-document `test` + `replace`, and a 401/403 ends the run. The open points are three gaps in its concurrency guarantees and one API bug that this PR works around instead of fixing.

## Important

1. **Creating a configuration with POST has no concurrency guard, and on a race it merges instead of replacing.** See `utils/view-copy.ts` l.341–347. When the target has no own document, the copy calls `setConfiguration` (POST). `ConfigurationHttp.SetConfiguration` takes no `If-Match`/`If-None-Match`, and, as the comment on l.344 says, it *merges* into an own document that has members. Say someone writes an own document in the target between the copy's read (l.330) and the POST. The result is then a merge of both documents, and it is reported as **Created**. The PR description says configurations are "guarded by the `test` of their patch", but that is only true for the update path.
   *Fix:* when `stored.version > 0` (an empty "Create empty" document is stored), use the same `patchConfiguration([{ op: 'test', path: '', value: {} }, { op: 'replace', path: '', value: document }])`, which is fully guarded. For `version === 0` the window stays open. Either compare the returned `Content` with `document` and report **Failed** ("changed meanwhile") when they differ, or add `If-None-Match: *` support to `SetConfiguration` in a follow-up. At minimum, change the "Known limits" wording.

2. **A check before production does not pin what the copy writes.** See `components/views/ViewCopyDialog.vue` l.150–155 and l.171–226. `needsCheck` only requires that *a* plan exists for the current options. The real copy then reads the target again and decides afresh, because `ViewCopyResult` does not record what the check saw. If the target changes between **Check** and **Copy** (which can be minutes apart), production can get writes the plan never showed, while the button still says "Copy N to default". The comparison page already solves this with `expected` (`compare.selection.vue` l.203–225).
   *Fix:* have the dry run collect the stamp or version it read per key (`annotationStamp(stored?.value)` / `stored.version`) into the result. Pass that as `expected` to the copy that follows the check, merged with `props.expected`. A key that moved is then **Skipped** with "It changed in default since it was compared", which is the behaviour the production gate implies.

3. **The API's JSON Pointer bug is worked around, not fixed or tracked.** See the spec l.45 and the spec review l.134: "The API does not decode the `~0` and `~1` of a JSON Pointer". That means the existing configuration editor (`utils/json-patch.ts` → `buildPatch`) already writes the wrong member today for any name containing `/` or `~`. That is a live data-corruption bug in the editor, outside this PR. `JsonExtensions.ApplyPatch` hands the patch to JsonPatch.Net (`ParsePatch`, l.179–191), which normally decodes RFC 6901 escapes, so the root cause may be somewhere else (body handling, a version quirk). It is worth a 10-minute look.
   *Fix:* add a failing test in `JsonPatchTests` (`replace` at `/a~1b` must change member `a/b`), and open a Linear issue for the API or the editor. The root-level replace in this PR is fine either way.

4. **Updating an annotation across origins uses `If-Match: *`.** See `utils/view-copy.ts` l.269–272. This is already listed in "Known limits". It is also the most likely way to silently lose a concurrent edit in production. The stamp check only helps from the comparison page (and from the dialog once item 2 is done).
   *Fix:* make `ETag` readable across origins with `Access-Control-Expose-Headers`. The App Service/Functions platform CORS may not be able to set that header, so the app or a proxy may have to send it. The code already prefers `stored.etag` once it can read it. I'd at least track this as a follow-up.

## Nits

- **The compare page preselects `default` from memory, but the dialog never does.** See `pages/.../modeling/compare.selection.vue` l.59–72 (`names.find((name) => name === last)`) vs `ViewCopyDialog.vue` l.75–79 (`!isDefaultView(name)`). A comparison only reads, so this is harmless, but **Copy N to default** is then one click away with a fixed target. For consistency, use the same rule, or keep it and add a comment saying it's deliberate.
- **`instant()` drops sub-millisecond precision.** See `utils/view-documents.ts` l.39–46 and l.63–64. `Date.parse` truncates .NET's 7-digit fractions, so `ValidFrom`/`ExpiresAt` values that differ by less than 1 ms compare as **Identical** and a copy reports **Unchanged**. That is unlikely to matter, but a comment saying so would help, or compare the trimmed ISO strings when both carry an offset.
- **The line diff runs synchronously in a `computed`, and can be slow.** See `utils/line-diff.ts` (`maxEdits = 8_000`, Myers O((N+M)·D)) and `composables/useViewCompare.ts` l.300–315. Every configuration gets two diffs (own and effective), up to 100 keys, all on the main thread. With a few large rewritten documents, the page can stutter while it loads. A lower `maxEdits` (e.g. 2,000) before falling back to `unorderedStats` would keep it snappy. The counts are only badges.
- **`files` is a `computed` with side effects.** See `useViewCompare.ts` l.352–371: it mutates `kept.own`, `kept.effective`, `kept.file` and reassigns `keptByKey`. It works, and the memoisation is well reasoned, but Vue doesn't guarantee when a computed is evaluated. A `watch(..., { flush: 'sync' })` into a `shallowRef` would make the caching explicit.
- **`view-transfer` store `read()` doesn't validate list items.** See `stores/view-transfer.ts` l.27–30. It checks `Array.isArray(entry[1])` but not that the items are strings, so a tampered `sessionStorage` entry would reach `uniqueKeys`/the API as non-strings. Add `entry[1].every((k) => typeof k === 'string')`.
- **The `$remove`/`$patch` guard only checks top-level members.** See `utils/view-copy.ts` l.303–311. That matches `ApplyPatchRequested`/`RemoveRequested`, which only look at the root, so it is correct. A one-line comment saying "top-level only, as the API" would stop someone from "fixing" it into a deep scan.
- **A copy is strictly sequential, with about 3–5 requests per key.** A 100-key copy to a cold API is several hundred round trips. That's fine for now, but the progress text could show an estimate, or reads (not writes) could reuse `createLimiter`.
- **`ConfigurationsPage` column constants shifted by one** (`SelectColumn = 0`). I checked `ConfigurationNavigationTests` and `ConfigurationCreateTests`: they use the constants, so nothing breaks. The deployed-UI suite was not run, as the PR says.

## Good

- **Safe failure defaults throughout.** The target must be a listed view (`view-copy.ts` l.384–388), and `useOtherViews` filters out discovered views. Deleted keys and deleted ancestors are looked up in batches of 100 before any write (l.390–397). Creates go under `If-None-Match: *`. A copy never deletes. 401/403 ends the run, while any other failure is one row.
- **Whole-document `test` + `replace` for configurations**, with three new backend tests. They pin root replacement, a 412 on a changed document, and that member order and `2.0` vs `2` don't count as a change. The last one matters because the browser sends back what it parsed.
- **Honest comparison semantics.** Annotations are compared by their editable content in the order of the export, with labels as a set and dates as instants. Configurations are compared canonically, whatever the member order. Integers beyond 2^53 are never reported as identical and are never copied.
- **Query keys line up with the existing path-prefix invalidation.** The keys of `useViewCompare.read` start with `['v1', org, project, view, 'annotations'|'configuration', key]`, so `invalidateAnnotation`/`invalidateConfiguration` refresh the comparison after a copy. A separate `includeDeleted` key for the target read keeps a view's source and target entries apart after **Swap views**.
- **The `createLimiter` is correct.** It hands the slot over, removes the waiter on abort and cleans up its listener, and it has its own 315-line test file.
- **Careful UX:** the double-click guard on **Copy** (`event.detail > 1`), **Stop** placed away from **Copy**/**Done**, `beforeunload` while copying, plans reset on any change of the options (`revision`), the dialog closing when the route's view changes, and focus management after the dialog closes.
- **Process:** the spec was reviewed before any code, the known limits are stated plainly, and the docs (`admin-ui.md`, README) are updated in the same PR.
