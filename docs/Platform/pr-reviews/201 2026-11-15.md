# Review of PR #201: [🔒️ fix(platform): keep the command-line values of sform out of its error reports (424-75)](https://github.com/akobr/mono.me/pull/201)

Reviewer: Harry · Review date: 2026-11-15

**Verdict: approve-ready, with two important follow-ups.** I found no path by which a command-line value reaches Sentry. The design is right: one `SentryClient` per report, no `SentrySdk.Init`, no static hub, no Serilog sink, no integrations, and command usage built from the parser model, not from the tokens. The tests check the envelope as it would be sent. What's left is about defense in depth (the Sentry drop-on-timeout path depends on SDK behavior and has no test) and about how readable the reports stay (the value scrubbing is broad enough to hide ordinary words).

## Important

1. **The Sentry side of "a regex that times out drops the event" depends on undocumented SDK behavior and has no test.** [`ReportScrubber.cs` L19](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ReportScrubber.cs#L19) and [`ErrorReporter.cs` L92](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ErrorReporter.cs#L92): `ScrubEvent` has no `try/catch`, so a `RegexMatchTimeoutException` escapes into the SDK. Sentry 6.x does catch it, and `DoBeforeSend` returns `null` with "The event will be dropped". Earlier Sentry versions (3.x) logged the error, added a breadcrumb and **sent the event anyway**. If that behavior ever came back, the raw message of the exception that timed out would go out. The only timeout test, `AScrubbingRuleThatTimesOut_…` (`ErrorReporterTests` L181), runs with `isOptedOut: true`, so it covers only the local log.
   *Fix:* wrap the callback yourself, for example `options.SetBeforeSend((e, _) => { try { return ReportScrubber.ScrubEvent(e, values, id); } catch { return null; } });`. Then add a test with a `RecordingTransport` and the 600k `eyJ…` message that asserts no envelope is sent.

2. **The value scrubbing is broad enough to make Sentry messages unreadable.** Every value shorter than 4 characters is replaced as a whole word ([`ReportScrubber.cs` L33, L288–290](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ReportScrubber.cs#L288-L290)). Every piece of 4 or more characters between `= , ; . / \\` is replaced as a case-insensitive substring ([`CommandLineValues.cs` L209](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/Telemetry/CommandLineValues.cs#L209)). On top of that come `Environment.UserName`, `MachineName` and every `SFORM_*__*` setting of 4 or more characters ([`ErrorReportingSettings.cs` L117–121](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ErrorReportingSettings.cs#L117-L121)). Some examples: `--count 1` or a key `a` masks every standalone "1" or "a" in the first line; a key path `app.connection` turns "The SSL connection could not be established" into "The SSL *** could not be established"; a view `prod` masks "product", "Process" and so on. Sentry keeps only the first line, so this affects exactly the text you triage by. It errs on the safe side, so it doesn't block the merge, but it's worth deciding on purpose.
   *Fix (for discussion):* (a) don't scrub short numeric values and switch-like values unless they come from a secret-bearing option (`--secret`, `--value`, …); (b) raise `MinimumPartLength` for substring matching of non-secret pieces to around 5–6, or match pieces on word boundaries the way short values already are; (c) add a "readability" test: a typical `HttpRequestException`/`IOException` message with common values like `dev`, `1` or `app.connection` should keep its wording.

## Nits

- **`RegexOptions.Compiled` on about 20 static patterns** ([`ReportScrubber.cs` L428](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ReportScrubber.cs#L428)). The first failure of a short-lived CLI pays the JIT cost of compiling all of them, which can add hundreds of milliseconds right when the tool is already failing. `[GeneratedRegex(..., matchTimeoutMilliseconds: 250)]`, which `CommandUsage` already uses, has no startup cost and keeps the timeout.
- **`double.TryParse(value, out _)`** ([`ErrorReportingSettings.cs` L121](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ErrorReportingSettings.cs#L121)) depends on the current culture: on a cs-CZ or sv-SE machine "1.5" is not a number but "1,5" is. Use `NumberStyles.Float, CultureInfo.InvariantCulture`.
- **`MachineAuthenticationService.KeepNames` appends on every credential load**, so the list collects duplicates. Use a `HashSet<string>(StringComparer.OrdinalIgnoreCase)` under the same lock and return a snapshot.
- **`CommandUsage.IsGiven`** ([`CommandUsage.cs` L53–59](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/Telemetry/CommandUsage.cs#L53-L59)) treats an option given explicitly with its default value (`--view default`) as not given. Its name drops out of the report, and its value drops out of the local log. That's harmless for privacy, because the args tokens still cover the value, but the usage line is then slightly wrong. A comment would help.
- **`Task.Run(() => Send(...))` + `using var client`** ([`ErrorReporter.cs` L62, L173](https://github.com/akobr/mono.me/blob/4fa8059f1e02f2105db46167961156312ace456c/src/Platform/Cli/src/ErrorReporting/ErrorReporter.cs#L173)): dispose flushes for up to the default `ShutdownTimeout`. That's the same as before, but it now matters most in the "service could not be reached" case, where Sentry is probably unreachable too. Set `ShutdownTimeout` explicitly (for example 2 s) so the delay at exit is a choice you made, not a default.
- **The fuzz test uses `Should.CompleteIn(…, 2s)`** 3,000 times. It's seeded and deterministic, but on a loaded CI agent a 2 s wall-clock limit can make it flaky. One overall budget, or a looser limit, would be safer.
- `ErrorReporter` re-reads `run.Values` (which rebuilds `Merge` + `WithParts`) on every access. It's read once per report today, so this is fine, but caching it in `CommandRun` once parsing has happened would make that guaranteed.

## Good

- No hub and no integrations, so there's no window in which another log entry or an unobserved task exception becomes an event. Dropping `Sentry.Serilog` closes the old leak at its source.
- Usage comes from the parser model, and option names pass a `SafeName` allow-list. Unknown commands are reported by the deepest command matched, never by the token or `NearestMatches`.
- The `BeforeSend` cleanup is thorough: mechanism data and meta, debug-image and frame paths, foreign tags, extras (overwritten, because the SDK can't remove them), an allow-list of contexts, and the SDK's MAC-based user id replaced. I checked: on desktop .NET the SDK sets no `Device.Name`, so the allowed `device` context carries no machine name.
- `RedactedException` builds the text once and keeps the types and stack traces. The fallback to "(the message is left out)" is a sensible failure mode.
- The McMaster raw-args Debug log is filtered both in MEL and in Serilog. The opt-out now also covers the error reports, as the docs promised, and `ProgramProcessTests` no longer send to the real project.
- The tests are strong: `ProgramReportTests` goes through `Program.RunAsync` with an injected run and reporter, so there's no static bleed between tests, and every assertion reads the serialized envelope.
