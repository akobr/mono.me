## Important

1. **A failed post-deploy check leaves the bad image live.** `.github/workflows/Platform.Storyteller.Mcp.yml` L195–257 runs `az containerapp update --image`, polls, and then curls the resource metadata. If the curl fails (L255), for example because the new revision is "ready" but crashes once it is woken from zero replicas, the job goes red. The new image stays on the app, though, and `main.bicep` will even keep it on later runs (`mcpExisting`, `main.bicep` L335). The runbook's "A bad image" rollback is manual. Suggested fix: before the update, read `properties.template.containers[0].image`. Then add an `if: failure()` step that re-applies that image with a `rb`-prefixed revision suffix, or at minimum print the exact rollback command to the step summary. The first is cheap and makes "approve" much safer with `minReplicas: 0`, where a started replica is only proven by that final curl.
2. **The image is not serialized against a manual `main.bicep` run.** `main.bicep` reads the running image (`mcp-existing.bicep` L15) and writes it back. If the owner runs `main.bicep` while a `deploy` job is between `update` and its checks, the template can write back the *previous* image. If that write lands after the workflow's one-time image check (L245–249), nothing notices the silent rollback. Both paths are owner-driven, so the risk is low. Still, add a line to the runbook ("don't run `main.bicep` while a Platform.Storyteller.Mcp deployment is running or waiting for approval"). Alternatively, make the post-deploy check compare against `$IMAGE` again after the curl.

## Nits

1. **The ingress timeout and the server's API timeout disagree.** The Container Apps ingress cuts requests at 240 s (`mcp.bicep` L165, runbook "A request through the ingress ends after 240 seconds"). The server's `ApiCallTimeout` is 5 minutes, used as both attempt and total timeout (`Mcp/src/Hosting/McpHostExtensions.cs` L20, ~L149–150). The client therefore sees a dropped connection instead of a clean tool error. Consider a setting with a production value below 240 s (say 200 s).
2. **The `latest` tag** (`Platform.Storyteller.Mcp.yml` L130–135). Nothing consumes it: deploys use the digest and `mcpInitialImage` uses the commit. Main runs don't serialize either (L49–50 group by `run_id`), so two merges in quick succession can leave `latest` on the older one. I'd drop it rather than offer a moving tag that looks deployable.
3. **"A commit is built once" depends on the registry probe** (L112). Any `imagetools inspect` failure counts as "not there", including a transient network or auth error. The SDK build isn't byte-reproducible, so a rebuild moves `:<commit>` to a new digest. Distinguishing "manifest unknown" from other errors (fail the job on the latter) would make the invariant actually hold.
4. **Missing parameter guard in `main.bicep`.** `mcpCustomDomain = true` with `mcpAppExists = false` is accepted. The runbook sets them together in phase 6, but a `fail()` next to `mcpInitialImageChecked` (L186) would stop a first run that tries an `Auto` binding before the CNAME/TXT records can exist.
5. **`mcpExchangeAppId` is checked only by `length(...) != 36`** (`main.bicep` ~L178–182). That's fine as a smoke check, but the message says "a GUID". Consider also checking the four `-` positions, or reword the message.
6. **Action pinning.** `docker/login-action@v3` and `azure/login@v2` are pinned by tag, not by SHA, in a job with `packages: write` and `id-token: write`. This matches the repo's existing workflows (`Platform.UI.Admin.yml`), so it's optional, but this is the first workflow that pushes images and holds an Azure federated token. SHA pins for the two third-party actions would be cheap hardening.
7. **TCP-only probes** (`mcp.bicep` L192–222). This is justified, because the Aspire health endpoints are Development-only (`Aspire.ServiceDefaults` `MapDefaultEndpoints`). A minimal anonymous `/alive` mapped in all environments would let liveness catch a hung (not crashed) Kestrel. That's for later, not this PR.
8. **PR body.** "After the merge, pull `main` in the main checkout. That checkout still has the spec and the runbook staged as new files" is a local-workspace note that doesn't belong in the PR description.

## Good

- **The `mcpEnabled` gate.** It works with `fail()` checks before anything is written, and the token exchange returns to exactly the previous `Auth__TokenExchange__Enabled: 'false'` when it's off (`functions.bicep`). The "same resources and settings as before" claim holds from what I read.
- **The actor identity is pinned tightly.** It uses the v1 issuer `https://sts.windows.net/<tenant>/`, `sub` = the identity's object id, and `aud` = `api://<exchange app id>`. A single subject audience (the MCP resource URL) is allowed, and the additional AuthKit issuer is added only while it differs from `Auth__AuthKit__Issuer`, which avoids the API's start-up refusal. `New-TokenExchangeApplication.ps1` refuses rather than "fixes" a v2 app or a foreign App ID URI. It also assigns the identity *before* turning on `appRoleAssignmentRequired`, so there is no lockout.
- **Least privilege in the workflow.** I verified it against the Azure CLI source: core `az containerapp update` reads only the app (the environment is read only with `--workload-profile-name`), and its provider-registration check swallows errors. The deploy identity therefore really does get by with Container Apps Contributor on the app alone. `--no-wait` with polling of the app, rather than a subscription-scoped operation, is the right call, and the runbook documents the fallback.
- **A good deploy design.** Deploys go by digest with an approval gate and their own non-cancelling concurrency group. There is a unique revision suffix per run and attempt, a 15-minute bounded wait, `Failed`/`Degraded` detection, and an image-equality check after readiness. `persist-credentials: false` is set and permissions are per job.
- **Container App config fits the server.** The server runs `HttpServerSessionMode.Stateless` (`McpHostExtensions`), so scaling 0–3 replicas needs no session affinity. `ResourceUrl` drives the OAuth metadata (no `X-Forwarded-*` dependence behind the ingress). Secret tools are off, `allowInsecure: false` is set, and there are no secrets in the template. Logs go through a diagnostic setting (no shared key).
- **A thoughtful custom-domain handling.** Because a Container App has no binding resource, existing bound domains are written back with their certificate ID, which avoids the classic "every redeploy drops the binding" bug.
- **A non-root chiseled image** built by the SDK, with no Dockerfile to maintain, and the OCI `source` label so the GHCR package links to the repo.
- **A thorough runbook.** It covers verification steps, rollback options and the AuthKit custom-domain transition.
