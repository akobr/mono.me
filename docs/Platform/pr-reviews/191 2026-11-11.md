# Review of PR #191: [fix(platform): strip definePage from an admin UI built through a junction](https://github.com/akobr/mono.me/pull/191)

Reviewer: Harry · Review date: 2026-11-11

**Verdict: approve-ready.** This is a small, well-aimed one-line config fix (+7/−1 in `src/Platform/ui.admin/src/vite.config.ts`). When I reviewed it, CI ("Lint, type-check, test, build") and CodeRabbit were still running, so merge once CI is green.

## Important

- **No guard against a regression.** `definePage()` left in the bundle passes lint, type-check and the build, and only fails at run time in the deployed app. That's exactly why this bug got through. Add a cheap build-time check. One option is a small plugin next to `sdkFreshness()` in `build/` that fails in `generateBundle` when any chunk still contains `definePage(`. The other is a CI step that runs `grep` on `dist/`. Either one also catches the next path mismatch, from a symlink, a `subst` drive, or a different drive-letter case.
- **Only the router plugin gets the real path.** Vite's own `root` and the `@` alias (`vite.config.ts` L35) still come from `import.meta.url`/cwd, i.e. the junction path. This works today because Vite resolves aliased ids to real paths, and the Nuxt UI auto-import/components scans only read files. But the config now uses two notions of "project root". Consider also setting Vite's top-level `root` (and the alias) from the same `root` constant, so every plugin that defaults to `config.root` sees one canonical path. If you deliberately keep the change minimal, a sentence in the comment saying why only `VueRouter` needs it would help.

## Nits

- `realpathSync.native` on Windows returns the drive letter as the filesystem reports it (usually uppercase `D:`), while the PR description says Vite's ids are `d:/…`. It evidently matches today, because the plugin normalizes case or the comparison is case-insensitive, and you validated the build. Still, the fix depends on that normalization. That's one more reason for the bundle check above.
- The comment (L11–13) is good. You could shorten it to two lines and link the upstream unplugin-vue-router/vue-router issue if one exists, so the line can be dropped once the plugin resolves `root` through `realpath` itself.
- `vitest.config.ts` reuses `viteConfig`, so unit tests pick up the same `root`. That's good, but it isn't mentioned in the PR's Validation section. Say that `vitest run` passes too.

## Good

- The root-cause analysis is correct and clearly written: Vite real-paths module ids, while the router plugin resolved `routesFolder` from `process.cwd()`. No page matched, so the `definePage` macro was never stripped.
- The fix is minimal and local. `dts: 'app/typed-router.d.ts'` now also resolves under the real root, which is consistent.
- It was validated both through the junction and directly from `D:`, before and after. No other Vite config in the repo uses file-based routing (`routesFolder` appears only here), so nothing else needs the same fix.
