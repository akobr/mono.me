# Review of PR #154: [🧪 test: run every test project on xUnit v3 and Microsoft.Testing.Platform (424-151)](https://github.com/akobr/mono.me/pull/154)

Reviewer: Harry · Review date: 2026-11-02

**Verdict: needs changes.** The migration itself is clean and well validated. But the branch conflicts with `main`, and since the branch was cut, `main` has given the UI suite a committed default target. That breaks the PR's main promise that one `dotnet test --solution 42.mono.slnx` exits 0 without setup.

## What I checked

- I read the description, all 8 commits and the full diff (71 files, +609/−194), plus the spec and the three phase reviews.
- I checked the changed files in context and confirmed that every test project is in `42.mono.slnx` and that no `Microsoft.NET.Test.Sdk`, `xunit` v2 or `Xunit.Abstractions` references remain.
- I did a three-way merge against the current `main` (`307648f1`).
- On Linux (SDK 10.0.403) I built and ran `Backend.Core.UnitTests` (1,221 passed) and `Configuration.UnitTests` (641 passed, which covers `UnixFact`) with `dotnet test --project`.
- `--filter "FullyQualifiedName~RelationNamesJson"` works unchanged under xUnit v3 on MTP (109 passed), so the docs that keep the VSTest-style filter are correct.
- The restore resolves a single `Microsoft.Testing.Platform` 2.5.2, so `TrxReport` 2.5.2, `xunit.v3` 4.0.2 and TUnit agree.
- CI reports no checks on the head commit (`31fdfda4`). CodeRabbit had only posted its "review in progress" placeholder.

## Blocking

1. **Merge conflicts with `main`** (`mergeable_state: dirty`).
   - **Where:** `CLAUDE.md` and `docs/Platform/UI.Admin.AutomationTests/automation-tests.md` conflict. `docs/Platform/development.md`, `docs/Libraries/Testing/UI.Automation/readme.md`, `src/Platform/UI.Admin.AutomationTests/README.md` and `sdk.typescript/README.md` merge on their own but touch the same paragraphs.
   - **Fix:** Rebase on `main` and re-read those docs after the merge. `main` rewrote the "Without a target" paragraph that this PR also edits, so the merged text has to describe both changes.

2. **The UI suite no longer skips by default, so the solution run won't exit 0 after the rebase.**
   - **Where:** `src/Platform/UI.Admin.AutomationTests/src/testsettings.json` on `main`. Commit `581c2a16` set `Target:BaseUrl` to `http://localhost:5173`, and the file's own comment says "which must be running (otherwise the target check times out)".
   - **Why it matters:** This PR removes `Test="false"` (`src/Directory.Build.proj`, `src/Platform/Directory.Build.proj`) and documents `dotnet test --solution 42.mono.slnx` as *the* test command in `CLAUDE.md` and `development.md`. That relies on "the UI suite skips without `Target:BaseUrl`". After the rebase, anyone without the admin UI dev server and the pool passwords in user secrets gets a timed-out target check and a failed run. That includes every agent and every Linux box.
   - **Fix (pick one):**
     - Keep the UI project out of the default solution test run. For example, gate `IsTestProject`/`IsTestingPlatformApplication` behind an opt-in property, or use a solution filter for "all unit and integration tests".
     - Move the localhost default into a `local` profile and keep the committed `BaseUrl` empty.
     - Make the documented solution command set `UITESTS_Target__BaseUrl=` explicitly.

     Whichever you pick, add the case to the Phase 3 validation table.

## Important

3. **The documented solution command fails on the Cosmos and Lowkey suites unless modules run one at a time.**
   - **Where:** `CLAUDE.md` (the MTP testing section) and `docs/Platform/development.md`.
   - **Why it matters:** Your own table shows 520 failures with the plain command and 0 with `--max-parallel-test-modules 1`. The VSTest baseline already had 273 environment failures, so the command was never clean, but now the fix is known and cheap. Right now the command a reader copies is the one that fails.
   - **Fix:** Put `--max-parallel-test-modules 1` in the primary documented command (and in the `mrepo.json` root script, if one runs the solution) until the per-module Cosmos and Lowkey fixtures are isolated. Alternatively, mark those two modules as non-parallel.

4. **Two `mrepo` regressions are knowingly shipped as follow-ups.**
   - **Where:** `mrepo build -t` in an area folder now falls back to `dotnet test Directory.Build.proj`, which MTP refuses. The `mrepo` scaffolding templates still generate xUnit v2 projects, and those can't restore now that `xunit`, `xunit.runner.visualstudio` and `Microsoft.NET.Test.Sdk` are gone from `Directory.Packages.props`.
   - **Fix:** The scaffolding one is the sharper edge, because every new project starts broken. Fix the template in this PR (it's small: the same csproj shape as the 29 migrated projects) or open a tracked Linear issue and link it from the PR description. For `build -t`, a one-line note in `docs/Monorepo/mrepo-json.md` would save someone a confusing error.

5. **Coverage collection is gone with no replacement.**
   - **Where:** `Directory.Packages.props` removes `coverlet.collector`.
   - **Why it matters:** Nothing in CI used it, so it's not a regression today. But `--collect "XPlat Code Coverage"` silently stops working for anyone who ran it locally.
   - **Fix:** Mention it in the PR notes. If coverage is wanted later, `Microsoft.Testing.Extensions.CodeCoverage` (with `--coverage`) is the MTP equivalent.

## Nits

6. **Stale schema example.** `src/Monorepo/Cli/src/mrepo.schema.json:351` still shows `"dotnet test test"` as the example script. It should be `dotnet test --project test` to match `mrepo.json`.
7. **Interface name clash.** `src/Platform/Storyteller/Backend.CosmosDb/test/ITestContext.cs` now shares its name with xUnit v3's `Xunit.ITestContext`. It compiles, because the local namespace wins, but `Startup : IAsyncLifetime, ITestContext` reads as the xUnit type. Consider renaming it to `ICosmosTestContext`.
8. **`UnixFactAttribute`.** Forwarding `[CallerFilePath]`/`[CallerLineNumber]` is right. In v3 you could drop the custom attribute and use `[Fact(SkipUnless = nameof(IsUnix), SkipType = typeof(...))]` or `Assert.SkipUnless(...)`, which reports the skip the same way and needs no subclass.
9. **Repeated csproj boilerplate.** The 29 csproj files repeat the same `OutputType`/`UseMicrosoftTestingPlatformRunner`/comment block. A `Directory.Build.props` condition on `test`/`testint` folders (or `IsTestProject`) would keep the next migration to a one-file change. That's optional, since an explicit per-project setup is a valid choice in a monorepo.
10. **Broad xUnit1051 downgrade.** `.editorconfig` downgrades xUnit1051 for all of `test/` and `testint/`. That's fine for the migration, but the follow-up to pass `TestContext.Current.CancellationToken` is what makes v3's cancellation useful. Give it a tracked issue too.
11. **Unexplained fix in `Binding.Object`.** On Windows its 2 baseline failures disappeared. The likely cause is that v3 runs each assembly in its own process, so shared static state no longer leaks between assemblies. A sentence in the Phase 3 review would stop someone thinking a real failure was masked.

## Good

- The validation is exemplary: per-assembly test counts match the VSTest baseline on both OSes, the warnings are compared by file, line and code, and the failures are explained by environment.
- The migration is consistent and minimal: `ValueTask` fixtures, `.Data` on `TheoryData` rows, typed `null` rows, and no behavior changes in the tests.
- The esproj `_NormalizePackagePropsPath` target fixes a real Linux build break (the literal `obj\Debug` folder), and the PR notes say how to clean up old checkouts.
- Deleting the two empty test projects is correct under MTP (exit code 8), and nothing references them anymore.
- The conformance workflow and docs were updated together, and the claim that `--filter` works unchanged checks out.
