# Review of PR #198: [perf(platform): read the outside parents of a delete and a restore in one ReadMany call (424-229)](https://github.com/akobr/mono.me/pull/198)

Reviewer: Harry · Review date: 2026-11-15

**Verdict: approve-ready.** This is a small, focused perf change: one runtime file, +11/−3. The rest is tests, docs and the spec. A soft delete and a restore now read their outside parents in one `ReadNodesAsync` call instead of one point read after another. As far as I can tell, the behaviour is the same as before. I found nothing blocking. Below are a cost question, a brittleness note on the tests, and a few nits.

**CI at review time (head `0968294`):** "Classic emulator", "vNext emulator" and CodeRabbit were still running. There were no reviews yet and one issue comment. The author reports 838 tests on vNext: 831 passed, 6 skipped, and 1 failure (a Lowkey Vault TLS handshake that passed on a re-run, so it's unrelated).

## Why I think it is correct

- **Key matching.** `DeleteCoreAsync` (`CosmosAnnotationService.Deletion.cs` L288–295) looks up `parents[group.Key]`. `group.Key` is `relation.Parent.ToString()`. `ReadNodesAsync` keys its dictionary by `AnnotationNode.KeyText`, which is `FullKey.Annotation.ToString()` of `FullKey.Create(group.First().Parent, fullKey)`. These are the same string, so the indexer can't miss. The restore path (L437–443) writes `known[keyText]` with the same key text that `known[parent.ToString()]` used before.
- **Missing, Deleted and Active.** `LoadManyAsync` leaves `Entity` null for an id that `ReadMany` doesn't return, so `State` is `Missing`. This matches the old `ReadDocumentAsync` handling of a 404. Deleted and active parents are handled exactly as before.
- **ETags.** The ETag now comes from the document's `_etag` instead of the response header. Cosmos gives the same value in both, so the `IfMatchEtag` on the relation replaces is unchanged. The new tests check this against the stored ETag.
- **Retries.** The read sits inside `DeleteCoreAsync` and `RestoreCoreAsync`, so every `RetryAsync` attempt reads the parents again with fresh ETags. The two retry tests cover this.
- **Errors.** A failed `ReadMany` now throws `CosmosRequestFailedException`, which is a `CosmosException` that also carries `RetryAfter` on a 429. Callers that catch `CosmosException` still see a `CosmosException`.
- **No parents.** When there are no parents, `LoadManyAsync` has no chunks and sends no request.

## Blocking

None.

## Important

1. **Request units for small N** (`CosmosAnnotationService.Deletion.cs` L289, L438). The common delete or restore has 1–3 outside parents. A point read costs about 1 RU. `ReadMany` runs a query per partition-key range, and for a handful of items that can cost more than the point reads it replaces. The gain is in latency (one round trip instead of N sequential ones), not necessarily in RU. I haven't measured this; please check it before calling the PR a pure perf win.
   *Suggestion:* log or assert `RequestCharge` for a 1-parent and a 3-parent delete in the emulator, and note the result in the spec. If single-parent cost turns out worse, `ReadNodesAsync` could use a point read when there is only one key. That would be one place to change, covering every caller.
2. **The known gap after a 412 on a parent** (pre-existing; it's under "Follow-up" in the description). If a parent changes between the read and the relations wave, the retry finds the tree already committed and leaves the parent's arrays stale. That is a real consistency bug, even though this PR doesn't cause it. Please file it in Linear, or link the issue if it exists, so it doesn't stay only in a review doc. Create already has the fix pattern in `CompleteParentRelationsWithRetriesAsync`.
3. **Brittle counts in the tests** (`CosmosAnnotationParentReadTests`). `ReadsOfMany.Should().ContainSingle()` and `.HaveCount(2)` count every read of many items the operation makes. If a later change batches some other read in delete or restore (descendants, snapshots), these tests break for reasons unrelated to parents.
   *Suggestion:* first filter to the reads that contain a parent id, e.g. `ReadsOfMany.Where(ids => ids.Intersect(parents).Any())`, then assert on those.

## Nits

- **Expired-usage theory** (`CosmosAnnotationLifecycleTests.Delete_WithAnOutsideParentDeletedOrExpired_ChangesOnlyTheActiveOne`). `using (await Container.DeleteItemStreamAsync(...)) { }` ignores the status code. Asserting `NoContent` would give a clearer failure than the later `after.Should().BeNull`. A real TTL expiry also removes the configuration and audit items. That doesn't matter here (`withAudit: false`), but a short comment would make the shortcut explicit.
- **What the retry tests touch.** Both retry tests force the 412 on the root or the usage, never on an outside parent. That is fine for "reads again", but a skipped test that documents the gap in Important #2 would pin it down.
- **Cancellation.** `ReadNodesAsync` takes a `CancellationToken`, but `DeleteCoreAsync` and `RestoreCoreAsync` don't pass one through. This was already true before the PR. It's worth threading a token through later when the public API gets one.
- **Comment wording** (L288). "every parent in one read of many items" isn't accurate past 1,000 keys, where `ReadNodesAsync` splits the read into chunks. Suggested wording: "in reads of many items (chunks of 1,000)".
- **`StorageInterceptor.ReadsOfMany`** stores the caller's `ids` list by reference. That's fine today because `InterceptedContainer` builds a new list for each call. A `.ToArray()` on enqueue would make the recording safe against later changes to the caller.

## Good

- A minimal change in the service that reuses the existing chunked `ReadNodesAsync` instead of adding a new read path.
- The new tests are precise and fail on the old code. They check the number of reads, that no parent is point-read, ETag reuse, and re-reads on retry. The new lifecycle theory builds its state only through public operations.
- The docs (`annotation-lifecycle.md`, `audit-operations.md`) and the spec and review were updated in the same PR.
