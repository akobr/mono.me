# Review of PR #145: [🐛 fix(platform): refuse a configuration patch without a stored version (424-100)](https://github.com/akobr/mono.me/pull/145)

Reviewer: Harry · Review date: 2026-10-31

**Verdict: approve-ready.** The fix is one condition in the right place. `PatchConfigurationAsync` now throws `ConfigurationNotFoundException` when the item is missing or is only a cache row (`!IsWrittenVersion`), and it does so inside the retry loop after `ReadForWriteAsync`. That ordering keeps the soft-delete check (`409 AnnotationDeleted`) and the completion of pending invalidations ahead of the refusal, and a row that turns into a cache row between attempts is refused on the retry. Choosing `IsWrittenVersion` over the issue's `!Content.HasValues` is well argued: an emptied version is a version everywhere since 424-50, and the content guard would break "Create empty" then Save, `sform config edit/patch` and the MCP tools. The tests cover the issue's exact sequence for both clear and delete, the no-row and cache-row cases of "Create empty", the refused patch finishing a failed clear's invalidation, the deleted annotation, and the race. The only check on `d730d49d` when I reviewed was CodeRabbit, still in progress; the test plan reports local runs of every affected suite.

## Blocking

None.

## Important

1. **Patch and clear now disagree on what is stored.** Patch accepts an emptied version (`CosmosConfigurationService.cs:507`), but `ClearConfigurationAsync` still returns `false` for it because it tests `Content.HasValues` (`:552-553`), and `DeleteAsync` only audits when content has values (`:579`). So a configuration created empty can be patched but not deleted through `DELETE` (it answers `404`), and the Admin UI's "Delete own" fails on it. The PR lists this under "Left for later", which is fine, but it is now a visible inconsistency in the contract rather than an edge case, so please open the ticket with this PR. The likely fix is to switch the clear to `IsWrittenVersion` as well and archive the emptied version, which the archive path already supports.
2. **Old patch leftovers stay in the data.** The new read filter hides an empty archive of version 0 (`:356`), and `inheritance.md` now says that an archive of a later version than the current item stays readable at `versions/{n}` but is not listed. Both are leftovers of the old cache-row patch. Hiding them on read is a reasonable defensive step, but nothing cleans them up, and a later write over such a key could still meet an archive with other content of the same number (the "earlier lifetime" rule handles it, but only by renumbering). If any environment actually ran the old path against real data, a one-off query or cleanup script would be worth it. If it never shipped beyond dev, say so in the spec and close the question.
3. **The read filter duplicates `IsWrittenVersion`.** `versionEntity.Version > 0 || versionEntity.Content.HasValues` (`:356`) is the same rule as `IsWrittenVersion` (`:1203-1205`) and the version list filter (`:307`), written a third time for `ConfigurationHistoryEntity`. Add an overload, or a small static helper taking `(ulong version, JObject content)`, so the definition of "a written version" lives in one place. That's the exact concept this PR is about, so drifting copies would be costly.

## Nits

1. **The backend exception names HTTP verbs.** `ConfigurationNotFoundException` (`Backend.Core/.../ConfigurationNotFoundException.cs:4`) now ends with "A PUT or POST writes a first document." Backend.Core shouldn't know about the transport, and the same text reaches MCP and the CLI, where the advice is `set_configuration` or `sform config set`. Keep the service message transport-neutral and add the PUT/POST hint in `ConfigurationHttp.cs:415`, or in the OpenAPI description only.
2. **The mock copies the message by hand.** `configuration-handlers.ts:421-427` repeats the backend text as a string literal. That's fine for a mock, but a test asserting on the message would fail silently the next time one side changes. A shared constant or a looser match keeps them aligned.
3. **The comment on `IConfigurationService` could name the exception's sibling cases.** It says the method throws `ConfigurationNotFoundException` when nothing is stored, which is good; adding that a soft-deleted annotation throws `ConflictException` with `AnnotationDeleted` first would document the ordering the recovery test pins down.
## Good

- The check sits after `ReadForWriteAsync`, so a refused patch still finishes a pending invalidation. The `FailedClearInvalidation_IsCompletedByARefusedPatch` test proves it for both the missing and cache-row states.
- `Patch_OfACacheRow_IsRefused_AndTheNextWritesContinueAfterTheArchivedVersions` turns the issue's reproduction into a regression test and checks that versions 1 and 2 keep their content and the next writes are 3 and 4.
- `ConfigurationPatchHttpTests` follows the repo's `DispatchProxy` style for Api tests and pins the `404` mapping and the message.
- The behaviour changes for raw API and SDK callers are spelled out in the description and in the public `configuration.md`, and the OpenAPI shape is unchanged, so no SDK regeneration is needed.
