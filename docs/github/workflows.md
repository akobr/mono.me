# GitHub Workflows

The workflows in `.github/workflows`: what each one does and when it runs. All push and pull request triggers use path
filters, so a workflow runs only when files in its area change. The naming of workflows, their files and the GitHub
environments is described in [naming-convention.md](naming-convention.md).

## Automatic checks (on pushes and pull requests)

| Workflow | What it does | When it runs |
|---|---|---|
| **Docs.42for.net** (`Docs.42for.net.yml`) | Builds the VitePress docs site and deploys it to Azure Static Web Apps | On a push or PR to `main` that touches `docs/42for.net/**` |
| **Platform.UI.Admin** (`Platform.UI.Admin.yml`) | `verify`: lints, type-checks, tests and builds the Vue admin UI and the TypeScript SDK, and runs the Playwright suites against the mocked API. `deploy`: deploys `main` to Azure Static Web Apps | On a push or PR to `main` that touches `src/Platform/ui.admin/**`, `src/Platform/Storyteller/sdk.typescript/**`, `src/Platform/Storyteller/DbCreator/src/data-sets/showcase/**` (DbCreator's set `showcase`, a snapshot of the showcase mock that `npm test` checks) or `src/Platform/Storyteller/conformance/project-settings.json` (the catalog of project settings, which the UI's colors, icons and date formats must equal). Only a push to `main` deploys |
| **Platform.Storyteller-conformance** (`Platform.Storyteller-conformance.yml`) | Runs the conformance suite: the Configuration and ConfigurationFormats tests and the project settings runner of Backend.Core (`ProjectSettingsConformanceTests`) on Linux and Windows, plus the TypeScript SDK tests | On a push or PR to `main` that touches the conformance vectors, `Abstractions.Annotations`, the project settings tests of Backend.Core, the Configuration or ConfigurationFormats libraries, either SDK, KeyValues.ClientEncryption, or the root build files (`global.json`, `nuget.config`, `version.json`, …). Also by hand, and called by the SDK release as its gate |
| **Platform.Storyteller.Api.Functions.UnitTests** (`Platform.Storyteller.Api.Functions.UnitTests.yml`) | Runs the unit tests of the Storyteller API (`Api.Functions/test`) twice: in Release, where the checks of users are on as in production (the tenant isolation tests and the role refusals), and in Debug, for the `DEV_AUTH` branches and the guard that keeps a Debug build off any deployment. Needs no Docker, emulator or secret | On a PR, or a push to `main`, that touches `src/Platform/Storyteller/**`, the libraries the API builds on (`ConfigurationFormats`, `Utils/Async`), the vendored packages (`.packages/**`), the StyleCop files or the root build files (`Directory.Build.props`, `Directory.Packages.props`, `global.json`, `nuget.config`, `stylecop.json` and the version files). Also by hand, or called by another workflow |
| **Platform.Storyteller.CosmosDb** (`Platform.Storyteller.CosmosDb.yml`) | Runs the backend's Cosmos DB suites (`Backend.CosmosDb/test`, `Access.Certificates/testint`, and `DbCreator/testint`, the seed of data sets, which also starts Lowkey Vault for the `Standard` key/value pairs) on Testcontainers emulators. A vNext job runs the tests without the `Emulator=Classic` trait, and the unit tests of DbCreator (also when a suite before them failed). A classic-emulator job runs only that trait on a PR (so only `Backend.CosmosDb`: the two integration suites have none), and the full suites otherwise. The emulator images are pinned by digest in `CosmosTestEmulator`. By hand (or called), `vnext_runs` (`1`, `5` or `10`) runs that many vNext jobs at once on the same commit, a check that the job is steady, and `classic: false` leaves out the classic job | On PRs that touch `src/Platform/Storyteller/**` or the root build files (no push trigger). Also by hand (`gh workflow run Platform.Storyteller.CosmosDb.yml --ref <branch> -f vnext_runs=10 -f classic=false`), or called by another workflow |
| **Platform.Cli.UnitTests** (`Platform.Cli.UnitTests.yml`) | Runs the `sform` unit tests and the CLI automation self tests and coverage checks. Needs no target and no secrets | On a PR, or a push to `main`, that touches the CLI, its automation tests, `Automation.Shared`, the UI.Automation libraries, the CLI Toolkit, `Sdk.NSwag`, the catalog of project settings (`conformance/project-settings.json`), the CLI test-case catalogue or `Directory.Packages.props` |
| **Platform.Deployment** (`Platform.Deployment.yml`) | Runs `bicep build` / `build-params` on the Azure templates and PSScriptAnalyzer on the scripts. Does not sign in to Azure | On a PR, or a push to `main`, that touches `src/Platform/Deployment/**` |
| **Platform.Storyteller.Mcp** (`Platform.Storyteller.Mcp.yml`) | `test`: the MCP server's unit tests. `image`: builds the server's container image with the .NET SDK (`PublishContainer`, no Dockerfile) and pushes it to `ghcr.io/akobr/2s-platform-mcp` with the commit as its tag; a commit that has an image already reuses it. `deploy`: after the approval of `prod.42.Platform`, runs that image by its digest on the Container App `prod-2s-mcp-ca` (`az containerapp update --image … --no-wait`), waits for the new revision and checks the server's resource metadata, and puts the previous image back when the check fails; one deployment at a time ([runbook](../Platform/Deployment/runbook-mcp-server.md)) | On a PR, or a push to `main`, that touches the MCP server, a project it builds on (`Sdk.NSwag`, `Abstractions.Annotations`, `KeyValues.ClientEncryption`, the catalog of project settings, `Aspire.ServiceDefaults`), the StyleCop files or the root build files `Directory.Build.props`, `Directory.Packages.props`, `global.json` and `nuget.config` (not the version files: a version bump alone deploys nothing). Also by hand. Only `main` (a push or a manual run) builds an image and deploys |

## Automation test runs (by hand or called)

| Workflow | What it does | When it runs |
|---|---|---|
| **Platform.UI.Admin.AutomationTests** (`Platform.UI.Admin.AutomationTests.yml`) | Runs the TUnit and Playwright tests of the admin UI (locally or on BrowserStack) against a deployed target, or against the mock build served inside the job (`use_mock_ui`). Can report results to Testiny | Only `workflow_dispatch` or `workflow_call`. Runs against deployed targets queue one at a time because they share the test users |
| **Platform.Cli.AutomationTests** (`Platform.Cli.AutomationTests.yml`) | Runs the real `sform` against a deployed API, with device-code sign-ins approved through Chromium. Can report results to Testiny | Only `workflow_dispatch` or `workflow_call`. Runs queue one at a time because they share the CLI test users |

## Releases (by hand)

| Workflow | What it does | When it runs |
|---|---|---|
| **Platform.Storyteller.Sdk-release** (`Platform.Storyteller.Sdk-release.yml`) | Releases the Storyteller NuGet and npm packages after the conformance workflow passes. A dry run unless `publish` is set | `workflow_dispatch` only (inputs `packages`, `publish`) |
| **Platform.GitHubAction-release** (`Platform.GitHubAction-release.yml`) | Releases `src/Platform/GitHubAction` to its own Marketplace repository: one commit, the tag `vX.Y.Z`, the major tag `vX` moved to it, and a draft release that the owner publishes from the release form | `workflow_dispatch` only (input `version`) |
