## What Was Done

### 2.1 `TestScopeOptions.Browser`

- **`TestScopeOptions.Browser`** (`bool`, default `true`). With `false`, `TestScope.BeginAsync` leases the user (and creates the data and the artifacts collector, as `Create` always did) and acquires no browser lease, context or page.
  - `Scope.Page` and `Scope.Context` throw `InvalidOperationException`: `The test scope has no page: it runs without a browser (TestScopeOptions.Browser is false); OpenBrowserAsync opens a context, whose NewPageAsync opens one.` (the same form for the context). `Scope.Browser` throws until `OpenBrowserAsync` acquired one.
  - The screenshot, trace and video policies do not apply: nothing in `BeginAsync` or `EndAsync` takes them without the main page and context. The artifacts are what the test attaches, plus the `console.log` of contexts it opened itself. A passing test that attaches nothing leaves no folder.
  - `TestScopeOptions.SignedIn` is ignored without a browser, and `Create` refuses `SignedIn` without `LeaseUser` only for a scope with a browser, so a browserless test without a user needs no `SignedIn = false`.
  - `IsStarted` is now a flag that `BeginAsync` sets when it finished (before: `page is not null`, the last step of the same method), so `CleanUpAsync` runs for a browserless test too. New: `UsesBrowser` (the option).
- **Attaching artifacts.** `Scope.Artifacts` (`GetPath`, `Add`, `WriteTextAsync`) was already public. New: **`TestScope.AttachTextAsync(fileName, content, kind = ArtifactKind.Output, ct)`**, which writes the text through the scope's `Redact`, so a command's output never reaches a reporter with a password in it. The TUnit adapter attaches every artifact of the report to TUnit's result, as before.
- **Secrets of the run** (added after the review of the phase: the settings' secrets do not cover a credential a test creates, such as the client secret `sform machine create` prints once). New: **`TestScope.AddSecret(value)`** and **`TestScope.Redact(text)`**. `Redact` is the session's `Redact` (the settings' secrets and the pool e-mails) followed by the secrets of `AddSecret`, through the same `SecretRedactor` (as is, trimmed, URL-encoded, JSON-escaped; a value of fewer than 4 characters is ignored). `AttachTextAsync` and the `console.log` lines use it; `console.log` is masked once more when it is written, and the failure and the output of the scope's report are masked after `CreateReport`, so a secret registered after it appeared is hidden there too. A file written before its secret was registered is not rewritten, and a file the test lists with `Artifacts.Add` is kept as written (the readme says so, and its limits list it).
- **The report** of a test that used no browser names no `provider`, `engine` or `device`: `AutomationSession.CreateReport` has a new optional `browser` parameter (default `true`, so every existing caller keeps them), and the scope passes `options.Browser || a lease was acquired`. The order of the properties is unchanged. The TUnit adapter's end receiver, which reports a test whose scope never began (skipped by `GetSkipReason` or by an attribute, or not an `AutomationTest`), follows the same rule (fixed after the review: it passed no `browser` and so named the browser for skipped browserless tests): `UiAutomationSession.ReportsBrowser(type)` is `true` for a `UiTest`, `false` for any other `AutomationTest` (its scope never began, so it opened no browser) and `null` for a plain test, which names the browser when the run starts it with the session (a run with a `UiTest`, as before) and not in a run without one (e.g. the CLI's coverage test).

### 2.2 `TestScope.OpenBrowserAsync`

- **`Task<IBrowserContext> OpenBrowserAsync(TestUser? asUser = null, CancellationToken ct = default)`**, after `BeginAsync`, in any scope:
  - In a scope without a browser, the first call acquires the scope's browser lease from the session's provider (`AcquireAsync(Test)`, so a BrowserStack session gets the test's name); later calls reuse it. A scope with a browser keeps the lease of `BeginAsync`.
  - It returns a new context through the existing `NewContextAsync`: signed in as `asUser` through the `StorageStateCache` when given (and a sign-in flow is set), not traced, its console in `console.log`.
  - The scope closes every such context, hands their sign-ins back to the cache (or drops them, as for the page's) and releases the lease at its end. Multiple calls are fine.
- Decision: **one lease per scope**, not one per call. A BrowserStack session per test would otherwise open one remote session per call. `Scope.Browser` returns the on-demand lease once it exists, so `NewContextAsync` works after it as well.
- The acquisition and the release share a semaphore, so a release at the end either sees the lease or makes a later acquisition fail with `The test scope has ended (EndAsync); it opens no more browser contexts.`; `NewContextAsync` refuses a scope whose contexts were closed.
- A context that is still opening when the scope ends (e.g. TUnit's timeout ends a test inside `OpenBrowserAsync`, then `EndUiTest` closes the scope) is not left open (fixed after the review: the closed flag was checked only before the context was created, so such a context joined a list nobody read again and, with the Local provider's shared browser, stayed open until the session stopped). `CloseContextsAsync` now sets the flag and takes its list under the scope's lock, and `NewContextAsync` checks the flag again under that lock before it adds the new context: the context is either closed with the others or closed by `NewContextAsync`, which then throws the same `Ended` message.

### 2.3 `AutomationTest` in `UI.Automation.Runtime.TUnit`

- **`AutomationTest`** (abstract, new) has everything of the former `UiTest` that is not the page: `User`, `Settings`, `Session`, `Data`, `Scope`, `RequiredUser`, `LeasesUser`, `CleanUpAsync`, `LeaseAnotherUserAsync`, `GetSkipReason`, the skip, the retries, the claim and the report, and the artifacts on TUnit's result. New members: `protected virtual bool UsesBrowser` (`false`) and `protected Task<IBrowserContext> OpenBrowserAsync(TestUser? asUser = null)`.
- **`UiTest : AutomationTest`** keeps `Page`, `Context` and `SignedIn`, and seals `UsesBrowser => true`. A `private protected virtual bool StartsSignedIn` (`UsesBrowser && LeasesUser` in `AutomationTest`, `SignedIn && LeasesUser` in `UiTest`) keeps `SignedIn` in `UiTest`, so a CLI base class is free to use that name for something else.
- **The hooks keep their names**, `BeginUiTest` and `EndUiTest`, now on `AutomationTest`: the library readme, the specs and the reviews refer to them, and TUnit orders a base class's hooks before the derived class's either way. The admin run (234 skipped through `BeginUiTest`'s skip) shows that TUnit finds them one level further up.
- The scope options are built by an internal `CreateScopeOptions(attempt, startedAt, testCancellation)`, which the xUnit tests call without TUnit's context.
- The comments of `[ReportResults]` and `UiAutomationSession` say `AutomationTest` where they said `UiTest`.

### 2.4 No browser provider before one is asked for

- The settings validator starts nothing (it only validates the `Browser` and `BrowserStack` sections); the session's start did: `AutomationSession.StartAsync` created and started the provider (the Local provider starts Playwright's driver and launches the browser, BrowserStack starts the driver).
- **`AutomationSessionOptions.BrowserProviderStart`** (new enum `Browsers.BrowserProviderStart`: `WithSession`, the default, or `OnFirstLease`). With `OnFirstLease` the session holds an internal **`LazyBrowserProvider`** that starts the real one at the first `AcquireAsync`:
  - once, also when several scopes ask at the same time, without the caller's token, so a test that gives up does not cancel the start for the others;
  - a start that failed is not tried again: every acquisition throws a new `BrowserUnavailableException` with its message (a Blocked test);
  - tests the session reported as completed before the start are handed to the started provider (a BrowserStack session per class knows which of its tests are done);
  - until then it knows `Kind` and the BrowserStack session limit from the settings, an empty device catalog and no properties, so the run descriptor of such a run has no browser version;
  - disposing it disposes the started provider and starts none.
- `Browser:Device` needs the device descriptors of Playwright's driver to build the context options, so a session that sets it starts its provider with the session even with `OnFirstLease` (logged).
- **The TUnit adapter chooses**: `UiAutomationSession.ChooseBrowserProviderStart` gives `WithSession` when a selected test class derives from `UiTest` (the admin suite: unchanged, missing browsers still fail the start before any test) and `OnFirstLease` otherwise (a run of `AutomationTest`s and plain tests). Deviation from the spec's wording ("the local provider is lazy"): the laziness belongs to the session, for every provider, and is on only for runs without a `UiTest`, which keeps the admin suite's fail-fast start as it was.

### 2.5 The target check without a page, and the library docs

- **`IUiAutomationSetup.TargetCheckUsesBrowser`** (default interface property, `true`), taken by `AutomationSessionOptions.FromSetup` into the new **`AutomationSessionOptions.TargetCheckUsesBrowser`**. With `false` the check's scope is a scope without a browser: it leases the user and opens no page.
- **`TargetCheckContext`**: `HasPage`; `Page` and `Context` throw `The target check has no page: the setup's TargetCheckUsesBrowser is false. Open a browser context when the check needs one (OpenBrowserAsync, or Scope.OpenBrowserAsync for another user).`; **`OpenBrowserAsync(ct)`** opens a context signed in as the check's user (`Scope.OpenBrowserAsync(User, ct)`). A browser that does not start fails the check like any exception (`The target check failed: BrowserUnavailableException: …`). The admin setup does not set it, so its check still gets its page.
- `docs/Libraries/Testing/UI.Automation/readme.md`: the section "Tests without a browser: `AutomationTest`" (the members, what changes without a browser, the lazy provider, the target check, an example), the setup's new member and the check without a page, the run steps, the Local provider, the `UiTest` table (`OpenBrowserAsync`, `AttachTextAsync`, `AddSecret`, `Redact`), the secrets of a run (`AddSecret` in the table, the settings' secrets paragraph and the limits), the end receiver's reports, the limits, and the shared Platform library.

### 3.5 `42.Platform.Automation.Shared`

- **`src/Platform/Automation.Shared/src/Automation.Shared.csproj`** (`42.Platform.Automation.Shared`, `_42.Platform.Automation.Shared`, `net10.0`, `IsPackable` `false`), referencing only `UI.Automation.Runtime` (no test engine). It is in `42.mono.slnx` (folder `/Platform/`) and built by the `src/Platform` traversal; it has no `version.json` and no `mrepo.json` item, like the admin project. A short `README.md` sits next to `src/`.
- **The AuthKit flow, split.** `AuthKitSignIn` opened the admin UI's `/login` with its page objects (`LoginPage`, `App`) and waited for the admin UI's shell, so it cannot move whole. The shared part:
  - `Access/AuthKitHostedPage` (static): `EnterCredentialsAsync(page, email, password)` (Email, Continue or Continue with email, Password, Sign in, typed), `ContinueButton` (the former `AuthKitSignIn.AuthKitContinue`), `PasswordOf(user)`, `TypeAsync`, `IsOnHost(url, site)`.
  - `Access/AuthKitSignInFlow` (abstract `ISignInFlow`): `FlowName` `AuthKit`, `Name`, `StoragePrefix` and `IsSignInStorageItem` (`workos:*`), abstract `SignInAsync`, virtual `IsSignedOutAsync`.
  - The admin project's `AuthKitSignIn` now derives from `AuthKitSignInFlow` and keeps its `/login` start, the wait for `/callback` and the user menu, and `IsSignedOutAsync`, with the same steps in the same order. `PlatformTest.SignInOnHostedPageAsync` uses `AuthKitHostedPage.EnterCredentialsAsync` and `IsOnHost` instead of its copies.
- **`Role`** and **`UserRoleAttribute`** moved (namespace `_42.Platform.Automation.Shared`; the admin project imports it with `<Using Include="_42.Platform.Automation.Shared" />`, so `[UserRole(Role.Reader)]` still needs no using). `[UserRole]` can be shared because its meaning is the Platform's: the roles map to pool users by the Platform's role names, which the CLI pool uses too. The reflection lookup with its cache moved with it as `UserRoleAttribute.Of(type, method)`.
- **`PlatformRoles`**: the role names, `Editing`, `Admin`, `Secrets` and `RequirementOf(role)`, the switch of `PlatformTest.RequiredUser`. `PlatformTest.EditingUser`, `AdminUser` and `SecretsUser` return them.
- **The target shape.** `PlatformTargetSettings : TargetSettings` has the generic keys `Organization`, `Project`, `View`, `RoleProjects` (case-insensitive), `Section`, `RoleProjectOf(role)` and `Validate(errors)`, with the admin setup's former messages for the names and the `RoleProjects` entries (`PlatformNames` holds the name pattern). Its comment says what `BaseUrl` is per project: the admin UI's URL, or the API's base with `/api` for the CLI. The admin project's `PlatformTarget` derives from it and keeps `MockScenario`, `EmailDomain`, `ApiTimeoutMs`, `ApiWriteTimeoutMs` and `IsMock`; `PlatformAutomationSetup.Validate` calls `target.Validate(errors)`. The only visible difference: a wrong `RoleProjects` entry is now listed before a wrong `MockScenario` or `EmailDomain` in the settings error.
- Stayed in the admin project, as the spec says: `PlatformTargetCheck`, `StorytellerApi`, the page objects, the mode attributes.
- **Decision: no AuthKit sign-in flow for the CLI in this phase.** The spec (section 3.2) planned the CLI's device-page context as signed in from the user's cached AuthKit storage state, made by "the admin project's AuthKit page flow, which moves to a shared place". That flow starts at the admin UI's `/login` and comes back to its `/callback`; a CLI run's `Target:BaseUrl` is the API's base, so the flow cannot be shared as it is, and a flow that starts on the AuthKit domain itself needs an entry URL (none of the shared `Target` keys holds it) and has not been tried against AuthKit. Phase 3 therefore starts from **`Target:SignIn None`**: `OpenBrowserAsync()` gives an anonymous context, the device page (`verificationUriComplete`) asks for the credentials, `AuthKitHostedPage.EnterCredentialsAsync(page, user.Email, AuthKitHostedPage.PasswordOf(user))` enters them, and the test confirms the code. This costs one hosted-page sign-in per pool user per run, because the user's `SFORM_HOME` keeps the CLI's session for the user's later tests (spec section 3.2), and the password is typed in a context of `OpenBrowserAsync`, which is not traced (Playwright's call log in a failure message is masked by the session's `Redact`). A CLI flow derived from `AuthKitSignInFlow` (with an AuthKit entry setting of the CLI project) stays possible if phase 3 finds that the device page takes a cached AuthKit session and the saved sign-ins are worth it.
- **Tests** (added after the review of the phase): `src/Platform/Automation.Shared/test` (`42.Platform.Automation.Shared.UnitTests`, xUnit v3 on Microsoft.Testing.Platform, Shouldly, in `42.mono.slnx`): `PlatformTargetSettingsTests` (binding through the settings loader with `RoleProjects` case-insensitive, every message of `Validate`: wrong names, a role no test acts as (`Any`, unknown, numeric), a path that is not `<org>/<project>[/<view>]` of Platform names; `RoleProjectOf` null for `Any` and for a role without an entry), `UserRoleAttributeTests` (the method's role over the class's, a base class's role and an inherited method's, any overload of the name, `Any` without the attribute), `PlatformRolesTests` (`RequirementOf` for every `Role`, exact roles not satisfied by a higher one), `PlatformNamesTests` and `Access/AuthKitHostedPageTests` (`IsOnHost`, `PasswordOf` with its message, `ContinueButton`).
- Docs: `docs/Platform/UI.Admin.AutomationTests/automation-tests.md` names the shared library where it describes `Target`, the roles and the AuthKit sign-in; the admin project's `README.md` table follows.

### For phase 3 (the CLI project)

- **A browserless test**: derive `CliTest` from `AutomationTest`; `User` is leased before the test (`RequiredUser` from `[UserRole]` with `UserRoleAttribute.Of` and `PlatformRoles.RequirementOf`, or `Target.RoleProjectOf`). Attach each `sform` run with `Scope.AttachTextAsync("sform-<n>.txt", text)` (redacted with the settings' secrets and those of `AddSecret`); put the per-test working directory under `Scope.Artifacts.GetPath(...)` and list a file with `Scope.Artifacts.Add(path, kind)`.
- **Secrets the CLI prints**: register a credential a command prints (a machine's client secret or API key, a token) with `Scope.AddSecret(value)` before the run's text is attached, so the attachment, `console.log` and the report show it as `***`; mask a file the test writes itself with `Scope.Redact(text)` before `Scope.Artifacts.Add`.
- **The device page's browser context**: with `Target:SignIn None` (the decision above), `await OpenBrowserAsync()` (or `Scope.OpenBrowserAsync(null, ct)`) gives an anonymous context; open `verificationUriComplete`, enter the user's credentials with `AuthKitHostedPage.EnterCredentialsAsync` and confirm. The first call starts the provider. A context is signed in from the cache (`OpenBrowserAsync(User)`) only when the CLI's setup registers a sign-in flow (`SignInFlows`, `Target:SignIn`): a CLI flow would derive from `AuthKitSignInFlow`, implement `SignInAsync` from an AuthKit entry URL of its own settings and use `AuthKitHostedPage` on the hosted page; `IsSignedOutAsync` decides whether the cached state is dropped at the end.
- **The target check without a page**: the CLI setup sets `bool TargetCheckUsesBrowser => false`; in `CheckTargetAsync`, `context.User` is the leased pool user, `sform account -o <org>` runs with that user's `SFORM_HOME`, and `await context.OpenBrowserAsync(ct)` opens the context that approves the code. A check that opens no browser (e.g. machine credentials only) starts no provider.
- **No browser up front**: a CLI run (no `UiTest`) gets `BrowserProviderStart.OnFirstLease`, so `CommandCoverageTests` and machine-only tests never start Playwright; the device-code tests start it once. Keep `Browser:Device` unset in the CLI profiles.
- **The target**: `CliTarget : PlatformTargetSettings`, `Settings.Bind<CliTarget>(PlatformTargetSettings.Section)`, `target.Validate(errors)` in the setup's `Validate`, then the CLI's own keys.
- Reference `src/Platform/Automation.Shared/src/Automation.Shared.csproj` and add `<Using Include="_42.Platform.Automation.Shared" />`.
