# 2S Admin UI

Single-page administration application of the 2S Platform: organizations, projects and views, annotations, configurations, templates and schemas, the export and import of a view, the values store, members and invitations, machines, shared certificates and trusted issuers, settings, monitoring and the access audit of an organization.

- **Stack:** Vue 3.5 + TypeScript, Vite, Vue Router 5 (file-based, typed routes), Nuxt UI 4 (through its Vite plugin, no Nuxt), Pinia, TanStack Query for Vue, VeeValidate + Zod 4.
- **API client:** the generated SDK [`@42for.net/2splatform.sdk`](../Storyteller/sdk.typescript/README.md) (fetch functions, Vue Query composables, Zod schemas, MSW mocks).
- **Sign-in:** WorkOS AuthKit (`@workos-inc/authkit-js`).
- **Specs:** [Administration UI for 2S Platform](../../../docs/Platform/ui.admin/specs/2026-10-09%20Administration%20UI%20for%202S%20Platform.md); the phase reviews are in `docs/Platform/ui.admin/specs/reviews/`.

## Getting started

The npm package lives in `src/`. Node 22.18 or newer is required; Node 24 LTS is pinned in `src/.nvmrc`.

```bash
# the SDK is a file: dependency and is installed as a packed copy (src/.npmrc install-links=true)
cd src/Platform/Storyteller/sdk.typescript/src && npm run prepare:local   # npm ci + npm run build, when needed
cd ../../../ui.admin/src && npm run prepare:local                           # npm ci, or a reinstall of a rebuilt SDK

npm run dev:mock   # http://localhost:5174, API served by MSW in the browser, fake signed-in user, showcase data
npm run dev        # http://localhost:5173, real API (VITE_API_BASE_URL) and AuthKit
```

`prepare:local` keeps a stamp of what it installed and skips what is up to date (`--force` redoes everything); the plain `npm ci` and `npm run build` work as well. After a change of the SDK, rebuild it and reinstall it here: `npm run prepare:local` in both folders, or by hand `rm -rf node_modules/@42for.net && npm install`. The SDK is a file: dependency, so a rebuilt SDK changes neither the lockfile nor the version, and the dev server would keep pre-bundling the old copy (two instances of `@tanstack/vue-query`: `client.defaultQueryOptions is not a function`). `build/sdk-freshness.ts` stamps the installed `dist`: a changed stamp forces the re-optimization at the start, and a running dev server re-optimizes and restarts when the reinstall lands.

The dev server pre-bundles every package imported in `app/` when it starts (`optimizeDeps.entries` in `vite.config.ts`), so moving to another page never re-optimizes the dependencies and reloads the app. A package that only a virtual module imports, like `vue-router/experimental` from the generated routes, goes into `optimizeDeps.include`. `test/unit/build/dependency-prebundling.test.ts` checks both.

### Mock mode

`npm run dev:mock` runs `build/dev-mock.ts`, which starts `vite --mode e2e` on port 5174 and passes the chosen dataset as `VITE_MOCK_DATASET`. `app/main.ts` then starts MSW in the browser with the hand-written handlers of `app/mock/handlers.ts` (a coherent in-memory data set, kept in `sessionStorage`) in front of the Orval-generated Faker handlers, and signs in a fake user, Ada Lovelace. The mock modules are loaded through static `import.meta.env.MODE === 'e2e'` checks and dynamic imports, so production builds do not contain them.

| Option (`npm run dev:mock -- <option>`) | Dataset | Content |
| --- | --- | --- |
| *(none)* | `showcase` | Fourteen projects that model the platform's examples (below) |
| `--legacy` | `default` | The previous standard dataset: `acme/billing`, `acme/shipping`, `northwind/portal`; the tests run on it |
| `--large` | `large` | 16,317 annotations in `acme/billing/default` (performance of the grid and the graph) |
| `--scenario=<name>` | any | `default`, `new-user` (no account, the onboarding wizard), `invited` (no account, a pending invitation), `large`, `showcase` |

Other arguments go to Vite (`npm run dev:mock -- --legacy --open`); two dataset options or an unknown name stop with the usage. A page load picks the dataset once (`applyStartScenario` in `app/mock/db.ts`): a valid `?mock-scenario=<name>` first, then the dataset of the launch when it differs from the one the tab last started with (a restart with another option takes effect at the next reload), else the tab's own dataset with its edits. A dataset that starts fresh is stored at once, clears the catalog snapshots in IndexedDB, and, for the showcase, stores the type names, colors, icons, time zone and date format of each project as its project settings on its access point (`app/mock/showcase/seed.ts`, `Version` 1); the projects of the other datasets start without settings (`Version` 0). Settings saved on the Settings page stay until the dataset starts fresh again. Every project of every dataset has a description, which the organization overview and Settings show: the three legacy projects have theirs in `app/mock/db.ts`, shared by the `default`, `large`, `new-user` and `invited` scenarios, and each showcase project has its `description`. Organizations have none. The legacy datasets also have the **exhibition**, the project `exhibition/exhibition` of another owner with a small catalog: the user is no member of it, so it shows only as an offer, in onboarding and as the last card of Organizations, until they join it; **Leave project** on its Settings ends the membership again. The mock answers `GET v1/access/exhibition` and `POST v1/access/exhibition/join` as the API does (`app/mock/access-handlers.ts`); the showcase has no exhibition. Playwright builds with `VITE_MOCK_DATASET=default` (`playwright.config.ts`), and Vitest uses the `default` dataset too.

To add a showcase project, write `app/mock/showcase/projects/<project>.ts` (a `ShowcaseProject`: its `description` of at most 500 characters, members, settings, views and a `build(builder)` that fills each view through the `ScopeBuilder` of `builder.ts`, like `invoicing-suite.ts`), add it to `showcaseProjects` in `app/mock/showcase/index.ts` (and its organization to `showcaseOrganizations`), and add `test/unit/mock/showcase/<project>.test.ts`. `test/unit/mock/showcase.test.ts` checks the rules every project follows: canonical keys with every ancestor, all statuses and deletions, the history lengths, configurations that satisfy their combined schema, the appearance, the views, the roles and the description.

**The data set `showcase` of DbCreator** is the `fabrikam` / `invoicing-suite` / `default` scope of the showcase, in the folder format of a view export, so a real platform can be seeded with it (`2sInitDb seed showcase`, the Aspire resource `db-seed`; see [Data sets](../../../docs/Platform/Storyteller/data-sets.md#showcase)). Its documents in `src/Platform/Storyteller/DbCreator/src/data-sets/showcase/` are written by `test/unit/mock/showcase-set.test.ts` and are never edited by hand:

- The test builds the scope with `buildShowcaseScope` under a frozen clock (`2026-11-01T00:00:00Z`), and writes what a Git export of the view would hold: an annotation file per active annotation (`annotationDocument`), and the current version of every document at the path `getPath` gives (`app/mock/archive-names.ts`), without the documents of deleted annotations or without content. It also writes `key-values.json` from the scope's values store (`app/mock/showcase/key-values.ts`): the current value of every pair that is not deleted, ordered by key, in the `2s.key-values.v1` format of the key/value export, which DbCreator seeds (424-265). Its keys must follow the platform's key rule (letters, digits and `_` between the dots, no hyphen) and its levels be `Public` or `Standard`, which the test checks; a `Standard` value there is a demo value in Git, never a real secret.
- Each file is a file snapshot (`toMatchFileSnapshot`), so `npm test` fails when the mock and the set part, naming the file, and a last test fails on files the scope no longer gives. With `CI=true` Vitest writes no snapshot, so a missing file fails too; locally Vitest writes it.
- After a change of the `invoicing-suite` project (`app/mock/showcase/projects/invoicing-suite.ts`, its builder, its pairs in `app/mock/showcase/key-values.ts` or the archive names), regenerate the set, delete the files the test reports as stale, and commit the set with the change:

  ```bash
  npx vitest run test/unit/mock/showcase-set.test.ts -u
  ```

  The path comes first: in Vitest 4, `-u` takes an optional value, so `vitest run -u <path>` would read the path as that value and run every test file.
- `set.json` of the set is the only file written by hand. The `Platform.UI.Admin` workflow also runs on changes of the set's folder, so a hand edit of a document fails `npm test` there.
- DbCreator's unit tests check that every binding of the set parses; the binding language takes no hyphen in a path (`@(northwind.adyenMerchant, primaryVault)`).

- `window.storytellerMock.reset(scenario?)` resets the data of the current (or the given) dataset, as a fresh start; `window.storytellerMock.addMachine(projectKey, machine)` adds a machine as the Owner of the project would, for what a lower role may do with it; `window.storytellerMock.changeProjectSettings(projectKey, patch)` merges a patch into the settings of a project as another member, for a change made meanwhile; `window.storytellerMock.setExhibition(null)` turns the exhibition off (an object with `Organization` and `Project` sets another one). Onboarding, Organizations and Settings keep the answer about the exhibition (a 404 included) while the app runs, so reload the app, a full page load, after the call.
- `window.storytellerMock.staleSignIn(stale?)` makes the sign-in of the tab stale (`false`: recent again), kept in `sessionStorage` (`app/mock/step-up.ts`); off by default, so the tests' mock profile is unchanged. Under it the mock API answers the [step-up](#step-up) `401` (`StepUpRequired`, `Details.MaxAge` 600, the `WWW-Authenticate` challenge) where the API does: a reveal, a compare and an export of secrets, the writes, imports and protection of secrets, role changes, removing another member, invitations, new and reset machine credentials, federation rules, a replaced issuer, shared certificates and recipients. Restore and purge answer `200` with `Forbidden` and `StepUpRequired` for the secrets, the resolved read sends `X-2S-Secrets-Withheld: step-up-required` (the mock never resolves secret bindings), and the mock token's `auth_time` is an hour old. The mock sign-in with `maxAge` (the step-up) makes it recent again and brings its marker back through `/callback`; a plain sign-in keeps it stale, as an AuthKit redirect that reuses the session does. The mock `GET v1/auth/configuration` reports `StepUp: { Enabled: true, MaxAge: 600 }`.
- The mock API keeps deleted annotations restorable and records a change history per key, like the API (`app/mock/annotation-handlers.ts`, `app/mock/audit.ts`). A re-created key starts without its configuration.
- The mock API keeps the access audit of every organization (`app/mock/access-audit.ts`, 424-263). `acme` of the legacy datasets and `fabrikam` of the showcase start with a seeded history, on first use: their projects and members, machines, trusted issuers, a shared certificate, the policies, a person acting through MCP (`Via`), a record of `System` and a removed member who keeps a name; any other organization starts empty. Every mocked access write records what the API records, with the signed-in user as the actor and the values the API stores, never a secret: a role changed and a member removed (`access-handlers.ts`), an accepted invitation (the invitee as the actor, with the invitation and its sender), a machine created, reset and deleted, federation rules, the machine authentication policy, trusted issuers, shared certificates issued and revoked, a new organization and project (two records for the first project of a new organization) and a project's description (`handlers.ts`), and the access view of the key/value policy and its recipients (`key-value-handlers.ts`; a verification or a rotation records nothing there). A change that changes nothing records nothing. `GET …/access/points/{key}/audit` answers the Owners and Administrators of the key itself: an organization key gives its whole trail, a project key the project's records; it filters by `project`, `action`, `target` (the exact id) and `from`/`to` (both inclusive), newest first, 100 records per page with the offset as the continuation token.
- A deleted configuration, template or schema keeps its versions (`app/mock/documents.ts`): lists leave it out, its versions stay listed and readable, and the next write continues their numbering. `POST …/versions/{version}/restore` of configurations, templates and the three schema kinds follows the API: the current version, or one with its content, is `Unchanged`; an unknown or expired version is `404 VersionNotFound`; a deleted annotation is `409 AnnotationDeleted` and a missing one `404 AnnotationNotFound`; the content is checked as the writes check it, unless `force=true`. The new version has `RestoredFrom`, and a configuration's history gets `ConfigurationRestored`.
- `GET`, `PUT` and `PATCH …/{organization}/{project}/settings` (`app/mock/project-settings-handlers.ts`, `app/mock/project-settings.ts`) follow the API: the settings live on the access point (`db.accessPoints[key].Settings`) and come with `GET v1/access/projects` too; every member reads them with the `ETag` (the `Version` in quotes, `304` for `If-None-Match`); Administrators write them under an optional `If-Match` (`412 SettingsPreconditionFailed` with `Details.Version`), checked by the SDK's `validateProjectSettings` (`400 InvalidSettings`), a PATCH as a JSON Merge Patch; a change raises the version, stamps `Modified` and appends `ProjectSettingsChange` to the audit trail, a write that changes nothing keeps the version.
- `POST …/annotations/simple` (bulk create) reads its lines as the API does (`app/mock/simple-lines.ts`): it creates the keys with their missing ancestors, skips existing keys, and answers `400` above 100 lines.
- `GET …/configuration/{key}/composition` (`compositionOf` in `app/mock/configuration-handlers.ts`) follows the mock Effective read, not the server: the ancestors' own documents at depth 1, the template of the key's type, then its own document, merged with `deepMerge` (arrays replaced, `null` overwrites). Its `Content` and hash are those of the mock Effective read, so the mock never warns of a stale view. It has no repeated source and no depth above 1; unit tests serve a fixture shaped like the server's composition of an execution for those.
- `GET …/configuration/{key}/resolved` evaluates `@config("…")` (the configuration being resolved), `@annotation("…"[, "<Type>"])` (the `Values` of the annotation or of its ancestor of that type), each with a JSON Pointer or a dotted JSONPath, and `@<key>/<path>`; sourced values (secrets), interpolation and math stay as written, and anything else unresolved answers `422 BindingFailed`.

### Aspire

`dotnet run --project src/Platform/Aspire.Host/src` starts the `ui-admin` resource:

- It runs `npm run dev:aspire` on port 5173 (the WorkOS redirect URI).
- It sets `VITE_API_BASE_URL` to the `api-functions` endpoint.
- It prepares itself first: `ui-admin-sdk` runs the SDK's `prepare:local`, then `ui-admin-installer` runs `npm run prepare:local` here; both skip what is up to date.

## Configuration

One build serves every environment. At start-up the app reads `/app-config.json` (written by the deployment) and falls back to the `VITE_*` variables:

| `app-config.json` | Variable | Meaning |
| --- | --- | --- |
| `apiBaseUrl` | `VITE_API_BASE_URL` | API root including `/api`, for example `https://api.2s.42for.net/api`. A relative value means the app's origin. |
| `authApiHostname` | `VITE_AUTH_API_HOSTNAME` | Custom AuthKit domain, for example `auth.42for.net`. **Required on every host except localhost**: without it AuthKit keeps the refresh token in `localStorage` (devMode), so the app refuses to start, unless `authLocalStorageSession` opts in. |
| `authLocalStorageSession` | `VITE_AUTH_LOCAL_STORAGE_SESSION` (`true`) | A deployed host without a custom AuthKit domain: AuthKit runs in devMode and keeps the refresh token in `localStorage`, where an injected script could read it. A deliberate stopgap until the custom domain exists (production until its first customer, see `docs/Platform/Deployment/decisions.md`); ignored when `authApiHostname` is set. |
| `environmentName` | `VITE_ENVIRONMENT_NAME` | Shown in the sidebar footer. |
| `sentryDsn` | `VITE_SENTRY_DSN` | Sentry DSN of the admin UI project; no Sentry without it. |
| `posthogProjectToken` | `VITE_POSTHOG_PROJECT_TOKEN` | PostHog project token (`phc_…`); no PostHog without it. |
| `posthogHost` | `VITE_POSTHOG_HOST` | PostHog API host; `https://eu.i.posthog.com` when missing. |
| `release` | — | The commit SHA, written by the deployment; the Sentry release. |

The sign-in provider and the AuthKit client ID come from the API (`GET v1/auth/configuration`). A deployment that uses another provider shows an "unsupported" page.

### WorkOS dashboard checklist

Every WorkOS environment has its own settings. The `localhost` entries belong to the **Staging** environment (the one `npm run dev` and the Aspire host sign in with), the `<admin-host>` ones to the environment of that deployment. The URIs are under **Redirects** of the admin UI's application.

- Redirect URIs: `https://<admin-host>/callback` (Staging: `http://localhost:5173/callback`).
- Sign-out URIs: `https://<admin-host>/login` (Staging: `http://localhost:5173/login`), set as the **default**. The app signs out through the WorkOS logout with `<origin>/login` as `returnTo`. WorkOS returns there only when it is one of the Sign-out URIs, and otherwise goes to the default one. With neither, the sign-out ends on WorkOS' error page `error.workos.com/user_management/app-homepage-url-not-found` ("Couldn't sign in"). The deprecated App homepage URL is not needed.
- Initiate login URI: `https://<admin-host>/login`.
- CORS allowed origins: `https://<admin-host>` (Staging: `http://localhost:5173`).
- JWT template with `aud`, `email`, `name` and `email_verified` (see `docs/Platform/Storyteller/authentication.md`).
- Invitation accept URL: `https://<admin-host>/invitations/accept`.
- A custom authentication domain (`auth.42for.net`) for every deployed environment.
- User impersonation off (**Authentication → Features**): the API refuses impersonation tokens (see `docs/Platform/Storyteller/authentication.md`).
- Multi-factor authentication: **Required** in the authentication settings of the production environment (Required since 2026-11-17), so every user enrols a factor and every sign-in without SSO (Magic Auth there) asks for a second factor, also the re-authentication of the [step-up](#step-up). Passkey and SSO sign-ins skip the challenge; an SSO customer's identity provider is responsible for its users' MFA. The API proves only a recent sign-in (`auth_time`), never the factor. Staging stays without MFA for the automation user pools.

The admin origin must also be in the CORS settings of the Function App.

### Step-up

Some operations need a recent sign-in, by default one within the last 10 minutes (`Auth:StepUp` of the API; `docs/Platform/Storyteller/authentication.md`, "Recent sign-in (step-up)"): revealing, comparing and exporting secret values, writing, importing, protecting, restoring and purging secrets, changing roles, removing members, inviting, new and reset machine credentials, federation rules, replacing a trusted issuer, shared certificates and recipients. A token refresh keeps the time of the last sign-in (`auth_time`), and a plain AuthKit redirect reuses the session, so the app signs in again with `max_age`.

- **Discovery:** the boot state keeps `GET v1/auth/configuration` (`authConfiguration`), also in mock mode; a tab caches it in `sessionStorage` for 5 minutes (`authConfigurationCacheMs`), so an API that turns its step-up on reaches open tabs at their next load after that; `getStepUpSettings()` (`boot/state.ts`) gives `StepUp.Enabled` and `StepUp.MaxAge`. An API without `StepUp` is treated as off.
- **The sign-in:** `SignInOptions.maxAge` (`boot/auth.ts`). authkit-js 0.20 has no such option, so `signIn` builds the URL with `getSignInUrl` (the same state, login hint and PKCE verifier) and appends `max_age`. The state carries a marker, `{ returnTo, stepUp: <start>, stepUpAuthTime: <the sign-in before it> }`, and `onRedirectCallback` records it only when the callback brings it back (`AuthService.getStepUpReturn()`). `AuthService.getAuthTime()` reads `auth_time` of the current access token with `getClaims`. The step-up's `stepUpAuthTime` is the `auth_time` of the last token the page got, read without a token request: a refresh that failed there would start a plain sign-in (`onRefreshFailure`) whose PKCE verifier replaces the step-up's.
- **The coordinator** (`composables/useStepUp.ts`, `components/shell/StepUpDialog.vue` in `App.vue`): the SDK's `onStepUpRequired` (`boot/api.ts`), a bulk item with `ErrorCode` `StepUpRequired` (the restore of a key, the bulk bar, the import dialog's Undo deletes) and the client hint open one confirmation however many requests failed: "Confirm it's you", with a note when the page has unsaved changes (they are lost; the browser's own leave prompt does not ask again), live while it is open: credentials shown once that arrive meanwhile add it, and the first **Sign in again** after that only shows it: an editor's `useUnsavedChanges`, or a dialog's typed or pasted input (`useDirtySource`: New key, Import, Invite, New machine, federation rules, a trusted issuer, a shared certificate, a recipient). **Sign in again** signs in with `maxAge: 0` (a forced re-authentication: a positive `max_age` and two clocks could loop), the current route as `returnTo` and the user's email as login hint. **Back** on the provider's page may restore the page from the back/forward cache with the redirect under way: `pageshow` with `persisted` makes the confirmation work again, turns the leave prompt back on and drops the Reveal stored for the return. A loop of requests (the bulk Delete, one key at a time) runs in `deferWhile`: the confirmation opens once the loop is done and the failed keys are selected. **Cancel** leaves the screen's error as it is; `describeError` gives `StepUpRequired` its own title and text ("Sign in again to continue", with the window of the API).
- **The loop guard:** after a return whose token's `auth_time` is not newer than the sign-in before the step-up (when that is unknown, a time newer than the start counts as moved and an older one proves nothing, as the start is the browser's clock), a step-up `401` shows "Your sign-in could not be confirmed. Sign out and sign in again." with **Sign out** instead of another redirect. A newer sign-in whose window ran out since opens the confirmation again.
- **The client hint** (`isSignInStale`): the token's `auth_time` against `StepUp.MaxAge` less a minute (half the window when it is shorter than two minutes), only while `StepUp.Enabled`. After a step-up whose sign-in moved, the browser's time of the return counts too, so a browser clock ahead of the provider's does not ask again at once. Before the person types what a redirect would lose, the screen runs the confirmation first: **Set new value** of a secret, a secret level in **New key**, **Check** and **Import** of a document with secret rows, **New machine**, **Invite** and a role change. The Resolved tab says that secret values are hidden until the person confirms, with the button, instead of claiming they are included: the API's `X-2S-Secrets-Withheld` is not readable cross-origin. It asks `isSignInTooOld` (the window itself, without the margin: the API withholds only then) with every response, the latest answer winning. That is an estimate by the browser's clock: within 30 seconds of the window's end it says the values may be hidden, and the text for a recent sign-in says they are included unless the sign-in is too old, which the browser can only estimate (a clock off by more than that can be wrong either way).
- **After the return** the page loads again, so reads run again. A Reveal that asked for the step-up (the value of a key, or a version) is kept in `sessionStorage` and repeated once, only right after the return: the first screen that asks once its data is there takes it, its own or not, so it never replays later without a click. Writes are never replayed, and a secret value is never stored: after a return whose sign-in moved, a toast says "You signed in again. Repeat the change if it did not finish."

Deploy the admin UI together with the API, or first: an older admin UI answers a step-up `401` with a plain sign-in redirect and never succeeds.

### Deployment

`.github/workflows/Platform.UI.Admin.yml` covers SDK and UI changes. On pull requests and on `main`, it runs these steps:

- `npm ci`, and a check that the generated SDK matches the OpenAPI document;
- lint, unit tests and the build;
- the Playwright suites in the Playwright image.

On `main` it also deploys `dist/` to Azure Static Web Apps (`skip_app_build`). The GitHub environment `prod.42.Platform` provides (`Set-GitHubEnvironment.ps1` of `src/Platform/Deployment` sets them):

| Name | Kind | Value |
| --- | --- | --- |
| `VITE_API_BASE_URL` | variable | `apiBaseUrl`; its origin goes into the CSP `connect-src` |
| `VITE_AUTH_API_HOSTNAME` | variable | `authApiHostname`; goes into `connect-src` and `form-action` |
| `VITE_AUTH_LOCAL_STORAGE_SESSION` | variable | `true` writes `authLocalStorageSession` and allows a deployment without `VITE_AUTH_API_HOSTNAME` (the CSP then names `api.workos.com`); ignored when the hostname is set |
| `VITE_ENVIRONMENT_NAME` | variable | optional `environmentName` |
| `VITE_SENTRY_DSN` | variable | optional `sentryDsn`; its origin, without the key, goes into `connect-src` |
| `VITE_POSTHOG_PROJECT_TOKEN` | variable | optional `posthogProjectToken`; puts the PostHog host into `connect-src` |
| `VITE_POSTHOG_HOST` | variable | optional `posthogHost`; its origin goes into `connect-src` (`https://eu.i.posthog.com` when missing) |
| `AZURE_STATIC_WEB_APPS_API_TOKEN` | secret | deployment token of the Static Web App |

The deploy step runs `node build/write-environment-config.ts` (Node 24 runs TypeScript). It writes `dist/app-config.json`, with `release` set to the commit SHA, and replaces `__API_ORIGIN__`, `__AUTH_HOSTNAME__`, `__SENTRY_ORIGIN__` and `__POSTHOG_ORIGIN__` in `dist/staticwebapp.config.json`. Without a DSN or a PostHog token, the Sentry or PostHog origin is empty, and a deployment without the three variables deploys as before. A DSN or host that is not an absolute `https` URL fails the step. Playwright serves `vite preview` without the CSP, so `test/unit/build/csp.test.ts` and `environment-config.test.ts` check the policy and the step, and `write-environment-config.test.ts` runs the script with Node, as the deploy step does: syntax that Node's type stripping rejects, such as an `enum`, fails `npm test` instead of the deployment. The config file (from `public/`) sets the following:

- the SPA navigation fallback;
- the headers: CSP, `Referrer-Policy`, `X-Content-Type-Options`;
- caching: `no-cache` by default, a year and `immutable` for the hashed `/assets/*`.

The CSP allows no `eval`. Keep these in mind when adding code:

- **Icons:** they are bundled at build time (the lucide icons used in `app/**/*.{vue,ts}`). An icon name built at runtime from parts is not found, and it would be fetched from the Iconify API, which the CSP blocks.
- **Fonts:** they are never inlined as `data:` URLs.
- **Validation:** JSON Schema validation uses `@cfworker/json-schema`, which interprets schemas, instead of Ajv, which generates code with `new Function`.
- **Zod:** it runs `jitless`.
- **Telemetry:** PostHog comes from `posthog-js/no-external`, which loads no script from PostHog. The default `posthog-js` injects its config, recorder and surveys from a CDN, which `script-src 'self'` blocks.

### Telemetry

Sentry reports errors and PostHog counts pages and clicks. Each starts only when the deployment sets its key (`sentryDsn`, `posthogProjectToken`). `boot/telemetry.ts`, the only module the app calls, loads the SDKs with dynamic imports, so a deployment without keys downloads neither. A failure to load or start an SDK is logged with `console.warn` and changes nothing else.

- **Off:** in the `e2e` and `test` modes (mock mode, Playwright, Vitest) neither SDK is imported, whatever the variables say, because Vite loads `.env.local` in these modes too. `public/app-config.json` and `.env.development` set no keys, so local development sends nothing.
- **URLs:** a page goes out as its route template, for example `https://<admin-host>/:org/:project/:view/key-values/:key`, without the query and the hash (`utils/telemetry-privacy.ts`). The AuthKit `code` and `state`, the `invitation_token` and the filter text stay in the browser, and no page URL names an organization, project, view or key. The names still leave the browser in two ways: a PostHog click keeps the text of its link or button, which is a name on the organizations page, in the context switcher, in the breadcrumb of an annotation and in the lists; and Sentry's request breadcrumbs keep the paths (without the query) of the API calls before the error, which name their organization, project, view and key.
- **Identity:** both get the AuthKit user id, never the e-mail, the name or the picture. Sign-out resets both.
- **Sentry** (`boot/sentry.ts`) gets errors only, with `environmentName` and `release`: Vue errors, unhandled errors and rejections, and the API errors of the global toast (network failures, timeouts and `5xx`). An API error is sent with its status and error code, never with its message, hint or body; a timeout is "Storyteller API did not answer in time" with its own fingerprint, so it does not merge with network failures. There is no tracing (no trace headers to the API), no replay, no release-health session and no component prop. There are no console, click or key-press breadcrumbs (Sentry writes the `aria-label`, `title` and `alt` of the clicked element into them, which can be a name or an e-mail) and no breadcrumbs of PostHog's own requests, and the `Referer` header is removed. Each event carries the `posthog_session_id` and `posthog_distinct_id` tags of the current PostHog session, so an error leads to the PostHog session and user.
- **PostHog** (`boot/posthog.ts`) gets a `$pageview` for the first page and for each change of the path (a change of the query only, such as typing a filter, is no new page), and the clicks on links and buttons, with their text (which can be an organization, project, view, annotation or key name) but no attributes. Recordings, exceptions, web vitals, heatmaps, dead clicks, surveys and feature flags stay off, whatever the project settings say. PostHog keeps its state in `localStorage` (no cookie), saves no referrer or campaign parameters (the `utm_*`, `gclid` and similar values and the search keyword it still reads from the entry URL are removed before sending), and honours Do Not Track and Global Privacy Control.
- **`ph-no-capture`:** clicks inside an element with this class send nothing to PostHog. It is on the root of every component that shows secrets (one-time secrets, new machines, shared certificates, key values and their versions, the key-value list on narrow screens, the create and import dialogs of key values), documents (the code, diff and document editors, the configuration form, the hunk list), personal data (the invite dialog, members, invitations, the invitations page, the user menu, the account page, the author and actor links of `AuditActorLink`, the stamps of an annotation, and the table of the access audit with the full values of a record) or typed text (the active terms of the filter sheet). A new component that shows secrets, documents or personal data gets it too. A dialog gets it on its `UModal`, which teleports its content out of the page.

- **Server state** lives in TanStack Query through the SDK's generated composables. The project settings (the time zone of new annotations, the date format and the names, colors and icons of the types, 424-266) are server state too: `useCurrentProjectSettings` (`queries/project-settings.ts`), mounted once in `App.vue`, reads `GET v1/{organization}/{project}/settings` of the current project, starting from the `Settings` of the cached `GET v1/access/projects`, and hands every answer of a settings query, also the one a save writes into the cache, to the `project-settings` store (sanitized by `fromApi` of `utils/project-settings.ts`, the defaults until the first answer, cleared on sign-out), which `type-appearance`, `date-format` and the New annotation dialog read. Settings saves its draft with one `PUT` under `If-Match: "<Version>"` (`projectSettingsEntityTag`), as the browser cannot read the `ETag` of another origin. `utils/legacy-project-settings.ts` only reads and removes the old per-browser entries (`localStorage['2s-admin:project-settings']`): Settings offers to save them while the project's settings are at `Version` 0 (it decides only on an answer cached under the current project's key, as on a project switch the query holds the previous project's answer for a moment), and `useCurrentProjectSettings` removes the entry of a project once an answer of that project's own query is above `Version` 0. **Client state** lives in Pinia: `session` (user, account, AccessMap), `context` (org, project and view of the route), `preferences` (UI state only, in `localStorage`, including the personal date format and personal names, colors and icons of the annotation types), `type-appearance` (resolves the type overrides, personal over the project's from the API over built-in, and applies them to `typeMeta` and the `--st-*` color tokens), `date-format` (resolves the date format, personal over project over `yyyy-mm-dd`, and applies it to the formatters of `utils/dates.ts`), `page-memory` (in memory only: per view, the last location and the URL-less state of the annotations, configurations and graph pages, and the last tab, detail and query of Modeling, restored by the `page-memory` router guard when the user returns to the plain list of one of these sections).
- **Merged pages:** the old Invitations, Certificates, Secrets, Audit and Usage pages of a project are redirect stubs (`definePage({ redirect })`) to the section that took them over: `members#invitations`, `machines#shared-certificates`, `settings#secrets` and `monitor` (`?tab=audit`). The router does not scroll to anchors, and the panel body is the scroll container, so `useHashScroll(ready)` scrolls the section of the hash into view once the content above it has loaded. The old Schemas, Templates, Export & Import, Deleted and Compare views pages of a view redirect to their tab, `modeling/{tab}`: `movedToModeling` (`utils/modeling.ts`) inserts `modeling` after the view and keeps the rest of the path, and `schemas/[[...path]].vue` and `templates/[[...path]].vue` cover the details below them too. The redirects return a path, so the query and the hash stay.
- **Errors:** the SDK throws `StorytellerError`. `5xx` and network failures show a global toast, and `reportApiError` sends the same errors to Sentry when it is configured ([Telemetry](#telemetry)); screens handle `4xx` themselves. Server stack traces are never shown. A `401 StepUpRequired` is neither refreshed nor retried by the SDK: it opens the confirmation of the [step-up](#step-up).
- **Timeouts** (`boot/api.ts`): every request ends. `configureApi` gives the SDK a `timeoutMs` by method: reads (`GET`, `HEAD`) 30 s (`apiReadTimeoutMs`, the read timeout of the .NET configuration provider too), every other method 120 s (`apiWriteTimeoutMs`: Bulk create, restore, delete and purge of subtrees, the schema writes and the bulk key-value actions grow with their input). The view import's upload and the export's download pass `apiTransferTimeoutMs` (10 minutes) per call. The limit counts the time the browser queues a request. A timeout is a status-0 `StorytellerError` with `timedOut`: `describeError` titles it "The API did not answer in time" (and sets `timedOut`), `ErrorState` shows `i-lucide-hourglass`, the global toast has the same title, and Sentry gets "Storyteller API did not answer in time" with the fingerprint `['storyteller-api', 'timeout']`, apart from network failures. Every `useQuery` therefore reaches its `ErrorState` with Retry, and every write its failure handling. The unit tests configure the SDK without a timeout (`test/setup.ts`); a test of a timeout sets a short one and restores the configuration.
- **Query defaults** (`boot/query.ts`): `staleTime` 30 s, `gcTime` 10 minutes, no refetch on window focus, mutations never retried. A failed read is retried once, but not a `4xx` (the same answer again) and not a timeout (a second wait before the error is worse than the error's Retry); so on a deployed API a cold start longer than 30 s shows the error on the first page. Writes do not wait for unrelated refreshes: the configuration save, the template save and delete, Bulk create (`createMany`) and restore (`restoreMany`, which still awaits the deleted lists) show their result after the write and invalidate the other queries in the background. A configuration save that timed out reads the own content again (`refreshOwn`, each read within the read timeout): equal to the document as sent (the editor stays editable during a save), the save is done ("Configuration saved"), the sent document becomes the base and an edit made meanwhile stays a change; different or unreadable, "The API did not answer in time; the change may have been saved. Reload before saving again." and the draft stays (the API may still be applying the patch it no longer answers, and a patch of `add` operations has no `test` guards, so sending it again could add an array element twice). The conflict dialog of a 412 shows the error of the stored content with Retry when it cannot be read, instead of a spinner. Until the own content is known the editor shows its error with Retry and `save()` does nothing.
- **Catalog** (`stores/catalog.ts`): the snapshot in IndexedDB first, then the seven per-type lists, at most four at once (`typeListConcurrency`: with the API on another origin the browser has six HTTP/1.1 connections, and the page's own requests must not queue behind the catalog), and the configuration summaries. A list that failed falls back to `GetAnnotations`, but not after a timeout (it would only wait again): the load ends with the error. `progress` (`lists` settled of `total`, the `annotations` of the map the load fills, `fallback` while `GetAnnotations` runs, `replacing` while a shown catalog waits to be replaced) is reset by every load and drives the strip of Annotations and the overlay of Graph (`catalogProgressText`: "Loaded 1,240 annotations, 3 of 7 types…", "Refreshing: …", "… all types…") with a determinate `UProgress`. A failed load always ends and clears `fromSnapshot`: `error` with nothing to show (a first load, which pages straight into the shown map, drops what it collected: a partial `ready` catalog would mark the ancestors of its missing types as missing in the breadcrumbs and the composition), otherwise `ready` with `error`, shown as the compact `ErrorState` "The catalog could not be refreshed" with Retry. A failed list of the summaries keeps those known (null only when there were none) and sets `configurationsError`, which Configurations shows with Retry (`refreshConfigurations`) and New configuration counts as a failure; `refreshConfigurations` has its own controller, aborted by the next refresh, a load and a reset, and writes only while the catalog still holds its view. "Reload the catalog" stays disabled while a load runs (the automation tests and e2e specs wait for it).
- **Roles:** `useRole()` and `<RoleGate>` read the caller's role from `Account.AccessMap` (an organization role does not grant project access). An organization page checks the organization's own role, since the context guard lets in every member of one of its projects: Members gates **Invite** and Audit gates itself (`useCan('manageAccess', 'org')`). The Machines page and the machine detail check the role before they ask for machines: below Contributor they show the API's refusal themselves (`roleRequiredError` in `utils/errors.ts`, "No access" with Retry, which reloads the account), because a Debug API (`DEV_AUTH`) skips its role checks of users and would list them (424-164).
- **Forms:** VeeValidate 4 with Zod 4 through `forms/typed-schema.ts` (`@vee-validate/zod` supports Zod 3 only).
- **Access audit** (`pages/[org]/audit.vue`, `components/access/AccessAuditTrail.vue` and `AccessAuditChange.vue`, `utils/access-audit.ts`, 424-263): the organization's trail of `GET v1/access/points/{org}/audit` ([access-audit.md](../../../docs/Platform/Storyteller/access-audit.md)), the **Audit** entry of the Organization section after Members (`minRole: 'Administrator'` on the organization). The project name `audit` is reserved, so `/{org}/audit` never hides a project. Below the organization's Administrator the page shows "Administrators only" and the query (`useAccessAudit` in `queries/scope.ts`, `meta.silent`, enabled by the role) sends nothing. Modelled on the Audit tab of Monitor: filters in a toolbar (project: the caller's projects of the organization and those of the records shown; action with readable labels; the target's exact id, sent after a pause in typing; from and to dates, the end date inclusive), a table that fills the panel with a sticky header, and **Load more** with the continuation token, whose page is dropped when the organization or a filter changed meanwhile. A record shows its time, action (a created access point as "Organization created" or "Project created", its detail on two lines at most), project ("Organization" for the organization's own records), target (the kind's icon, the name and the id), change (roles as badges, other values cut to one line; JSON, a long value or a long detail opens in full and indented from the button at the end), actor ("Ada Lovelace via mcp" when an actor acted for the person) and the first 8 characters of the correlation id with its copy button. The empty state names the retention, two years. `invalidateAccess`, `invalidateProject` and `invalidateKeyValuePolicy` (`queries/invalidation.ts`) also refresh the organization's audit, so a change made elsewhere is on the page when it opens again.
- **Values store** (`pages/[org]/[project]/[view]/key-values*`, `components/key-values/`, `components/secrets/`, `components/monitor/`): the key values of a view with their levels, the detail with Reveal (masked again after 60 seconds, never cached) and Set new value, versions loaded only on request, import in three steps and export through a Blob URL, the Secrets section of the project's Settings (allowed levels, keys and rotation, the BYOK wizard, recipients), and the Usage and Audit tabs of the Monitor page (`pages/[org]/[project]/monitor.vue`, `?tab=audit`). - **Modeling** (`pages/[org]/[project]/[view]/modeling.vue`, `pages/[org]/[project]/[view]/modeling/`, `components/modeling/ModelingHeader.vue`, `utils/modeling.ts`): the Schemas, Templates, Export & Import, Deleted and Compare views pages of a view, a tab each, at `modeling/{tab}`; `modeling/index.vue` redirects to `modeling/schemas`. From outside the Modeling of the view (another section, a project page or another view), the `page-memory` guard then returns to its last Modeling location; it reads the plain `modeling` from `to.redirectedFrom`, because the redirect runs before any guard, and it lets the next pass of its own redirect through by the identity of the navigation, not by comparing URLs, which the browser and the router may spell differently. From within it, the plain `modeling` stays on Schemas, which is how the user starts over. The tab is in the path, not in `?tab=` as on Monitor: the schema and template details keep their own `?tab=versions`, and `useUnsavedChanges` asks only when the path changes, once per navigation, also when a guard redirects it (the leave guards run again on the redirected pass). `modeling.vue` is a bare `<RouterView />` for every role, so each tab page keeps its panel and its detail outlet as children of the dashboard group. Below Contributor the tab pages are read-only and hide their writes themselves (424-272), as the API reads them with `Reader`: the schema and template editors are read-only with a **Read-only** badge, a missing schema shows a Reader "No schema" instead of the starter document, and Deleted has no selection and no bulk toolbar, and only **Show details** in its row menu; Export & Import keeps its own lock (`useCan('transfer')`). The header of the opened page scrolls its tab into view (the tabs scroll sideways on phones) and takes the focus over when the tabs had it. It shares the views query of `ContextSwitcher` and disables **Compare views** once the views are known and none of them is another view. `compare.vue` compares `?to=` with the view of its route, not of the context store: a `?to=` that names the page's own view is no target, so the only other view is preselected over it. The context guard sets the store before a navigation lands, so until the store and the route agree again the page neither preselects (a `router.replace` would cancel the navigation) nor requests the diff and the two documents.
